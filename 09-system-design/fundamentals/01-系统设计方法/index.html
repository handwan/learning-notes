    系统设计方法¶

    系统设计不是先画一堆方框，也不是先选中间件。它要先把问题问清楚，再在约束下做选择，并明确选择带来的代价。

    这篇不教某个具体架构，而是给一套可重复的顺序：

    问题 → 需求 → 约束 → 容量 → 边界 → 候选 → 决策 → 失败 → 演进

    后面所有文章都按这个顺序展开。

    1. 先问问题，不先画图¶

    拿到需求时，先问：

    • 谁在用？用户、租户、内部系统还是机器？
    • 核心动作是什么？读、写、搜索、通知、支付、上传？
    • 哪条路径最重要？失败时用户看到什么？
    • 现在怎么解决？为什么不够？
    • 是一次性任务，还是长期演进的产品？
    • 哪些是硬约束，哪些只是偏好？

    如果这些问题答不出来，画出来的架构图大概率是在猜。

    2. 需求：功能和非功能¶

    功能需求¶

    写成用户能感知的行为：

    用户可以创建短链
访问短链时跳转到原 URL
创建者可以查看点击统计
管理员可以封禁恶意链接

    不要写“系统要有 URL 服务”这种实现描述。

    非功能需求¶

    系统设计真正难的部分通常在这里：

    维度 要问什么
    规模 多少用户、QPS、数据量、增长
    延迟 p50/p95/p99、TTFT、端到端
    一致性 强一致、最终一致、能否容忍旧读
    可用性 几个 9、故障时降级还是拒绝
    持久性 能否丢数据、备份/恢复要求
    安全 认证、授权、租户隔离、审计
    成本 单请求/单租户/每月预算
    运维 团队能不能维护、发布频率
    合规 数据驻留、隐私、保留期

    非功能需求要尽量量化。不能量化的，也要写清“优先级”和“可接受的最坏情况”。

    3. 约束：硬约束和偏好分开¶

    约束分两类：

    • 硬约束：必须满足。现有数据库、合规、预算、团队规模、交付时间。
    • 偏好：最好满足。语言、框架、云厂商、代码风格。

    把偏好当硬约束，系统会过度设计；把硬约束当偏好，上线会出事故。

    常见约束：

    • 只能用现有 PostgreSQL
    • 团队只有 3 个后端
    • 不能跨境传数据
    • 发布窗口每周一次
    • 峰值是均值的 5 倍
    • 故障时不能丢订单

    这些约束会直接排除一批方案。

    4. 非目标：明确不做什么¶

    非目标能防止范围膨胀：

    第一版不做多地域
不做实时推荐
不做自定义域名
不承诺 99.99%
不支持超过 1 万字符的 URL

    非目标不是“永远不做”，而是“当前版本不为它做设计”。写出来，评审时才有边界。

    5. 容量：先算数量级¶

    容量估算不需要精确，但要避免数量级错误。

    至少算：

    • 平均 QPS / 峰值 QPS
    • 读写比
    • 每日新增数据 / 保留期 / 总存储
    • 平均/峰值带宽
    • 缓存命中率和回源量
    • 单请求成本 / 每月成本

    原则：

    • 所有假设写出来
    • 峰值系数单独标
    • 用数量级，不用假装精确
    • 用计算结果筛方案，不用它当 benchmark

    容量计算见下一篇 需求与容量估算。

    6. 划边界：先模块，后服务¶

    边界不是“微服务数量”，而是：

    • 哪些数据归谁所有
    • 哪些操作必须同步
    • 哪些可以异步
    • 哪些模块可以独立变化
    • 哪些依赖必须隔离

    一个实用顺序：

    领域边界 → 模块边界 → 数据所有权 → 部署边界

    先做模块化单体通常比一上来拆微服务更容易验证边界。等团队、发布频率、故障隔离真的需要时再拆。

    7. 候选方案：最多三个¶

    每个关键决策列 2–3 个候选，不要列十个：

    决策 候选
    形态 模块化单体 / 微服务
    存储 PostgreSQL / KV
    通信 同步 API / 队列
    缓存 本地 / Redis
    入口 云 LB / Nginx / Envoy

    每个候选写：

    • 适用条件
    • 不适用条件
    • 关键语义
    • 运维成本
    • 迁移/退出成本

    8. 决策：写清代价¶

    一个决策至少包含：

    Context：背景和约束
Decision：选了什么
Why：为什么
Consequences：换来什么、付出什么
Alternatives：放弃了什么
Revisit：什么条件下重新评估

    不要只写“采用微服务”。要写：

    • 采用微服务换来了独立部署
    • 代价是分布式事务、网络故障、运维复杂度
    • 团队是否具备对应能力
    • 什么时候退回模块化单体

    9. 失败模式：设计的一半¶

    系统设计要看失败：

    • 依赖超时/不可用
    • 重试放大/雪崩
    • 队列积压/重复消费
    • 缓存穿透/热 key
    • 部分写入/数据不一致
    • 租户越权/密钥泄漏
    • 发布回滚失败
    • 容量估算错误

    每个关键组件都问：

    它坏了，用户看到什么？
会丢数据吗？
会放大故障吗？
怎么发现、怎么降级、怎么恢复？

    没有失败模式的设计，只是 happy path 草图。

    10. 演进：留缝，不预留过度¶

    好的设计不是“未来什么都能做”，而是：

    • 当前简单
    • 关键边界可替换
    • 有迁移路径
    • 有回滚方案

    留缝的例子：

    • 存储接口隔离，未来可换实现
    • 事件格式版本化
    • 同步调用可降级为异步
    • 功能开关控制新路径
    • 数据迁移可双写/校验

    不要为了“未来可能”提前上十层抽象。

    11. 一个例子：通知服务¶

    下面的数字是示例假设，不是实际业务数据。

    需求：

    • 发送邮件/站内信
    • 每天 100 万条
    • 创建后 5 秒内进入发送队列
    • 至少一次投递，允许极少重复
    • 支持退订和租户隔离
    • 小团队维护

    约束：

    • 已有 PostgreSQL
    • 不想自建消息集群
    • 预算有限
    • 不需要 99.99%

    候选：

    方案 代价
    单体 + 数据库轮询 简单；吞吐/延迟有限
    模块化单体 + 托管队列 稍复杂；依赖云服务
    微服务 + 自建 Kafka 扩展强；运维成本高

    决策：

    第一版：模块化单体 + PostgreSQL + 托管队列

    理由：

    • 当前规模不需要拆服务
    • 队列解耦发送和重试
    • 托管服务降低运维
    • 数据仍在 PostgreSQL，事务边界简单

    失败模式：

    • 队列积压 → 监控 lag，扩容消费者
    • 重复发送 → 幂等键/去重表
    • 邮件商限流 → backoff + 分级队列
    • 租户滥用 → 配额/限流
    • 队列不可用 → 本地暂存/降级站内信

    演进条件：

    • 消费者成为瓶颈 → 拆发送 worker
    • 多地区合规 → 区域队列
    • 日发送到亿级 → 重新评估存储/队列

    这不是唯一答案，而是展示“约束如何推出决策”。

    12. 设计检查表¶

    评审时至少问：

    • 功能需求和非功能需求分别是什么？
    • 哪些是硬约束，哪些是偏好？
    • 非目标写了吗？
    • QPS/存储/带宽的数量级对吗？
    • 数据归谁所有？同步/异步边界在哪？
    • 最坏情况下用户看到什么？
    • 依赖坏了会怎样？会放大吗？
    • 有没有幂等、重试、降级、回滚？
    • 成本谁承担？团队能维护吗？
    • 哪些决策需要 ADR？
    • 什么时候重新评估？

    13. 常见坑¶

    1. 先选技术，再找问题 先问约束，再选 Redis/Kafka/微服务。

    2. 把偏好当硬约束 “我们只用 Go”可能只是团队偏好，不是业务约束。

    3. 只写功能，不写非功能 延迟、一致性、成本才是设计难点。

    4. 容量只拍脑袋 至少算 QPS、存储、带宽的数量级。

    5. 一上来拆微服务 先用模块化单体验证边界，必要时再拆。

    6. 只画 happy path 失败模式、降级、恢复才是设计的一部分。

    7. 决策不写代价 “采用 X”不是决策记录；要写换来了什么、失去了什么。

    8. 过度预留 为不确定的未来加十层抽象，当前复杂度先爆炸。

    14. 要点回顾¶

    1. 系统设计从问题、需求、约束开始，不从中间件开始
    2. 功能需求写行为，非功能需求尽量量化
    3. 硬约束和偏好分开；非目标要写出来
    4. 容量估算看数量级，假设要标注
    5. 先划领域/模块/数据边界，再决定部署边界
    6. 每个决策列 2–3 个候选，写清代价和退出条件
    7. 失败模式、降级、恢复是设计的一半
    8. 演进靠可替换边界和回滚，不靠过度抽象
    9. 用 ADR 记录决策，用检查表做评审
