    结构化输出¶

    结构化输出不是“让模型输出 JSON”这么简单。至少要分三层：

    层 问题 例子
    语法 能不能被 JSON parser 解析？ 代码围栏、前后废话、trailing comma
    schema 字段/类型/枚举/必填是否符合契约？ needs_human 应是 boolean，模型给了 "yes"
    语义 值本身对不对？ schema 合法，但把技术问题分类成 billing

    很多系统只做了第一层，就在线上遇到第二、三层问题。这篇讲 schema、生成端约束、校验/重试和评测，最后跑一个 8 个样本的校验漏斗。解码/sampling 基础见 LLM 第 6 篇；工具参数校验见 Agent 与工具调用。

    1. 先定义契约¶

    下游要消费的不是“一段看起来像 JSON 的文本”，而是一个明确的结构。先写 schema，再选模型和生成方式。

    一个工单分类的 schema：

    {
  "type": "object",
  "properties": {
    "category": {"type": "string", "enum": ["billing", "technical", "account"]},
    "priority": {"type": "string", "enum": ["low", "normal", "high"]},
    "summary": {"type": "string", "minLength": 8, "maxLength": 80},
    "needs_human": {"type": "boolean"},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  },
  "required": ["category", "priority", "summary", "needs_human", "confidence"],
  "additionalProperties": false
}

    设计规则：

    • 类型明确：string/number/boolean/array/object；不要用“字符串里再塞 JSON”。
    • 枚举优先：分类、优先级、状态用 enum，不要让模型自由发挥。
    • 必填明确：required 写全；缺字段不能靠下游猜。
    • 拒绝额外字段：additionalProperties: false；否则模型加一个 urgency 也可能混过去。
    • 范围/长度：minimum/maximum、minLength/maxLength、数组 items。
    • 可空显式：需要 null 就写 ["string", "null"] 或 anyOf，不要靠空字符串代替。
    • 结构扁平：嵌套越深，约束解码和校验越容易出问题；能拆成多次调用就拆。
    • schema 版本化：字段重命名/类型变化要版本化；日志里记录 schema 版本。
    • format 不是万能：format: "date" 在 JSON Schema 里常是注解，是否强制取决于校验器/约束器。

    schema 是应用契约，不是给模型看的“建议”。模型可以不知道 schema 的实现，但运行时必须按它校验。

    2. 生成端的几种做法¶

    做法 能保证 不能保证
    Prompt 里写“只输出 JSON” 几乎没有 语法、schema、语义
    JSON mode JSON 语法可解析 字段/类型/枚举符合 schema
    Schema 约束解码 / structured outputs 在支持的 schema 子集内保证语法和 schema 语义正确、业务规则
    Function/tool calling 参数通常按 tool schema 生成 运行时仍要校验；语义仍可能错
    生成后校验 + 重试 能拦住并修复一部分错误 延迟/成本；修复可能掩盖问题
    微调 风格/格式更稳定 仍可能违反 schema；需要评测

    几个容易混淆的点：

    • JSON mode ≠ schema 约束：它只保证“能 parse”，不保证字段齐全、类型正确。
    • structured outputs / strict schema：不同厂商支持的是 JSON Schema 子集，限制要看文档；不是所有关键字都能约束。
    • function calling：模型输出的是调用意图，执行前仍要校验参数和权限。
    • 微调：能学格式，但不能替代运行时校验。

    OpenAI 的 structured outputs 示例见 OpenAI Cookbook；开源侧可以看 Outlines、XGrammar、vLLM structured outputs 和 llama.cpp GBNF。

    3. 约束解码怎么工作¶

    普通解码每一步从词表 logits 里选 token。约束解码多了一步：

    prefix → schema/grammar 状态
      → 计算允许的下一个 token
      → 把不允许的 logits 置为 -inf
      → 采样/贪心
      → 更新状态

    例如 schema 要求 category 只能是三个枚举值，那么生成到 "category": 之后，只有能构成这三个值的 token 序列被保留。实现上不一定真的“逐 token 掩码”，也可能是 grammar/automaton、regex 或专门的结构化输出引擎，但核心都是“把无效前缀剪掉”。

    它能保证：

    • 输出是合法 JSON（在实现正确且 schema 受支持时）
    • 枚举/必填/类型/部分范围约束不会被违反

    它不能保证：

    • 值在现实世界里正确
    • 跨字段业务规则成立
    • 模型没有把错误信息填进合法结构
    • 所有 JSON Schema 关键字都被支持

    常见限制：

    • oneOf/anyOf/递归/复杂 regex 可能不支持或性能很差
    • format 可能只是注解
    • tokenizer 的空白、Unicode、转义会影响 mask
    • 约束解码有额外开销；高并发要测吞吐
    • 结构化输出可能要求 additionalProperties: false、所有字段都进 required，具体看厂商

    不要自己手写一个“JSON 状态机”上生产。用成熟实现，并用自己的 schema 做回归测试。JSON Schema 的基础见 Understanding JSON Schema。

    4. 校验、修复和重试¶

    即使生成端做了约束，运行时仍要校验，因为模型/引擎/版本都可能出问题。

    推荐链路：

    raw text
  → 严格 json.loads
  → 失败才尝试提取代码块/首个 JSON 对象（记录日志）
  → JSON Schema 校验
  → 语义/业务规则校验
  → 接受 / 带错误重试 / 降级

    处理原则：

    • 先严格解析：不要一上来就用正则抠 JSON；先把原始输出保留下来。
    • 错误带路径：告诉模型 needs_human: expected boolean，比“格式不对”有用。
    • 重试有上限：2～3 次足够；每次带原始输出、schema 和具体错误。
    • 不要静默强转："yes" 不要自动变成 true；这会掩盖模型没遵循契约。
    • 确定性修复要保守：去掉代码围栏、trailing comma 可以；改字段名/猜值不可以。
    • 修复要审计：记录修了什么；修复率突然上升通常说明上游变了。
    • 语义检查单独做：跨字段、金额、日期、权限、引用、业务规则都不属于 JSON Schema。

    重试提示可以很短：

    上一次输出违反了 schema：
- needs_human: expected boolean, got string

请只修复这些错误，保持其他字段不变，重新输出完整 JSON。

    不要把所有历史对话和整篇文档再塞一遍；错误路径 + 原输出 + schema 通常够。

    5. 语义正确是另一层¶

    schema 只能证明“形状对”，不能证明“内容对”。

    例子：

    {"category":"billing","priority":"high","summary":"API returns 500 on every login","needs_human":true,"confidence":0.90}

    这个对象完全符合上面的 schema，但分类明显错了。约束解码会很高兴地生成它，JSON Schema 也会通过。

    语义检查包括：

    • 跨字段一致性：start <= end、priority=high 是否要求 needs_human=true
    • 业务规则：退款金额不能超过订单金额；日期不能是未来
    • 引用/grounding：摘要里的结论能否回到原文
    • 权限：这个用户能不能看到这个工单
    • 分类/抽取准确率：和 gold label 比

    这些检查通常要用代码、规则、检索或人工，不要指望 schema 或一句 prompt 解决。

    6. 服务化细节¶

    • 截断：max tokens 太小会在 JSON 中间截断；检查 finish_reason，不要解析半截。
    • 流式：可以流式展示，但不要在对象完整前执行写操作；需要增量解析就使用流式 JSON parser。
    • 超时/重试：重试是新的生成，成本和延迟都会增加；和普通请求一样要有 deadline。
    • 缓存：同输入、prompt、schema、模型/参数版本才可复用；schema 变了不能命中旧缓存。
    • 版本：记录模型、prompt、schema、约束引擎版本；否则线上回归无法定位。
    • 降级：多次失败返回 422/人工处理，比把坏 JSON 写进下游好。

    7. 评测¶

    至少分开看：

    指标 说明
    JSON parse rate 能否解析
    schema pass rate 字段/类型/枚举/必填是否通过
    semantic accuracy 分类/抽取/业务规则是否正确
    field-level F1 抽取任务按字段算
    repair/retry rate 有多少请求需要修复
    latency/cost 约束解码和重试的代价
    failure distribution 缺字段、类型错、枚举错、截断各多少

    测试集要覆盖：

    • 代码围栏、前后废话、trailing comma
    • 错误类型、缺字段、多字段、null
    • 枚举边界、空字符串、超长文本
    • Unicode、转义、数字/布尔混淆
    • 截断、超时、空输出
    • schema 合法但语义错误
    • 不同模型、temperature、schema 版本

    只统计 json.loads 通过率不够；只统计 schema 通过率也不够。最终要回到任务正确率。

    8. 实验：JSON 校验/重试漏斗¶

    这个实验用 8 个脚本样本覆盖常见失败模式，不是模型跑分，也不代表某个模型的真实成功率。

    样本包括：

    • 正常 JSON
    • Markdown 代码围栏
    • 前后带解释文字
    • trailing comma
    • needs_human 类型错
    • 缺 confidence
    • 多一个 urgency
    • schema 合法但分类错

    实验流程：严格解析 → 提取/保守修复 → schema 校验 → 带错误重试 → 语义检查。

def validate(schema, value, path="$"):
    errors = []
    kind = schema.get("type")
    if kind == "object":
        if not isinstance(value, dict):
            return [f"{path}: expected object"]
        props = schema.get("properties", {})
        if schema.get("additionalProperties") is False:
            for key in value:
                if key not in props:
                    errors.append(f"{path}.{key}: additional property")
        for key in schema.get("required", []):
            if key not in value:
                errors.append(f"{path}.{key}: required")
        for key, sub in props.items():
            if key in value:
                errors.extend(validate(sub, value[key], f"{path}.{key}"))
        return errors
    if kind == "string":
        if not isinstance(value, str):
            return [f"{path}: expected string"]
        if "enum" in schema and value not in schema["enum"]:
            errors.append(f"{path}: not in enum")
        if len(value) < schema.get("minLength", 0):
            errors.append(f"{path}: too short")
        if "maxLength" in schema and len(value) > schema["maxLength"]:
            errors.append(f"{path}: too long")
        if "pattern" in schema and not re.fullmatch(schema["pattern"], value):
            errors.append(f"{path}: pattern mismatch")
        return errors
    if kind == "number":
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            return [f"{path}: expected number"]
        if "minimum" in schema and value < schema["minimum"]:
            errors.append(f"{path}: below minimum")
        if "maximum" in schema and value > schema["maximum"]:
            errors.append(f"{path}: above maximum")
        return errors
    if kind == "boolean":
        return [] if isinstance(value, bool) else [f"{path}: expected boolean"]
    return [f"{path}: unsupported schema type {kind}"]


def parse_payload(raw):
    try:
        return json.loads(raw), "raw"
    except json.JSONDecodeError:
        pass
    start, end = raw.find("{"), raw.rfind("}")
    if start < 0 or end < start:
        raise ValueError("no JSON object found")
    candidate = raw[start:end + 1]
    try:
        return json.loads(candidate), "extract"
    except json.JSONDecodeError:
        pass
    # demo only: this can damage commas inside strings
    repaired = re.sub(r",\s*([}\]])", r"\1", candidate)
    return json.loads(repaired), "repair"


def semantic_ok(parsed, expected):
    for key, want in expected.items():
        if parsed.get(key) != want:
            return False, f"{key}={parsed.get(key)!r} expected={want!r}"
    return True, ""


def run(sample):
    raw_ok = True
    try:
        json.loads(sample["raw"])
    except json.JSONDecodeError:
        raw_ok = False
    try:
        parsed, mode = parse_payload(sample["raw"])
        parse_ok = True
    except ValueError:
        parsed, mode, parse_ok = {}, "fail", False
    first_errors = validate(SCHEMA, parsed)
    retry_used = False
    if first_errors and "retry" in sample:
        retry_used = True
        try:
            parsed, retry_mode = parse_payload(sample["retry"])
            parse_ok = True
        except ValueError:
            retry_mode, parse_ok = "fail", False
        mode = f"{mode}->retry:{retry_mode}"
    final_errors = validate(SCHEMA, parsed)
    semantic, reason = semantic_ok(parsed, sample["expected"])
    return {
        "id": sample["id"],
        "raw_ok": raw_ok,
        "parse_mode": mode,
        "parse_ok": parse_ok,
        "first_errors": first_errors,
        "final_errors": final_errors,
        "retry": retry_used,
        "semantic": semantic,
        "reason": reason,
    }


if __name__ == "__main__":
    results = [run(sample) for sample in SAMPLES]
    for r in results:
        first = "ok" if not r["first_errors"] else "FAIL"
        final = "ok" if not r["final_errors"] else "FAIL"
        sem = "ok" if r["semantic"] else f"FAIL({r['reason']})"
        print(
            f"sample {r['id']} raw={'ok' if r['raw_ok'] else 'FAIL'} "
            f"parse={r['parse_mode']} schema1={first} retry={int(r['retry'])} "
            f"schema2={final} semantic={sem}"
        )
    total = len(results)
    print("\nsummary")
    print("raw_json      ", f"{sum(r['raw_ok'] for r in results)}/{total}")
    print("parsed        ", f"{sum(r['parse_ok'] for r in results)}/{total}")
    print("schema_first  ", f"{sum(not r['first_errors'] for r in results)}/{total}")
    print("schema_final  ", f"{sum(not r['final_errors'] for r in results)}/{total}")
    print("semantic      ", f"{sum(r['semantic'] for r in results)}/{total}")

    9. 常见坑¶

    1. 把 JSON mode 当 schema 约束 能 parse 不代表字段、类型、枚举正确。

    2. 只在 prompt 里写“只输出 JSON” 模型仍可能加解释、代码围栏或漏字段。

    3. schema 太松 没有 additionalProperties: false、没有 required，错误字段会混过去。

    4. 只校验 JSON 语法 {"needs_human":"yes"} 是合法 JSON，但不是合法 boolean。

    5. 静默强转 把 "yes" 改成 true、把字符串数字改成 number，会掩盖契约违反。

    6. schema 合法就当正确 分类/抽取错值仍然符合 schema。

    7. 重试不带错误信息 模型不知道哪里错，容易重复同样的输出。

    8. 无限重试 浪费成本，还会放大延迟；要设上限和降级。

    9. 修复逻辑太激进 猜字段、改值、正则乱替换，会把问题藏起来。

    10. 把 format 当强制校验 日期/邮箱等格式是否强制取决于实现。

    11. 忽略截断 只看到 { 就开始解析，或把半截 JSON 写库。

    12. 流式结果提前执行 JSON 还没闭合就调用工具/写数据库。

    13. 没有版本记录 schema、prompt、模型、约束引擎变了，回归无法定位。

    10. 要点回顾¶

    1. 结构化输出分三层：JSON 语法、schema、语义；只过第一层不够
    2. 先写清楚 schema：类型、枚举、必填、额外字段、范围、可空、版本
    3. JSON mode 只保证可解析；schema 约束/structured outputs 才约束结构
    4. 约束解码在生成端 mask 无效 token；在支持子集内保证语法/schema，不保证语义
    5. function calling 的参数仍要在运行时校验；schema 不是权限边界
    6. 运行时链路：严格解析 → schema 校验 → 语义/业务检查 → 重试/降级
    7. 修复要保守、可审计、有上限；不要静默强转
    8. 评测同时看 parse、schema、semantic、修复率、延迟/成本
    9. 实验里 schema 最终 8/8，但语义只有 7/8：合法 JSON 不等于正确输出
