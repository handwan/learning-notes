    应用评测¶

    模型评测回答“模型能力怎么样”；应用评测回答“这个产品在真实任务上能不能用、有没有变坏”。

    两者不能互相替代：

    模型 benchmark 高分
  ≠ RAG 能召回正确文档
  ≠ Agent 会选对工具
  ≠ 拒答/权限/格式都正确
  ≠ 线上延迟和成本可接受

    这篇讲应用级评测集、判分、回归门禁和线上指标，最后建一个 30 条回归集，用两个脚本版本演示“总分提升但安全回归”。RAG 评测见 RAG；Agent 轨迹见 Agent 与工具调用；模型评测/安全见 LLM 第 9 篇。

    1. 先定义任务¶

    “应用成功”必须先写成可判定的条件。否则评测会退化成“看起来还行”。

    一个客服助手可以定义：

    维度 成功条件
    回答 包含正确事实，且引用正确文档
    拒答 证据不足时明确拒绝，不编造
    工具 选对工具，参数正确，不越权
    安全 不泄露密钥/跨租户数据，不执行注入指令
    结构化 JSON 可解析，字段/类型/枚举正确
    体验 p95 延迟、成本、错误率在预算内

    注意：

    • 任务成功是二值还部分得分，要提前定；不要评测完再改标准。
    • 事实正确、引用正确、格式正确要分开，不然定位不了问题。
    • 安全是硬条件，不和“回答得漂亮”做加权平均。
    • 多轮任务要看最终状态，不只看最后一句话。

    2. 回归集怎么建¶

    30 条不是“随便写 30 个问题”，而是按风险和失败模式分层。

    一个可用的分层：

    组 数量 例子 判分
    正常回答 10 退款、发票、SSO、限流 事实 + 引用
    不可回答 6 私人手机号、未公开路线图 必须拒答
    工具调用 6 查订单、查发票、搜帮助 工具名 + 参数
    安全 4 系统 prompt、跨租户、注入 拒绝 + 无危险动作
    结构化 4 意图/紧急度抽取 JSON + 字段

    来源优先级：

    1. 线上事故和用户投诉
    2. 客服/人工工单里的常见问题
    3. 红队/注入/越权用例
    4. 产品需求和边界条件
    5. 最后才是“编几个看起来像的问题”

    每条 case 至少记录：

    id, slice, input, must, must_not, source, owner, tags

    还要记录评测时的：

    app_version, model, prompt_version, schema_version, tool_versions

    否则两周后你不知道这个分数对应哪个版本。

    30 条够做冒烟/回归门禁，不够证明统计显著性。它应该持续长，不是一次写完就冻结。

    3. 指标¶

    至少分开看：

    指标 说明
    task success 通过 case 数 / 总数
    slice success 每个分组的通过率，防止平均掩盖短板
    retrieval recall@k gold 文档是否被召回
    citation correctness 引用是否支持结论
    refusal rate 该拒答时是否拒答
    tool selection / arg exact 工具名和参数是否正确
    schema pass rate JSON/字段/类型是否合法
    safety violation 越权、泄漏、注入成功；目标为 0
    p95 latency / cost 体验和预算
    error/timeout/cancel 失败率，不要只统计成功请求

    不要只报一个总分：

    • 总分 +4 可能来自简单题，同时安全从 3/4 掉到 2/4。
    • 通过率 90% 可能意味着 10 个安全 case 全错，只是占比小。
    • 平均值会掩盖长尾和特定租户/语言的失败。

    随机系统要重复跑：

    • 同一 case 跑 N 次，报 mean 和最差，不只报一次最好结果。
    • Agent 任务可用 pass^k 这类“k 次都成功”的指标；参考 τ-bench。
    • 安全用 any-violation：只要有一次越权，就不能当通过。

    4. 判分器¶

    优先级：

    1. 程序化判分：精确匹配、包含、JSON Schema、工具名/参数、数据库状态。
    2. 规则/检索判分：引用是否能回到原文，权限是否被遵守。
    3. LLM-as-judge：开放式回答、语气、帮助性；需要校准。
    4. 人工：高风险、争议、抽样审计。

    LLM-as-judge 的注意点：

    • 有位置偏差、长度偏差、自我偏好；要换顺序/多 judge/人工校准。
    • 不能把 judge 当 ground truth；要报告 judge 版本和 prompt。
    • 对安全/权限/金额这类硬条件，优先程序化检查。
    • 判分 rubric 要具体到“什么算通过”，不要只说“回答得好”。

    程序化判分也有坑：

    • 字符串包含会误判（“不支持退款”包含“退款”）。
    • 精确匹配会漏掉同义表达；抽取任务更适合字段级比较。
    • JSON 能 parse 不等于 schema 对；schema 对不等于语义对。
    • 测试用例不能泄漏进 prompt 或训练集。

    5. 回归门禁¶

    每次改动都跑同一套回归集，对比 baseline 和 candidate：

    candidate vs baseline
  → 总分变化
  → 每个 slice 变化
  → 新增失败 case
  → 安全/权限/格式硬指标
  → 延迟/成本

    门禁规则要提前写死：

    • 任何安全违规：BLOCK。
    • 工具参数错误/越权：BLOCK 或人工复核。
    • 关键 slice 通过率下降超过阈值：BLOCK。
    • p95 延迟/成本超预算：BLOCK 或降级。
    • 已知失败要有 owner、原因、豁免期限；不能默默忽略。

    门禁不是“总分不低于 baseline 就发”。一个版本可以总分更高、但把安全搞坏；这类版本不能上。

    6. 线上指标¶

    离线回归集覆盖不了真实分布，线上要看：

    • 任务成功率/人工接管率/转人工率
    • 用户反馈（点赞/点踩/重试/追问）
    • 工具错误率/超时/限流
    • 安全拦截/越权尝试/注入告警
    • p95 延迟、token、单任务成本
    • 按租户/语言/渠道/模型版本分片

    上线方式：

    • shadow：只记录不生效，先看分布
    • canary：小流量，设自动回滚阈值
    • A/B：看任务成功和成本，不只看点击
    • 人工抽检：高风险/低置信样本

    线上反馈要回流到回归集，但要去重、脱敏、标注，不要直接把用户数据塞进 prompt。

FAILURES = {
    "v1": {"A03", "A07", "U02", "U05", "T01", "T04", "S02", "J02", "J03"},

def good_output(case):
    kind = case["kind"]
    if kind == "answer":
        return {"type": "answer", "text": case["gold"] + "。", "citations": [case["cite"]]}
    if kind == "unanswerable":
        return {"type": "refusal", "text": "证据不足，无法回答。", "citations": []}
    if kind == "tool":
        return {"type": "tool_call", "tool": case["tool"], "args": case["args"]}
    if kind == "safety":
        return {"type": "refusal", "text": "不能提供该信息或执行该操作。", "citations": []}
    return {"type": "json", "value": case["expected"]}


def bad_output(case):
    kind = case["kind"]
    if kind == "answer":
        return {"type": "answer", "text": "我不知道。", "citations": []}
    if kind == "unanswerable":
        return {"type": "answer", "text": "大概是 42。", "citations": []}
    if kind == "tool":
        return {"type": "tool_call", "tool": "search_help", "args": {"query": case["q"]}}
    if kind == "safety":
        return {"type": "unsafe", "text": f"here is {case['forbidden'][0]}", "citations": []}
    return {"type": "json", "value": {"intent": case["expected"]["intent"]}}


def run_system(case, version):
    return bad_output(case) if case["id"] in FAILURES[version] else good_output(case)


def grade(case, output):
    kind = case["kind"]
    if kind == "answer":
        text = output.get("text", "")
        cites = output.get("citations", [])
        ok = output.get("type") == "answer" and case["gold"] in text and case["cite"] in cites
        return ok, "answer/citation"
    if kind == "unanswerable":
        ok = output.get("type") == "refusal" and "证据不足" in output.get("text", "")
        return ok, "refusal"
    if kind == "tool":
        ok = (output.get("type") == "tool_call"
              and output.get("tool") == case["tool"]
              and output.get("args") == case["args"])
        return ok, "tool/args"
    if kind == "safety":
        text = output.get("text", "")
        ok = output.get("type") == "refusal" and not any(x in text for x in case["forbidden"])
        return ok, "safety"
    ok = output.get("type") == "json" and output.get("value") == case["expected"]
    return ok, "json/schema"


def evaluate(version):
    rows = []
    for case in CASES:
        output = run_system(case, version)
        ok, check = grade(case, output)
        rows.append({"id": case["id"], "kind": case["kind"], "ok": ok, "check": check})
    passed = sum(r["ok"] for r in rows)
    by_kind = {}
    for kind in ["answer", "unanswerable", "tool", "safety", "json"]:
        subset = [r for r in rows if r["kind"] == kind]
        by_kind[kind] = (sum(r["ok"] for r in subset), len(subset))
    failed = [r["id"] for r in rows if not r["ok"]]
    failed_by_kind = {
        kind: [r["id"] for r in rows if r["kind"] == kind and not r["ok"]]
        for kind in by_kind
    }
    return {"version": version, "passed": passed, "total": len(rows),
            "by_kind": by_kind, "failed": failed, "failed_by_kind": failed_by_kind}


def show(result):
    parts = " ".join(f"{k}={v[0]}/{v[1]}" for k, v in result["by_kind"].items())
    rate = result["passed"] / result["total"]
    print(f"{result['version']} total={result['passed']}/{result['total']} ({rate:.1%}) {parts}")
    print(f"  failed: {' '.join(result['failed']) or 'none'}")


if __name__ == "__main__":
    v1 = evaluate("v1")
    v2 = evaluate("v2")
    show(v1)
    show(v2)

    8. 常见坑¶

    1. 只报一个总分 平均分会掩盖安全、工具、某个租户的退化。

    2. 用模型 benchmark 代替应用评测 benchmark 高分不代表 RAG/工具/拒答/格式都对。

    3. 测试集和 prompt 混在一起 把 case 写进 system prompt，分数虚高；要隔离。

    4. 只测正常路径 没有不可回答、工具错误、超时、越权、注入。

    5. 判分标准模糊 “回答得好”不可复现；要写 must/must_not 和 rubric。

    6. 字符串包含当语义判断 “不支持退款”会被“退款”命中；要按任务设计判分。

    7. LLM judge 不校准 judge 有偏差；要人工抽检、多 judge、换顺序。

    8. 只看新增失败 历史安全失败也不能带病发布；要有豁免和期限。

    9. 小样本过度解读 30 条差 1 条可能只是波动；安全硬失败除外。

    10. 不固定版本 模型/prompt/schema/工具变了，分数无法比较。

    11. 只看离线 线上分布、延迟、成本、用户行为可能完全不同。

    12. 反馈数据直接进测试集 泄漏、过拟合、隐私问题；要脱敏、去重、审核。

    9. 要点回顾¶

    1. 模型评测和应用评测是两件事；应用要看端到端任务成功
    2. 回归集按风险分层：正常、不可回答、工具、安全、结构化
    3. 指标要看总分 + slice + 安全/工具/格式 + 延迟/成本
    4. 判分优先程序化，LLM-as-judge 只做辅助并校准
    5. 随机系统重复跑；安全用 any-violation，不用平均
    6. 回归门禁提前定；安全/权限/关键 slice 是硬条件
    7. 总分提升不能抵消安全回归；实验里 v2 +4 但仍 BLOCK
    8. 线上用 shadow/canary/A-B/人工抽检，反馈回流要脱敏
    9. 30 条是回归冒烟集，不是统计显著性的证明
