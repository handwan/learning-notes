    CPU 与流水线¶

    一条指令要经过"取指→译码→执行→访存→写回"——流水线让多条纹令重叠执行，而"流水线被打断"就是性能问题的直接来源（分支预测、依赖、缓存缺失）。

    1. 指令周期与数据通路¶

    取指(IF) → 译码(ID) → 执行(EX) → 访存(MEM) → 写回(WB)
    • 数据通路：寄存器堆、ALU、存储器之间传数据的线路（教材里画很多图）
    • 控制器：产生控制信号——硬布线（快但改不了）vs 微程序（灵活但慢，教材考点，现代 CPU 用硬布线为主）
    • 这两块属于"硬件怎么搭"（细节见速查篇）；工程上要记的是：每条指令的这 5 步是可以重叠的↓

    2. 流水线：5 级重叠¶

    时钟:      T1   T2   T3   T4   T5   T6
指令1:     IF   ID   EX  MEM   WB
指令2:          IF   ID   EX  MEM   WB
指令3:               IF   ID   EX  MEM   WB
→ 理想情况：每周期完成 1 条（CPI = 1）

    三类冒险（流水线被打断的原因）：

    冒险 原因 解决
    结构冒险 硬件资源冲突（同时要访存） 增加端口/分离指令缓存与数据缓存
    数据冒险 后一条要用前一条的结果 转发（forwarding）、流水线停顿（stall）
    控制冒险 分支跳转，不知道下一条取哪 分支预测 + 预测失败冲刷

    实测：分支预测的威力（同样 6700 万次比较，只是数据顺序不同）：

    数据 耗时
    有序（分支高度可预测） 基准
    打乱（随机分支） 慢约 10 倍

    读法：两次执行的指令条数几乎一样，差距全在"预测失败 → 流水线清空重来"（一次失败损失十几个周期）。所以：

    • 热点循环里减少不可预测的分支（用无分支写法：位运算/cmov/数学技巧）
    • 编译器可能把 if 变成条件传送（实测：不加 -fno-if-conversion 时这个基准测不出差距）——说明"写出什么"和"生成什么"是两回事

    3. 超标量、乱序与 IPC¶

    现代 CPU 不止"一条流水线"：

    • 超标量：每周期取/发射多条指令（宽度 4~8）
    • 乱序执行：不按程序顺序执行，只看数据依赖——用 寄存器重命名 + 重排序缓冲 保证结果正确
    • 推测执行：分支预测后先执行，猜错再回滚（Spectre 等安全漏洞就来自这里）

    指标：IPC = 每周期完成指令数（理想 1，超标量可 >1）；CPI = 1/IPC。

    为什么 IPC 上不去：

    1. 分支预测失败（控制冒险）
    2. 依赖链：后一条指令必须等前一条（延迟绑定）
    3. 缓存缺失（等内存 ~100 ns，见存储篇）

    实测：依赖链 vs 独立链（同样是 2 亿次加法）：

    写法 耗时
    单条链 x = x + 1（每步依赖前一步） 基准
    拆成 4 条独立链（可并行执行） 快 1.6 倍

    结论：做多个独立累加器/分块计算，让 CPU 的乱序引擎有活干——这就是"循环展开/多累加器"优化的原理。

    4. SIMD：一条指令算一批数据¶

    SIMD（单指令多数据）：SSE/AVX 一条指令处理 4/8 个 float；编译器能自动向量化（-O3 -march=native），也可手写 intrinsics。

    实测（1600 万 float 加法，自动向量化 -O2）：

    指标 实测
    算力 偏低（不是瓶颈）
    内存流量 读 2 数组 + 写 1 数组 = 200 MB → ~5 GB/s（带宽受限）

    关键认知：加法本身是算力无限的（SIMD 白送），但这里被内存带宽卡住（5.2 GB/s ≈ 本机顺序读带宽）——"向量化没提速"常常不是指令问题，是数据没进缓存/带宽不够。优化顺序：先数据布局（连续、分块、SoA），再谈 SIMD。（具体数字随实现/编译选项浮动，结论一致：都是内存受限）

    （perf 计数器能直接看 IPC/缓存缺失率，但本项目环境是 WSL、perf 不可用——用"墙钟时间 + 对照实验"替代；裸机上 perf stat 是首选工具。更细的对比见 §5：自动向量化 vs 手写 AVX2。）

    5. 深入：分支预测怎么做的、乱序执行怎么跑的¶

    分支预测器（硬件里的一整套机制）¶

    级别 做法 特点
    静态预测 总是跳/总是不跳、向后跳预测为跳（循环） 编译期决定，简单
    1 位动态 记录"上次跳没跳" 循环最后一次会猜错
    2 位饱和计数器 连续两次猜错才翻转 循环场景几乎不猜错
    两级/相关预测 用"全局历史 + 分支地址"索引 能识别模式
    TAGE 类（现代） 多张不同长度的历史表投票 预测率 95%+（但 5% 失败就是 10 倍差距）

    预测失败的代价（用实测反推）：随机分支比有序慢约 10 倍，折算到 6700 万次循环 → 每次预测失败约 15~20 个周期（流水线被冲刷重填）——这就是"分支密集 + 不可预测"的代码为什么慢。

    写代码的启示：热点里排序数据（让分支可预测）、用无分支写法（cmov/位运算/查表）、或让编译器把短分支转成条件传送。

    乱序执行是怎么"快"的¶

    前端：取指 → 译码（x86 变长指令 → 微操作）
      ↓
乱序核心：
  ① 寄存器重命名 —— 消除"假依赖"（写后写/写后读）
  ② 发射队列/调度器 —— 谁的源操作数都齐了就发给执行单元
  ③ 重排序缓冲（ROB）—— 按程序顺序提交结果（保证正确性）
      ↓
后端：多个执行单元（ALU/FP/SIMD/访存），每周期发射 4~8 条

    启示：CPU 会自动利用指令间的并行性——但写代码要给它"素材"：

    • 少写依赖链（多累加器/循环展开，实测 1.6 倍）
    • 让访存与计算交错（预取/流水线化），别让 ROB 填满等待
    • 控制流可预测（上一条）

    推测执行的安全代价：Spectre/Meltdown——CPU 会执行"预测路径"，虽然结果被丢弃，但缓存状态留下了痕迹，可以被侧信道读出（安全领域的大话题，理解到这里即可）。

    SIMD：自动向量化 vs 手写¶

    实测（1677 万 float 的 z = x + 2y）：

    写法 耗时 带宽
    自动向量化（-O3 -march=native） 基准 ~10 GB/s
    手写 AVX2（8 宽） 快 2.7 倍 ~26 GB/s

    读法：编译器自动向量化不一定到顶（这里的差距来自向量宽度/指令选择）；性能关键路径要看汇编（objdump -d）+ 必要时手写 intrinsics。另外别忘 FMA（a*b+c 一条指令）——AI 推理里的算力数字（TFLOPS）都按 FMA 计。

    测量工具：本项目是 WSL，perf 没装、rdtsc 读数不动 → 全部用墙钟 + 对照实验；裸机上 perf stat -e cycles,instructions,branch-misses,cache-misses 是分析 IPC 的首选。

    6. 数据冒险实例：load-use 与转发¶

    能转发（不停顿）：ALU 结果在 EX 末尾就能"旁路"给下一条：

    I1: add x1, x2, x3     ← EX 出结果
I2: sub x4, x1, x5     ← 下一条就用 x1：转发路径直接送过来

    不能转发（要停 1 拍）：load 的结果要到 MEM 末尾才有：

    I1: lw  x1, 0(x2)      ← MEM 阶段才拿到数据
I2: add x3, x1, x4     ← EX 阶段就需要 x1
时间线：IF ID EX MEM        I1
            IF ID [停顿] EX MEM   I2 ← 插了 1 个气泡

    怎么减少停顿：

    • 编译器调度：把无关指令插进气泡（指令重排）
    • 乱序执行：硬件自动去执行后面就绪的指令（不用等）
    • 写代码：拉远"载入-使用"的距离（别紧挨着用刚读的值）

    这和前面的实测对得上：依赖链拆分后变快，就是"停顿被乱序引擎用别的指令填上"的证据。

    7. 流水线的量化（教材公式 + 实测对照）¶

    k 段流水线执行 n 条指令（理想、每段 1 周期）：

    总周期 = k + (n - 1)          （填满流水线 k 拍，之后每拍出 1 条）
吞吐率 = n / (k + n - 1) 周期/条 → n 大时 ≈ 1 条/周期
加速比 = 串行周期数 / 流水线周期数 ≈ k（段数）—— 理想上限

    实测对照：加法吞吐"单条依赖链 vs 4 条独立链 = 1.6 倍"——理想是接近 4 倍（4 个执行单元），差的那部分是发射宽度/延迟的限制；而分支预测失败（10.9 倍差距）就是"流水线被清空重填"（公式里的 k 拍白白浪费）。

    两个推论：

    • 流水线加深（段数 k 变大）能提吞吐，但冒险代价也变大（现代 CPU 流水线 15~20 级，一次预测失败损失 15~20 拍）
    • 指令数少不一定快：CPI 被冒险拖高就白搭——三要素要一起看（概述篇）

    8. 两个"知道名字"的机制¶

    • 动态调度算法 Tomasulo：乱序执行的经典算法（1967，IBM 360/91）——用"保留站 + 寄存器重命名"消除假依赖；现代 CPU 发射队列的思想一脉相承（知道它解决什么即可，不必会推演）
    • 精确异常（precise exception）：异常发生时"之前的全完成、之后的没发生"——靠 ROB 按序提交保证；这是乱序执行与异常/中断共存的关键（细节见 OS/体系结构教材）

    9. 要点回顾¶

    1. 指令周期 5 步：IF/ID/EX/MEM/WB；流水线让相邻指令重叠 → 理想 CPI=1
    2. 三类冒险：结构（加硬件）、数据（转发/停顿）、控制（分支预测）
    3. 分支预测失败代价巨大：实测随机分支比有序慢 10.9 倍（指令数一样）
    4. 超标量 + 乱序 + 推测执行 = IPC 可以 >1；上不去的原因：分支、依赖链（实测 1.6 倍差距）、缓存缺失
    5. 依赖链优化：多累加器/循环展开——让乱序引擎并行起来
    6. SIMD：算力白送但常被内存带宽卡住（实测 0.43 GFLOP/s、5.2 GB/s）→ 先布局后向量化
    7. perf 看 IPC/缺失率最直接（本项目 WSL 下不可用，用对照实验代替）
    8. 分支预测器：2 位计数器/历史相关/TAGE；失败代价 ~15-20 周期（实测反推）
    9. 乱序执行：寄存器重命名 + 发射队列 + ROB；写代码要"喂素材"（破依赖链、可预测分支）
    10. SIMD 别迷信自动向量化：手写 AVX2 实测快 2.7 倍（26.3 vs 9.6 GB/s）
