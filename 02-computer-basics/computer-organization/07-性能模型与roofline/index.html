    性能模型与 roofline¶

    性能优化最怕"瞎试"——roofline 模型用两个上限（算力、带宽）告诉你"这段代码卡在哪、值不值得上 GPU"。

    1. 算术强度：算得比搬得多吗¶

    算术强度（Arithmetic Intensity, AI）= 浮点运算次数 / 访存字节数   （FLOP/Byte）
    • AI 高（算得多、搬得少）→ 瓶颈是算力（compute-bound）
    • AI 低（算得少、搬得多）→ 瓶颈是带宽（memory-bound）

    两个实测例子：

    负载 运算量 访存 算术强度 实测性能
    矩阵乘 1024³ 2n³ = 21.5 亿 FLOP 3n²·4B ≈ 12.6 MB（理想） 170.7 FLOP/Byte 24.6 GFLOP/s（-O2 版；-O3 -march=native 见 §6）
    向量加法 1600 万 float 1670 万 FLOP 200 MB 0.083 FLOP/Byte 0.64 GFLOP/s（7.6 GB/s，-O3 -march=native）

    读法：矩阵乘每个字节做 170 次运算（算力吃紧）；向量加法每个字节只做 0.08 次（带宽吃紧）——同一个"优化提速"，两边要干的事完全不同。

    2. roofline 图¶

    性能
(GFLOP/s)
  │            ┌──────────── 峰值算力（水平线，如单核 ~112 GFLOP/s AVX2 FMA）
  │           /
  │          /   ← 带宽斜线：性能 = 带宽 × 算术强度
  │         /       （本机 ~6 GB/s → 斜线斜率 = 6 GFLOP/s per FLOP/Byte）
  │        /
  │       /
  └──────┴────────────────────── 算术强度 (FLOP/Byte)
        ↑拐点 = 峰值算力 / 带宽 ≈ 112 / 6 ≈ 19 FLOP/Byte
    • 算术强度 < 拐点：在斜线上 → 无论 CPU 多强都卡带宽（提升只能靠减少访存）
    • 算术强度 > 拐点：在水平线上 → 卡算力（提升靠 SIMD/多核/GPU）

    实测定位：矩阵乘 AI=170.7 远高于拐点 ~19 → 理论在"算力区"；但实测只跑到 24.6 GFLOP/s（远低于峰值 ~112）→ 说明朴素循环顺序没做分块，实际还受缓存/带宽拖累——这正是"roofline 定位 + 下一步优化"的用法。

    3. 按瓶颈选手段¶

    瓶颈 手段 例子
    带宽（AI 低） 减少访存：分块（tiling）、算子融合、量化（FP16/INT8 直接减半字节数）、缓存友好布局 向量加法 → 量化/融合；GEMV → 分块
    算力（AI 高） 提高算力：SIMD 向量化、多线程、上 GPU/NPU、更快的低精度算力（Tensor Core） 矩阵乘 → GPU、Tensor Core
    延迟（单次操作慢） 缓存、预取、减少依赖链、异步/流水线 指针追逐 → 改数据布局
    串行部分 Amdahl：先打串行瓶颈再谈并行 见概述篇

    关键：先定位再优化——"矩阵乘慢"和"向量加法慢"的解法完全相反（前者加算力、后者减访存）。

    4. 实测：并行的收益也受模型约束¶

    • 多线程求和：1/2/4/8 线程 = 1.00/1.81/2.66/2.17×（内存带宽型负载，扩展受限，见并行篇）
    • 矩阵乘如果做分块（提高数据复用、降低带宽压力）→ 才可能从 24.6 GFLOP/s 往峰值靠
    • GPU 的本质：算力峰值高一个量级 + 显存带宽高几倍 → 算术强度高的工作负载（矩阵乘、卷积、attention）从斜线右侧跳一大截

    5. 性能分析流程（工程版）¶

    ① 量基线：同样的输入，测当前耗时（别凭感觉）
② 算强度：FLOP/Byte → 判断 compute-bound 还是 memory-bound
③ 找证据：perf 计数器（IPC/缓存缺失/分支失败）——本项目 WSL 无 perf，用对照实验
④ 动手：按瓶颈选手段（§3），一次只改一个变量
⑤ 复测：确认提升，并检查没有引入新瓶颈（Amdahl：串行部分会浮现）

    常见陷阱：微基准被编译器优化掉（实测中遇到多次：死代码消除/条件传送/向量化）；测的时候没做 warm-up；对比时输入规模不同。

    6. 深入实测：分块优化与算子矩阵¶

    用 roofline 指导一次真实优化（矩阵乘分块）¶

    实测（1024³，-O3 -march=native）：

    实现 算力 提速
    朴素 i-k-j ~33 GFLOP/s 1×
    分块（B=64） ~42 GFLOP/s 1.28×

    为什么分块有效：矩阵乘理想算术强度 170 FLOP/Byte，但朴素顺序反复把 B/C 从内存里拉（O(n³) 的访存）；分块后每块数据在缓存里反复用 → 实际带宽压力下降、更靠近"算力区"。结论：roofline 说"你是带宽受限"→ 手段就是提高数据复用（分块/tiling），实测 1.28 倍。

    不同算子的算术强度（实测）¶

    算子 算术强度（FLOP/Byte） 实测性能 落点
    向量加法 0.083 0.64 GFLOP/s（7.6 GB/s） 斜线（带宽受限）
    点积 0.25 3.31 GFLOP/s（13.2 GB/s） 斜线
    矩阵乘（n=1024） 170.7 32.7 GFLOP/s 水平线附近（算力受限）

    一张图记住：同样的"GFLOP/s 数字"，斜线上的算子怎么加核都上不去（带宽已满），水平线上的算子才值得堆算力（SIMD/多核/GPU）。

    GPU 为什么是"换一条 roofline"¶

    • 算力峰值：CPU 单核 ~100 GFLOP/s 级 → GPU 单卡 TFLOPS 级（高 1~2 个数量级）
    • 带宽：DDR ~几十 GB/s → 显存 几百 GB/s ~ TB/s
    • 所以算术强度高的算子（矩阵乘、卷积、attention）在 GPU 的 roofline 上"斜线右移 + 水平线抬高" → 收益巨大；而低强度算子（elementwise、加减）在 GPU 上依旧是带宽受限——搬来搬去反而更贵（PCIe 只有 ~32 GB/s，见总线篇）

    部署判据：算子够"方"（算得比搬得多）才值得上 GPU；否则先做融合/量化（减少字节数 = 提高算术强度）。

    优化收益的"经验顺序"（从便宜到贵）¶

    1. 算法/复杂度（砍掉无用的计算）        ← 收益最大、最便宜
2. 数据表示（量化/低精度/更小类型）
3. 数据布局（连续、SoA、分块、避免 4KB 步长）
4. 编译优化（-O3、-march、自动向量化）
5. 手写 SIMD / 多线程
6. 上 GPU / 多卡                       ← 最贵（改架构、数据搬运）

    7. 要点回顾¶

    1. 算术强度 = FLOP/Byte：决定 compute-bound 还是 memory-bound（矩阵乘 170.7 vs 向量加法 0.083，实测）
    2. roofline 两段：斜线（带宽限制）和水平线（算力限制），拐点 = 峰值算力/带宽（本机 ~19 FLOP/Byte）
    3. 矩阵乘实测 24.6 GFLOP/s 远低于单核峰值 ~112 → 朴素实现没分块；roofline 指出"下一步该做什么"
    4. 按瓶颈选手段：带宽型→减少访存（分块/融合/量化）；算力型→SIMD/多核/GPU；延迟型→缓存/预取/破依赖链
    5. GPU 的定位：把高算术强度的负载从"算力上限"直接抬高一个量级
    6. 流程：基线 → 强度 → 证据 → 单变量改动 → 复测；小心微基准的坑
    7. 这一篇是"推理性能优化"的理论底座（量化=降字节数、分块/融合=降访存、Tensor Core=提算力）
    8. 分块优化实测：矩阵乘 32.7 → 41.9 GFLOP/s（1.28×）——"提高数据复用"是带宽受限的标准解
    9. 优化顺序：算法 → 数据表示（量化）→ 布局/分块 → 编译选项 → SIMD/多线程 → GPU（越往后越贵）
