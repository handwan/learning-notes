    构建与调试¶

    编译型语言在 Docker 里的两个问题：构建时工具链太大、运行时镜像里没有调试工具。以 C/C++ 为主例，Go/Rust 同理；Python/Node 这类解释型语言见 §6。

    类型 例子 编译步骤 多阶段收益
    编译型 C/C++、Go、Rust 有 大：builder 编译，runtime 只拷产物
    字节码 Java、C# 有 中：builder 编译，runtime 只装运行时
    解释型 Python、Node 无（或只有打包/转译） 小：通常单阶段 + slim + 锁文件

    1. 多阶段构建¶

    思路：builder 阶段用完整工具链编译 → runtime 阶段只拷产物。

    # ---------- 阶段 1：builder（有完整工具链） ----------
FROM ubuntu:22.04 AS builder

RUN apt-get update && apt-get install -y \
    build-essential cmake git \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /src
COPY . .
RUN cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
    && cmake --build build -j"$(nproc)"

# ---------- 阶段 2：runtime（只要运行时） ----------
FROM ubuntu:22.04 AS runtime

RUN apt-get update && apt-get install -y libstdc++6 \
    && rm -rf /var/lib/apt/lists/*

COPY --from=builder /src/build/app /app/app
CMD ["/app/app"]

    效果：镜像从 1.5GB+ 降到 ~100MB。

    要点：

    • AS builder 给阶段起名
    • COPY --from=builder <路径> 从上一阶段拿产物
    • runtime 阶段只装运行时依赖（libstdc++6 等），不装编译器
    • rm -rf /var/lib/apt/lists/* 必须和 apt-get install 写在同一 RUN——分开写不减小体积（层机制）
    • .dockerignore 排除 .git、build/，别让它们进构建上下文

    只构建 builder 阶段（比如先验证编译）：

    docker build --target builder -t myapp-builder .

    其他编译型语言¶

    语言 builder 镜像 runtime 镜像 注意
    Go golang:1 scratch / gcr.io/distroless/static-debian12 CGO_ENABLED=0 才是静态二进制；用了 cgo 就要带 libc
    Rust rust:1 与 builder 同版本的 debian:*-slim 默认依赖 glibc；runtime 的 glibc 不能比 builder 旧；换 musl 目标才能进 scratch
    C/C++ ubuntu + build-essential ubuntu + libstdc++6 动态库用 ldd 查

    Go 的完整例子（静态二进制 + scratch）：

    FROM golang:1 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -o /out/app ./cmd/app

FROM scratch
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]

    scratch 里没有 CA 证书和时区文件；程序要发 HTTPS 请求或用时区，就从 builder 拷 /etc/ssl/certs/ca-certificates.crt、/usr/share/zoneinfo。

    2. 构建环境容器化¶

    目的：统一团队的编译器/CMake 版本（"我的 GCC 是 12，你的是 9"是常见事故源）。

    推荐团队维护一个预装工具链的镜像，构建时用当前用户，避免宿主留下 root 所有的文件：

    docker run --rm \
    --user "$(id -u):$(id -g)" \
    -v "$(pwd):/src" -w /src \
    myteam/cpp-toolchain:13 \
    bash -c "cmake -S . -B build && cmake --build build -j"

    myteam/cpp-toolchain:13 是示例名；实际换成团队自己构建并推送的镜像。

    临时用官方镜像、以 root 构建也可以，但要把产物改回当前用户：

    docker run --rm -v "$(pwd):/src" -w /src gcc:13 \
    bash -c "apt-get update -qq && apt-get install -y -qq cmake && \
             cmake -S . -B build && cmake --build build -j && \
             chown -R $(id -u):$(id -g) build"

    ⚠️ gcc 官方镜像不带 cmake——要么像上面那样在容器里装，要么自己准备一个"预装好工具链"的镜像（团队里更常见）。

    CI 里尤其常见：CI 机器只要装了 Docker，就能构建任意版本的工具链。

    3. BuildKit：缓存与密钥¶

    Docker 23+ 默认用 BuildKit；老版本加 DOCKER_BUILDKIT=1。

    缓存挂载¶

    普通层缓存只复用“指令没变”的层；依赖下载这类耗时操作，可以用 cache mount 跨构建复用，而且缓存不进最终镜像：

    RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

    cache mount 默认只在本机复用；CI 要跨机器缓存，用 buildx 的 --cache-to/--cache-from。

    密钥¶

    不要把 .env、.npmrc、私钥 COPY 进镜像；用 BuildKit secret，只在构建时挂载：

    RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci

    docker build --secret id=npmrc,src="$HOME/.npmrc" -t app .
    • secret 只在那条 RUN 里可见，不写入镜像层
    • --build-arg、--env 可能留在镜像历史/配置里，不能当 secret
    • CI 里用 --secret id=...,env=... 从环境变量传，别写进命令行历史

    4. 动态库（C/C++）¶

    C++ 程序常依赖 .so，容器里必须有：

    ldd ./app                 # 看依赖了哪些 .so

    三种策略：

    策略 做法 适用
    静态链接 -static（连 libc 一起静）或 -static-libstdc++ -static-libgcc（只静 C++ 运行时，更常用） 镜像里少装库
    拷 .so COPY --from=builder 把用到的 .so 一起拷 有第三方动态库时
    runtime 装包 apt-get install libxxx 系统库，版本能对上时

    -static 在 glibc 下并非所有程序都能用：NSS、dlopen 等场景会受限。C++ 项目更常见的是只静 libstdc++/libgcc，libc 仍用动态。

    alpine 的坑：alpine 用 musl libc，不是 glibc——glibc 编译的二进制不能直接在 alpine 跑；gcompat 兼容层也不保证 100%（复杂 C++ 程序常翻车）。图省事就用 ubuntu:22.04 / debian:bookworm-slim。

    拷 .so 时，同发行版、同 glibc 版本最稳；跨发行版拷贝很容易缺符号或加载器不匹配。拷到 /app/lib 后还要让加载器找得到：编译时加 -Wl,-rpath,/app/lib，或运行时设 ENV LD_LIBRARY_PATH=/app/lib。

    5. 调试容器¶

    ⚠️ 下面的 ptrace 权限仅开发调试用，生产环境不要开。

    运行镜像通常只装运行时，没有 gdb。三种做法：

    做法一：debug 阶段¶

    在多阶段 Dockerfile 里加一个 debug 阶段：

    FROM runtime AS debug

USER root
RUN apt-get update && apt-get install -y gdb \
    && rm -rf /var/lib/apt/lists/*

    docker build --target debug -t myapp-debug .
docker run --rm -it --cap-add=SYS_PTRACE --security-opt seccomp=unconfined \
    myapp-debug gdb /app/app

    要看源码：COPY --from=builder /src /src 把源码带进 debug 镜像，或运行时把源码挂到 /src。二进制要带调试信息；Release 默认没有，用 RelWithDebInfo 或单独保留符号。

    做法二：从另一个容器 attach¶

    调试容器和目标容器共享 PID 命名空间：

    docker run --rm -it \
    --pid=container:<c> \
    --cap-add=SYS_PTRACE --security-opt seccomp=unconfined \
    myapp-debug gdb -p 1

    PID 用目标容器内的 ps 查（单进程容器通常是 1）；docker top 显示的是宿主 PID，不能直接拿来用。

    做法三：目标镜像里装了 gdb¶

    docker exec -it <c> bash
gdb -p 1

    只有镜像里确实有 gdb 才可行；容器启动时也要有 ptrace 权限。

    core dump¶

    容器里的 core 大小由 Docker 的 ulimit 决定（可能继承宿主，也可能被设为 0）；先进容器 ulimit -c 确认，需要时用 --ulimit core=-1。core 存哪由宿主机 kernel.core_pattern 决定（容器里通常改不了）：

    # 宿主先看 core_pattern
cat /proc/sys/kernel/core_pattern
    • 以 | 开头：交给管道程序（apport、systemd-coredump 或宿主自己的 handler）处理，不会按 core_pattern 路径生成文件；用宿主机的 coredumpctl 或对应工具取。
    • 相对路径（如 core）：落在进程工作目录，可以 -w 到挂载卷。
    • 绝对路径：容器里要有对应的可写目录（通常挂载进去）。

    相对路径的用法：

    mkdir -p cores
docker run --ulimit core=-1 -v "$(pwd)/cores:/cores" -w /cores myapp

    容器里的用户要对 /cores 可写；非 root 运行时用 --user 对齐宿主 UID，或提前改好目录权限。

    6. 解释型语言：通常不需要多阶段¶

    Python/Node 没有编译成机器码的步骤。Docker 里直接单阶段即可：见 基础 §4 的 Python Dockerfile，换成 python:*-slim 基础镜像就是常见的最小写法。

    多阶段只在两种情况下值得：

    场景 做法
    依赖含 C 扩展，且没有预编译 wheel builder 装编译工具，pip wheel 产出 wheel；runtime 只装 wheel
    想把构建工具和缓存隔离出运行镜像 builder 负责构建，runtime 只拷产物

    Node/TypeScript 同理：有 npm run build（打包/转译）时，builder 跑构建，runtime 只拷 dist 和生产依赖。

    调试也不一样：Python 用 pdb/debugpy，Node 用 inspector；GDB 只用于 CPython 本身或 C 扩展。

    7. 一句话¶

    编译型：多阶段构建（builder 编译 → runtime 只拷产物）+ pin 基础镜像 + 动态库用 ldd 查清；解释型：单阶段 slim + 锁文件；调试工具单独做 debug 镜像。
