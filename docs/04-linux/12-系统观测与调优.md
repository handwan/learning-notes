# 系统观测与调优

按"CPU / 内存 / 磁盘 / 网络"四维看系统状态、用 sysctl/ulimit 调参、绑核与大页、容器底层的 namespace/cgroup，外加 perf 剖析、WSL 环境差异与部署检查清单。

## 1. 观测工具总览

| 维度 | 首选 | 看什么 |
|------|------|--------|
| CPU | `top` / `htop`、`vmstat`、`mpstat`、`pidstat` | 使用率、负载、每核、每进程 |
| 内存 | `free -h`、`/proc/meminfo`、`vmstat` 的 si/so | 可用内存、换页、OOM |
| 磁盘 | `iostat -x`、`iotop`、`df -hi` | %util、await、谁在读写 |
| 网络 | `ss -s`、`sar -n DEV`、`tcpdump` | 连接数、流量、抓包 |
| 历史 | `sar`（sysstat 收集） | "昨天三点发生了什么" |

> CPU/内存的基础（top、load average、僵尸进程）见 [进程与作业控制](04-进程与作业控制.md)；磁盘空间与 inode 见 [磁盘与文件系统](07-磁盘与文件系统.md)。

**随手看变化**：`watch -n 1 -d 'ss -s'`（每秒刷新、高亮变化——看计数怎么涨特别直观）。

**其他常用观测**：

```bash
pidstat -w 1 5            # 上下文切换/秒（sysstat）
slabtop -o                # 内核 slab 占用（排内核内存）
numastat                  # NUMA 命中/未命中统计
systemd-cgtop             # 按 cgroup 看 CPU/内存/IO
docker stats              # 容器资源（Docker 环境）
sudo bpftrace -l 'tracepoint:syscalls:*'  # 列出可追踪的 eBPF 探针
```

## 2. CPU 观测

```bash
vmstat 1 5                 # 每秒采样，共 5 次（sysstat 不是必须，procps 自带）
# 关键列：
# r  可运行队列长度（> 核数说明在排队）
# b  不可中断睡眠数（多在等 IO）
# us/sy/id/wa  用户态/内核态/空闲/IO 等待百分比
# si/so  换页（swap in/out，持续非 0 说明内存吃紧）

mpstat -P ALL 1 3          # 每个核的占用（sysstat 包）——找出"一个核跑满"的进程
pidstat -u 1 5             # 按进程看 CPU（sysstat 包）
pidstat -d 1 5             # 按进程看磁盘 IO

sar -u 1 5                 # CPU 使用率（sysstat）
sar -u -f /var/log/sysstat/sa20   # 看"20 号"的历史数据（排查过去的问题）
```

**负载怎么读**：`uptime` / `/proc/loadavg` 的 1/5/15 分钟平均值要**对着核数**看（`nproc`）——满负载大约是"核数 × 1"。

## 3. 内存观测

```bash
free -h
# 关键：available 才是"还能给新程序用多少"（不是 free）
# buff/cache 是可回收的缓存，别当成占用

vmstat 1 5                 # 看 si/so：持续非 0 = 真的在换页，内存不足
cat /proc/meminfo          # 全量字段：MemAvailable / Dirty / SwapCached / HugePages_*
```

**单进程内存**：

```bash
ps -eo pid,rss,vsz,cmd --sort=-rss | head       # RSS = 实际占用物理内存
pmap -x <pid> | tail -1                          # 进程地址空间汇总
cat /proc/<pid>/smaps_rollup                     # 更细的内存构成（Pss 是平摊共享后的）
```

**OOM（被系统杀掉）排查**：

```bash
sudo dmesg -T | grep -i "out of memory\|oom-kill"    # -T 显示可读时间
journalctl -k | grep -i oom                          # 内核日志里找
# 现象：进程"莫名消失"、exit code 137（= 128+9，被 SIGKILL）
```

## 4. 磁盘 IO 观测

```bash
iostat -x 1 5              # -x 扩展指标（sysstat 包）
# 关键列：
# %util    设备繁忙度（接近 100% = 饱和）
# await    平均 IO 等待（含排队，ms）
# r_await/w_await  读/写分开看
# aqu-sz   平均队列长度

NVMe/SSD 上 `%util` 不一定能代表饱和；结合 `await`、`aqu-sz` 和吞吐一起看。

sudo iotop -oPa            # 谁在读写（-o 只显示有 IO 的、-P 按进程、-a 累计）
cat /proc/<pid>/io         # 单进程读写的字节数（rchar/wchar/read_bytes/write_bytes）
```

**排查链**：`vmstat` 看到 `b` 大 / `wa` 高 → `iostat -x` 确认设备饱和 → `iotop` 或 `pidstat -d` 找到进程。

## 5. 网络观测

```bash
ss -s                      # 连接数概览（TIME_WAIT 多不多）
cat /proc/net/dev          # 每块网卡的收发字节/包/错误（脚本友好）
sar -n DEV 1 3             # 网卡流量（sysstat）
sar -n TCP,ETCP 1 3        # TCP 层：重传、连接建立/失败
nload / iftop              # 实时流量图（需要装）
```

## 6. 调参：sysctl 与 ulimit

### sysctl（内核参数）

```bash
sysctl -a | grep swappiness        # 看一个参数
sysctl net.ipv4.ip_local_port_range
sudo sysctl -w vm.swappiness=10    # 临时改（重启失效）
```

**永久生效**：写 `/etc/sysctl.d/99-local.conf`，然后 `sudo sysctl --system`。

**常用参数**（部署服务会碰到的）：

| 参数 | 作用 | 常见调整 |
|------|------|---------|
| `vm.swappiness` | 换页倾向（0–100） | 服务器常设 10，尽量别换页 |
| `vm.overcommit_memory` | 内存过度分配策略 | Redis 等建议 1；默认 0 一般够 |
| `fs.file-max` | 系统级最大 fd 数 | 高并发调大 |
| `net.core.somaxconn` | listen 队列长度上限 | 高并发服务调大（配合应用 backlog） |
| `net.ipv4.tcp_tw_reuse` | 复用 TIME_WAIT 连接 | 主要影响主动发起连接的一方；服务端出站多时再看 |
| `net.ipv4.ip_local_port_range` | 本地端口范围 | 短连接多时扩大 |
| `vm.max_map_count` | 进程最大 mmap 区域数 | 大模型/数据库可能要调大（先看当前值） |

### ulimit（进程资源限制）

```bash
ulimit -a                  # 全部限制
ulimit -n                  # 打开文件数（fd 上限）
ulimit -u                  # 进程/线程数
ulimit -c                  # core dump 大小（0 = 不生成）

ulimit -n 65535            # 只对当前 shell 及子进程生效（软限制可调到硬限制以内）
ulimit -Hn                 # 看硬限制
```

**永久改**：`/etc/security/limits.conf`（或 `/etc/security/limits.d/*.conf`）：

```
*    soft nofile 65535
*    hard nofile 65535
```

**注意**：systemd 服务**不读 limits.conf**——要在 unit 里写 `LimitNOFILE=65535`（见 [服务与定时任务](05-服务与定时任务.md)）。容器里则看 `--ulimit` 和 runtime 配置。

**fork bomb**（`:(){ :|:& };:`）就是无限 fork 打爆进程表——防御正是 `ulimit -u`（单用户进程数上限）。别好奇去跑它。

## 7. CPU 亲和性与 NUMA

```bash
lscpu                      # CPU/核/超线程/NUMA 节点概览
taskset -c 0-3 ./server    # 绑定到 0–3 号核（减少迁移、提升缓存命中）
taskset -pc <pid>          # 查某进程当前亲和性
taskset -pc 2 <pid>        # 改运行中进程的亲和性

numactl --hardware         # NUMA 拓扑（节点/距离/内存）
numactl --cpunodebind=0 --membind=0 ./server   # 绑节点+绑内存（避免跨节点访问）
```

**为什么关心**：跨 NUMA 节点访问内存延迟明显更高；推理/训练这类内存密集型任务绑核+绑节点常有收益。多线程程序要让线程数和物理核数匹配（别把超线程当物理核）。

## 8. 大页（Huge Pages）

```bash
grep -i huge /proc/meminfo         # HugePages_Total/Free/Rsize（默认 2M）
cat /sys/kernel/mm/transparent_hugepage/enabled   # THP 状态（[always]/[madvise]/never）

sudo sysctl -w vm.nr_hugepages=1024    # 预留 1024 × 2M 的显式大页
```

**用途**：减少 TLB miss（大块连续内存的数据库/虚拟化/推理服务）。**THP（透明大页）** 由内核自动合并，三种模式：`always`（尽量用，有时造成延迟毛刺）/ `madvise`（应用按需声明，很多发行版默认这个）/ `never`。用 `cat /sys/kernel/mm/transparent_hugepage/enabled` 看当前值（**方括号里的是生效的**）。

## 9. 容器底层：namespace 与 cgroup

**容器 ≈ namespace（隔离"看得到什么"）+ cgroup（限制"能用多少"）**，加上一层文件系统（镜像/overlay）。

```bash
# namespace：让进程"看不见"外面的东西
sudo unshare --pid --fork --mount-proc bash    # 新的 PID namespace（里面只有自己）
lsns                                            # 当前系统有哪些 namespace
ls -l /proc/<pid>/ns/                           # 某进程所属的各 namespace

# cgroup v2：限制资源（systemd 用的就是它）
mount | grep cgroup2                            # 确认是 v2（统一层级）
cat /proc/self/cgroup                           # 自己在哪个 cgroup
ls /sys/fs/cgroup/                              # 层级：系统 → user.slice → ...
cat /sys/fs/cgroup/system.slice/<svc>/memory.max   # 某服务的内存上限
cat /sys/fs/cgroup/system.slice/<svc>/cpu.max      # CPU 带宽上限
cat /sys/fs/cgroup/system.slice/<svc>/pids.max     # 进程/线程数上限
```

**和 docker 的对应**：`docker run --memory/--cpus` → cgroup 限制；`--pid/--net/--ipc` → namespace 选择；`/dev/shm` 大小（默认 64M）用 `--shm-size` 调。容器里看到的 CPU 数、内存上限都来自 cgroup。

**容器里的 PID 1**：容器第一个进程就是它的"init"——要负责**转发信号**（`docker stop` 先给 PID 1 发 TERM）和**收尸**（wait 子进程）。entrypoint 是普通程序时它得自己处理；如果是"会拉子进程的脚本"，标准做法是 `docker run --init`（塞一个小 init）或镜像里用它做 ENTRYPOINT。

**chroot**：换根目录的"老派隔离"（`sudo chroot /newroot cmd`）——只换"看得到的根"，没有进程/网络隔离；容器早期就由它 + namespace 演进而来。

## 10. 部署相关设置（检查清单）

| 项 | 检查 | 问题与调整 |
|----|------|-----------|
| **共享内存** | `df -h /dev/shm` | 容器默认 64M → DataLoader/多进程报 `Bus error`/`No space` → `--shm-size` 或改用文件 |
| **fd 上限** | `ulimit -n` | 高并发服务默认 1024 太小 → unit 里 `LimitNOFILE` / limits.conf |
| **端口范围** | `sysctl net.ipv4.ip_local_port_range` | 短连接多时扩大（如 `10240 65535`） |
| **TIME_WAIT** | `ss -s` | 客户端侧可开 `tcp_tw_reuse`；服务端调 backlog/somaxconn |
| **OOM** | `dmesg \| grep -i oom` | 进程莫名消失（exit 137）多半是被 OOM 杀；看 cgroup 的 memory.max |
| **NUMA** | `lscpu`/`numactl --hardware` | 多路机器绑核绑节点；线程数按物理核 |
| **大页** | `grep Huge /proc/meminfo` | 延迟敏感场景考虑 |
| **mmap 上限** | `sysctl vm.max_map_count` | 大模型/数据库可能超默认值 |
| **cgroup 限额** | `cat /sys/fs/cgroup/.../memory.max` | 容器里"内存不够"先看它 |

## 11. perf：性能剖析

```bash
sudo perf stat ./app              # 运行并汇总：cycles/instructions/cache-miss/分支预测
sudo perf top                     # 全局热点（符号聚合，谁在烧 CPU）
sudo perf record -g ./app         # 采样（-g 带调用栈）
sudo perf record -g --call-graph dwarf ./app   # 栈不准时用 dwarf
sudo perf report                  # 交互看（钻到函数/代码行）
sudo perf record -g -p <pid> -- sleep 30   # 对运行中的进程采 30 秒
```

- 顺序：`perf stat` 判断是不是 CPU 瓶颈（指令数/周期数）→ `perf top` 找热点函数 → `perf record/report` 下钻
- 报 `perf_event_paranoid` 限制时按提示调低（`sysctl kernel.perf_event_paranoid`）或加 sudo
- 更轻的替代：`strace -c`（系统调用耗时统计）

## 12. WSL 环境差异

WSL2（Windows Subsystem for Linux）上跑 Linux 时，和原生 Linux 有几处差异：

- **项目/数据放 Linux 侧**（`~/`）：`/mnt/c/...` 的 IO 走 9p，跨文件系统读写慢得多（编译、训练数据都别放那边）
- **`/mnt/c` 上 inotify 不可靠**：Windows 侧改文件，Linux 的 watch 常常收不到事件——前端/Node 的热重载别指望它
- **双向访问**：Windows 侧走 `\\wsl.localhost\<发行版>`（旧写法 `\\wsl$\<发行版>`）；WSL 里 `explorer.exe .` 打开当前目录，`wslpath -w .` 转成 Windows 路径
- **互操作**：能直接跑 `notepad.exe`、`cmd.exe`；Windows 目录默认拼进 `$PATH`，不想要就在 `wsl.conf` 的 `[interop]` 设 `appendWindowsPath=false`
- **systemd**：`wsl --install` 装的 Ubuntu 镜像默认开，其他发行版要写 `/etc/wsl.conf` 的 `[boot] systemd=true`（WSL 0.67.6+）；不开的话 `systemctl` 用不了
- **网络**：默认 NAT（WSL 在内部子网，Windows 侧靠 localhost 转发访问）；新版可切 mirrored 模式；局域网要访问 WSL 服务得相应配置
- **内存/CPU**：内存默认约为 Windows 的一半，CPU 默认用全部逻辑核；`%UserProfile%\.wslconfig` 的 `[wsl2]` 段可设 `memory=12GB`、`processors=8`、`swap=4GB`，`free` 看到的"总内存"就是它
- **磁盘**：`ext4.vhdx` 默认上限 1TB、按需增长；删文件不会自动缩，缩容要 `wsl --shutdown` 后用 `diskpart` 的 `compact vdisk`，扩容用 `wsl --manage <发行版> --resize 200GB`（WSL 2.5+）
- **文件权限**：`/mnt/c` 下默认所有文件 777（Windows 元数据限制），要真实权限得开 metadata 挂载选项
- **重启**：`wsl --shutdown`（Windows 侧）整体重启；只重启一个发行版用 `wsl --terminate <发行版>`；改 `.wslconfig`/`wsl.conf` 后必须重启才生效

## 13. 要点回顾

1. **负载看核数**；`vmstat` 的 `r`/`b`/`wa`/`si/so` 四组数能快速定位瓶颈类型
2. **内存看 `available`**（不是 free）；`si/so` 持续非 0 才是在换页；进程消失先查 OOM（`dmesg -T | grep -i oom`，exit 137）
3. **磁盘看 `iostat -x`**（%util/await/aqu-sz）→ `iotop` 定位进程；和 `vmstat` 的 `b`/`wa` 联动；NVMe 的 %util 要结合 await/吞吐看
4. **网络** `ss -s` 看连接、`sar -n DEV` 看流量、`tcpdump` 抓包
5. **sysctl 调参**写 `/etc/sysctl.d/*.conf`（`sysctl --system` 生效）；常用：swappiness、somaxconn、tw_reuse、max_map_count
6. **ulimit** 改 fd/进程数；**systemd 服务不读 limits.conf**，要写 `LimitNOFILE`
7. **绑核/绑 NUMA**（`taskset`/`numactl`）对内存密集任务常有收益；线程数按物理核算
8. **容器 = namespace（隔离）+ cgroup（限额）**；`docker --memory/--shm-size` 都是它们在起作用
9. **部署检查清单**：`/dev/shm`、fd 上限、端口范围、OOM、NUMA、大页、max_map_count
10. **perf 三步**：`stat` 判断瓶颈类型 → `top` 找热点 → `record/report` 下钻
11. **WSL**：项目放 `~/`（`/mnt/c` 的 IO 慢、inotify 不可靠）、内存/CPU 在 `.wslconfig` 调、`ext4.vhdx` 只增不减、改配置要 `wsl --shutdown` 才生效
12. **其他观测**：`pidstat -w` 上下文切换、`slabtop` 内核 slab、`numastat`、`systemd-cgtop`、`bpftrace`
