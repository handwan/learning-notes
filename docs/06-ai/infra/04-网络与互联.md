# 网络与互联

多卡训练的性能，不只取决于单卡算力，还取决于 GPU 之间怎么“说话”。

常见网络层级：

```text
GPU 内：HBM / L2
GPU 间：NVLink / NVSwitch
节点内：PCIe
节点间：InfiniBand / RoCE / Ethernet
```

这一层的问题经常表现成：

- GPU 利用率不高，但在等 all-reduce
- TP 扩不出去，跨机后变慢
- NCCL hang、超时、重传
- 多网卡/多 rail 没配好
- 训练吞吐随节点数增加不升反降

这篇讲 PCIe/NVLink/InfiniBand、RDMA、集合通信、拓扑和并行映射，最后算一次 all-reduce 时间。

## 1. 带宽和延迟

先分清单位：

- **Gb/s**：网络常用，bit/s
- **GB/s**：存储/内存常用，Byte/s
- $1\,\text{GB/s}=8\,\text{Gb/s}$

所以：

- 400G IB ≈ 50 GB/s
- 800G IB ≈ 100 GB/s
- PCIe Gen4 x16 理论约 32 GB/s
- NVLink 4 每 GPU 双向聚合约 900 GB/s，单向约 450 GB/s（具体看型号）

这三个数的口径不同：32 是 PCIe x16 单链路单向，50 是 400G IB 单端口单向，900 是 NVLink 每 GPU 双向聚合（单向约 450）。下面 all-reduce 公式里的 `B` 指该次集合通信的**单向有效带宽**（可以是多条链路的聚合），不是双向聚合带宽，也不是单端口规格；不要直接用这三个数横比“谁快几倍”。

实际带宽还要乘效率：

- 协议开销
- 编码/重传
- 拥塞
- 消息大小
- 网卡/PCIe 瓶颈
- GPU Direct 是否启用

## 2. PCIe、NVLink、NVSwitch

| 互联 | 范围 | 特点 |
|---|---|---|
| PCIe | 节点内 | 通用，带宽较低，CPU-GPU/网卡 |
| NVLink | GPU 间 | 高带宽、低延迟 |
| NVSwitch | 机内多卡 | 多 GPU 全互联 |
| InfiniBand | 节点间 | RDMA、低延迟、HPC 常用 |
| RoCE | 节点间 | 以太网上的 RDMA，成本低但调优复杂 |
| Ethernet | 节点间 | 通用，适合管理/存储/部分推理 |

拓扑例子：

- 8 卡 NVLink 域：TP 放域内
- 多机：每机有多个 IB 网卡/rail
- fat-tree：多级交换，bisection bandwidth 决定跨机带宽
- rail-optimized：每张 GPU 固定走一张网卡，减少交叉

## 3. RDMA 与 GPUDirect

RDMA（Remote Direct Memory Access）：

- 绕过内核，减少 CPU 拷贝
- 零拷贝/单边操作
- IB 原生支持；RoCE 用以太网承载

GPUDirect RDMA：

- 网卡直接读写 GPU 显存
- 避免 GPU→CPU→网卡拷贝
- 需要驱动/网卡/拓扑支持

RoCE 注意：

- PFC/ECN 配置不好会拥塞/丢包
- 需要无损网络或精细拥塞控制
- 交换机/网卡/驱动版本要匹配

## 4. 集合通信

常见集合操作：

- broadcast：一发给所有
- reduce：所有归约到一个
- all-reduce：所有归约，所有拿到结果
- all-gather：所有收集所有
- reduce-scatter：归约后切分
- all-to-all：每对 rank 交换不同数据

Ring all-reduce 的粗略时间：

$$
T_{\mathrm{AR}}
\approx 2\frac{N-1}{N}\frac{S}{B}
$$

- $N$：rank 数
- $S$：消息字节数
- $B$：单向有效带宽

$N$ 很大时接近 $2S/B$。其他集合的系数不同：

| 操作 | 粗略时间 |
|---|---|
| all-gather | $\frac{N-1}{N}\frac{S}{B}$ |
| reduce-scatter | $\frac{N-1}{N}\frac{S}{B}$ |
| all-to-all | $\frac{N-1}{N}\frac{S}{B}$ |
| broadcast/reduce | 约 $S/B$（树/环实现不同） |

小消息更受 **latency** 影响，大消息更受 **bandwidth** 影响。

## 5. 并行怎么映射到网络

| 并行 | 主要通信 | 网络敏感点 |
|---|---|---|
| DP | 梯度 all-reduce | 大消息、带宽 |
| TP | 每层 all-reduce/all-gather | 小消息多、延迟 |
| PP | 相邻 stage 点对点 | 流水线 bubble、带宽 |
| EP（MoE） | all-to-all | 路由不均、拥塞 |
| ZeRO/FSDP | reduce-scatter/all-gather | 通信量增加 |

经验：

- TP 尽量放同机 NVLink 域
- DP 可以跨机，但梯度 all-reduce 很大
- PP 跨机要控制 microbatch 和 stage 数
- EP 的 all-to-all 对拓扑和负载均衡很敏感

## 6. 实验：all-reduce 时间

7B/70B 模型，BF16 梯度约 14GB/140GB。8 卡 ring all-reduce（`B` 是单向有效带宽的量级示例）：

??? note "代码：实验：all-reduce 时间"
    ```python
    def allreduce_ms(size_gb, bw_gbps, n=8):
        return 2 * (n - 1) / n * size_gb / bw_gbps * 1000

    for model, size in [("7B", 14.0), ("70B", 140.0)]:
        print(model, "gradient", size, "GB")
        for link, bw in [("PCIe", 32), ("IB 400G", 50), ("NVLink", 450)]:
            print(f" {link:8s} bw={bw:4d}GB/s time={allreduce_ms(size, bw):8.1f}ms")
    ```

输出：

```text
7B gradient 14.0 GB
 PCIe     bw=  32GB/s time=   765.6ms
 IB 400G  bw=  50GB/s time=   490.0ms
 NVLink   bw= 450GB/s time=    54.4ms
70B gradient 140.0 GB
 PCIe     bw=  32GB/s time=  7656.2ms
 IB 400G  bw=  50GB/s time=  4900.0ms
 NVLink   bw= 450GB/s time=   544.4ms
```

读法：

- 7B 梯度 14GB，NVLink 约 54ms；IB 400G 约 490ms；PCIe 约 766ms
- 70B 梯度 140GB，NVLink 约 544ms；IB 400G 约 4.9s；PCIe 约 7.7s
- 这是单次 all-reduce 的粗略时间，不含 latency、拥塞和协议效率
- TP 每层都要通信，小消息的延迟占比更高
- DP 每步一次大 all-reduce，带宽占比更高
- 真实性能要用 `nccl-tests` 实测；上面的数字只用于理解数量级

## 7. 拓扑与 NCCL

NCCL 会探测拓扑，选择 ring/tree 等算法。要确认：

- `nvidia-smi topo -m`：GPU/网卡/NUMA 关系
- `nvidia-smi nvlink -s`：NVLink 状态
- `ibstat` / `ibv_devinfo`：IB 端口
- `ib_write_bw`：网卡带宽
- `nccl-tests`：all-reduce/all-gather 实测
- `NCCL_DEBUG=INFO`：算法/拓扑日志

常见问题：

- 网卡和 GPU 不在同一 NUMA/PCIe 根
- 多网卡只用了其中一张
- rail 配错，跨机走错交换机
- 交换机 oversubscription 太高
- NCCL 选错算法/通道数
- PFC 风暴、ECN 配置不当
- MTU/防火墙/容器网络问题

## 8. 常见坑

1. **Gb/s 和 GB/s 混用**
   400G 不是 400GB/s，是约 50GB/s。

2. **拿理论带宽当有效带宽**
   协议、拥塞、消息大小都会打折。

3. **只看聚合带宽，不看 bisection**
   跨机流量可能被上层交换机卡住。

4. **TP 跨机**
   每层小消息多，跨机延迟会把收益吃掉。

5. **DP 梯度 all-reduce 太大**
   70B BF16 梯度 140GB，跨机带宽不够会很慢。

6. **多网卡没绑对 GPU**
   网卡和 GPU 跨 NUMA/PCIe，带宽和延迟都变差。

7. **NCCL 拓扑探测错误**
   容器/虚拟化/网卡命名会影响算法选择。

8. **RoCE 当 IB 用**
   RoCE 需要无损/拥塞控制配置，不是插上就能跑。

9. **忽略小消息 latency**
   TP/EP 的很多通信是延迟主导，不是带宽主导。

10. **PP 的 bubble**
    流水线 stage 不均衡，GPU 会等。

11. **EP 路由不均**
    专家负载不均会造成 all-to-all 拥塞。

12. **不跑 nccl-tests**
    只看训练日志，很难区分网络、算法和框架问题。

## 9. 要点回顾

1. 节点内看 PCIe/NVLink/NVSwitch，节点间看 IB/RoCE/Ethernet
2. 400G IB ≈ 50GB/s；不要和 400GB/s 混
3. RDMA/GPUDirect 减少拷贝；RoCE 需要无损/拥塞控制
4. all-reduce 粗略 $2(N-1)/N \cdot S/B$（B 为单向有效带宽），大 N 接近 $2S/B$
5. DP 是大消息带宽问题；TP 是小消息延迟问题
6. TP 放 NVLink 域；DP/PP/EP 的拓扑约束不同
7. 用 `nvidia-smi topo`、`ibstat`、`nccl-tests`、`NCCL_DEBUG` 验证
8. 网络问题经常表现成 GPU 利用率低，不一定是 GPU 本身慢
