# 可观测性

“GPU 利用率 100%”不代表服务正常；loss 下降也不代表训练没卡在 dataloader。

可观测性要回答：

- 现在发生了什么？
- 为什么慢/为什么挂？
- 哪个租户/任务/副本受影响？
- 是否已经违反 SLO？
- 下次怎么提前发现？

这篇讲 metrics / logs / traces / profiles、GPU 与训练/推理指标、SLO 和排障，最后算一组延迟分位数与错误预算。

## 1. 四类信号

| 信号 | 回答 | 例子 |
|---|---|---|
| Metrics | 趋势、告警 | GPU 利用率、QPS、TTFT、loss |
| Logs | 事件细节 | OOM、NCCL 错误、请求 ID |
| Traces | 请求链路 | 网关 → 服务 → 模型 → 工具 |
| Profiles | 性能热点 | kernel、CPU flame graph、NCCL |

只靠 dashboard 不够；没有日志/trace，异常时无法定位。

## 2. GPU 指标

`nvidia-smi` 的“GPU 利用率”是时间占比，不是算力利用率。

更有信息量：

- SM occupancy
- tensor core active
- HBM 带宽利用率
- 显存 used/reserved
- 功耗/温度/时钟
- PCIe/NVLink 吞吐
- ECC / Xid
- MIG 实例状态

工具：

- DCGM / DCGM Exporter
- `nvidia-smi`
- `nvidia-smi dmon`
- Nsight Systems / Compute
- PyTorch profiler

常见误读：

- 利用率 100% 但吞吐低：可能在搬数据/等内存
- 利用率低但延迟高：可能在等网络/CPU/队列
- 显存 used 高但 reserved 更高：缓存/碎片

## 3. 训练指标

每步看：

- step time
- tokens/s
- MFU（实际 FLOPS / 峰值）
- loss、grad norm
- learning rate
- dataloader wait
- checkpoint 时间
- NCCL/通信时间
- OOM/重试/重启

诊断：

- loss 不降：数据、标签、lr、初始化
- loss NaN：lr、logits、数值稳定
- step time 抖动：straggler、网络、存储、其他租户
- GPU 空闲：dataloader/CPU/存储
- 吞吐随卡数不升：通信/拓扑/并行策略

训练要有“每步耗时拆解”，不要只有一个总 step time。

## 4. 推理指标

核心：

- QPS / RPS
- TTFT（time to first token）
- TPOT / ITL（time per output token / inter-token latency）
- 吞吐（tokens/s）
- 队列长度/等待时间
- batch size / running / waiting
- KV cache 使用率
- prefix cache 命中率
- preemption/抢占
- 错误率/超时率
- p50/p95/p99

在线服务看尾延迟，不看平均：

- 平均 100ms 可能 p99 2s
- 用户感知的是 p95/p99
- 排队时间和 TTFT 要分开

推理特有：

- prefill 和 decode 要分开看
- 长 prompt 的 TTFT
- 长输出的 TPOT
- KV cache 打满会触发 preemption/排队

## 5. SLO 与错误预算

SLO 例子：

> 95% 的请求延迟 < 200ms

真实服务可以把 TTFT、TPOT、端到端延迟分别设 SLO；下面用通用请求延迟做示例。

错误预算：

$$
\text{budget}= (1-\text{SLO})\times N
$$

- N=10000，SLO=95%，预算 500 个慢请求
- 实际 476 个慢请求，预算剩 24
- burn rate = 476/500 = 0.95

如果 burn rate 长期 >1，说明 SLO 守不住；要扩容/优化/降级。

看分位数：

- p50 看典型体验
- p95/p99 看尾延迟
- max 看极端，但容易被单个异常带偏

## 6. 实验：平均值会骗人

生成 10000 个带长尾的延迟，SLO 设为 95% 请求 <200ms：

??? note "代码：实验：平均值会骗人"
    ```python
    import numpy as np

    rng = np.random.default_rng(0)
    latency = rng.lognormal(mean=np.log(0.08), sigma=0.55, size=10000)

    print("avg", round(float(latency.mean() * 1000), 1), "ms")
    for p in [50, 95, 99, 99.9]:
        print(f"p{p}", round(float(np.percentile(latency, p) * 1000), 1), "ms")
    print("max", round(float(latency.max() * 1000), 1), "ms")

    slo = 0.200
    violations = int((latency > slo).sum())
    budget = int(len(latency) * 0.05)
    print("over200", violations, "budget", budget, "remaining", budget - violations)
    print("burn", round(violations / budget, 2))
    ```

输出：

```text
avg 93.2 ms
p50 79.6 ms
p95 197.1 ms
p99 285.2 ms
p99.9 412.8 ms
max 543.0 ms
over200 476 budget 500 remaining 24
burn 0.95
```

读法：

- 平均 93.2ms 看起来很好
- p95 已经 197.1ms，贴着 200ms SLO
- p99 285ms，p99.9 413ms，max 543ms
- 95% SLO 的预算 500，实际 476，只剩 24；burn 0.95
- 只看平均会错过尾延迟和 SLO 风险

## 7. 指标管道

典型：

```text
metrics：DCGM / node exporter / app metrics
→ Prometheus / OpenTelemetry
→ Grafana / alertmanager

logs：应用/系统日志 → Loki / ELK
traces：应用埋点 → Tempo / Jaeger
profiles：Nsight / PyTorch profiler
```

注意：

- 指标 label 不要无限膨胀（request_id、user_id 不要进 label）
- 日志要带 request_id/trace_id
- trace 采样率要可调
- profile 有开销，不要长期全量开
- 多租户要有 tenant label，但注意基数

## 8. 排障 playbook

### GPU 利用率高、吞吐低

- 看 HBM 带宽、tensor core、occupancy
- 是否 memory-bound
- batch 太小/太大
- kernel 是否低效

### GPU 利用率低、延迟高

- 队列/调度
- CPU/dataloader
- 网络/NCCL
- 存储
- 其他租户抢占

### OOM

- 权重/KV/激活/优化器
- batch/序列长度
- 碎片/reserved
- MIG 显存

### NCCL hang

- `NCCL_DEBUG=INFO`
- 网卡/拓扑/MTU/防火墙
- 超时/重试
- 是否有慢节点

### Pending

- 配额
- taint/toleration
- device plugin
- 碎片化
- 镜像/存储

## 9. 常见坑

1. **只看平均延迟**
   p95/p99 才是用户体验和 SLO。

2. **把 GPU 利用率当算力利用率**
   可能只是在搬数据。

3. **没有 per-tenant 指标**
   无法配额、计费、定位噪声邻居。

4. **label 基数爆炸**
   request_id/user_id 进 metrics，Prometheus 会被打爆。

5. **日志没有 request_id**
   出问题无法把网关、服务、模型串起来。

6. **只看 GPU，不看 dataloader/存储/网络**
   瓶颈可能在 GPU 之外。

7. **告警没有 runbook**
   告警响了没人知道怎么处理。

8. **告警阈值拍脑袋**
   没有 SLO/burn rate，容易疲劳。

9. **MIG 指标混在一起**
   切分后要按实例/租户看。

10. **profile 长期全量开**
    开销大，影响生产。

11. **只看训练 loss**
    不看 step time/吞吐/通信，训练可能很慢。

12. **没有容量/成本指标**
    不知道每个租户/模型花多少钱。

## 10. 要点回顾

1. 可观测性 = metrics + logs + traces + profiles
2. GPU 利用率不等于算力利用率；看带宽/occupancy/tensor core
3. 训练看 step time、tokens/s、MFU、dataloader、NCCL
4. 推理看 TTFT、TPOT、队列、KV cache、p95/p99
5. SLO 用错误预算和 burn rate，不只看平均值
6. 指标管道要控制 label 基数，日志带 trace/request ID
7. 排障先分 GPU/CPU/网络/存储/调度，再看具体 kernel
8. 多租户要有 tenant label、配额和成本
