# 部署与多租户

模型训练完只是开始。部署要回答：

- 单卡、单机多卡，还是多机多副本？
- 一个副本能扛多少并发？要几个副本？
- 多个团队/客户怎么隔离？
- 多地域怎么部署、怎么故障切换？
- 发布新版本时怎么不中断服务？

这篇讲部署形态、副本容量、K8s 对象、多租户隔离、多地域和冷启动，最后算一个副本容量实验。

## 1. 部署形态

| 形态 | 适合 | 关键点 |
|---|---|---|
| 单卡单副本 | 小模型、低流量、开发 | 简单，容量有限 |
| 单机多卡 TP | 单卡放不下的大模型 | NVLink、TP 通信 |
| 单机多副本 | 中小模型、吞吐优先 | 显存、端口、负载均衡 |
| 多机多副本 | 生产、跨机容灾 | 网络、调度、版本一致 |
| 多地域 | 低延迟、数据驻留 | 复制、路由、合规 |

大模型常见：

- 一个副本用 TP=2/4/8 跨卡
- 多个副本做水平扩展
- 副本之间用负载均衡/路由

小模型常见：

- 一张卡跑多个副本
- 或者用 MIG/MPS 切分/共享

## 2. 副本与容量

先算并发：

$$
\text{concurrency}\approx \text{QPS}\times\text{latency}
$$

这是 Little's law 的简化：系统里同时有多少请求。

一个副本能承载的并发受限于：

- 显存：权重 + KV cache + 激活
- batch/continuous batching
- 计算/带宽
- 延迟 SLO
- 安全余量

副本数：

$$
\text{replicas}
=\left\lceil
\frac{\text{concurrency}}{\text{per-replica capacity}}
\right\rceil
$$

注意：

- 要留 headroom（故障、突发、碎片）
- 副本不是越多越好：调度、冷启动、成本
- 有状态/前缀缓存时，路由会影响命中率

## 3. K8s 部署对象

常见对象：

- **Deployment**：无状态副本
- **StatefulSet**：有状态/固定身份
- **Service**：稳定访问入口
- **Ingress / Gateway**：外部流量
- **HPA**：水平扩缩容
- **ConfigMap / Secret**：配置和凭证
- **ResourceQuota / LimitRange**：命名空间配额
- **NetworkPolicy**：租户/服务隔离
- **PodDisruptionBudget**：限制节点维护/驱逐时的自愿中断，不控制滚动更新

GPU 部署常见：

- node pool 按 GPU 型号/显存分池
- taint/toleration 隔离团队
- topology spread 打散副本
- readiness 等模型加载完再接流量
- init container 预拉模型/权重
- emptyDir/local NVMe 做模型缓存

扩缩容指标不要只看 CPU：

- 队列长度
- TTFT / TPOT
- GPU 利用率/显存
- 并发请求数
- 错误率

## 4. 多租户隔离

多租户不只是“多个 namespace”：

| 维度 | 手段 |
|---|---|
| 权限 | RBAC、ServiceAccount |
| 配额 | ResourceQuota、LimitRange、队列 |
| 计算 | node pool、taint、MIG、MPS |
| 网络 | NetworkPolicy、Ingress 隔离 |
| 存储 | PVC、加密、按租户 bucket |
| 模型 | 按租户 adapter、模型缓存、路由 |
| 数据 | 租户 ID、行级权限、审计 |
| 成本 | 按 namespace/tenant 计量 |

常见隔离级别：

- 共享 GPU：成本低，噪声/安全弱
- MIG：硬件切分，隔离较好
- 独占节点：隔离最好，成本最高
- 独立集群/地域：强隔离，运维成本高

多租户最容易出的问题：

- 一个租户打满 GPU/队列，其他租户饿死
- 共享模型缓存被污染/串数据
- 日志/指标混在一起，无法计费
- 网络策略缺失，租户间可互访
- 每租户 LoRA adapter 加载/卸载抖动

## 5. 多地域

多地域要考虑：

- 数据驻留/合规
- 用户延迟
- 故障隔离
- 模型/版本一致
- 流量路由
- 成本

模式：

| 模式 | 特点 |
|---|---|
| 单地域 | 简单，延迟/容灾弱 |
| 主备 | 故障切换，成本较低 |
| 双活 | 低延迟/高可用，数据一致性复杂 |
| 边缘 | 超低延迟，运维/模型分发复杂 |

多地域的难点不是“部署两份”，而是：

- 模型版本/配置同步
- 租户数据复制/驻留
- 故障切换时的容量
- 跨区流量成本
- 监控和告警统一

## 6. 发布与冷启动

发布策略：

- rolling update
- blue-green
- canary
- shadow（影子流量）

GPU 服务发布要注意：

- 模型加载慢，readiness 要等加载完
- maxSurge/maxUnavailable 控制滚动更新，按容量算
- PDB 保护节点维护/驱逐，不控制滚动更新
- 新旧版本可能同时占显存
- 回滚要能快速切回

冷启动来源：

- 镜像拉取
- 驱动/CUDA 初始化
- 模型权重下载/加载
- 编译/CUDA graph
- KV cache/暖机

优化：

- 预热池
- 本地模型缓存
- 快照/预加载
- 更小的镜像
- 就绪探针前完成 warmup

## 7. 实验：副本容量

80GB GPU，7B 模型权重约 16GB，激活 2GB，每条序列 KV cache 约 0.5GB，留 20% headroom。

??? note "代码：实验：副本容量"
    ```python
    import math

    def max_concurrency(gpu_gb, weights_gb, activation_gb, kv_per_seq_gb, headroom=0.8):
        usable = gpu_gb * headroom - weights_gb - activation_gb
        return max(0, int(usable / kv_per_seq_gb))

    def replicas(qps, latency_s, concurrency):
        need = qps * latency_s
        if concurrency <= 0:
            return None, need
        return math.ceil(need / concurrency), need

    for name, weights in [("7B", 16), ("70B", 140)]:
        if weights >= 80:
            print(name, "weights", weights, "GB > 80GB: needs multi-GPU")
            continue
        cap = max_concurrency(80, weights, 2, 0.5)
        n, need = replicas(50, 2, cap)
        if n is None:
            print(name, "does not fit: concurrency 0")
            continue
        print(name, "concurrency", cap, "need", need, "replicas", n, "util", f"{need / (n * cap):.1%}")
        for share in [0.6, 0.4]:
            print("  tenant total capacity", share, int(n * cap * share))
    ```

输出：

```text
7B concurrency 92 need 100 replicas 2 util 54.3%
  tenant total capacity 0.6 110
  tenant total capacity 0.4 73
70B weights 140 GB > 80GB: needs multi-GPU
```

读法：

- 80GB × 0.8 = 64GB 可用；减权重 16GB、激活 2GB，剩 46GB
- 每条序列 0.5GB KV，最多约 92 并发
- 50 QPS × 2s = 100 并发，需要 2 个副本
- 两个副本总并发容量 184，并发容量利用率约 54.3%
- 60/40 配额下，租户总并发容量约 110/73
- 70B 按 FP16 权重 140GB，单卡 80GB 放不下，需要 TP/多卡；量化后另算

这是粗略容量模型；实际要压测 TTFT/TPOT、KV cache 增长、batch 调度和故障余量。

## 8. 安全与可观测

安全：

- 认证/授权：API key、OIDC、RBAC
- 租户隔离：namespace、NetworkPolicy、独立 node pool
- 模型/数据：加密、访问审计、密钥管理
- 供应链：镜像签名、SBOM、依赖扫描
- 输入/输出：内容过滤、PII、prompt injection 防护

可观测：见 [可观测性](06-可观测性.md)。部署侧至少要保证指标能按租户/模型/副本归属；没有 per-tenant 指标，就无法做配额、计费和故障定位。

## 9. 常见坑

1. **HPA 只看 CPU**
   GPU 服务瓶颈常是队列/显存/延迟；要用自定义指标。

2. **没有 PDB**
   节点维护/驱逐时一次杀太多副本，容量瞬间不够。

3. **readiness 太早**
   模型没加载完就接流量，请求超时。

4. **没有配额**
   一个租户打满 GPU/队列，其他租户饿死。

5. **共享 GPU 不隔离**
   MPS/time-slicing 下，噪声邻居影响延迟。

6. **模型缓存击穿**
   多副本同时下载/加载同一模型，打爆存储。

7. **多地域版本漂移**
   不同地域模型/配置不一致，行为不同。

8. **忽略数据驻留**
   跨区复制可能违反合规。

9. **发布时新旧版本同时占显存**
   canary/blue-green 需要额外容量。

10. **没有 backpressure**
    队列无限增长，延迟爆炸；要限流/拒绝。

11. **每租户 adapter 频繁换入换出**
    LoRA 加载/卸载抖动；要缓存/路由。

12. **只算峰值，不留故障余量**
    一个副本挂了就超 SLO；要 N+1。

## 10. 要点回顾

1. 部署形态：单卡、单机 TP、多副本、多机、多地域
2. 容量用 Little's law：并发 ≈ QPS × latency；副本 = ceil(并发/单副本容量)
3. 显存要算权重、KV cache、激活和 headroom
4. K8s 用 Deployment/Service/HPA/PDB/NetworkPolicy/Quota
5. 多租户隔离包括权限、配额、计算、网络、存储、模型和数据
6. 多地域要处理数据驻留、版本一致、故障切换和成本
7. 发布要 readiness、maxSurge/maxUnavailable、warmup、回滚；PDB 保护节点维护/驱逐
8. 没有 per-tenant 指标，就没有真正的配额和计费
