# 集群与调度

一张 GPU 能跑模型；一堆 GPU 要跑任务，就需要集群和调度。

集群调度要同时满足：

- 任务能跑起来（资源、驱动、拓扑）
- GPU 不空转（利用率）
- 多用户公平（配额、优先级、抢占）
- 故障能恢复（重试、漂移、隔离）

这篇讲 K8s 和 Slurm 两条主流路线、GPU 资源怎么暴露、拓扑和碎片化，以及一个调度模拟实验。

## 1. 集群里有什么

一个 GPU 集群至少有：

```text
控制面
├── API / 调度器 / 控制器
├── 用户、配额、权限
└── 监控、日志、告警

计算节点
├── CPU / 内存
├── GPU + 驱动 + CUDA
├── 本地盘 / 共享存储
└── 网络：PCIe / NVLink / InfiniBand / RoCE
```

调度器要做的是：把“任务需要的资源”映射到“节点上可用的资源”。

## 2. Kubernetes 路线

K8s 的核心对象：

- **Node**：一台机器
- **Pod**：最小调度单元
- **Job / CronJob**：批处理任务
- **Deployment / StatefulSet**：长期服务
- **ResourceQuota / LimitRange**：命名空间配额
- **PriorityClass**：优先级和抢占
- **Taint / Toleration**：节点排斥/容忍
- **Affinity / AntiAffinity**：亲和/反亲和
- **TopologySpreadConstraints**：拓扑打散

GPU 不是 K8s 原生资源，需要：

- NVIDIA driver
- container toolkit
- device plugin
- GPU Operator（把上面这些打包）
- DCGM exporter（监控）
- MIG Manager（MIG 切分）

Pod 里申请 GPU：

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

注意：

- 标准 device plugin 下，GPU 是整数资源，默认不能超卖；MIG、MPS、time-slicing 是另外的共享方式
- request 和 limit 通常要一致
- 没装 device plugin，Pod 会一直 Pending
- MIG 会暴露成不同资源名，如 `nvidia.com/mig-1g.5gb`

常见调度能力：

- nodeSelector / affinity：指定 GPU 型号、机房、池
- taints：把 GPU 节点留给特定团队
- topology-aware：尽量把 Pod 放到同一 NVLink/IB 域
- gang scheduling：一组 Pod 要么一起跑，要么都不跑
- queue / quota：多团队排队和配额
- preemption：高优先级任务挤掉低优先级

原生 K8s 调度器不擅长 gang scheduling 和复杂队列，常见扩展：

- Volcano
- Kueue
- YuniKorn
- 自研 scheduler plugin

## 3. Slurm 路线

Slurm 是 HPC 常见调度器：

```bash
sinfo
squeue
sbatch train.sbatch
srun --gres=gpu:8 ...
scancel <jobid>
```

关键概念：

- **partition**：队列/分区
- **GRES**：GPU 等通用资源，如 `--gres=gpu:8`
- **QOS**：服务质量、优先级、限制
- **fair-share**：按历史使用量公平分配
- **accounting**：记账和审计
- **topology**：按交换机/机架/NVLink 域调度

Slurm 更强的地方：

- 批处理、队列、公平分享
- 拓扑感知和大规模 HPC
- 作业数组、依赖、回填
- 成熟的记账/限额

K8s 更强的地方：

- 服务发现、滚动升级、云原生生态
- 多租户、RBAC、Operator
- 在线服务和批处理混部

很多团队是 K8s + Slurm 并存，或 K8s 上跑 Volcano/Kueue。

## 4. GPU 共享

一张 GPU 给多个任务：

| 方式 | 隔离 | 典型场景 |
|---|---|---|
| MIG | 硬件切分，较硬隔离 | 多租户、小模型推理 |
| MPS | 进程共享 SM | 多进程推理/训练 |
| time-slicing | 时间片轮转 | 开发/测试、低负载 |
| vGPU | 虚拟化 | 桌面/VDI |

取舍：

- MIG 切得越碎，单块显存/带宽越小
- MPS 提高利用率，但故障/安全隔离弱
- time-slicing 适合交互，不适合延迟敏感服务
- 共享 GPU 会让性能预测变难

## 5. 调度目标

没有单一最优调度器，只有目标权衡：

| 目标 | 倾向 |
|---|---|
| 利用率 | bin packing，尽量塞满节点 |
| 公平 | 配额、fair-share、队列 |
| 延迟 | 预留、优先级、抢占 |
| 拓扑 | 同 NVLink/IB 域、少跨机 |
| 隔离 | 独占节点、MIG、taint |
| 成本 | 混合部署、自动缩容、spot |

常见策略：

- **bin packing**：把任务塞进已有节点，减少碎片
- **spread**：打散到不同节点，降低相关性故障
- **gang scheduling**：分布式任务整组调度
- **backfill**：用短任务填等待大任务的空档
- **preemption**：高优先级抢占低优先级

## 6. 实验：碎片化

4 个节点，每个 8 张 GPU。先来 4 个 5 卡任务，再来了一个 8 卡任务。

??? note "代码：实验：碎片化"
    ```python
    def first_fit(nodes, jobs):
        free = nodes.copy()
        placed = []
        pending = []
        for name, need in jobs:
            for i in range(len(free)):
                if free[i] >= need:
                    free[i] -= need
                    placed.append((name, i))
                    break
            else:
                pending.append((name, need))
        return free, placed, pending

    nodes = [8, 8, 8, 8]

    small_first = [
        ("a", 5), ("b", 5), ("c", 5), ("d", 5), ("big", 8),
    ]
    free, placed, pending = first_fit(nodes, small_first)
    print("small first: free", free, "total", sum(free), "largest", max(free))
    print("placed", placed)
    print("pending", pending)

    big_first = [
        ("big", 8), ("a", 5), ("b", 5), ("c", 5), ("d", 5),
    ]
    free2, placed2, pending2 = first_fit(nodes, big_first)
    print("big first:   free", free2, "total", sum(free2), "largest", max(free2))
    print("placed", placed2)
    print("pending", pending2)
    ```

输出：

```text
small first: free [3, 3, 3, 3] total 12 largest 3
placed [('a', 0), ('b', 1), ('c', 2), ('d', 3)]
pending [('big', 8)]
big first:   free [0, 3, 3, 3] total 9 largest 3
placed [('big', 0), ('a', 1), ('b', 2), ('c', 3)]
pending [('d', 5)]
```

读法：

- 先跑 4 个 5 卡任务后，总空闲 12 张，但最大单节点只有 3 张，8 卡任务仍然 Pending
- **总空闲 ≠ 可调度容量**
- 先调度 8 卡任务后，4 个 5 卡任务只能放下 3 个
- 调度顺序/优先级会改变利用率和等待时间
- 真实集群还要考虑 NVLink 域、MIG、配额、抢占和回填

## 7. 可观测性与故障

看：

- GPU 利用率、显存、温度、功耗
- Pod/Job Pending 原因
- 队列长度、等待时间
- 节点 NotReady、驱动版本
- NCCL 错误、网络重传
- 存储 IO、dataloader 等待

常见工具：

- DCGM exporter + Prometheus + Grafana
- `nvidia-smi`
- `kubectl describe pod` / events
- Slurm `squeue` / `sacct`
- NCCL debug 日志

常见故障：

- device plugin 没起，GPU 没注册
- 驱动/容器 toolkit 版本不匹配
- taint 导致 Pod 无法调度
- quota 不够
- 碎片化导致大任务 Pending
- NCCL hang：网卡/拓扑/MTU/防火墙
- GPU 掉卡、ECC、Xid 错误

## 8. 常见坑

1. **只看总空闲 GPU**
   总空闲够，不代表单节点/单 NVLink 域能满足。

2. **GPU 没注册**
   device plugin、driver、toolkit 任一没装好，Pod 都会 Pending。

3. **request/limit 不一致**
   GPU 资源通常要 request=limit；否则调度和实际使用不一致。

4. **忽略 taint/toleration**
   GPU 节点被独占/隔离，普通 Pod 调度不上去。

5. **配额/优先级没设计**
   多团队会互相挤占；要有 ResourceQuota、PriorityClass、队列。

6. **gang scheduling 缺失**
   分布式任务部分 Pod 起来、部分 Pending，占着资源不干活。

7. **拓扑不感知**
   跨机 all-reduce 变慢；TP 应该尽量放同 NVLink 域。

8. **MIG 切太碎**
   单块显存/带宽不够，大模型跑不了。

9. **共享 GPU 不隔离**
   MPS/time-slicing 下，一个任务可能拖慢另一个。

10. **自动扩容太慢**
    GPU 节点冷启动、驱动初始化、镜像拉取都要时间。

11. **不监控排队时间**
    只看利用率会忽略用户在排队；要看等待时间和成功率。

12. **K8s/Slurm 两套系统重复建设**
    要明确哪类任务走哪套，避免资源和权限割裂。

## 9. 要点回顾

1. 集群调度 = 资源、拓扑、公平、优先级、故障恢复
2. K8s 用 device plugin/GPU Operator 暴露 GPU；Pod 申请 `nvidia.com/gpu`
3. Slurm 用 partition/GRES/QOS/fair-share 管 HPC 批处理
4. GPU 共享有 MIG/MPS/time-slicing，隔离和吞吐要权衡
5. 调度目标有 bin packing、spread、gang、backfill、preemption
6. 总空闲 GPU 不等于可调度容量；碎片化会让大任务 Pending
7. 拓扑感知对 NVLink/InfiniBand 上的分布式训练很关键
8. 监控要看利用率、排队时间、Pending 原因和 NCCL 错误
