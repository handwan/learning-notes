# 微调：全参数微调 vs LoRA/QLoRA

微调不是“把模型再训一遍”这么简单。先问：

- 显存够不够全量？
- 要学的是格式/风格/领域，还是新知识？
- 要维护一个模型，还是多个任务 adapter？
- 能不能接受 4-bit 量化的质量和速度？
- 合并成一个模型，还是 base + adapter 分开部署？

这篇讲 full FT / LoRA / QLoRA 的工程取舍：显存账、rank/alpha、目标模块、合并、8GB 级显卡示例配方，最后以 8GB 为例做 7B 显存账和 merge 校验。SFT/DPO/偏好数据见 [LLM 第 7 篇](../llm/07-微调与对齐.md)；这里不重复训练流程。

## 1. 三种做法

| 方法 | 训练什么 | base 精度 | 7.2B 权重+梯度+优化器 | 适合 |
|---|---|---|---|---|
| Full FT | 全部参数 | BF16 + FP32 master | 约 115GB | 领域迁移大、显存充足、追求最大效果 |
| LoRA | 低秩 adapter | BF16 | 约 15GB | 显存有限、多任务、快速迭代 |
| QLoRA | 低秩 adapter | 4-bit | 约 4.5GB | 8–24GB 显存、7B–30B；70B 约 48GB+ |

QLoRA = 4-bit base + LoRA，不是另一种完全不同的方法。

三种方法都还要算激活、CUDA context、碎片和临时 buffer；上表只是权重+梯度+优化器状态。

## 2. 显存账

### Full FT

常见混合精度 AdamW：

- 权重 BF16：2 bytes/param
- 梯度 BF16：2 bytes/param
- FP32 master：4 bytes/param
- Adam m/v：8 bytes/param

合计约 **16 bytes/param**。

- 7.2B：约 115GB
- 70B：约 1.12TB

这还没算激活。不 offload、全部放 GPU 时，8GB 卡放不下 7B 全量微调。

ZeRO/FSDP、8-bit optimizer、CPU offload 能降，但代价是通信、速度或多机。

### LoRA

base 冻结，只存 base 权重 + adapter：

- base BF16：2 bytes/param
- adapter：参数量很小，但也要权重/梯度/优化器状态

7.2B BF16 base 约 14.4GB；adapter（r=16，all-linear）约 0.67GB；合计约 15.1GB。

**不 offload 时，7B 的 BF16 LoRA 也放不进 8GB**。8GB 上要么换 1.5B–3B 模型，要么把 base 量化。

### QLoRA

4-bit NF4 + double quantization：

- base：约 0.5–0.6 bytes/param
- 量化常数：额外一点
- adapter：BF16，和 LoRA 一样
- 计算时反量化到 BF16

7.2B 约 3.6GB base + 0.67GB adapter + 0.2GB 常数 ≈ **4.5GB**。

以 8GB 为例，名义值还剩约 3.5GB 给激活、CUDA context 和碎片；实际可用可能只有 ~6.9GB，剩约 2.4GB。seq 512 有机会，1024 需要实测，2048 很紧。

### 激活

激活取决于 batch、序列长度、层数、hidden、是否 checkpointing。经验：

- 朴素 attention 的 score 矩阵是 seq²；FlashAttention/分块 attention 下这部分接近线性，但激活仍随 seq 增长；batch 是线性项。先降 seq/batch。
- gradient checkpointing 用时间换显存
- `use_cache=False` 和 checkpointing 一起用
- 长上下文/大 batch 时，激活可能超过权重

## 3. rank、alpha 与学习率

LoRA 的增量：

$$
W'=W+\frac{\alpha}{r}BA
$$

- $A$：`r × d_in`
- $B$：`d_out × r`
- 初始化时 $B=0$，所以训练开始时增量为 0
- $\alpha/r$ 是缩放；改 $\alpha$ 等价于改有效学习率

rank 怎么选：

- r=8/16 是常用起点
- r=32/64 用于更难的任务/更大的领域迁移
- rank 越大，adapter 参数线性增加，容量和过拟合风险也增加
- rank 太小会欠拟合；不是越小越优雅

alpha：

- 常见 `alpha=2r`（r=16 → 32）
- 也有固定 alpha=16/32 的配方
- alpha 和 learning rate 要一起调；只改一个可能效果变差

学习率：

- LoRA 常用 1e-4–3e-4
- Full FT 常用 1e-5–5e-5
- warmup 3–5%，cosine/linear 衰减
- batch 小就梯度累积，不要硬堆 batch

dropout 常用 0.05；bias 一般不加（`bias="none"`）。

## 4. 目标模块

原版 LoRA 常挂 `q_proj`、`v_proj`；现在常见三种覆盖：

| 覆盖 | 模块 | 特点 |
|---|---|---|
| 最小 | q/v | 参数少，适合格式/风格 |
| 注意力 | q/k/v/o | 容量更大，常用 |
| 全线性 | q/k/v/o + gate/up/down | 领域/代码任务更稳，参数更多 |

以 7.2B、hidden 4096、FFN 14336、32 层、GQA 8 KV heads 为例：

| 目标 | r=8 | r=16 | r=32 | r=64 |
|---|---|---|---|---|
| attention | 6.8M | 13.6M | 27.3M | 54.5M |
| all linear | 21.0M | 41.9M | 83.9M | 167.8M |

r=16 时，attention-only 约占 7.2B 的 0.189%，all-linear 约占 0.583%。

注意：

- GQA 的 k/v 更小，adapter 参数量也更少
- 不同架构的模块名不同，用 `named_modules()` 查
- embeddings/lm_head 默认不要加；词表大，adapter 会很大
- target 模块不是越多越好；任务简单时全线性可能更容易过拟合

## 5. 合并与部署

合并：

$$
W_{\text{merged}}=W+\frac{\alpha}{r}BA
$$

合并后推理没有 adapter 开销，适合单模型部署。

不合并：

- base + adapter 分开，适合多任务/多租户
- 切换 adapter 要做路由和缓存
- 多 LoRA 服务要确认引擎支持（如 vLLM multi-LoRA）

量化 base 的坑：

- 4-bit base 不能直接和 BF16 adapter 相加
- 要么先反量化再合并，要么保持 adapter 分开
- 合并后要重新做精度/任务评测

保存：

- 只保存 adapter 时，必须记录 base 模型版本、tokenizer 版本、target modules、r/alpha
- 否则加载时对不上，效果会莫名变差

## 6. QLoRA 的工程细节

- base 用 NF4，double quantization
- 计算 dtype 用 BF16（不是 4-bit 计算）
- `prepare_model_for_kbit_training` 冻结 base、准备梯度 checkpointing
- optimizer 用 paged AdamW 8-bit，减少峰值显存
- 只训练 adapter；base 不更新
- 4-bit 会影响长上下文、工具调用、多语言；要自己的评测集验证
- 合并需要反量化；不合并就用 adapter 部署

QLoRA 不是“免费把 70B 塞进 8GB”：激活、序列长度、batch 仍然限制你。

## 7. 8GB 级显卡配方（示例）

8GB 是示例目标，不是最低配置。实际可用显存通常比标称少 0.5–1.5GB（显示/驱动/CUDA context）；换卡时把 8 换成你的可用显存，按同样公式重算。

| 项 | 建议 |
|---|---|
| 模型 | 7B QLoRA，或 1.5B–3B LoRA |
| base | 4-bit NF4 + double quant |
| r / alpha | 16 / 32 |
| target | all-linear；先跑 attention-only 也可以 |
| seq | 512–1024 |
| batch | 1，梯度累积 8–16 |
| checkpointing | 开 |
| optimizer | paged AdamW 8-bit |
| 计算精度 | BF16 |
| 学习率 | 1e-4–3e-4，warmup 3% |
| 评测 | 留出集 + 任务指标，不只看 loss |

OOM 的调整顺序：

1. 降 seq
2. 降 batch
3. 开 gradient checkpointing
4. base 换 4-bit
5. 减 target modules
6. 降 rank
7. 最后才考虑 CPU offload

`device_map="auto"` 可能把层 offload 到 CPU，显存看着够，速度会非常慢；用 `max_memory` 明确限制。

gradient checkpointing 和 `use_cache=True` 一起用可能冲突/警告；训练时关 cache。

## 8. 实验：7B 显存账与 merge 校验

以 7.2B 量级配置为例：hidden 4096、FFN 14336、32 层、GQA 8 KV heads。

计算：

- 不同 rank/target 的 adapter 参数量
- Full FT / LoRA / QLoRA 的权重+梯度+优化器显存
- 8GB 示例预算下 QLoRA 还剩多少给激活
- LoRA 合并前后输出是否一致

??? note "代码：7B 显存账与 merge 校验"
    ```python
    import torch
    from torch import nn

    hidden, ffn, layers = 4096, 14336, 32
    heads, kv_heads = 32, 8
    head_dim = hidden // heads
    kv_dim = kv_heads * head_dim

    def lora_params(r, modules):
        return sum(r * (d_in + d_out) for d_in, d_out in modules) * layers

    attn = [(hidden, hidden), (hidden, kv_dim), (hidden, kv_dim), (hidden, hidden)]
    mlp = [(hidden, ffn), (hidden, ffn), (ffn, hidden)]

    print("adapter params (M)")
    for name, mods in [("attention", attn), ("all linear", attn + mlp)]:
        for r in [8, 16, 32, 64]:
            p = lora_params(r, mods)
            print(f"{name:10s} r={r:2d} {p/1e6:6.1f}M  {p/7.2e9:.3%} of 7.2B")

    params_b = 7.2
    adapter = lora_params(16, attn + mlp)
    full = params_b * 16
    lora = params_b * 2 + adapter * 16 / 1e9
    qlora = params_b * 0.5 + adapter * 16 / 1e9 + 0.2
    print("memory GB (weights + gradients + optimizer, no activations)")
    print(f"full FT     {full:.1f}")
    print(f"LoRA BF16   {lora:.1f}")
    print(f"QLoRA 4-bit {qlora:.1f}")
    print(f"QLoRA 8GB left {8-qlora:.1f}")

    torch.manual_seed(0)
    r, alpha = 8, 16
    scale = alpha / r
    base = nn.Linear(64, 32, bias=False)
    A = torch.randn(r, 64) * 0.01
    B = torch.randn(32, r) * 0.01
    x = torch.randn(8, 64)
    y_adapter = base(x) + (x @ A.T @ B.T) * scale
    W = base.weight + scale * (B @ A)
    y_merged = x @ W.T
    print("merge max diff", (y_adapter - y_merged).abs().max().item())
    print("merge allclose", torch.allclose(y_adapter, y_merged, atol=1e-6))
    ```

输出：

```text
adapter params (M)
attention  r= 8    6.8M  0.095% of 7.2B
attention  r=16   13.6M  0.189% of 7.2B
attention  r=32   27.3M  0.379% of 7.2B
attention  r=64   54.5M  0.757% of 7.2B
all linear r= 8   21.0M  0.291% of 7.2B
all linear r=16   41.9M  0.583% of 7.2B
all linear r=32   83.9M  1.165% of 7.2B
all linear r=64  167.8M  2.330% of 7.2B
memory GB (weights + gradients + optimizer, no activations)
full FT     115.2
LoRA BF16   15.1
QLoRA 4-bit 4.5
QLoRA 8GB left 3.5
merge max diff 4.172325134277344e-07
merge allclose True
```

读法：

- 7.2B 全量微调权重+梯度+优化器状态约 115GB；8GB 不 offload 放不下
- BF16 LoRA 约 15.1GB；7B 不 offload 也放不进 8GB
- QLoRA 约 4.5GB；8GB 名义值还剩 3.5GB（实际可用 ~6.9GB，约 2.4GB），seq 512 有机会，1024 需实测
- all-linear r=16 的 adapter 约 41.9M，只占 7.2B 的 0.583%
- merge 前后最大误差 4.17e-07，`allclose` 通过

这是权重+梯度+优化器的规划模型，不含激活、CUDA context、碎片和框架开销；真实显存要自己压测。

## 9. 怎么选

| 场景 | 选择 |
|---|---|
| 8GB 级（示例），7B | QLoRA，seq 512 起步；1024 需实测 |
| 8GB 级（示例），1.5B–3B | LoRA；3B 的 BF16 base 也接近上限 |
| 多任务/多租户 | LoRA adapters，按请求路由 |
| 大领域迁移、追求最大效果 | Full FT + ZeRO/FSDP，多卡 |
| 快速迭代/格式/风格 | LoRA，r=8/16，attention-only 起步 |
| 需要单模型部署 | LoRA 合并；量化 base 先反量化 |
| 数据量很大、显存充足 | Full FT 或 LoRA 全线性，做对比 |

经验：

- 数据质量 > 微调方法；LoRA 不会把坏数据变成好数据
- LoRA 在格式/风格/领域适配很强，但大领域迁移可能不如 full FT；也有“LoRA 学得少、忘得少”的取舍
- QLoRA 省显存但更慢；4-bit 后一定要重测
- 先用小模型/小数据跑通，再上大模型

## 10. 常见坑

1. **8GB 级显卡上 7B 全量或 BF16 LoRA**
   权重+梯度+优化器就不够；用 QLoRA 或换小模型。

2. **rank 太小**
   容量不够，loss 降不下去；r=8/16 起步，再往上试。

3. **rank 太大**
   adapter 参数和过拟合风险上升；不是越大越好。

4. **alpha 和学习率不匹配**
   改 alpha 等于改有效更新；要一起调。

5. **target modules 只做 q/v**
   领域/代码任务可能不够；试 all-linear。

6. **4-bit 后不重测**
   长上下文、工具调用、多语言可能掉；用自己的评测集。

7. **merge 量化 base 未反量化**
   直接相加会出错；先 dequant 或保持 adapter 分开。

8. **只保存 adapter，忘记 base/tokenizer 版本**
   加载时对不上，效果变差。

9. **`device_map="auto"` 偷偷 offload**
   显存够了但速度很慢；用 `max_memory` 明确限制。

10. **gradient checkpointing + use_cache**
    训练时关 cache；否则冲突/浪费。

11. **SFT packing 标签 mask 错**
    把 prompt 或跨样本 token 算进 loss；见[数据管道](01-数据管道.md)。

12. **在训练集上评测**
    loss 好看不代表泛化；留出集 + 任务指标。

13. **多 adapter 路由/缓存没设计**
    每租户 adapter 切换会抖动；要缓存/路由。

## 11. 要点回顾

1. Full FT 约 16 bytes/param；7.2B 约 115GB，8GB 不 offload 放不下
2. BF16 LoRA 约 15GB；7B 不 offload 也放不进 8GB
3. QLoRA 4-bit 约 4.5GB；8GB 级（示例）可跑 7B，但要小 seq/batch + checkpointing
4. LoRA 增量 $W'=W+(\alpha/r)BA$；rank 管容量，alpha 管缩放
5. target modules 从 q/v 到 all-linear；GQA 的 k/v adapter 更小
6. 合并公式 $W+\frac{\alpha}{r}BA$；量化 base 要先反量化
7. 8GB 级示例配方：4-bit base、r=16/alpha=32、all-linear、seq 512 起步、batch 1、梯度累积
8. 数据质量 > 方法；4-bit 后必须重测
9. 保存 adapter 时同时记录 base/tokenizer/target/rank/alpha
