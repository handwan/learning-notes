# 数据管道

训练卡在 GPU 之前，常见原因不是模型，而是数据管道：

- tokenize 太慢，GPU 等 CPU
- padding 太多，token 预算浪费
- shuffle 不够，样本顺序有偏
- packing 把不同文档拼在一起，attention 串了
- worker 太少/太多，dataloader 成瓶颈
- 断点恢复后数据顺序变了

这篇讲训练侧的数据管道：tokenize、packing、shuffle、dedup、dataloader、吞吐与可复现。数据质量、配比和污染见 [LLM 第 4 篇](../llm/04-预训练数据.md)；BPE/WordPiece 细节见 [LLM 第 1 篇](../llm/01-Tokenizer.md)。

## 1. 管道全貌

```text
raw text
→ clean / filter
→ dedup
→ tokenize
→ pack
→ shuffle
→ batch
→ GPU
```

| 阶段 | 产物 | 关键决定 |
|---|---|---|
| clean / filter | 文本 | 质量、语言、长度、PII |
| dedup | 文档 ID / 哈希 | 精确/近似、训练/评测隔离 |
| tokenize | token IDs + 文档边界 | 词表、dtype、EOS、是否缓存 |
| pack | 固定长度 block + segment/loss mask | padding vs packing、跨文档隔离 |
| shuffle | 顺序 / 分片 | 全局/分片/buffer、seed |
| batch | input_ids / labels / mask | 按样本/按 token、动态 batch |
| GPU | 前向/反向 | dataloader wait、H2D |

两条原则：

- 不要让 GPU 等数据
- 不要让数据顺序改变训练语义

第一条规定吞吐，第二条规定正确性和可复现性。很多“训练慢”其实是第一条，很多“效果不稳定”是第二条。

## 2. Tokenize 一次

大模型预训练不该在每个 epoch 重新 tokenize。tokenizer 主要吃 CPU（Python 实现还有解释器开销），重复做会把 GPU 饿死。

离线 tokenization 的产物：

- token IDs：最大 ID < 65536 可用 `uint16`，更大用 `uint32`
- 每个文档的长度和 EOS
- tokenizer 版本、词表、特殊 token
- 数据/代码版本、shard 元数据

存储建议：

- 二进制 shard（`.bin`、`.npy`、Arrow/Parquet）
- 顺序读大文件，不要用 JSON/CSV 存 token
- 用 memmap/流式读，避免把全量 token 读进 Python list
- shard 大小按“读得动、传得快、好重试”定，常见几百 MB 到几 GB

存储层级、对象存储和并行文件系统的取舍见 [Infra 第 3 篇](../infra/03-存储与数据.md)。

tokenizer 要冻结版本。词表、normalization、special token 变了，token ID 的含义就变了；用旧 checkpoint 加载新 tokenizer，等于换了一套输入。

什么时候可以 on-the-fly：

- 小规模 SFT，数据量不大，chat template 经常变
- 在线数据增强/截断
- 调试/小样本过拟合

即使 on-the-fly，也尽量缓存 tokenize 结果；至少把 tokenizer 版本写进实验记录。

SFT 的 chat template 见 [LLM 第 7 篇](../llm/07-微调与对齐.md)；这里只强调：template 也是数据格式的一部分，训练和推理要一致。

## 3. Packing

padding baseline：

- 每条样本 pad 到固定 `max_len`
- 有效 token 占比 = 总有效 token / (`样本数 × max_len`)
- attention mask 告诉模型 pad 不算，但算力和显存已经花了

短样本多时，padding 浪费会很大。实验里平均 334 token、`max_len=2048`，利用率只有 16.3%。

packing：

- 文档之间插 EOS
- 把所有 token 拼成固定长度 block
- 用 segment IDs / `cu_seqlens` / block-diagonal attention 标记文档边界
- loss mask 掉 padding；SFT 还要 mask 掉 prompt token

关键不是“拼起来”，而是“拼起来之后模型怎么知道边界”。

- 预训练可以接受一定程度的跨文档注意力（有 EOS 分隔），但更稳的是按文档隔离
- SFT/对话建议按样本隔离；否则后一条样本会看到前一条样本的 prompt/response
- position IDs 要明确：按文档重置，还是在 block 内连续；训练和推理保持一致

长文档：

- 超过 `max_len` 的文档截断或切段
- 切段时保留 EOS/BOS 语义，别把一句话切一半还没有边界
- 丢弃长文档会改变数据分布；切段会改变样本数，要记录

packing 的代价：

- 需要 segment/attention 隔离，kernel 要支持 varlen
- batch 组成变了，token 数比样本数更适合做 batch 预算
- 数据顺序和文档边界要能恢复，否则断点续训对不上

## 4. Shuffle

shuffle 的目标：

- 打散文档顺序、来源、长度
- 分布式训练不重不漏
- 每个 epoch 可复现

shuffle 有两个层次：

- pack 前按文档 shuffle：混合来源/长度，避免一个 block 全是同一来源
- pack 后按 block shuffle：打散 batch 顺序

通常两层都要。下面的 buffer 实验是文档级 shuffle。

三种常见做法：

| 做法 | 适合 | 代价 |
|---|---|---|
| 全局 shuffle | 数据能放进内存/本地盘 | 需要随机访问 |
| 分片 shuffle | 对象存储/大文件 | 通常打散 shard + shard 内 |
| buffer shuffle | 流式读、内存有限 | buffer 大小影响随机性 |

buffer shuffle 的思路：维护一个大小为 K 的 buffer，每来一个新样本，随机换出一个旧样本；流结束后把 buffer 洗牌输出。

- K 太小：局部顺序残留，来源/长度仍然成簇
- K 太大：内存和随机访问成本上升
- K 接近数据量：接近全局 shuffle

实验里 K=10 时仍有 5.58% 的相邻样本在原始数据里相邻；K=1000 降到 0.02%，已经接近全量 shuffle。

分布式：

- 每个 rank 拿互斥的 index/shard
- `DistributedSampler` 会把数据 pad 到 world_size 的整数倍；不想重复就 `drop_last` 或按 rank 调整
- seed 用 `base_seed + epoch`；worker 的 seed 再按 worker_id 派生
- 别让所有 worker 用同一个随机种子，否则数据增强/负采样会重复

恢复：

- 保存 epoch、shard、sample index、buffer 内容和 RNG 状态
- 只保存模型/优化器，不保存数据状态，恢复后样本顺序会变
- 评测集不 shuffle；固定顺序才能复现

## 5. 去重放在哪

去重应该在 tokenize 之前：

- 省 tokenize 的 CPU
- 省存储
- 省训练算力
- 避免同一文档在 train/eval 两边出现

常见层次：

- 精确去重：规范化文本后做 hash
- 近似去重：MinHash/SimHash，按文档/段落/代码行
- 跨 split 去重：train 和 eval 之间也要查

去重算法、质量过滤、数据配比见 [LLM 第 4 篇](../llm/04-预训练数据.md)。这里只强调管道位置：**先去重，再 tokenize**。

保留去重统计和 hash，方便复现“为什么少了这么多数据”。

## 6. DataLoader

DataLoader 的目标是“喂得饱、喂得稳、可恢复”。

- worker 太少：GPU 等数据
- worker 太多：CPU/内存/磁盘互相抢，反而更慢
- `prefetch_factor`：每个 worker 预取多少 batch
- `persistent_workers=True`：epoch 之间不重启 worker，省启动开销
- `DataLoader(pin_memory=True)` + `.to(device, non_blocking=True)`：CPU→GPU 拷贝重叠

batch 策略：

- 按样本数 batch：实现简单，但长样本会爆 token
- 按 token 数 batch：固定 token 预算，长短样本混排
- length bucketing：把长度接近的样本放一起，减少 padding
- 动态 batch：按当前 batch 的实际 token 数调整

worker 随机性：

- `worker_init_fn` 里设置 `random`/`numpy`/`torch` 的 seed
- seed 用 `base_seed + worker_id`
- 数据增强、负采样、mask 都走同一套 seed

可恢复：

- 保存 epoch、shard、batch/sample index、RNG、buffer
- 恢复后先 skip 到断点，再继续
- 记录数据/代码/tokenizer 版本

监控：

- tokens/s、samples/s
- dataloader wait / input queue
- CPU 利用率、磁盘/网络吞吐
- GPU 空闲时间

只看 GPU 利用率不够；GPU 100% 也可能是数据在搬，见 [Infra 第 6 篇](../infra/06-可观测性.md)。

## 7. 实验：packing、shuffle 与 tokenize 一次

构造 10000 个长度不均的文档，比较：

- padding 到 2048 的 token 利用率
- packing 成 2048 block 的利用率
- 不同 buffer 大小的 shuffle 程度
- tokenize 一次 vs 每个 epoch 重做的时间模型

实验里超过 2048 的文档截断到 2048，padding baseline 按“每条文档一个 2048 block”算；真实训练可以切段而不是丢弃。

??? note "代码：packing、shuffle 与 tokenize 一次"
    ```python
    import math
    import random

    rng = random.Random(0)
    n = 10000
    lengths = []
    for _ in range(n):
        r = rng.random()
        if r < 0.80:
            L = rng.randint(50, 300)
        elif r < 0.95:
            L = rng.randint(300, 1000)
        else:
            L = rng.randint(1000, 4000)
        lengths.append(L)

    max_len = 2048
    doc_tokens = [min(L, max_len - 1) + 1 for L in lengths]  # +1 EOS
    total = sum(doc_tokens)
    print("docs", n, "tokens", total, "avg", round(total / n, 1), "max_raw", max(lengths))

    padding_slots = n * max_len
    pack_blocks = math.ceil(total / max_len)
    pack_slots = pack_blocks * max_len
    print("padding blocks", n, "slots", padding_slots, "util", f"{total / padding_slots:.1%}")
    print("packing blocks", pack_blocks, "slots", pack_slots, "util", f"{total / pack_slots:.1%}")

    def buffer_shuffle(items, size, rng):
        buf = []
        out = []
        it = iter(items)
        for _ in range(size):
            try:
                buf.append(next(it))
            except StopIteration:
                break
        for x in it:
            j = rng.randrange(len(buf))
            out.append(buf[j])
            buf[j] = x
        rng.shuffle(buf)
        out.extend(buf)
        return out

    ids = list(range(n))
    print("shuffle")
    for k in [1, 10, 100, 1000, 10000]:
        out = buffer_shuffle(ids, k, random.Random(1))
        adj = sum(out[i] == out[i - 1] + 1 for i in range(1, n)) / (n - 1)
        delta = sum(abs(out[i] - i) for i in range(n)) / n
        print(f" buffer={k:5d} adjacent={adj:6.2%} mean_abs_delta={delta:8.1f}")

    epochs = 4
    read_ms, tokenize_ms, pack_ms_per_1k, shuffle_ms = 0.05, 0.30, 0.01, 0.001
    per_epoch = n * read_ms + total / 1000 * pack_ms_per_1k + n * shuffle_ms
    once = n * tokenize_ms + epochs * per_epoch
    each = epochs * (n * (read_ms + tokenize_ms) + total / 1000 * pack_ms_per_1k + n * shuffle_ms)
    print("tokenize once", round(once / 1000, 2), "s")
    print("each epoch", round(each / 1000, 2), "s")
    print("speedup", round(each / once, 2), "x")
    ```

输出：

```text
docs 10000 tokens 3336641 avg 333.7 max_raw 3999
padding blocks 10000 slots 20480000 util 16.3%
packing blocks 1630 slots 3338240 util 100.0%
shuffle
 buffer=    1 adjacent=100.00% mean_abs_delta=     0.0
 buffer=   10 adjacent= 5.58% mean_abs_delta=     7.0
 buffer=  100 adjacent= 0.56% mean_abs_delta=    72.4
 buffer= 1000 adjacent= 0.02% mean_abs_delta=   688.7
 buffer=10000 adjacent= 0.01% mean_abs_delta=  3337.3
tokenize once 5.17 s
each epoch 14.17 s
speedup 2.74 x
```

读法：

- 10000 个文档、334 万 token，平均 333.7 token，最长原始文档 3999 token
- padding 到 2048：2048 万个 token 槽位，只有 16.3% 有效
- packing：1630 个 block、333.8 万个槽位，利用率约 100.0%（最后一个 block 只浪费约 1600 个 token）
- buffer=1 完全不 shuffle；buffer=10 还有 5.58% 的相邻样本保持原顺序
- buffer=1000 的相邻率 0.02%，接近全量 shuffle；`mean_abs_delta` 也从 0 涨到 688.7
- tokenize 一次：4 个 epoch 合计 5.17s；每个 epoch 重做：14.17s；约 2.74 倍差距
- 这是固定成本模型，不含真实 I/O/tokenizer 差异；实际要压测自己的管道

packing 的 100.0% 不代表免费：还要做 segment/attention 隔离，否则跨文档注意力会改变训练语义。

## 8. 常见坑

1. **每个 epoch 重新 tokenize**
   tokenizer 是 CPU 密集的；预训练要离线 tokenize，SFT 至少缓存。

2. **padding 到固定 max_len**
   短样本多时利用率很低；用 packing 或 length bucketing。

3. **packing 不做隔离**
   直接把文档拼起来，SFT 会让后一条样本看到前一条样本的 prompt/response。

4. **position IDs / segment IDs 错**
   packing 后位置和文档边界对不上，模型学到错误的位置关系。

5. **shuffle buffer 太小**
   局部顺序和来源仍然成簇；实验里 K=10 还有 5.58% 相邻。

6. **分布式重复/漏样本**
   sampler 的 pad、`drop_last`、rank 分配要一起看。

7. **worker seed 相同**
   数据增强/负采样重复，等于减小了数据多样性。

8. **去重放在 tokenize 之后**
   多花 tokenize 和存储；先去重再 tokenize。

9. **训练/评测集污染**
   benchmark 或 eval 数据混进训练集；跨 split 也要去重。

10. **断点恢复不保存数据状态**
    只存模型/优化器，恢复后样本顺序和 RNG 变了，实验不可复现。

11. **只看 GPU 利用率**
    GPU 忙不代表数据供得上；看 dataloader wait、input queue、tokens/s。

12. **用 JSON/CSV/Python list 存 token**
    体积大、解析慢、内存开销高；用二进制 shard/memmap/Arrow。

## 9. 要点回顾

1. 数据管道：clean → dedup → tokenize → pack → shuffle → batch → GPU
2. tokenize 一次并冻结 tokenizer 版本；用二进制 shard 存 token
3. padding 会浪费 token；packing 要用 segment/attention 隔离文档
4. packing 后 position IDs、loss mask、长文档切段都要一致
5. shuffle 用全局/分片/buffer；buffer 大小影响随机性和内存
6. 分布式 sampler 要保证不重不漏；worker seed 要按 worker_id 派生
7. 去重放在 tokenize 之前；训练/评测跨 split 也要查
8. 保存数据状态（epoch/shard/index/RNG/buffer），否则断点恢复不可复现
9. 用 tokens/s、dataloader wait、input queue 判断管道是否喂得饱
