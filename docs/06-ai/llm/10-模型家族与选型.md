# 模型家族与选型

没有“最好的模型”，只有“和约束最匹配的模型”。

选型不是看一张 leaderboard，而是先定硬约束，再小规模评测，最后算成本和风险。这篇讲：

- Llama、Qwen、Kimi、GLM、DeepSeek 这些家族各有什么取向
- 许可证、上下文、benchmark 的常见陷阱
- 私有部署、API、成本、延迟怎么权衡
- 给一个具体任务做加权选型表

## 1. 先定硬约束

选型第一步不是比分数，而是排除：

| 约束 | 问题 |
|---|---|
| 部署 | 必须私有部署，还是可以用 API？ |
| 许可 | 商用、再分发、改名、蒸馏有限制吗？ |
| 数据 | 数据能不能出公司/出境？ |
| 上下文 | 标称 128k，真实任务能用多少？ |
| 模态 | 只需文本，还是要图像/语音/视频？ |
| 工具 | 要 function calling、JSON、MCP 吗？ |
| 延迟 | 在线对话、批处理、离线评测要求不同 |
| 预算 | 按 token 付费，还是买 GPU？ |
| 语言 | 中文、英文、多语言、代码占比 |
| 运维 | 有没有推理引擎、量化、微调、监控能力？ |

硬约束不满足，分数再高也不选。

## 2. 模型家族

下面是“家族取向”，不是最新版本榜单；具体版本、参数、上下文、许可都要看模型卡。

| 家族 | 常见取向 | 注意 |
|---|---|---|
| Llama | 生态广、工具链成熟、英文/多语言 | 社区许可不是 OSI 开源；商用条款要读 |
| Qwen | 中文、多语言、代码、尺寸覆盖广 | 不同代际/尺寸许可可能不同；逐模型确认 |
| Kimi | 长上下文、Agent、MoE | 总参数/激活参数、部署成本要分开算 |
| GLM | 中文、工具调用、Agent | 开放权重版本和许可逐模型确认 |
| DeepSeek | 推理、代码、MoE | V3/R1 是不同取向；总参数和激活参数不同 |
| 闭源 API | 质量/工具/托管省心 | 数据、供应商锁定、价格、限流 |

几个判断：

- **中文客服/RAG**：Qwen、GLM，以及 Llama 的多语言版本或社区中文微调都可进 shortlist；要看中文评测和工具调用。
- **代码/Agent**：DeepSeek、Qwen、Kimi 常被拿来比；主要看工具调用、长任务、失败恢复。
- **推理/数学**：DeepSeek-R1、Qwen thinking 系列；看 pass@1、token 成本、是否需要长 CoT。
- **边缘/端侧**：Qwen 小尺寸、Llama 小尺寸；量化和延迟优先。
- **强合规/私有数据**：开放权重 + 私有部署；许可和数据驻留优先。

不要按“家族”直接下结论；同一家族不同尺寸/版本差异很大。

## 3. 许可与合规

“开放权重”不等于“OSI 开源”。

要看：

- 商用是否允许
- 再分发/托管服务是否允许
- 改名/衍生模型是否允许
- 蒸馏/合成数据是否有限制
- 用户数量/收入门槛
- 可接受使用政策
- 权重和代码的许可是否分开
- 训练数据/输出是否有额外限制

常见误区：

- 看到“open”就当成 Apache/MIT
- 只看代码 license，不看权重 license
- 忽略 acceptable use / 使用政策
- 忽略商标、命名和背书限制
- 把 API 条款当成模型许可

合规问题要在选型前问法务，不要等上线后补。

## 4. 上下文不是标称数字

模型卡写 128k，不代表你的任务能稳定用 128k。

要区分：

- **标称上下文**：位置编码支持的最大长度
- **有效上下文**：长文档问答、检索、代码库理解的实际表现
- **成本上下文**：KV cache、延迟、吞吐能不能承受

长上下文测试要看：

- needle-in-a-haystack（找针）
- 多跳/聚合（不是只找一个事实）
- 长代码/长表格
- 中间位置的信息
- 语言/格式变化

长上下文不是 RAG 的替代品。RAG 负责“找对材料”，长上下文负责“读更多材料”；两者的成本和准确率要一起算。

## 5. Benchmark 陷阱

benchmark 的污染、饱和、prompt/解码差异、自报分数、Arena 偏好和语言/领域偏差，都会让分数不可比。评测方法和 clean/contaminated 检查见[第 9 篇：LLM 评测与安全](09-评测与安全.md)。

选型时只问三件事：

- 测试集是否可能进过训练数据？
- 模型是否用同一套 prompt/解码/工具格式？
- 分数是否只来自英文/单一领域？

不要用一张 leaderboard 代替自己的任务评测。

## 6. 成本

两条路线：

### API

- 按 token 计费
- 没有 GPU 运维
- 受供应商限流/价格/数据政策影响
- 长上下文、输出 token、缓存价格要算清

### 自托管

- GPU 采购/租赁
- 权重显存 + KV cache + 激活
- 吞吐/利用率/MFU
- 运维、监控、升级
- 量化/蒸馏/推理引擎

粗略比较：

$$
\text{cost per 1M tokens}
=
\frac{\text{GPU 小时成本}}{\text{每小时生成 token 数}}\times 10^6
$$

MoE 要分开看：

- 显存按总参数
- 计算按激活参数
- 专家并行有通信成本

## 7. 选型流程

1. **硬约束过滤**：部署、许可、数据、上下文、模态
2. **Shortlist**：每类留 2–3 个候选
3. **小评测集**：用你自己的任务，不用公开榜代替
4. **成本/延迟**：按真实流量算，不只看单价
5. **Pilot**：小流量上线，监控失败率、延迟、成本
6. **回退方案**：版本 pin、备用模型、降级策略

自己的评测集至少覆盖：

- 常见任务
- 难例/长尾
- 多语言/代码
- 工具调用/结构化输出
- 安全/拒答
- 失败恢复

## 8. 任务选型表

| 任务 | 优先看 | 候选方向 |
|---|---|---|
| 中文客服 RAG | 中文、工具、私有部署、成本 | Qwen / GLM；Llama 多语言版或社区中文微调 |
| 代码 Agent | 工具调用、长任务、代码 | DeepSeek / Qwen / Kimi |
| 数学/推理 | pass@1、token 成本、CoT | DeepSeek-R1 / Qwen thinking |
| 端侧/边缘 | 小尺寸、量化、延迟 | Qwen 小模型 / Llama 小模型 |
| 长文档 | 有效上下文、KV cache | Kimi / Qwen / Llama 长上下文版本 |
| 强合规 | 许可、数据驻留、私有部署 | 开放权重 + 自托管 |
| 快速验证 | 托管、工具、低运维 | 闭源 API |

## 9. 实验：加权选型表

任务设定：中文客服 RAG + 工具调用，必须私有部署，32k 上下文，成本敏感。

权重：

- 中文 0.25
- 工具/结构化 0.20
- 私有部署/许可 0.20
- 长上下文 0.10
- 成本/延迟 0.15
- 生态/微调 0.10

分数是示例，不是 benchmark；真实选型要用自己的评测替换。

??? note "代码：实验：加权选型表"
    ```python
    weights = {
        "中文": 0.25,
        "工具": 0.20,
        "许可": 0.20,
        "上下文": 0.10,
        "成本": 0.15,
        "生态": 0.10,
    }

    candidates = {
        "Qwen 系列": dict(中文=5, 工具=4, 许可=4, 上下文=4, 成本=4, 生态=5, self_host=True),
        "GLM 系列": dict(中文=5, 工具=4, 许可=4, 上下文=4, 成本=4, 生态=4, self_host=True),
        "DeepSeek 系列": dict(中文=4, 工具=4, 许可=4, 上下文=4, 成本=3, 生态=4, self_host=True),
        "Kimi 系列": dict(中文=4, 工具=5, 许可=3, 上下文=5, 成本=2, 生态=3, self_host=True),
        "Llama 系列": dict(中文=3, 工具=4, 许可=3, 上下文=5, 成本=3, 生态=5, self_host=True),
        "闭源 API": dict(中文=5, 工具=5, 许可=2, 上下文=4, 成本=2, 生态=5, self_host=False),
    }

    eligible = {name: s for name, s in candidates.items() if s["self_host"]}

    ranked = []
    for name, s in eligible.items():
        score = sum(weights[k] * s[k] for k in weights)
        ranked.append((score, name))

    for score, name in sorted(ranked, reverse=True):
        print(f"{name:12s} {score:.2f}")

    print("excluded", [name for name, s in candidates.items() if not s["self_host"]])
    ```

输出：

```text
Qwen 系列      4.35
GLM 系列       4.25
DeepSeek 系列  3.85
Kimi 系列      3.70
Llama 系列     3.60
excluded ['闭源 API']
```

读法：

- 私有部署是硬约束，闭源 API 直接排除
- Qwen/GLM 在中文和成本上得分高
- Kimi 工具/上下文强，但成本得分低
- Llama 生态强，但中文和许可得分偏低
- 分数是示例；换权重/换任务，排序会变

## 10. 常见坑

1. **只看排行榜**
   leaderboard 不等于你的任务；污染、饱和、prompt 差异都会影响。

2. **把开放权重当开源**
   权重许可、代码许可、使用政策是分开的。

3. **忽略数据驻留**
   API 方便，但数据出公司/出境可能不合规。

4. **标称上下文当有效上下文**
   128k 标称不代表长文档任务能稳定用。

5. **只看单价，不算总成本**
   长输出、缓存、重试、限流、运维都要算。

6. **MoE 只看总参数**
   显存按总参数，计算按激活参数，通信另算。

7. **用错 tokenizer/chat template**
   同一模型不同模板，工具调用和格式遵循会差很多。

8. **量化后不重测**
   4-bit 可能掉工具调用/多语言/长上下文能力。

9. **不 pin 版本**
   供应商升级/模型下线会改变行为；要固定版本和回退。

10. **忽略工具调用失败恢复**
    Agent 任务不只看一次成功率，还要看重试、超时、幂等。

11. **合规后置**
    许可、隐私、内容政策要在选型前过，不是上线后补。

12. **只选一个模型**
    生产要有备用/降级；不同任务可以路由到不同模型。

## 11. 要点回顾

1. 选型先定硬约束：部署、许可、数据、上下文、模态、预算
2. 模型家族各有取向，但同家族不同版本差异很大
3. 开放权重不等于 OSI 开源；许可要逐模型确认
4. 标称上下文不等于有效上下文；长上下文要实测
5. benchmark 有污染、饱和、prompt/judge 偏差
6. 成本要按真实流量算：token、GPU、KV cache、运维
7. 用自有评测集做 shortlist，再做 pilot
8. 生产要 pin 版本、准备回退和降级
