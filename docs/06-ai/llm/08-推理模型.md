# 推理模型（Reasoning）

普通 LLM 直接给答案；推理模型先花更多 token 想，再给答案。

这条线要解决的问题是：**能不能用推理时的计算换准确率？**

- 长 CoT：把中间步骤写出来
- RLVR：用可验证奖励训练推理
- test-time compute：采样、验证、搜索
- thinking / non-thinking：按任务切换思考预算

这篇讲这些机制、代价和评测，最后用一个 parity 玩具实验比较“直接答”和“逐步想”。

## 1. 从 CoT 开始

Chain-of-Thought（CoT）就是让模型先写步骤：

```text
问题：一个班 35 人，转走 7 人，又来了 12 人，现在多少人？
思考：35 - 7 = 28；28 + 12 = 40
答案：40
```

CoT 的作用：

- 把多步计算拆开，降低单步难度
- 提供中间监督信号
- 让模型在推理时“多想一会儿”

但 CoT 不是万能的：

- 简单题上写很长，纯浪费 token
- CoT 可能不忠实：写出来的步骤不一定是模型真实计算过程
- 错误会沿步骤传播
- 训练数据里的 CoT 格式会影响输出风格

## 2. RLVR：可验证奖励

RLVR（Reinforcement Learning with Verifiable Rewards）用规则/测试/答案匹配给奖励：

- 数学：最终答案对不对
- 代码：测试是否通过
- 工具调用：参数/结果是否合法
- 结构化任务：格式/约束是否满足

和 RLHF 的区别：

| | RLHF | RLVR |
|---|---|---|
| 奖励来源 | 人类偏好/奖励模型 | 规则、测试、答案 |
| 成本 | 标注贵 | 可自动验证 |
| 风险 | reward hacking、标注偏差 | 奖励漏洞、测试覆盖不足 |
| 典型任务 | 对话、写作、风格 | 数学、代码、推理 |

RLVR 常见算法：

- PPO / GRPO
- 结果奖励（只看最终答案）
- 过程奖励（PRM，给中间步骤打分）
- 拒绝采样 + SFT

DeepSeek-R1 是典型代表：用 RLVR 训练长 CoT，再蒸馏到小模型。

## 3. Test-time compute

推理时多花计算，常见方式：

- **多次采样**：生成多个答案，投票/选一个
- **Self-consistency**：对最终答案做多数投票
- **Best-of-N**：生成 N 个候选，用 verifier 选最好的
- **PRM / verifier**：给中间步骤或最终答案打分
- **搜索**：树搜索、beam、回溯
- **长 CoT**：让模型自己写更多步骤

代价：

- token 数线性增长
- 延迟线性增长
- 需要 KV cache/批处理支撑
- 简单题上收益很小，甚至变差

test-time compute 不是越多越好。要按题目难度分配预算：简单题少想，难题多想。

## 4. Thinking / Non-thinking

混合模型可以让同一个模型切换：

- **non-thinking**：直接回答，延迟低、成本低
- **thinking**：先写 CoT，再回答，准确率更高但更慢
- **budget**：限制 thinking token 数/时间
- **routing**：简单请求走 non-thinking，难请求走 thinking

关键指标不是只看准确率；先把 token 成本和延迟成本按业务权重折算成同一单位（比如钱），再除以准确率：

$$
\text{cost per correct answer}
=
\frac{C_{\text{token}} + C_{\text{latency}}}{\text{accuracy}}
$$

不要直接把 token 数和毫秒相加；两者单位不同。$C_{\text{token}}$、$C_{\text{latency}}$ 是按价格/时延权重折算后的成本。

如果 thinking 把准确率从 70% 提到 75%，但 token 翻 10 倍，很多场景并不划算。

路由也会犯错：把难题分到 non-thinking，准确率会掉；把简单题分到 thinking，浪费成本。

## 5. 训练推理模型

常见流程：

```text
预训练 → SFT（带 CoT 的数据）→ RLVR → 蒸馏/量化 → 部署
```

SFT、DPO、ORPO 的细节见[第 7 篇：微调与对齐](07-微调与对齐.md)。

数据来源：

- 人类写步骤
- 强模型生成步骤 + 验证器筛选
- 拒绝采样：只保留答案正确的轨迹
- 自我博弈/合成题
- 过程奖励模型标注

注意：

- 只保留最终答案正确的轨迹，可能学到“错过程 + 对答案”
- 过程奖励更贵，但能减少捷径
- 训练题要覆盖难度梯度，否则模型只会在简单题上写长
- 蒸馏长 CoT 到小模型，可能学到冗长风格而不是推理能力

## 6. 实验：直接答 vs 逐步想

任务：6 位二进制串的奇偶校验。

- 输入 6 个 bit
- 输出最后一位 parity（0/1）
- 直接模式：只输出 final parity
- thinking 模式：输出每一步的 running parity，最后一位就是答案

同一个 TinyLM、同样参数量、同样训练步数。训练 48 条，验证 16 条。

模型定义与第 7 篇相同；下面假设已经执行第 7 篇的 `Block` / `TinyLM` 代码，08 不再重复一份。单独运行 08 时，先把第 7 篇的模型定义复制过来。

??? note "代码：实验：直接答 vs 逐步想"
    ```python
    import itertools
    import math
    import random
    import torch
    import torch.nn as nn
    import torch.nn.functional as F

    torch.manual_seed(0)

    bits = list(itertools.product([0, 1], repeat=6))
    rng = random.Random(0)
    rng.shuffle(bits)
    train_bits = bits[:48]
    val_bits = bits[48:]

    vocab = ["<pad>", "<bos>", "<sep>", "<eos>", "0", "1"]
    stoi = {w: i for i, w in enumerate(vocab)}
    itos = {i: w for w, i in stoi.items()}
    V = len(vocab)

    def running_parity(seq):
        out = []
        p = 0
        for b in seq:
            p ^= b
            out.append(p)
        return out

    def encode_direct(seq):
        p = running_parity(seq)[-1]
        return [stoi["<bos>"]] + [stoi[str(b)] for b in seq] + [stoi["<sep>"], stoi[str(p)], stoi["<eos>"]]

    def encode_cot(seq):
        return [stoi["<bos>"]] + [stoi[str(b)] for b in seq] + [stoi["<sep>"]] + [stoi[str(p)] for p in running_parity(seq)] + [stoi["<eos>"]]

    def train(mode, steps=600):
        torch.manual_seed(0)
        model = TinyLM(V, max_len=16)
        enc = encode_direct if mode == "direct" else encode_cot
        data = torch.tensor([enc(seq) for seq in train_bits])
        x = data[:, :-1]
        y = data[:, 1:]
        mask = torch.zeros_like(y, dtype=torch.bool)
        for i, row in enumerate(data):
            sep = (row == stoi["<sep>"]).nonzero().item()
            mask[i, sep:] = True

        opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
        for _ in range(steps):
            logits = model(x)
            loss = F.cross_entropy(logits[mask], y[mask])
            opt.zero_grad()
            loss.backward()
            opt.step()
        return model, loss.item()

    def evaluate(model, mode, data_bits):
        model.eval()
        correct = 0
        tokens = 0
        for seq in data_bits:
            ids = [stoi["<bos>"]] + [stoi[str(b)] for b in seq] + [stoi["<sep>"]]
            prompt_len = len(ids)
            n = 1 if mode == "direct" else 6
            with torch.no_grad():
                for _ in range(n):
                    logits = model(torch.tensor([ids[-16:]]))
                    ids.append(logits[0, -1].argmax().item())
            pred = itos[ids[prompt_len:][-1]]
            target = str(running_parity(seq)[-1])
            correct += pred == target
            tokens += len(ids) - prompt_len
        return correct / len(data_bits), tokens / len(data_bits)

    direct, direct_loss = train("direct")
    cot, cot_loss = train("cot")

    print("direct loss", round(direct_loss, 4), "val", evaluate(direct, "direct", val_bits))
    print("cot loss", round(cot_loss, 4), "val", evaluate(cot, "cot", val_bits))
    print("direct train", evaluate(direct, "direct", train_bits))
    print("cot train", evaluate(cot, "cot", train_bits))
    ```

输出：

```text
direct loss 0.0006 val (0.125, 1.0)
cot loss 0.0004 val (1.0, 6.0)
direct train (1.0, 1.0)
cot train (1.0, 6.0)
```

读法：

- direct 训练集 100%，验证集只有 `0.125`：记住了 48 条，没学会 parity
- CoT 训练集 100%，验证集 `1.0`：逐步算 running parity，泛化到了未见过的串
- 代价：每个答案从 1 个 token 变成 6 个 token
- 这是玩具实验，不是 LLM；但它展示了“用 token 换推理”的基本权衡

## 7. 评测

推理模型至少看：

- pass@1：一次答对率
- pass@k：多次采样至少一次答对
- majority vote：多次采样投票
- verifier/best-of-N：用验证器选
- token 数 / 延迟 / 成本
- 难度分层：简单/中等/难题分别看
- 污染检查：题目是否在训练集里

只看 pass@1 会低估 test-time compute 的价值；只看 pass@k 会高估部署效果。要同时报告“花多少 token 得到多少准确率”。

## 8. 常见坑

1. **以为 CoT 一定提升**
   简单题上长 CoT 可能更慢、更差。

2. **把 CoT 当真实解释**
   CoT 可能不忠实，是模型生成的文本，不是内部计算的透明记录。

3. **只看最终答案奖励**
   过程错了但答案对了，模型会学捷径；要过程奖励或更强验证器。

4. **RLVR 奖励漏洞**
   测试覆盖不足、答案匹配太松，模型会钻空子。

5. **长度 hacking**
   奖励长 CoT，模型会写废话；要长度惩罚/难度分层。

6. **pass@k 当 pass@1**
   采样多次的分数不能直接代表单次部署效果。

7. **thinking 预算一刀切**
   简单题也想很久，成本高；要路由/预算。

8. **蒸馏只学风格**
   小模型学到冗长格式，不一定学到推理；要验证。

9. **训练题太简单/太难**
   太简单学不到推理，太难全是失败信号。

10. **测试集污染**
    推理题很容易被背；要动态/私有题集。

11. **忽略延迟**
    thinking 可能几十秒，产品体验差；要分场景。

12. **安全/越狱**
    长 CoT 可能暴露更多内部信息，也可能被诱导绕过安全策略。

## 9. 要点回顾

1. 推理模型用更多推理时 token 换准确率
2. CoT 把多步计算拆开，但不一定忠实
3. RLVR 用可验证奖励训练，适合数学/代码/工具任务
4. test-time compute：多次采样、投票、verifier、搜索
5. thinking/non-thinking 是成本/准确率的路由问题
6. 评测要同时看 pass@1、pass@k、token、延迟、难度分层
7. 训练要防奖励漏洞、长度 hacking、污染
8. 小模型蒸馏长 CoT 不等于学会推理
