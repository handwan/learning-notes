# 批处理与调度

推理引擎的吞吐/延迟，很大一部分不是模型算出来的，而是调度出来的：

- 请求怎么排队
- 一个 batch 装多少
- prefill 和 decode 怎么混
- KV cache 怎么分块/回收
- 长请求会不会挡住短请求

这篇讲 static/continuous batching、prefill/decode 干扰、PagedAttention、chunked prefill 和调度策略，最后用模拟比较静态 vs 连续 batching。prefill/decode/KV 基础见[推理基础](01-推理基础.md)；引擎选型见[推理引擎](02-推理引擎.md)。

## 1. Static batching

做法：

- 凑够 B 个请求（或等超时）
- 一起 prefill，一起 decode
- 整个 batch 跑完才接下一批

问题：

- batch 里长短不一，短请求完成后 slot 空着
- 长请求拖住整批，尾延迟高
- 新请求要等整批结束，TTFT 变差
- padding 浪费算力/显存

适合：

- 离线批处理
- 长度比较均匀
- 对延迟不敏感

## 2. Continuous batching

做法：

- 以 token/iteration 为粒度调度
- 请求完成就退出，slot 立刻接新请求
- 新请求可以在其他请求 decode 时加入
- 不需要等整个 batch 结束

好处：

- GPU 利用率高
- 短请求不被长请求拖住
- TTFT/吞吐通常更好

代价：

- 调度器复杂
- KV cache 要动态分配/回收
- prefill 和 decode 会互相干扰
- 公平性/优先级/饥饿要处理

Orca 是连续 batching 的代表工作；vLLM/SGLang/TGI/TensorRT-LLM 都支持类似机制。

## 3. Prefill 与 decode 的干扰

Prefill 和 decode 共享 GPU：

- 长 prefill 会占住算力，decode 被推迟
- decode 是延迟敏感的；prefill 是吞吐敏感的
- 混在一起，TPOT 可能抖动

常见手段：

- **Chunked prefill**：把长 prompt 切成 chunk，和 decode 交错
- **Prefill/decode 分离**：不同资源池，KV 传输
- **优先级**：decode 优先，或按 SLO 分配
- **Piggyback**：prefill 和 decode 拼在一个 batch

Chunked prefill 的 tradeoff：

- chunk 太小：调度开销大，prefill 吞吐低
- chunk 太大：decode 被挡，TPOT 抖动
- 要按 SLO/负载调

分离部署（如 DistServe）能分别优化 prefill/decode，但增加 KV 传输和运维复杂度。

## 4. KV cache 管理

### PagedAttention

把 KV cache 切成固定大小的 block：

- 每个请求有 block table
- block 可以不连续
- 按需分配，减少预分配/碎片
- 支持前缀共享/copy-on-write

好处：

- 显存利用率高
- batch 能装更多
- 长上下文/变长请求更稳

block size 的取舍：

- 太小：block table/管理开销大
- 太大：内部碎片多
- 常见 16/32 token 量级；按引擎/负载调

### Prefix caching

多轮/共享 system prompt 场景，前缀 KV 可以复用：

- RadixAttention/radix tree（SGLang）
- vLLM 的 automatic prefix caching
- 命中率高时，TTFT 和算力都省

注意：

- 缓存会占显存，要和 KV 预算一起算
- 驱逐策略影响命中率
- 前缀要和 tokenizer/template 完全一致才命中

### 抢占/回收

KV 不够时：

- 换出到 CPU（swap）
- 丢弃后重算（recompute）
- 拒绝/排队（admission control）

抢占会影响 TPOT/尾延迟；要监控 preemption 次数。

## 5. 调度策略

常见策略：

- FCFS：简单，长请求会挡短请求
- 优先级：按租户/任务/SLO
- SJF/MLFQ：短请求优先，可能饿死长请求
- SLO-aware：按 TTFT/TPOT 目标分配
- 公平调度：多租户配额/权重

batching 预算不只看序列数：

- `max_num_seqs`：最多多少条
- `max_num_batched_tokens`：一个 batch 多少 token
- `max_prefill_tokens`/chunk size
- KV cache 预算

指标：

- TTFT/TPOT
- 吞吐（tokens/s、requests/s）
- goodput（满足 SLO 的吞吐）
- p95/p99
- 排队时间/拒绝率
- 公平性/饥饿

吞吐和延迟是 tradeoff：batch 越大，吞吐越高，但 TTFT/TPOT 可能变差。

## 6. 实验：静态 vs 连续 batching

用离散时间模拟，只换调度策略：

- 16 个请求，每 50ms 到一个
- prompt 128 token；输出长度 8/32 交替
- max batch 4
- prefill 2 token/ms；decode 0.1 token/ms
- 0.1 token/ms = 每 token 10ms

- Static：凑 4 个跑一批，整批结束再接下一批。
- Continuous：slot 空出来就接新请求。

??? note "代码：静态 vs 连续 batching"
    ```python
    def simulate(policy, n=16, interval=50, prompt=128, max_batch=4,
                 prefill_rate=2.0, decode_rate=0.1, max_time=20000):
        outputs = [8 if i % 2 == 0 else 32 for i in range(n)]
        arrivals = [i * interval for i in range(n)]
        waiting = list(range(n))
        active = []
        records = {}
        t = 0
        last_arrival = arrivals[-1]

        def admit():
            if policy == "static":
                if active:
                    return
                ready = [i for i in waiting if arrivals[i] <= t]
                if len(ready) >= max_batch:
                    take = ready[:max_batch]
                elif t >= last_arrival and ready:
                    take = ready
                else:
                    return
            else:
                free = max_batch - len(active)
                ready = [i for i in waiting if arrivals[i] <= t]
                take = ready[:free]
            for i in take:
                waiting.remove(i)
                active.append({"id": i, "arrival": arrivals[i], "prefill": prompt,
                               "decode": outputs[i], "first": None, "finish": None})

        while t < max_time and (waiting or active):
            admit()
            for r in active:
                if r["prefill"] > 0:
                    r["prefill"] -= prefill_rate
                    if r["prefill"] <= 0 and r["first"] is None:
                        r["first"] = t + 1
            for r in active:
                if r["prefill"] <= 0 and r["decode"] > 0:
                    r["decode"] -= decode_rate
                    if r["decode"] <= 0 and r["finish"] is None:
                        r["finish"] = t + 1
            done = [r for r in active if r["finish"] is not None]
            for r in done:
                records[r["id"]] = r
            active = [r for r in active if r["finish"] is None]
            t += 1

        ttfts = sorted(records[i]["first"] - arrivals[i] for i in records)
        e2es = sorted(records[i]["finish"] - arrivals[i] for i in records)
        makespan = max(records[i]["finish"] for i in records)

        def pct(xs, p):
            return xs[min(len(xs) - 1, int(round((len(xs) - 1) * p)))]

        return {
            "done": len(records),
            "avg_ttft": sum(ttfts) / len(ttfts),
            "p95_ttft": pct(ttfts, 0.95),
            "avg_e2e": sum(e2es) / len(e2es),
            "makespan": makespan,
            "tput": len(records) / (makespan / 1000),
        }

    for policy in ["static", "continuous"]:
        r = simulate(policy)
        print(policy, {k: (round(v, 1) if isinstance(v, float) else v) for k, v in r.items()})
    ```

输出：

```text
static {'done': 16, 'avg_ttft': 413.5, 'p95_ttft': 713, 'avg_e2e': 613.0, 'makespan': 1682, 'tput': 9.5}
continuous {'done': 16, 'avg_ttft': 141.6, 'p95_ttft': 240, 'avg_e2e': 341.1, 'makespan': 1303, 'tput': 12.3}
```

读法：

- static：平均 TTFT 413.5ms，p95 713ms，吞吐 9.5 req/s
- continuous：平均 TTFT 141.6ms，p95 240ms，吞吐 12.3 req/s
- 短请求在 static batch 里提前完成，但 slot 要等长请求结束；continuous 立刻接新请求
- 这个实验只改调度，不改模型/kernel/KV；真实引擎差异还需要压测
- 如果所有请求长度一样，static 的劣势会小很多；变长请求放大 batch barrier

## 7. 常见坑

1. **静态 batching 配变长请求**
   短请求完成但 slot 空等，尾延迟高。

2. **按序列数 batch，不按 token 数**
   长 prompt 可能一个 batch 就爆显存/延迟。

3. **忽略 prefill/decode 干扰**
   长 prefill 挡住 decode，TPOT 抖动。

4. **KV cache 预分配/碎片**
   显存浪费，batch 上不去；用 PagedAttention/块管理。

5. **前缀缓存没命中**
   tokenizer/template 不一致，或缓存被驱逐；命中率要监控。

6. **队列无上限**
   延迟爆炸；要 admission control/限流。

7. **只按 FCFS**
   长请求挡短请求；按 SLO/优先级/公平性调。

8. **batch 越大越好**
   TTFT/TPOT 变差；吞吐和延迟要一起看。

9. **chunk size 拍脑袋**
   太小调度开销大，太大挡 decode；按负载调。

10. **抢占太频繁**
    recompute/swap 增加 TPOT；监控 preemption。

11. **只看平均延迟**
    尾延迟/排队才是体验；看 p95/p99。

12. **不按真实长度分布压测**
    平均长度掩盖长尾；要覆盖长短混合。

## 8. 要点回顾

1. Static batching 有 batch barrier，短请求会空等；适合离线/均匀长度
2. Continuous batching 按 token/iteration 调度，slot 空出就接新请求
3. Prefill/decode 会互相干扰；chunked prefill/分离部署/优先级是常见手段
4. PagedAttention 用 block/block table 管 KV，减少碎片、支持前缀共享
5. Prefix caching 复用共享前缀 KV；命中率受 tokenizer/template/驱逐影响
6. 调度不只看序列数，还要看 token 预算、KV 预算、SLO
7. 吞吐和延迟是 tradeoff；看 TTFT/TPOT/goodput/p95/p99
8. 模拟里 continuous 把平均 TTFT 从 413.5ms 降到 141.6ms，吞吐 9.5→12.3 req/s
9. 真实引擎差异还要看 kernel/KV/量化/网络；调度只是其中一层
