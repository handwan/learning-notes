# 压测与容量规划

容量规划不是“跑一次 benchmark 看最大 QPS”。它要回答：

- 在什么 SLO 下？
- 什么输入/输出长度分布？
- 多少并发/什么到达模式？
- 单副本能扛多少？要几个副本？
- 故障/峰值/增长留多少余量？
- 成本是多少？

这篇讲 SLO、指标、负载模型、压测方法、Little's law 和容量规划，最后用 M/M/c 队列模拟延迟-QPS 曲线。SLO/错误预算见 [Infra 第 6 篇](../infra/06-可观测性.md)；部署/多租户见 [Infra 第 5 篇](../infra/05-部署与多租户.md)；TTFT/TPOT 定义见[推理基础](01-推理基础.md)。

## 1. 先定 SLO

容量是“在 SLO 下能扛多少”，不是“最大吞吐”。

常见 SLO：

- TTFT p95 < 500ms
- TPOT p95 < 50ms
- 端到端 p95 < 2s
- 错误率 < 0.1%
- 可用性 99.9%

要注意：

- TTFT/TPOT/端到端可以分别设 SLO
- 按租户/模型/路由分
- 有时间窗口（1h/1d/30d）
- 有错误预算/burn rate
- SLO 不是“平均值”

## 2. 指标

- TTFT：首 token
- TPOT/ITL：后续 token 间隔
- 吞吐：tokens/s、requests/s
- goodput：满足 SLO 的吞吐
- p50/p95/p99：尾延迟
- 错误率/超时率/取消率
- 队列长度/等待时间
- GPU 利用率/显存/KV cache
- 每租户/模型/路由
- 成本：每百万 token/每请求

关键：

- **goodput** 比裸吞吐更有用
- p99 比平均更能暴露排队
- 错误/超时要单独看，不要只统计成功请求
- 压测客户端也要记录延迟，不能只信服务端

## 3. 负载模型

压测前先定义负载：

- prompt 长度分布（平均 + p95/p99）
- output 长度分布
- 请求类型：聊天/补全/工具/结构化
- 多轮/前缀复用比例
- 租户/模型/路由占比
- 到达模式：Poisson/固定 QPS/突发
- 冷/热缓存

开环 vs 闭环：

- 闭环：收到响应再发下一个；并发固定，容易低估排队
- 开环：按固定到达率发请求；更接近线上，能暴露队列
- 闭环+固定并发容易“协调遗漏”（coordinated omission）：系统慢时请求发得更少，延迟看起来还好
- 压测要用开环/固定到达率，或至少记录计划发送时间

负载类型：

- load：正常峰值
- stress：逐步加压到饱和
- soak：长时间稳定负载，查泄漏/降频
- spike：瞬时突发
- breakpoint：找拐点

## 4. 压测方法

固定变量：

- 同一模型/版本/精度
- 同一引擎/配置
- 同一硬件/驱动/CUDA
- 同一 tokenizer/template/sampling
- 同一负载分布/并发/到达模式

流程：

1. warmup：加载模型/CUDA graph/编译
2. 低负载基线
3. 逐步加压，记录 TTFT/TPOT/p95/p99/goodput/错误/显存
4. 找到拐点/饱和点
5. 多轮重复，报告方差
6. 保存配置/版本/日志

不要：

- 不同模型/精度横比
- 只看平均值
- 用闭环压测代替开环
- 忽略长 prompt/长输出
- 忽略错误/超时

## 5. Little's law 与容量

Little's law：

$$
\text{concurrency}\approx \text{QPS}\times\text{latency}
$$

容量：

$$
\text{replicas}
=
\left\lceil
\frac{\text{target QPS}}{\text{per-replica capacity at SLO}}
\right\rceil
$$

再留：

- N+1：一个副本故障
- 峰值/平均比
- 增长趋势
- 冷启动/扩容时间
- 地域/故障域

注意：

- 接近饱和时，延迟非线性上升；不要按 100% 利用率规划
- 单副本容量要在 SLO 下测，不是最大 QPS
- 副本不是越多越好：调度、冷启动、成本
- 有状态/前缀缓存时，路由会影响命中率

## 6. 实验：延迟-QPS 曲线

用 M/M/c 队列模拟：

- 4 个 server
- 平均服务时间 0.2s（单副本理论上限 20 QPS）
- Poisson 到达，指数服务时间
- 每个 QPS 模拟 2000 个请求
- 看 p95、最大队列

??? note "代码：M/M/c 延迟-QPS"
    ```python
    import heapq
    import math
    import random
    from collections import deque

    def simulate(qps, n=2000, servers=4, service=0.2, seed=0):
        rng = random.Random(seed)
        arrivals = []
        t = 0.0
        for _ in range(n):
            t += rng.expovariate(qps)
            arrivals.append(t)

        free = servers
        queue = deque()
        departures = []
        completed = []
        max_q = 0

        for arr in arrivals:
            while departures and departures[0][0] <= arr:
                end, start = heapq.heappop(departures)
                completed.append(end - start)
                free += 1
                if queue:
                    qstart = queue.popleft()
                    free -= 1
                    heapq.heappush(departures, (end + rng.expovariate(1 / service), qstart))

            if free > 0:
                free -= 1
                heapq.heappush(departures, (arr + rng.expovariate(1 / service), arr))
            else:
                queue.append(arr)
                max_q = max(max_q, len(queue))

        while departures:
            end, start = heapq.heappop(departures)
            completed.append(end - start)
            if queue:
                qstart = queue.popleft()
                heapq.heappush(departures, (end + rng.expovariate(1 / service), qstart))

        completed.sort()

        def pct(p):
            return completed[min(len(completed) - 1, int(round((len(completed) - 1) * p)))]

        return pct(0.95), max_q

    print("servers=4 mean_service=0.2s capacity=20 qps")
    for qps in [10, 14, 15, 16, 18, 20, 22]:
        p95, max_q = simulate(qps)
        print(f"qps={qps:2d} p95={p95:.2f}s max_q={max_q}")

    capacity = 15
    target = 50
    need = math.ceil(target / capacity)
    n1 = need + 1
    print("capacity at SLO", capacity, "qps")
    print("target", target, "replicas", need, "n+1", n1,
          "util", f"{target / (n1 * capacity):.1%}")
    ```

输出：

```text
servers=4 mean_service=0.2s capacity=20 qps
qps=10 p95=0.62s max_q=7
qps=14 p95=0.77s max_q=14
qps=15 p95=0.89s max_q=17
qps=16 p95=1.04s max_q=22
qps=18 p95=1.50s max_q=34
qps=20 p95=3.11s max_q=66
qps=22 p95=9.52s max_q=203
capacity at SLO 15 qps
target 50 replicas 4 n+1 5 util 66.7%
```

读法：

- 理论容量 20 QPS，但 p95<1s 的 SLO 下只能到约 15 QPS
- 14→15 QPS，p95 从 0.77 到 0.89；16 QPS 1.04，越过 SLO
- 18/20/22 QPS 延迟非线性上升，队列 34/66/203
- 50 QPS：每个副本按 15 QPS 算，需要 4 个；N+1 是 5 个，利用率 66.7%
- 这是 M/M/c 模型，不是实际引擎；真实服务时间/到达/长度分布不同，要实测
- 这里用的是请求延迟；TTFT/TPOT 要单独压测/设 SLO

## 7. 常见坑

1. **只看平均延迟**
   p95/p99 才是排队/体验；平均会骗人。

2. **闭环压测/协调遗漏**
   系统慢时请求发得更少，延迟被低估。

3. **不 warmup**
   加载/编译/CUDA graph 污染结果。

4. **不同模型/精度横比**
   数字不可比；固定模型/精度/硬件。

5. **按 100% 利用率规划**
   饱和点延迟爆炸；留 headroom。

6. **只看吞吐，不看 goodput**
   吞吐高但 SLO 不达标，没用。

7. **不分开 TTFT/TPOT**
   首 token 和后续 token 是不同瓶颈。

8. **忽略长 prompt/长输出**
   平均长度掩盖长尾；要覆盖 p99。

9. **忽略冷启动/扩容**
   自动扩容不是瞬时；GPU/模型加载要时间。

10. **不留 N+1**
    一个副本故障就超 SLO。

11. **忽略增长/峰值**
    按当前平均规划，几个月后不够。

12. **不记录配置/版本**
    复现不了；引擎/驱动/模型版本都会影响。

13. **把模拟当实测**
    M/M/c 只是直觉；真实要开环压测。

## 8. 要点回顾

1. 容量是“SLO 下的 QPS”，不是最大吞吐
2. 指标看 TTFT/TPOT/p95/p99/goodput/错误/队列/成本
3. 负载要定义长度分布/到达模式/多轮/缓存；用开环压测
4. 固定模型/精度/硬件/配置，warmup，多轮，报告方差
5. Little's law：并发 ≈ QPS × latency
6. 副本 = ceil(target QPS / 单副本 SLO 容量)，再留 N+1/峰值/增长
7. 接近饱和延迟非线性上升；不要按 100% 利用率规划
8. M/M/c 模拟可用于直觉；真实容量要压测
9. TTFT/TPOT/端到端要分别设 SLO；不要只看一个数
