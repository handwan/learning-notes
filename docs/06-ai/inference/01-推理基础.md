# 推理基础

训练把数据变成权重，推理把权重变成 token。两者的瓶颈不一样：

- 训练看吞吐、显存、通信
- 推理看 TTFT、TPOT、并发、KV cache、成本

这篇讲推理的两个阶段、KV cache、显存账、roofline、TTFT/TPOT 和 batching，最后手算一个模型的 KV cache 与并发。GPU/roofline 的基础见 [Infra 第 1 篇](../infra/01-GPU与加速器.md)；部署/容量见 [Infra 第 5 篇](../infra/05-部署与多租户.md)；可观测性见 [Infra 第 6 篇](../infra/06-可观测性.md)。

## 1. Prefill 与 decode

| 阶段 | 输入 | 计算 | 常见瓶颈 | 指标 |
|---|---|---|---|---|
| Prefill | 整段 prompt | 大矩阵乘、并行度高 | 长 prompt 通常 compute-bound | TTFT |
| Decode | 上一步 token | 每步读权重 + KV cache | 通常 memory-bound | TPOT/ITL |

- Prefill 决定首 token 延迟；decode 决定后续 token 的速度和吞吐
- Prefill 可以 chunk；decode 可以 batching
- 两者混在一起会互相干扰：长 prefill 会挡住 decode

## 2. KV cache

自回归生成时，每步都要用到之前所有 token 的 K/V。不缓存就要重算，缓存就要占显存。

每个 token 的 KV 大小：

$$
\text{KV/token}
=
2\times L\times H_{kv}\times d_{head}\times \text{bytes}
$$

- 2：K 和 V
- L：层数
- $H_{kv}$：KV heads
- $d_{head}$：每个 head 的维度
- bytes：FP16/BF16 通常 2

几个例子（FP16/BF16）：

| 模型 | 层数 | KV heads | head_dim | KV/token |
|---|---|---|---|---|
| 7B MHA | 32 | 32 | 128 | 512 KiB |
| 8B GQA | 32 | 8 | 128 | 128 KiB |
| 70B GQA | 80 | 8 | 128 | 320 KiB |

GQA/MQA 减少 KV heads，KV cache 直接按比例下降；MLA 用低秩压缩，思路类似。

KV cache 是**每条序列**的，不是每个模型一份：

- 一条 32k 的 7B MHA：16 GiB
- 一条 32k 的 8B GQA：4 GiB
- 一条 32k 的 70B GQA：10 GiB

所以长上下文/高并发时，KV cache 可能超过权重。

## 3. 显存账

推理显存大致是：

```text
权重
+ KV cache
+ 激活/临时 buffer
+ CUDA context / 碎片
```

- 7B FP16 权重约 14GB；8B 约 16GB；70B 约 140GB
- 4-bit 权重约 3.5GB / 4GB / 35GB，但 KV cache 还是按原 dtype/层数算
- KV cache 随 `batch × seq` 线性增长
- 长上下文先吃 KV，再吃权重

最大并发粗算：

$$
\text{max seqs}
\approx
\left\lfloor
\frac{\text{GPU}\times\text{headroom}-\text{weights}}
{\text{KV/token}\times\text{seq}}
\right\rfloor
$$

还要留激活、临时 buffer、碎片；实际比这个数小。

## 4. Roofline：prefill 和 decode 为什么不同

算术强度：

$$
\text{AI}=\frac{\text{FLOPs}}{\text{bytes}}
$$

Prefill：

- 一次处理 T 个 token，FLOPs 约 $2NT$
- 权重/激活被复用，AI 高
- 长 prompt 通常 compute-bound

Decode：

- 每步只生成 1 个 token，FLOPs 约 $2N$
- 要读权重 + KV cache
- batch=1 时 AI 很低，通常 memory-bound
- batch 增大，权重复用，AI 上升；但 KV 也随 batch 增长

所以：

- Prefill 优化算力/kernel
- Decode 优化带宽/KV cache/batching
- 量化、GQA、PagedAttention、speculative decoding 都在改这两个瓶颈

Roofline 的细节见 [Infra 第 1 篇](../infra/01-GPU与加速器.md)。

## 5. TTFT、TPOT 与吞吐

指标：

- **TTFT**：请求到首 token 的时间；含排队、prefill、网络
- **TPOT / ITL**：首 token 之后，每个输出 token 的间隔
- **端到端**：`TTFT + TPOT × (output_tokens - 1)`
- **吞吐**：tokens/s 或 requests/s
- **并发**：同时在处理的请求数

Little's law：

$$
\text{concurrency}\approx \text{QPS}\times\text{latency}
$$

所以 QPS 和延迟要一起看；只看 tokens/s 会掩盖排队。

在线服务要分开设 SLO：

- TTFT：首 token 体验
- TPOT：流式输出速度
- p50/p95/p99：尾延迟
- 错误率/超时率

SLO/错误预算见 [Infra 第 6 篇](../infra/06-可观测性.md)。

## 6. Batching 与调度

- 静态 batching：凑够一批再跑；简单，但排队/尾延迟差
- Continuous batching：请求完成就换出，GPU 不空等
- PagedAttention：KV cache 分页，减少碎片/预分配
- Chunked prefill：长 prefill 切片，别一次挡住 decode
- Prefill/decode 分离：不同资源池，分别优化
- Speculative decoding：小模型草稿 + 大模型验证，降 TPOT
- 量化：权重/KV 量化，降显存/带宽

这些是后续文章的主题；这里先建立“prefill 和 decode 要分开看”的框架。

## 7. 实验：KV cache 与并发

以三个模型为例：

- 7B MHA：32 层、32 KV heads、head_dim 128、FP16 权重约 14GB
- 8B GQA：32 层、8 KV heads、head_dim 128、FP16 权重约 16GB
- 70B GQA：80 层、8 KV heads、head_dim 128、FP16 权重约 140GB

计算：

- 每 token KV
- 4k/32k/128k 的 KV
- 80/24/8GB 卡在 32k 下的最大并发（0.9 headroom）
- batch=1、32k、2TB/s 的 TPOT 下限

??? note "代码：KV cache 与并发"
    ```python
    GIB = 1024**3

    def kv_gib_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
        return 2 * layers * kv_heads * head_dim * dtype_bytes / GIB

    def kv_gib(per_token, seq):
        return per_token * seq

    def max_seqs(gpu_gb, weights_gb, per_token, seq, headroom=0.9):
        usable = gpu_gb * headroom - weights_gb
        if usable <= 0:
            return 0, usable
        return int(usable // (per_token * seq)), usable

    configs = [
        ("7B MHA", 32, 32, 128, 14),
        ("8B GQA", 32, 8, 128, 16),
        ("70B GQA", 80, 8, 128, 140),
    ]

    print("KV per token")
    for name, L, KVH, D, W in configs:
        per = kv_gib_per_token(L, KVH, D)
        print(f"{name:9s} {per*1024**2:6.0f} KiB/token")

    print("\nKV at context (GiB)")
    for name, L, KVH, D, W in configs:
        per = kv_gib_per_token(L, KVH, D)
        print(f"{name:9s} 4k={kv_gib(per,4096):5.2f}  32k={kv_gib(per,32768):5.2f}  128k={kv_gib(per,131072):5.2f}")

    print("\nmax sequences (32k, 0.9 headroom)")
    for name, L, KVH, D, W in configs:
        per = kv_gib_per_token(L, KVH, D)
        vals = []
        for gpu in [80, 24, 8]:
            if W >= gpu * 0.9:
                vals.append(f"{gpu}GB=needs TP")
            else:
                n, _ = max_seqs(gpu, W, per, 32768)
                vals.append(f"{gpu}GB={n}")
        print(f"{name:9s} " + "  ".join(vals))

    print("\nTPOT lower bound (batch 1, 32k, 2TB/s)")
    for name, L, KVH, D, W in configs:
        per = kv_gib_per_token(L, KVH, D)
        bytes_read = W * 1e9 + kv_gib(per, 32768) * GIB
        ms = bytes_read / 2e12 * 1000
        print(f"{name:9s} {ms:6.1f} ms")
    ```

输出：

```text
KV per token
7B MHA       512 KiB/token
8B GQA       128 KiB/token
70B GQA      320 KiB/token

KV at context (GiB)
7B MHA    4k= 2.00  32k=16.00  128k=64.00
8B GQA    4k= 0.50  32k= 4.00  128k=16.00
70B GQA   4k= 1.25  32k=10.00  128k=40.00

max sequences (32k, 0.9 headroom)
7B MHA    80GB=3  24GB=0  8GB=needs TP
8B GQA    80GB=14  24GB=1  8GB=needs TP
70B GQA   80GB=needs TP  24GB=needs TP  8GB=needs TP

TPOT lower bound (batch 1, 32k, 2TB/s)
7B MHA      15.6 ms
8B GQA      10.1 ms
70B GQA     75.4 ms
```

读法：

- 7B MHA 每 token 512 KiB，32k 就 16 GiB；8B GQA 只要 4 GiB
- 70B GQA 每 token 320 KiB，32k 10 GiB
- 80GB 上 7B MHA 32k 只能放约 3 条；8B GQA 约 14 条
- 24GB 上 8B GQA 32k 只能 1 条；7B MHA 32k 放不下
- 8GB 上 FP16 的 7B/8B 都放不下；4-bit 8B 权重约 4GB，4k 可放几条，32k 仍不行
- 70B 单 80GB 放不下权重，要 TP/多卡；长上下文还要更多卡
- TPOT 下限：7B MHA 15.6ms、8B GQA 10.1ms、70B 75.4ms（batch=1，32k，2TB/s）
- 70B 的 75.4ms 是按单设备 2TB/s 的量级示例；70B 实际要 TP，按聚合带宽/分片算，不能直接当单卡下限
- 7B MHA 比 8B GQA 的 TPOT 更高，因为 KV 更大；这是 MHA vs GQA 的直接代价

这是规划模型，不含 kernel/调度/网络/碎片；真实性能要压测。

## 8. 常见坑

1. **只算权重，不算 KV cache**
   长上下文/高并发时 KV 可能超过权重。

2. **把标称 context 当可用 context**
   128k 标称不代表 128k 并发/延迟能接受。

3. **忽略 KV dtype**
   FP16/BF16 KV 是 2 bytes；FP8/INT8 减半，但影响精度。

4. **Prefill/decode 混在一起看**
   一个看算力，一个看带宽；优化手段不同。

5. **只看平均延迟**
   TTFT/TPOT/p95/p99 才是体验；平均会掩盖排队。

6. **batch 越大越好**
   batch 提高吞吐，但增加 TTFT/TPOT 和 KV 显存。

7. **静态 batching**
   请求长短不一，GPU 空等；连续 batching 更好。

8. **KV cache 碎片**
   预分配/碎片会浪费显存；PagedAttention 之类要按块管理。

9. **长 prefill 挡住 decode**
   用 chunked prefill/分离部署，别让一个长 prompt 卡住所有流。

10. **8GB 上硬上长上下文**
    权重+KV 很快爆；量化/小模型/短上下文更现实。

11. **只看 tokens/s**
    不看 TTFT/TPOT/SLO，吞吐再高也可能不可用。

12. **不按真实长度分布压测**
    平均长度和 p99 长度差很多；要覆盖长尾。

## 9. 要点回顾

1. 推理分 prefill 和 decode：前者看算力/TTFT，后者看带宽/TPOT
2. KV cache = 2×L×KV heads×head_dim×bytes/token
3. GQA/MQA 减少 KV heads，长上下文/高并发收益大
4. 显存 = 权重 + KV cache + 激活/临时 buffer；KV 随 batch×seq 增长
5. Prefill 长 prompt 通常 compute-bound；decode batch=1 通常 memory-bound
6. TTFT、TPOT、吞吐、并发要一起看；用 Little's law 和分位数
7. Batching 提高吞吐但增加延迟；continuous batching/PagedAttention/chunked prefill 是常见手段
8. 7B MHA 32k KV 约 16GiB；8B GQA 约 4GiB；70B GQA 约 10GiB
9. 8GB 上 FP16 7B/8B 放不下；4-bit/小模型/短上下文才现实
