# 推理引擎

模型权重不会自己变成服务。推理引擎要做：

- 加载模型/权重格式
- 图优化、kernel 选择、CUDA graph
- KV cache 管理
- batching/调度
- 量化/并行
- HTTP/gRPC/OpenAI API、流式、指标

这篇讲主流引擎的定位、选型维度、内部结构和压测方法，最后做一个引擎选型矩阵。prefill/decode/KV cache 的基础见[推理基础](01-推理基础.md)；batching 的调度实验放在下一篇。

## 1. 主流引擎

| 引擎 | 定位 | 强项 | 注意 |
|---|---|---|---|
| ONNX Runtime | 跨平台推理运行时 | CPU/GPU/边缘、图优化、ORT GenAI | LLM 特性不如专用引擎全；导出/算子覆盖 |
| TensorRT-LLM | NVIDIA 编译型引擎 | FP8/INT4、in-flight batching、多卡 | 按 GPU/精度编译；版本耦合；NVIDIA only |
| vLLM | Python serving 引擎 | PagedAttention、continuous batching、OpenAI API、模型覆盖广 | 版本/显存/内核适配要跟 |
| SGLang | serving 引擎 | RadixAttention/前缀缓存、结构化输出、高吞吐 | 生态相对小；版本迭代快 |
| TGI | Hugging Face 生产服务 | HF 集成、continuous batching、量化 | 特性/性能按版本确认 |
| llama.cpp | C++/GGUF 本地推理 | CPU/Apple/边缘、低资源 | 不适合高吞吐多租户 GPU 服务 |
| Triton | 服务框架（不是引擎） | 多后端、指标、K8s 集成 | 要配 TensorRT-LLM/vLLM 等后端 |

不是“哪个最快”这么简单：硬件、模型、量化、功能、运维都会改变排序。

## 2. 选型维度

先定硬约束：

- 硬件：NVIDIA / AMD / CPU / Apple
- 模型：架构、GQA/MoE/MLA、多模态、上下文长度
- 量化：FP8/INT4/AWQ/GPTQ，引擎是否支持
- 功能：前缀缓存、结构化输出、multi-LoRA、speculative、chunked prefill、分离部署
- 接口：OpenAI API、gRPC、流式、鉴权
- 并行：TP/PP/多机、KV cache 分片
- 运维：指标、日志、K8s、升级/回滚
- 生态：文档、社区、版本节奏
- 成本：GPU 利用率、显存、冷启动

再看性能：

- 同一模型/版本/精度
- 同一硬件/驱动/CUDA
- 同一输入/输出长度分布
- 同一并发/到达模式
- 同一 cache 状态（冷/热）
- warmup 后再测

不要拿厂商 PPT 的不同精度/不同模型数字横比。

## 3. 引擎内部

一个 LLM 引擎大致有：

```text
模型加载/权重格式
→ 图/算子优化
→ KV cache 管理
→ batching/调度
→ attention/GEMM/量化 kernel
→ 流式输出/服务层
```

关键模块：

- **Scheduler**：静态/连续 batching、prefill/decode、chunked prefill、优先级
- **KV cache manager**：分页/块、前缀缓存、驱逐、显存池
- **Kernels**：FlashAttention/FlashInfer、GEMM、量化、CUDA graph
- **Model runner**：forward、sampling、stop 条件
- **Serving**：HTTP/gRPC、OpenAI API、流式、metrics

引擎的差异，很多时候不在“模型算得有多快”，而在：

- 调度能不能把 GPU 喂满
- KV cache 会不会碎片/浪费
- 前缀缓存能不能命中
- 量化 kernel 是否真的快
- 多卡通信/并行是否高效

## 4. 压测方法

指标：

- TTFT：首 token 延迟
- TPOT/ITL：后续 token 间隔
- 吞吐：tokens/s、requests/s
- p50/p95/p99：尾延迟
- GPU 显存/利用率
- 启动/加载时间
- 错误率/超时率

负载：

- prompt/output 长度分布（平均 + p99）
- 并发/QPS/到达模式
- 多轮/前缀复用比例
- 冷启动 vs 热缓存
- 长上下文/短请求混合

对比：

- 固定模型/精度/硬件
- 固定 tokenizer/template
- 固定 sampling 参数
- 固定 batch/并发上限
- 记录版本/commit/驱动
- 跑多轮，报告方差

“引擎 benchmark”是系统 benchmark，不是模型 benchmark。

## 5. 实验：引擎选型矩阵

真实跑 vLLM/TensorRT-LLM/SGLang 需要对应的 CUDA/模型/服务环境；这篇先做选型矩阵，下一片做 batching 调度实验。

矩阵的分数是**示例**，不是 benchmark；分差小于 0.3 视为同一档，不要按小数点排序；真实选型要拿自己的模型/负载压测。

??? note "代码：引擎选型矩阵"
    ```python
    engines = {
        "ONNX Runtime": dict(nvidia=3, model=3, features=2, ops=4, portability=5, multi_gpu=3, quant=3, ecosystem=4, prefix=1),
        "TensorRT-LLM": dict(nvidia=5, model=3, features=4, ops=2, portability=1, multi_gpu=5, quant=5, ecosystem=3, prefix=3),
        "vLLM": dict(nvidia=4, model=5, features=5, ops=4, portability=3, multi_gpu=4, quant=4, ecosystem=5, prefix=4),
        "SGLang": dict(nvidia=4, model=4, features=5, ops=3, portability=2, multi_gpu=4, quant=4, ecosystem=4, prefix=5),
        "TGI": dict(nvidia=4, model=4, features=4, ops=4, portability=2, multi_gpu=4, quant=4, ecosystem=4, prefix=4),
        "llama.cpp": dict(nvidia=2, model=3, features=2, ops=4, portability=5, multi_gpu=2, quant=5, ecosystem=4, prefix=2),
    }

    scenarios = {
        "NVIDIA 高吞吐 API": dict(nvidia=.25, model=.20, features=.20, ops=.15, multi_gpu=.10, quant=.10),
        "最大性能/FP8": dict(nvidia=.35, quant=.20, multi_gpu=.15, features=.15, model=.10, ops=.05),
        "多轮/前缀/结构化": dict(prefix=.40, features=.20, model=.10, ops=.10, nvidia=.10, ecosystem=.10),
        "CPU/边缘": dict(portability=.40, ops=.20, model=.15, quant=.15, ecosystem=.10),
        "快速原型": dict(ops=.35, ecosystem=.20, portability=.20, model=.15, nvidia=.10),
    }

    for scenario, weights in scenarios.items():
        ranked = []
        for name, scores in engines.items():
            score = sum(w * scores[k] for k, w in weights.items())
            ranked.append((score, name))
        print(scenario)
        for score, name in sorted(ranked, reverse=True)[:4]:
            print(f"  {name:13s} {score:.2f}")
    ```

输出：

```text

  SGLang        4.05
  TGI           4.00
  TensorRT-LLM  3.95
最大性能/FP8
  TensorRT-LLM  4.50
  vLLM          4.25
  SGLang        4.10
  TGI           4.00
多轮/前缀/结构化
  SGLang        4.50
  vLLM          4.40
  TGI           4.00
  TensorRT-LLM  3.30
CPU/边缘
  llama.cpp     4.40
  ONNX Runtime  4.10
  vLLM          3.85
  TGI           3.20
快速原型
  vLLM          4.15
  ONNX Runtime  3.95
  llama.cpp     3.85
  TGI           3.60
```

读法：

- 平衡的 NVIDIA API：vLLM 领先；SGLang/TGI 紧随；TensorRT-LLM 因运维复杂度排在后面
- 最大性能/FP8：TensorRT-LLM 领先；vLLM/SGLang 次之
- 多轮/前缀/结构化：SGLang 领先，vLLM 紧随；前缀缓存权重大时排序会变
- CPU/边缘：llama.cpp/ONNX Runtime
- 快速原型：vLLM/ONNX/llama.cpp 都可，取决于硬件
- 换权重/换场景，排序会变；不要把这个表当 benchmark

## 6. 常见坑

1. **只看吞吐，不看 TTFT/TPOT**
   吞吐高但首 token 慢，交互体验差。

2. **拿不同精度/模型横比**
   FP8 vs FP16、不同模型版本，数字不可比。

3. **忽略输入/输出长度分布**
   长 prompt 和长输出是两种负载；平均会骗人。

4. **不 warmup**
   首次加载/CUDA graph/编译会污染结果。

5. **忽略前缀缓存命中**
   多轮/共享 system prompt 场景，命中率影响很大。

6. **静态 batching 当 continuous batching**
   请求长短不一，静态 batch 会空等/尾延迟高。

7. **KV cache 碎片/预分配**
   显存浪费，batch 上不去；看 PagedAttention/块管理。

8. **量化 kernel 没真正生效**
   权重是 4-bit，算的还是 BF16/FP16；看实际 kernel/吞吐。

9. **多卡只看单卡**
   TP 通信、KV 分片、负载均衡会改变结果。

10. **忽略版本/驱动**
    引擎、CUDA、驱动、模型格式版本不匹配，性能/正确性都变。

11. **把 Triton 当引擎**
    Triton 是服务框架，后端才是 TensorRT-LLM/vLLM 等。

12. **不做回归**
    升级引擎/模型后，TTFT/TPOT/质量/安全都要重测。

## 7. 要点回顾

1. 引擎负责加载、图优化、KV cache、调度、kernel、服务层
2. ONNX Runtime 偏跨平台/边缘；TensorRT-LLM 偏 NVIDIA 极致性能；vLLM 平衡；SGLang 偏前缀/结构化；llama.cpp 偏本地/CPU
3. 选型先定硬件/模型/量化/功能/运维，再看性能
4. 压测要固定模型/精度/硬件/长度分布/并发，并 warmup
5. 指标看 TTFT、TPOT、吞吐、p95/p99、显存、启动
6. 引擎差异常在调度、KV cache、前缀缓存、量化 kernel
7. 多轮/前缀场景要单独测 SGLang/vLLM 的缓存命中
8. Triton 是服务框架，不是引擎
9. 真实选型用自有负载压测；矩阵只是起点
