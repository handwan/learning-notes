# 高级推理优化

基础的 prefill/decode、batching、量化做完后，还可以从这些方向继续优化：

- speculative decoding：用 draft 换 target 的 forward 次数
- prefill/decode 分离：不同资源池，分别优化 TTFT/TPOT
- KV cache 压缩：量化/驱逐/架构压缩
- multi-LoRA：共享 base，多任务/多租户
- prefix caching / chunked prefill：复用/调度（见[批处理与调度](03-批处理与调度.md)）

这篇讲这些技术的收益、代价和组合方式，最后用延迟模型比较 speculative decoding。prefill/decode/KV 基础见[推理基础](01-推理基础.md)；量化见[量化](04-量化.md)。

## 1. 优化地图

| 技术 | 优化目标 | 主要收益 | 代价 |
|---|---|---|---|
| Speculative decoding | TPOT/吞吐 | 低 batch、memory-bound decode | draft 计算、acceptance 低会变慢 |
| Prefill/decode 分离 | TTFT/TPOT/goodput | 独立扩缩容、SLO | KV 传输、调度、运维 |
| KV cache 压缩 | 显存/带宽/长上下文 | 更高并发/更长上下文 | 精度、实现复杂 |
| Multi-LoRA | 多任务/多租户 | 共享 base、adapter 小 | 路由/缓存/隔离 |
| Chunked prefill | TTFT/TPOT 平衡 | 长 prefill 不挡 decode | 调度复杂 |
| 量化 | 显存/带宽 | 权重/KV 更小 | 精度/kernel 支持 |

没有免费午餐：每个优化都在换某个资源，必须用自己的负载 ablation。

## 2. Speculative decoding

思路：

1. draft 模型/头先生成 γ 个候选 token
2. target 模型一次 forward 验证这 γ+1 个位置
3. 接受最长正确前缀，第一个拒绝位置由 target 给一个 token
4. 重复

acceptance rate α 下，每轮期望接受 token 数：

$$
E[\text{accepted}]
=
\sum_{i=0}^{\gamma}\alpha^i
=
\frac{1-\alpha^{\gamma+1}}{1-\alpha}
$$

每轮时间：

$$
T_{\text{round}}
=
\gamma\times t_{\text{draft}}+T_{\text{target}}
$$

TPOT：

$$
\text{TPOT}
=
\frac{T_{\text{round}}}{E[\text{accepted}]}
$$

所以：

- α 高、draft 便宜、target forward 贵 → 收益大
- α 低、draft 贵 → 可能比普通 decode 更慢
- γ 太大：draft 成本/验证成本上升，收益可能下降

变体：

- Medusa：多个解码头，不一定要独立 draft 模型
- EAGLE：在 feature 层做 draft
- Lookahead/tree：候选树 + 并行验证
- 这些本质仍是“draft + target 验证”，acceptance/成本模型类似

工程注意：

- draft/target 的 tokenizer/template 要一致
- sampling 要实现正确，否则输出分布会变
- draft 的 KV cache/显存也要算
- target 验证 γ+1 个 token 的 kernel/attention 要支持
- 高 batch/compute-bound 时，target 验证成本上升，收益会缩小

## 3. Prefill/decode 分离

Prefill 和 decode 的瓶颈不同：

- prefill：compute-bound，影响 TTFT
- decode：memory-bound，影响 TPOT

分离部署：

- prefill pool + decode pool
- prefill 完成后把 KV cache 传给 decode pool
- 两边独立扩缩容/调度
- DistServe 是代表工作

好处：

- 按 SLO 分配资源
- prefill 不挡 decode
- 长 prompt/高并发更稳

代价：

- KV 传输占带宽/延迟
- 需要拓扑/调度/故障处理
- 两套池子的利用率和运维
- 不是小部署的默认选择

替代方案：

- chunked prefill（单池内交错）
- 优先级调度
- 把长 prompt 放到单独队列

## 4. KV cache 压缩

三条路：

1. **量化**：FP8/INT8 KV；显存/带宽减半或更多；影响长上下文
2. **驱逐**：只保留 heavy hitters/sink tokens；H2O、StreamingLLM 等
3. **架构**：GQA/MQA/MLA，从模型结构上减少 KV/token

还要配合：

- PagedAttention/块管理（减少碎片）
- Prefix caching（复用共享前缀）
- 长上下文评测（检索/多跳/位置）

注意：

- 驱逐可能丢关键信息；要看任务
- KV 量化对长上下文/工具调用更敏感
- 架构压缩在训练时就定了，推理侧只能选模型
- “权重 4-bit”不代表 KV 也 4-bit；要单独设

## 5. Multi-LoRA

做法：

- 一个 base 模型 + 多个 LoRA adapter
- 请求按 tenant/task 路由到 adapter
- adapter 小，base 共享
- 引擎支持 multi-LoRA batching/缓存

好处：

- 多任务/多租户不用复制 base
- adapter 切换/存储成本低
- 适合风格/格式/领域适配

代价：

- adapter 加载/换入换出抖动
- 路由/缓存/隔离复杂
- 不同 adapter 的 batch 可能降低 kernel 效率
- 大领域迁移可能不如全量微调

工程：

- adapter cache/上限
- 按租户限流/配额
- adapter 版本 pin
- 评测每个 adapter，不只测 base
- 安全/越权：adapter 不能绕过 base 的策略

LoRA 训练/合并见[微调](../training/02-微调.md)。

## 6. 实验：speculative decoding 延迟模型

假设：

- 普通 decode：target 10ms/token → 100 tok/s
- speculative：γ=4，draft 1ms/token，target 验证 10ms
- acceptance rate α 变化

??? note "代码：speculative decoding 延迟模型"
    ```python
    def speculative(t_target=10.0, t_draft=1.0, gamma=4, alpha=0.7):
        expected = sum(alpha ** i for i in range(gamma + 1))
        round_time = gamma * t_draft + t_target
        tpot = round_time / expected
        return expected, tpot, t_target / tpot

    print("normal tpot", 10.0, "ms throughput", 100.0, "tok/s")
    print("gamma=4 draft=1ms target=10ms")
    for alpha in [0.1, 0.3, 0.5, 0.7, 0.9]:
        e, tpot, speed = speculative(alpha=alpha)
        print(f"alpha={alpha:.1f} expected={e:.4f} tpot={tpot:.2f}ms speedup={speed:.2f}x")

    print("alpha=0.7, gamma sweep")
    for gamma in [1, 2, 4, 8]:
        e, tpot, speed = speculative(gamma=gamma, alpha=0.7)
        print(f"gamma={gamma} expected={e:.4f} tpot={tpot:.2f}ms speedup={speed:.2f}x")
    ```

输出：

```text
normal tpot 10.0 ms throughput 100.0 tok/s
gamma=4 draft=1ms target=10ms
alpha=0.1 expected=1.1111 tpot=12.60ms speedup=0.79x
alpha=0.3 expected=1.4251 tpot=9.82ms speedup=1.02x
alpha=0.5 expected=1.9375 tpot=7.23ms speedup=1.38x
alpha=0.7 expected=2.7731 tpot=5.05ms speedup=1.98x
alpha=0.9 expected=4.0951 tpot=3.42ms speedup=2.93x
alpha=0.7, gamma sweep
gamma=1 expected=1.7000 tpot=6.47ms speedup=1.55x
gamma=2 expected=2.1900 tpot=5.48ms speedup=1.83x
gamma=4 expected=2.7731 tpot=5.05ms speedup=1.98x
gamma=8 expected=3.1988 tpot=5.63ms speedup=1.78x
```

读法：

- α=0.1 时 speculative 反而慢（0.79x）；draft 成本收不回来
- α=0.3 基本打平；α=0.5 约 1.38x；α=0.7 约 1.98x；α=0.9 约 2.93x
- α=0.7 时 γ=4 最优；γ=8 因 draft/验证成本上升，降到 1.78x
- 这是延迟模型，不是实际引擎 benchmark；真实要看 draft 成本、acceptance 分布、batch、kernel
- 高 batch/compute-bound 时 target 验证更贵，收益会缩小

## 7. 怎么组合

| 场景 | 优先技术 |
|---|---|
| 低 batch、decode memory-bound | speculative decoding |
| 长 prompt、prefill 挡 decode | chunked prefill / 分离部署 |
| KV 显存/长上下文 | KV 量化、驱逐、GQA/MLA |
| 多租户/多任务、共享 base | multi-LoRA |
| 显存/带宽整体不够 | 量化 + PagedAttention/prefix cache |
| 高吞吐离线 | batching + 量化；speculative 收益可能小 |

组合原则：

- 先做基础：batching、KV 管理、量化
- 再做 speculative/分离；一次只加一个，做 ablation
- 每个优化都测 TTFT/TPOT/吞吐/质量/显存
- 不要把所有开关一起打开；定位不了收益

## 8. 常见坑

1. **acceptance 低还上 speculative**
   draft 成本收不回来，TPOT 变差。

2. **忽略 target 验证成本**
   γ 越大，target 一次验证的 token 越多，计算/attention 成本上升。

3. **draft/target 模板不一致**
   tokenizer/template 不同，候选对不上。

4. **sampling 实现错误**
   输出分布变了，质量/复现都出问题。

5. **高 batch 还指望 speculative**
   target 已经 compute-bound，收益小甚至变慢。

6. **分离部署忽略 KV 传输**
   KV 传输成新瓶颈；拓扑/带宽要算。

7. **KV 驱逐丢关键信息**
   长上下文/检索任务掉点；要任务评测。

8. **KV 量化不测长上下文**
   短 prompt 好看，长上下文/工具调用坏了。

9. **multi-LoRA 频繁换入换出**
   adapter 抖动，吞吐下降；要缓存/路由。

10. **multi-LoRA 隔离不足**
    租户越权/数据泄漏；要权限/审计。

11. **一次开太多优化**
    归因不了，回滚困难；做 ablation。

12. **只看 TPOT**
    忽略 TTFT/吞吐/质量/显存；SLO 是组合指标。

## 9. 要点回顾

1. speculative decoding 用 draft 换 target forward 次数；acceptance/成本决定收益
2. 期望接受 token 数 `(1-α^(γ+1))/(1-α)`；TPOT = (γ·t_draft + T_target)/期望
3. α 低/draft 贵/高 batch 时，speculative 可能不划算
4. prefill/decode 分离按瓶颈分池；KV 传输是代价
5. KV 压缩有量化/驱逐/架构三条路；要测长上下文
6. multi-LoRA 共享 base，适合多任务/多租户；路由/缓存/隔离是关键
7. 优化要组合，但一次只加一个，做 ablation
8. 指标看 TTFT/TPOT/吞吐/质量/显存，不只看一个数
