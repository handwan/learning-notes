# 架构风格

架构风格不是成熟度阶梯。单体不是“落后”，微服务也不是“先进”；它们是不同约束下的组织方式。

这篇比较五种常见风格：

- 单体
- 模块化单体
- 微服务
- 事件驱动
- CQRS

这里不背定义，关心每种风格换来什么、付出什么、什么时候不该用。

## 1. 先看约束

选架构风格前，先确认：

| 约束 | 会改变什么 |
|---|---|
| 团队数量/边界 | 是否需要独立发布 |
| 发布频率 | 是否要拆部署单元 |
| 领域边界 | 能否划清服务边界 |
| 数据一致性 | 能否接受最终一致 |
| 故障隔离 | 一个模块挂了要不要拖垮全部 |
| 运维能力 | 能否维护服务网格/消息/追踪 |
| 延迟/吞吐 | 同步调用还是异步 |
| 合规/租户 | 是否需要物理/逻辑隔离 |
| 成本 | 机器、人力、复杂度预算 |

架构风格解决的是“边界、部署、数据、故障”的组合问题，不是“代码看起来高不高级”。

## 2. 单体

一个应用、一份代码、一个部署单元、通常一个数据库。

适合：

- 早期产品、领域还没稳定
- 小团队
- 强事务、简单部署
- 请求量还不需要独立扩缩容

代价：

- 模块边界容易腐烂
- 一个模块的故障/资源占用可能影响全部
- 发布要整体进行
- 代码耦合后拆分成本高

单体不是问题；**没有边界的单体**才是问题。

## 3. 模块化单体

一个部署单元，但内部按领域/模块划清边界：

```text
orders module  →  order schema
billing module →  billing schema
notify module  →  notify schema
```

模块之间：

- 通过明确接口调用，不直接读对方表
- 数据所有权清晰
- 可以独立测试
- 未来需要时，按模块边界拆服务

适合：

- 大多数新系统
- 团队不大、领域还在演进
- 需要强事务、低运维成本
- 想保留未来拆分的选择

代价：

- 需要纪律：模块边界不能只写在文档里
- 共享数据库要按 schema/权限隔离
- 一个进程仍然可能被慢模块拖累

模块化单体是很多系统的合理起点，不是“过渡方案”的同义词。

## 4. 微服务

多个独立部署的服务，每个服务有自己的数据所有权和发布节奏。

适合：

- 多个团队，边界相对稳定
- 需要独立发布/扩缩容
- 故障隔离是硬需求
- 组织已经具备运维/观测能力

代价：

- 网络调用、超时、重试、幂等
- 分布式事务、最终一致
- 版本兼容、契约测试
- 部署、追踪、日志、告警复杂度
- 数据重复/同步
- 本地开发环境变重

微服务不是性能银弹：远程调用通常比进程内调用慢，服务拆得不对会更糟。

### 拆服务的条件

可以拆的信号：

- 团队按领域长期独立负责
- 发布互相阻塞
- 某模块需要独立扩缩容
- 故障隔离有明确收益
- 数据边界可以切开

不该只因为：

- 代码文件多
- 想用新技术
- 听说微服务“先进”
- 组织图看起来像服务图

### 分布式单体

最常见的坏结果：

```text
服务拆了，但共享一个数据库
每次发布要一起发
调用链强耦合
一个变更要改多个服务
```

这叫分布式单体：拿到了分布式的复杂度，没拿到独立演进。

## 5. 事件驱动

服务之间通过事件/消息解耦：

```text
OrderCreated → 库存预留
OrderCreated → 通知
OrderCreated → 报表投影
```

适合：

- 异步解耦
- 削峰
- 多消费者
- 审计/回放
- 长流程编排

代价：

- 最终一致
- 重复消费、顺序、幂等
- 事件 schema 演进
- 积压、死信、重放
- 调试链路更长

事件驱动不是“所有调用都异步”。同步查询、强一致写、用户等待结果的操作，仍可能需要同步路径。

事件设计和事务模式见后续分布式章。

## 6. CQRS

命令查询职责分离：写模型和读模型分开。

```text
write side → 事件/变更 → projection → read side
```

适合：

- 读写负载差异大
- 读模型复杂、需要多种视图
- 需要独立扩展读/写
- 可以接受投影延迟

代价：

- 读模型最终一致
- 投影重建/修复
- 双模型维护
- 事件版本和幂等

CQRS 不等于事件溯源。可以只做读写模型分离，不保存完整事件历史。

普通 CRUD 系统上 CQRS，通常只是增加复杂度。

## 7. 对比

| 风格 | 部署 | 数据 | 一致性 | 运维成本 | 适合 |
|---|---|---|---|---|---|
| 单体 | 一个单元 | 一个库 | 强/本地事务 | 低 | 早期、小团队、强事务 |
| 模块化单体 | 一个单元 | 分 schema/所有权 | 强/本地事务 | 低-中 | 多数新系统、可演进 |
| 微服务 | 多服务 | 每服务自有 | 最终/分布式 | 高 | 多团队、独立发布 |
| 事件驱动 | 多服务/worker | 事件 + 各自存储 | 最终 | 中-高 | 异步、削峰、多消费者 |
| CQRS | 读写分离 | 写库 + 读模型 | 通常最终 | 中-高 | 读写差异大、多视图 |

## 8. 一个演进例子

订单系统，包含订单、支付、通知、报表。

### 阶段 1：模块化单体

```text
orders / payments / notifications / reports
一个部署单元，schema 分开
```

理由：

- 领域还在变
- 团队小
- 需要订单/支付强事务
- 通知和报表可以先同步/定时

### 阶段 2：拆通知 worker

通知需要重试、限流、隔离第三方故障。

```text
orders → 事件/队列 → notification worker
```

不是为了“微服务化”，而是通知有独立的失败模式和扩缩容需求。

### 阶段 3：报表读模型

报表查询复杂、压力大，不影响下单。

```text
订单事件 → 报表投影 → 读模型
```

这就是 CQRS 的局部使用，不是全系统重写。

演进原则：

> 按边界和故障模式拆，不按技术分层拆。

## 9. 决策清单

- 团队是否按领域独立负责？
- 发布是否互相阻塞？
- 是否需要独立扩缩容/故障隔离？
- 数据边界能否切开？
- 能否接受最终一致？
- 是否具备消息、追踪、告警、回滚能力？
- 拆了之后，跨服务查询/事务怎么处理？
- 是否只是“代码多”，而不是边界问题？
- 能否先做模块化单体，保留拆分缝？
- 谁维护新增的部署/消息/观测设施？

## 10. 常见坑

1. **把微服务当默认答案**
   先看团队、边界、故障隔离和运维能力。

2. **按技术层拆服务**
   controller/service/dao 各一个服务，不是领域边界。

3. **共享数据库**
   服务独立部署，却共享表；最后变成分布式单体。

4. **没有数据所有权**
   每个服务都能写所有表，边界形同虚设。

5. **低估分布式事务**
   跨服务强一致会引入 Saga/Outbox/补偿，不是加个注解。

6. **事件没有 schema 版本**
   消费者升级不同步，事件一变就炸。

7. **CQRS 用在普通 CRUD**
   读写都简单时，双模型只增加维护成本。

8. **模块化单体没有边界**
   只是把单体代码分了文件夹，模块仍然互相读表。

9. **一次全拆**
   没有迁移/回滚/双写/校验，拆到一半无法收场。

10. **只看架构图**
    发布、数据、故障、运维才决定风格是否成立。

## 11. 要点回顾

1. 架构风格是约束下的选择，不是成熟度阶梯
2. 单体不是问题，没有边界的单体才是
3. 模块化单体是很多系统的合理起点
4. 微服务换来独立发布/隔离，也带来网络、数据、运维复杂度
5. 按领域和故障模式拆，不按技术分层拆
6. 事件驱动适合异步/削峰/多消费者，代价是最终一致和消息治理
7. CQRS 适合读写差异大/多视图，不是 CRUD 默认选项
8. 分布式单体是最常见的坏结果
9. 演进要留迁移、回滚和校验路径
