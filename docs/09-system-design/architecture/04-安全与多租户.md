# 安全与多租户

安全不是上线前加一个 WAF，也不是“加个登录”。它要先回答：

- 保护什么资产
- 谁可以访问
- 信任边界在哪
- 失败时会不会越权/泄漏
- 怎么发现和追责

多租户把这套问题放大：同一套服务、数据库、缓存、队列、日志里，住着多个客户。

## 1. 先做威胁模型

威胁模型不需要一开始很复杂，但必须写：

| 资产 | 谁能碰 | 风险 |
|---|---|---|
| 用户数据 | 用户/租户/运营 | 越权读取、泄漏 |
| 凭证/密钥 | 服务/运维 | 泄漏、滥用 |
| 管理接口 | 管理员 | 提权、误操作 |
| 计费/配额 | 租户 | 逃费、资源滥用 |
| 审计日志 | 安全/合规 | 篡改、删除 |

四步：

1. 画信任边界：浏览器 → 网关 → 服务 → 数据库/队列/第三方
2. 列入口：API、Webhook、文件上传、管理后台、运维脚本
3. 列威胁：STRIDE 或“越权/注入/泄漏/重放/滥用”
4. 写控制：认证、授权、隔离、加密、审计、限流

威胁模型不是一次性文档；架构变更时要更新。

## 2. 认证和授权

先分清：

- **认证（AuthN）**：你是谁
- **授权（AuthZ）**：你能做什么

常见方式：

| 场景 | 方式 |
|---|---|
| 用户登录 | OIDC/OAuth2、 session |
| 服务间调用 | mTLS、workload identity、短期 token |
| 第三方 API | API key + scope |
| 管理后台 | 强认证 + 角色/审批 |

原则：

- 默认拒绝
- 最小权限
- 授权在服务端/数据层，不在前端
- 不信任客户端自报的 tenant/user/role
- API key 不是用户身份；服务身份和最终用户分开
- 高风险操作二次认证/审批

RBAC/ABAC：

- RBAC：角色 → 权限，简单
- ABAC：属性/策略，灵活但复杂
- 复杂系统可用 PDP（策略决策）+ PEP（策略执行），但不要为了“架构感”上策略引擎

## 3. 多租户模型

| 模型 | 隔离 | 成本 | 适合 |
|---|---|---|---|
| Silo | 每租户独立实例/库 | 高 | 强合规、大客户 |
| Pool | 共享实例/库，按 tenant_id 隔离 | 低 | SaaS 常规 |
| Bridge | 共享服务，部分独立资源 | 中 | 混合 |

选择看：

- 合规/数据驻留
- 大客户要求
- 运维能力
- 成本
- 租户规模差异

没有“最安全”的模型，只有约束下的隔离级别。

## 4. 租户隔离要落到每一层

只在数据库加 `tenant_id` 不够。

### 请求上下文

- 从 token/session 解析 tenant
- 请求体里的 tenant 不作为授权依据
- 每个下游调用都携带可信 tenant 上下文
- 异步任务/重试不能丢 tenant

### 数据库

- 每张业务表有 `tenant_id`
- 查询必须带 tenant 条件
- 复合唯一键包含 tenant
- 行级安全/视图/权限
- 跨租户管理查询单独授权

### 缓存

- key 包含 tenant：`tenant:{id}:order:{id}`
- 不要用全局 key 缓存租户数据
- 失效/清理按租户
- 防缓存穿透/污染

### 对象存储

- 路径/前缀按租户
- 预签名 URL 带租户/权限
- 不让客户端直接猜 key
- 生命周期/删除按租户

### 搜索/检索索引

- 索引/命名空间按租户或 filter
- 检索必须带租户过滤
- 索引版本/重建按租户评估
- 防止“先检索再过滤”泄漏

### 队列/异步

- 消息带 tenant_id、request_id
- worker 不能跨租户复用未授权上下文
- 死信/重放也要隔离
- 配额按租户

### 日志/指标

- 日志字段可关联 tenant，但访问受限
- 不要记录完整 PII/密钥
- 指标按租户聚合时防泄漏
- 支持租户级审计/导出/删除

## 5. 数据保护

- 传输：TLS，内部服务也尽量加密
- 存储：磁盘/数据库/对象加密
- 密钥：KMS/HSM，短期凭证，定期轮换
- 信封加密：数据密钥 + 主密钥
- 大客户可要求 BYOK/独立密钥
- 密钥不进代码、镜像、日志、请求
- PII 最小化：能不收就不收
- 保留期/删除/导出要可执行

加密不是授权：有密钥不等于有权限。

## 6. API/应用安全

常见问题：

| 风险 | 控制 |
|---|---|
| IDOR | 每次按资源 owner/tenant 校验 |
| SQL/命令注入 | 参数化、argv、输入校验 |
| SSRF | URL allowlist、禁私网/metadata |
| 路径穿越 | 规范化路径、根目录限制 |
| 文件上传 | 类型/大小/病毒扫描/隔离存储 |
| CSRF/CORS | SameSite、CSRF token、严格 origin |
| 重放 | nonce/时间戳/幂等键 |
| 暴力/滥用 | 限流、配额、验证码/风控 |
| Webhook 伪造 | 签名、时间戳、幂等 |

授权检查要覆盖：

- 列表/详情/导出
- 批量操作
- 搜索/报表
- 文件/附件
- 管理接口
- 异步任务

只在详情接口做校验，列表/导出/搜索仍可能越权。

## 7. 审计与运营

审计日志至少记录：

```text
who, tenant, action, resource, result, time, request_id
```

要求：

- 追加写/防篡改
- 访问受限
- 脱敏
- 保留期
- 可按租户/用户/资源查
- 高风险操作告警

监控：

- 跨租户访问失败
- 权限拒绝突增
- 密钥/配置变更
- 大量导出/删除
- 异常登录/限流

事件响应要有：隔离、吊销、回滚、通知、复盘。

## 8. 一个 SaaS 工单系统

租户 A/B 共用服务，但要求数据隔离。

请求：

```text
Authorization: Bearer <token>
token: user_id, tenant_id, roles
```

服务：

1. 从 token 取 tenant，不从 body 取
2. 查工单时 `WHERE tenant_id=? AND ticket_id=?`
3. 缓存 key 带 tenant
4. 附件路径 `tenant/{tenant_id}/ticket/{ticket_id}/...`
5. 搜索 filter 带 tenant
6. 异步通知消息带 tenant
7. 审计记录 tenant/user/action
8. 导出接口再次做权限/租户校验
9. 每租户限流/配额

测试：

- 租户 A 的 token 查租户 B 的 ID
- 缓存 key 冲突
- 搜索/导出越权
- 队列消息丢 tenant
- 备份恢复后 tenant 边界
- 日志/错误信息泄漏

## 9. 检查清单

- 资产和信任边界画了吗？
- 认证/授权在服务端吗？
- 默认拒绝吗？
- tenant 从 token 还是 body 取？
- 数据库/缓存/对象/搜索/队列/日志都隔离了吗？
- 列表/搜索/导出/批量也校验了吗？
- 密钥/凭证怎么存、怎么轮换？
- PII 最小化/保留/删除做了吗？
- 审计能追到 who/tenant/resource 吗？
- 跨租户测试进 CI 了吗？

## 10. 常见坑

1. **只做登录，不做授权**
   登录用户仍可能访问别人的资源。

2. **tenant 从 body 取**
   改一个参数就跨租户。

3. **只查详情，不查列表/导出**
   IDOR 常出现在列表、搜索、导出。

4. **缓存 key 不含 tenant**
   一个租户看到另一个租户的数据。

5. **队列丢 tenant**
   worker 用错上下文，异步越权。

6. **搜索先检索再过滤**
   过滤太晚，已经泄漏。

7. **日志记录完整 PII/密钥**
   审计系统变成泄漏源。

8. **密钥进代码/镜像**
   轮换困难，泄漏面大。

9. **只靠前端隐藏按钮**
   直接调 API 就绕过。

10. **没有跨租户测试**
   上线后才发现隔离漏洞。

## 11. 要点回顾

1. 安全从威胁模型开始：资产、入口、信任边界、控制
2. 认证解决“你是谁”，授权解决“你能做什么”
3. 默认拒绝，授权在服务端/数据层，不信任客户端 tenant
4. 多租户有 Silo/Pool/Bridge，按合规/成本/运维选
5. 隔离要覆盖数据库、缓存、对象、搜索、队列、日志
6. tenant 从 token 取，异步任务也要携带
7. 列表/搜索/导出/批量都要资源级授权
8. 加密、密钥、PII、保留期、审计要一起设计
9. 跨租户测试要进 CI，不能只靠代码评审
