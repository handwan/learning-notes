# 演进与技术债

架构不是一次性设计完的。它会随着需求、流量、团队和组织变化而演进。

演进做不好，通常不是“没规划未来”，而是：

- 一次改太多，无法回滚
- 数据和代码一起切，没法验证
- 新旧路径长期并存，没人清理
- 技术债不可见，最后集中爆发

这篇讲演进策略、迁移模式、数据变更、弃用和技术债管理。

## 1. 演进的基本单位

一次演进应该尽量满足：

- 小步
- 可验证
- 可回滚
- 行为可对比
- 有 owner
- 有退出/清理时间

不要做“半年后一次性上线”的大迁移。大爆炸式变更把风险集中到最后一天，出问题也没有退路。

## 2. 单向门和双向门

决策分两类：

| 类型 | 特点 | 做法 |
|---|---|---|
| 双向门 | 可逆、成本低 | 快速试，保留回滚 |
| 单向门 | 难回滚、影响大 | 多评审、分阶段、先验证 |

单向门例子：

- 数据格式不可逆转换
- 公开 API 破坏性变更
- 删除旧系统/旧数据
- 跨租户/跨地域迁移
- 强绑定某家云服务

单向门不是不能做，而是要把验证、备份、回滚和审批做足。

## 3. 技术债

技术债不全是坏事。为了赶窗口有意简化，是“借款”；关键是：

- 记录
- 付息
- 到期还

技术债类型：

| 类型 | 例子 |
|---|---|
| 代码债 | 重复逻辑、坏命名、缺测试 |
| 设计债 | 边界不清、循环依赖、共享表 |
| 数据债 | schema 混乱、缺主键、脏数据 |
| 接口债 | 无版本、错误码混乱、契约漂移 |
| 运维债 | 手工发布、无监控、无备份 |
| 依赖债 | 过期框架、无人维护的库 |
| 安全债 | 密钥硬编码、权限过宽 |

债的“利息”表现为：

- 改一个需求要动很多地方
- 发布越来越慢
- 故障越来越多
- 新人上手越来越难
- 测试/回滚成本上升

### 技术债台账

至少记录：

```text
id, 描述, 影响, 利息, owner, 触发条件, 计划, 状态
```

不要只写“重构”。要写清：

- 哪个边界/模块
- 影响什么指标
- 什么时候必须还
- 不还的后果

## 4. 迁移模式

| 模式 | 适合 | 风险 |
|---|---|---|
| Strangler | 逐步替换旧系统 | 新旧并存时间长 |
| Branch by abstraction | 替换实现 | 抽象层可能泄漏 |
| Expand-contract | schema/契约变更 | 双写/回填复杂 |
| Dual write | 新旧存储同时写 | 不一致、顺序 |
| Shadow read | 新路径只读对比 | 只验证读，不验证写 |
| Backfill | 历史数据迁移 | 压垮源库、校验难 |
| Canary | 小流量验证 | 指标/回滚要完整 |
| Feature flag | 控制新旧路径 | 开关积累、组合爆炸 |

不要同时上三种迁移模式。先选一个主路径，再配验证和回滚。

## 5. 代码/服务迁移

从模块化单体拆通知 worker：

```text
阶段 1：模块内接口，单体调用
阶段 2：抽事件/队列，worker 旁路消费
阶段 3：shadow 对比，验证结果
阶段 4：小流量切 worker
阶段 5：全量切，保留回滚开关
阶段 6：删除旧路径
```

每一步都要有：

- 观测指标
- 回滚开关
- 数据校验
- owner/on-call

不要“代码 merge 完就算迁移完成”。迁移完成的标准是旧路径删除、监控稳定、账单/数据一致。

## 6. 数据迁移

数据迁移通常比代码迁移难：

1. 双写/变更捕获
2. 历史数据回填
3. 新旧对比/校验
4. 读路径灰度
5. 写路径切换
6. 旧存储下线

要点：

- 先扩 schema，再写新字段
- 回填限速，避免打垮源库
- 幂等/断点续跑
- 校验行数、checksum、抽样
- 保留回滚窗口
- 删除旧字段前确认没有读者

schema 变更常用 expand-contract：

```text
expand：加新字段/新表，双写
migrate：回填/校验
contract：切读、停旧写、删旧字段
```

不要在低峰期“一把 ALTER + 全量回填 + 切流量”同时做。

## 7. API/事件版本

- 新增可选字段通常兼容
- 删除/改类型/改语义是破坏
- 事件要有 schema 版本和消费者兼容策略
- 旧版本要有弃用期和迁移文档
- 监控旧版本调用量

API 版本细节见 [API 与契约](03-API与契约.md)；跨服务事务见后续分布式章。

## 8. 弃用和清理

弃用不是发个公告：

1. 标记 deprecated
2. 通知消费者
3. 提供迁移路径/工具
4. 监控调用量
5. 到截止日期拒绝/删除
6. 清理代码/配置/文档

没有清理时间表的“临时兼容”，最后会变成永久双路径。

## 9. 技术债与演进的组织问题

架构演进不只是技术：

- 谁拥有这个模块
- 谁 on-call
- 谁批准 breaking change
- 谁付迁移成本
- 谁清理旧路径

如果团队边界和架构边界长期错位，演进会很痛。架构跟着组织走，但也要给组织调整留时间。

## 10. 例子：替换通知服务

旧路径：

```text
orders 直接调用 notify.send()
```

新路径：

```text
orders 发布 OrderCreated
notification worker 消费并发送
```

迁移：

1. 保留 `notify.send()`，加事件发布（双路径）
2. worker 旁路消费，shadow 对比发送结果
3. 小租户切 worker
4. 监控失败率/延迟/重复
5. 全量切，保留开关
6. 删除直接调用

风险：

- 重复发送 → 幂等键
- 事件丢失 → outbox/重试
- 顺序错 → 版本/序列号
- 回滚 → 开关切回同步调用

## 11. 检查清单

- 这次变更是双向门还是单向门？
- 能否小步上线/灰度？
- 旧路径还能回滚吗？
- 数据双写/回填/校验做了吗？
- 新旧结果怎么对比？
- API/事件兼容吗？
- 旧版本什么时候下线？
- 技术债记录了吗？谁还？
- 观测/告警/on-call 就绪了吗？
- 迁移完成后谁删除旧路径？

## 12. 常见坑

1. **大爆炸重写**
   一次性替换，风险集中，无法回滚。

2. **只迁代码，不迁数据**
   代码切了，数据不一致。

3. **双写没有校验**
   新旧库悄悄分叉。

4. **回填打垮源库**
   没限速/断点/低峰策略。

5. **新旧路径长期并存**
   没有弃用时间表，复杂度翻倍。

6. **没有 shadow/canary**
   直接全量切，出事才发现。

7. **技术债不可见**
   只在口头说“以后重构”，没有 owner/触发条件。

8. **把重构当迁移**
   重构不改行为；迁移要验证数据/契约/流量。

9. **删除太快**
   旧客户端/旧数据还在，直接 404/丢数据。

10. **没有清理**
   开关、旧表、旧事件、旧文档永久残留。

## 13. 要点回顾

1. 演进要小步、可验证、可回滚、有 owner
2. 区分双向门和单向门；单向门要多验证/备份/审批
3. 技术债要记录影响、利息、owner 和触发条件
4. 迁移模式：strangler、expand-contract、双写、shadow、backfill、canary
5. 数据迁移通常比代码迁移难：双写、回填、校验、灰度、回滚
6. schema 变更用 expand-contract，不要一步到位
7. API/事件变更要版本化、监控旧版本、设弃用期
8. 迁移完成的标准是旧路径删除、数据一致、监控稳定
9. 架构演进也是组织问题：ownership、on-call、审批和迁移成本
