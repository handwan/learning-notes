# 边界与依赖

边界不是文件夹，也不是“服务数量”。边界是：

- 谁拥有哪份数据
- 谁可以修改哪种状态
- 谁能调用谁
- 变更时谁需要一起发布

依赖是边界的另一面：只要模块互相读表、互相调用内部实现，边界就只是命名。

## 1. 边界由什么定义

| 维度 | 要回答的问题 |
|---|---|
| 业务能力 | 这个模块负责什么结果 |
| 数据所有权 | 哪张表/哪类状态归它写 |
| 行为边界 | 哪些操作必须在它内部完成 |
| 契约 | 对外暴露 API、事件还是查询 |
| 部署边界 | 是否需要独立发布/扩缩容 |
| 团队边界 | 谁长期维护、谁 on-call |
| 一致性边界 | 哪些数据必须同事务 |

先有业务/数据边界，再谈服务边界。按 controller/service/dao 分层拆服务，不是领域边界。

## 2. 领域边界

一个订单系统可以分成：

```text
orders    订单、订单行、状态机
billing   发票、支付、退款
notify    邮件、短信、站内信
report    报表、投影、聚合
```

每个模块拥有自己的语言和数据：

- `orders` 说“订单已创建”
- `billing` 说“发票已开具”
- `notify` 说“通知已发送”
- `report` 说“某日成交额”

不要把“订单状态”拆给四个模块共同写。一个状态只能有一个写入者。

## 3. 依赖方向

依赖应该指向更稳定的东西：

```text
接口/应用层 → 领域层
基础设施 → 领域层（通过端口实现）
```

而不是：

```text
领域层 → ORM
领域层 → HTTP 框架
领域层 → 某个云厂商 SDK
```

可以用 ports & adapters / 六边形：

- 领域定义接口（端口）
- 数据库、消息、第三方 API 做适配器
- 依赖倒置：外层依赖内层，不是反过来

这不是要求每个项目上完整框架；核心是：**业务规则不要被基础设施细节绑死**。

## 4. 依赖图

把模块画成有向图：

```text
orders ──→ billing contract
orders ──→ notify events
billing ──→ notify events
report ──→ orders events
```

规则：

- 尽量无环
- 依赖指向稳定契约，不指向实现
- 不跨模块读表
- 公共模块只放真正稳定的基础能力

检查：

- 有没有循环依赖
- 有没有模块直接 import 另一个模块的 internal
- 有没有共享表/共享 ORM entity
- 有没有“common”模块变成垃圾场
- 一个变更是否需要多个模块一起发布

工具可以帮忙：ArchUnit、import-linter、dependency-cruiser、构建系统模块边界。工具不是边界本身，但能把边界变成 CI 检查。

## 5. 数据所有权

每个模块只写自己的数据：

| 模块 | 拥有 | 不直接访问 |
|---|---|---|
| orders | orders、order_items | billing 表 |
| billing | invoices、payments | orders 表 |
| notify | notifications | 订单/发票表 |
| report | 读模型/投影 | 各模块写库 |

跨模块查询：

- 调用对方 API
- 订阅事件维护读模型
- 明确的数据共享契约

不要：

- 直接 join 对方表
- 让多个模块写同一张表
- 把 ORM entity 当跨模块 DTO

共享数据库不是绝对禁止；共享表写入和跨模块 join 才是边界破坏。

## 6. 同步与异步

| 方式 | 适合 | 代价 |
|---|---|---|
| 同步 API | 用户等待结果、强一致查询 | 耦合、超时、级联故障 |
| 异步事件 | 解耦、削峰、多消费者 | 最终一致、重复、顺序、积压 |
| 共享读模型 | 报表/查询优化 | 投影延迟、重建 |

同一条业务链可以混合：

```text
下单：同步写 orders
开票：异步消费 OrderCreated
通知：异步消费 InvoiceIssued
报表：异步投影
```

跨模块强事务要谨慎。Saga/Outbox/补偿的细节在后续分布式章。

## 7. 契约

跨边界只暴露契约：

- API：请求/响应 schema、错误码、版本
- 事件：事件名、字段、版本、幂等键
- 查询：分页、排序、过滤
- 权限：调用者能看什么

契约要独立于内部实现：

- 不要把数据库 entity 直接序列化出去
- 不要让消费者依赖你的表结构
- 事件字段变更要兼容/版本化
- 契约测试要覆盖消费者

## 8. 示例：订单、计费、通知、报表

### 坏边界

```text
orders 直接读 billing.invoices
billing 直接改 orders.status
notify import orders 的内部 service
report join 所有模块的表
```

结果：

- 改一张表影响所有模块
- 无法独立发布
- 事务边界混乱
- 报表查询拖慢订单库

### 好边界

```text
orders 拥有订单，发布 OrderCreated
billing 消费 OrderCreated，拥有发票/支付
notify 消费 OrderCreated/InvoiceIssued
report 消费事件，维护读模型
```

依赖图：

```text
orders ──event──→ billing
orders ──event──→ notify
billing ──event──→ notify
orders/billing ──event──→ report
```

规则：

- 订单状态只由 orders 写
- 发票状态只由 billing 写
- 通知失败不回滚订单
- 报表延迟不影响下单

## 9. 演进与拆分

从模块化单体开始：

1. 先按领域分模块
2. 每模块独立 schema/权限
3. 跨模块只走接口/事件
4. 用依赖检查防止反向 import
5. 需要独立发布/扩缩容时，再按模块拆服务

拆分前要准备：

- 数据迁移/双写/校验
- 契约版本
- 回滚路径
- 观测和告警
- 团队 ownership

不要一次全拆。先拆一个边界清楚、故障隔离收益最大的模块。

## 10. 检查清单

- 每个模块的数据写入者是谁？
- 有没有跨模块 join/共享表写入？
- 依赖图有环吗？
- 依赖指向契约还是内部实现？
- 同步调用链有多长？失败会级联吗？
- 跨模块事务怎么处理？
- 事件有 schema 版本/幂等吗？
- 契约测试覆盖消费者吗？
- 模块能否独立测试/发布？
- 变更时谁需要一起上线？

## 11. 常见坑

1. **按技术层拆服务**
   controller/service/dao 各一个服务，不是业务边界。

2. **共享表/共享写入**
   服务拆了，数据还耦合，最后变分布式单体。

3. **跨模块 join**
   报表直接 join 所有表，查询和发布都互相拖累。

4. **循环依赖**
   A 调 B，B 回调 A；最后只能一起发布。

5. **common 模块变垃圾场**
   所有不确定的东西都塞进去，边界消失。

6. **ORM entity 跨边界**
   内部字段一改，所有消费者崩。

7. **同步链太长**
   一个下游慢，整个链路排队/超时。

8. **事件没有版本**
   消费者升级不同步，字段一变就坏。

9. **事务边界不清**
   一个操作跨三个模块写，失败后无法恢复。

10. **只画图不检查**
    依赖图很漂亮，代码里仍然互相 import 内部实现。

## 12. 要点回顾

1. 边界由数据所有权、行为、契约、部署和团队共同定义
2. 先划领域/数据边界，再谈服务边界
3. 依赖指向稳定契约，不指向内部实现
4. 依赖图尽量无环；用工具把边界变成 CI 检查
5. 每个模块只写自己的数据；跨模块查询走 API/事件/读模型
6. 同步适合强一致/用户等待，异步适合解耦/削峰/多消费者
7. 跨边界用 API/事件契约，不暴露 ORM entity
8. 模块化单体可以保留拆分缝，不必一开始上微服务
9. 拆分要准备迁移、双写、回滚、观测和 ownership
