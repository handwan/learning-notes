# 发布回滚与容灾

发布和容灾解决两个不同问题：

- **发布**：新版本怎么安全上线，出问题怎么回退
- **容灾**：机房/区域/数据坏了，怎么恢复服务

两者都依赖同几件事：可观测、可回滚、数据可恢复、有人负责。

## 1. 发布是风险管理

发布前先问：

- 改动影响哪些服务/数据/接口？
- 能否灰度？
- 出问题看什么指标？
- 回滚还是 roll-forward？
- 数据库变更能回退吗？
- 谁 on-call？runbook 在哪？

不能回滚的发布，要有更强的预发/灰度/审批。

## 2. 发布策略

| 策略 | 特点 | 风险 |
|---|---|---|
| 滚动发布 | 逐批替换实例 | 新旧版本并存 |
| 蓝绿 | 两套环境切流量 | 成本/数据兼容 |
| Canary | 小流量验证 | 指标/样本/回滚 |
| Feature flag | 部署与发布解耦 | 开关堆积/组合爆炸 |
| Shadow | 影子流量验证 | 只验证读/不产生副作用 |

选择看：

- 是否有状态
- 数据库兼容
- 回滚速度
- 流量规模
- 团队运维能力

## 3. Canary

Canary 不是“发 1% 就完了”：

- 选对流量切片（租户/地区/版本）
- 看错误率/延迟/业务指标
- 自动/手动回滚阈值
- 样本量足够
- 依赖/下游也看
- 不把关键写流量先放进去（除非有隔离）

指标：

- 5xx/超时
- p95/p99
- 业务成功率
- 队列/DB 饱和度
- 版本差异

## 4. 回滚 vs roll-forward

回滚：

- 代码/配置回旧版本
- 快，但数据库变更可能不可逆

Roll-forward：

- 修复后继续向前
- 适合 schema 已迁移/数据已写

原则：

- 数据库变更尽量向前兼容
- 回滚方案要提前演练
- 不要假设“回滚代码 = 回滚数据”

## 5. 数据库变更

发布中最难的是 schema：

- 先 expand：加字段/表/索引，双写
- 再 migrate：回填/校验
- 最后 contract：切读、停旧写、删旧字段

不要在一个发布里：

```text
改 schema + 回填 + 切读写 + 删旧字段
```

任何一步失败都可能无法回退。

## 6. Feature flag 和配置

- 部署 ≠ 发布
- 开关控制新路径
- 按租户/百分比/环境
- 开关要有 owner/过期时间
- 开关组合要测试
- 配置变更也要审计/回滚

长期不清理的 flag 会变成隐藏分支。

## 7. 备份和恢复

备份不是“有备份文件”：

- 全量/增量
- WAL/binlog 归档
- 加密/离线/不可变
- 跨区域
- 恢复演练
- 恢复时间/数据丢失

RTO/RPO：

| 指标 | 含义 |
|---|---|
| RTO | 多久恢复服务 |
| RPO | 能接受丢多少数据 |

例：

```text
RTO=1h：1 小时内必须恢复
RPO=15min：最多丢 15 分钟数据
```

## 8. 容灾

模式：

- 冷备：灾难时再拉起
- 温备：数据同步，服务待启动
- 热备/多活：持续接流量

难点：

- 数据复制延迟
- 切换一致性
- 脑裂
- DNS/TTL
- 流量切换
- 回切
- 成本

多活不是默认答案；先看 RTO/RPO 和预算。

## 9. 故障演练

- 单实例/单 AZ 故障
- 依赖超时
- 备份恢复
- 区域切换/回切
- 配置/证书过期
- 发布回滚

演练要有：

- 假设/范围
- 观测指标
- 回滚/停止条件
- 复盘/改进

没演练过的容灾方案，等于没有。

## 10. 实验：RTO/RPO

2 TB 数据，恢复吞吐 200 MB/s：

??? note "代码：恢复时间与 RTO 吞吐"
    ```python
    SIZE_TB = 2.0
    MBPS = 200.0
    RTO_H = 1.0

    size_mb = SIZE_TB * 1_000_000
    restore_s = size_mb / MBPS
    restore_h = restore_s / 3600
    required_mbps = size_mb / (RTO_H * 3600)

    print(f"size={SIZE_TB:.0f} TB restore_rate={MBPS:.0f} MB/s")
    print(f"restore_time={restore_h:.2f} h")
    print(f"rto={RTO_H:.0f} h requires={required_mbps:.1f} MB/s")
    print("rpo=15 min -> backup/WAL must cover <=15 min of data loss")
    ```

输出：

```text
size=2 TB restore_rate=200 MB/s
restore_time=2.78 h
rto=1 h requires=555.6 MB/s
rpo=15 min -> backup/WAL must cover <=15 min of data loss
```

读法：

- 2 TB / 200 MB/s 约 2.78 小时
- 1 小时 RTO 需要约 555.6 MB/s
- RPO=15 分钟，备份/WAL 必须覆盖不超过 15 分钟的数据丢失
- 真实恢复还受解压/校验/索引重建/网络影响
- 这是容量计算，不是演练结果

## 11. 检查清单

- 发布能否灰度/回滚？
- 数据库变更向前兼容吗？
- 回滚演练过吗？
- Canary 指标/阈值/owner 清楚吗？
- Feature flag 有清理计划吗？
- 备份覆盖全量/增量/WAL 吗？
- 恢复演练过吗？RTO/RPO 达标吗？
- 跨区域/脑裂/回切怎么处理？
- 配置/证书过期有告警吗？
- 故障演练有 runbook 吗？

## 12. 常见坑

1. **回滚代码不回滚数据**
   schema 已迁移，旧代码读不了。

2. **大爆炸发布**
   一次改 schema+代码+配置，无法定位。

3. **Canary 只看错误率**
   延迟/业务指标/下游也要看。

4. **备份没恢复过**
   真故障时发现备份坏了。

5. **把副本当备份**
   误删/逻辑错误会同步到副本。

6. **RTO/RPO 没定义**
   灾难时不知道先恢复什么。

7. **多活没处理冲突**
   双写/脑裂导致数据分叉。

8. **DNS 切换当瞬时**
   TTL/缓存/客户端会拖时间。

9. **Flag 永久不清理**
   隐藏分支越来越多。

10. **没有演练**
    方案只在文档里成立。

## 13. 要点回顾

1. 发布是风险管理：灰度、观测、回滚、owner
2. 滚动/蓝绿/Canary/flag/shadow 各有代价
3. 数据库变更是发布最难部分，尽量向前兼容
4. 回滚代码不等于回滚数据
5. 备份要加密/离线/跨区，且必须恢复演练
6. RTO 是恢复时间，RPO 是能丢多少数据
7. 容灾模式按 RTO/RPO/成本选，多活不是默认
8. 故障演练覆盖实例/AZ/依赖/恢复/回切
9. 没演练过的容灾方案等于没有
