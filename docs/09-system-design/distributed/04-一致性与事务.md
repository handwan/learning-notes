# 一致性与事务

一个本地数据库事务能保证：

```text
要么全成功，要么全失败
```

跨服务/跨库以后，这个保证不再免费：

- 网络会超时
- 服务会部分成功
- 消息会重复/乱序
- 补偿不一定能撤销外部副作用

CAP/复制见[CAP 与一致性](01-CAP与一致性.md)；这里讲事务模式。

分布式事务不是“加个注解”，而是选择一种可接受的失败语义。

## 1. 先问要不要分布式事务

能避免就避免：

- 同一服务/同一数据库：用本地事务
- 能合并边界：先合并，不要为了“微服务”拆事务
- 能异步：接受最终一致
- 能用状态机：用状态流转代替跨服务锁
- 能用幂等+重试：避免强协调

只有业务确实要求跨资源原子性时，才引入分布式事务。

## 2. 2PC

两阶段提交：

```text
prepare：所有参与者准备，锁资源
commit/abort：协调者决定，参与者执行
```

优点：

- 强一致的原子提交语义
- 数据库/中间件有成熟实现

代价：

- 协调者故障会阻塞
- 参与者在 prepare 后长期持锁
- 网络分区时可能不可用
- 运维/排障复杂

2PC 适合少量、短事务、强一致要求高的场景；不适合长流程、跨多个外部系统。

## 3. TCC

Try-Confirm-Cancel：

```text
Try：预留资源（冻结库存/额度）
Confirm：确认使用
Cancel：释放预留
```

适合：

- 库存/额度/优惠券
- 能明确预留和释放
- 业务能接受中间状态

难点：

- Try 要幂等
- Cancel 要处理“空回滚”（Try 没成功也要能 Cancel）
- Confirm/Cancel 可能重复
- 需要防悬挂（Cancel 先到、Try 后到）

TCC 不是“业务层 2PC”那么简单；它要求每个参与方实现三套幂等逻辑。

## 4. Saga

Saga 把长事务拆成多个本地事务：

```text
T1 → T2 → T3
失败：执行 C2、C1 补偿
```

两种编排：

- Orchestration：中心协调器知道流程
- Choreography：服务订阅事件，自己决定下一步

优点：

- 不长期持锁
- 适合长流程/跨服务
- 每步本地事务简单

代价：

- 没有隔离性：中间状态对外可见
- 补偿不是回滚：邮件已发、货已出库，不能真正撤销
- 补偿也可能失败，需要重试/人工
- 需要状态机/幂等/去重
- 调试链路长

Saga 适合“可补偿、可中间态”的业务，不适合“绝不能出现中间状态”的强一致场景。

## 5. Outbox

本地事务同时写业务表和 outbox：

```text
BEGIN
  update order
  insert outbox(OrderCreated)
COMMIT
```

relay 读 outbox 发消息，成功后标记已发。

优点：

- 业务写和事件写同事务
- 不会“业务成功、事件丢失”
- 实现相对简单

代价：

- 至少一次投递，消费者要幂等
- relay 要处理重试/顺序/积压
- outbox 表要清理/分区
- 多实例 relay 要避免重复并发

Outbox 不提供 exactly-once；它提供“事件不丢 + 至少一次”。

## 6. CDC

CDC 从数据库日志捕获变更：

```text
DB log → CDC → event stream → consumers
```

适合：

- 数据同步
- 缓存失效
- 搜索/数仓更新
- 不想改业务写入

注意：

- 重复/乱序
- schema 变更
- 事务边界/快照
- 消费者幂等
- 初始快照与增量衔接

CDC 不是“零成本实时同步”；运维和一致性要设计。

## 7. Exactly-once 的真相

端到端 exactly-once 很难：

- 网络超时不知道成功没成功
- 消费者可能处理完但 offset 没提交
- 生产者可能重复发

常见做法：

```text
at-least-once + 幂等消费 + 去重表
```

幂等键：

- 业务唯一键
- 消息 ID
- 操作 ID + 版本

去重要有保留期；否则表无限增长。

## 8. 隔离与中间状态

Saga/TCC 的中间状态可能被读到：

- 订单“已预留，未支付”
- 库存“冻结”
- 优惠券“锁定”

处理：

- 状态机明确合法状态
- 语义锁/预留标记
- 读模型过滤中间态
- 超时释放
- 对账修复

不要假设“没提交就看不见”；跨服务没有全局事务隔离。

## 9. 实验：订单 Saga

流程：

```text
reserve 库存 → charge 支付 → ship 发货
失败则反向补偿：release/refund/cancel
```

??? note "代码：Saga 补偿顺序"
    ```python
    STEPS = [
        ("reserve", "release"),
        ("charge", "refund"),
        ("ship", "cancel_shipment"),
    ]


    def run_saga(fail_at=None):
        done = []
        log = []
        for name, compensate in STEPS:
            if name == fail_at:
                log.append(f"{name}:fail")
                break
            done.append((name, compensate))
            log.append(f"{name}:ok")
        else:
            log.append("commit")
            return log

        for name, compensate in reversed(done):
            log.append(f"{compensate}:ok")
        return log


    if __name__ == "__main__":
        for case in [None, "reserve", "charge", "ship"]:
            label = "success" if case is None else f"fail_at={case}"
            print(label + ":")
            print("  " + " -> ".join(run_saga(case)))
    ```

输出：

```text
success:
  reserve:ok -> charge:ok -> ship:ok -> commit
fail_at=reserve:
  reserve:fail
fail_at=charge:
  reserve:ok -> charge:fail -> release:ok
fail_at=ship:
  reserve:ok -> charge:ok -> ship:fail -> refund:ok -> release:ok
```

读法：

- 成功：三步都完成
- 库存失败：没有已完成的步骤，无需补偿
- 支付失败：释放库存
- 发货失败：退款 + 释放库存
- 这是补偿顺序示意，不是完整 Saga 引擎
- 真实系统还要处理补偿失败、重复、超时、人工介入

## 10. 决策表

| 需求 | 方案 | 代价 |
|---|---|---|
| 单库原子性 | 本地事务 | 无跨服务 |
| 跨服务强原子 | 2PC | 阻塞/协调者/可用性 |
| 可预留资源 | TCC | 三套幂等逻辑 |
| 长流程/可补偿 | Saga | 无隔离、补偿失败 |
| 业务+事件不丢 | Outbox | 至少一次、relay |
| 数据同步 | CDC | 重复/顺序/schema |
| 可重试消费 | 幂等/去重 | 存储/保留期 |

## 11. 检查清单

- 真的需要跨服务原子吗？
- 能否本地事务/合并边界？
- 中间状态业务能接受吗？
- 补偿逻辑真的能撤销副作用吗？
- Try/Confirm/Cancel 幂等吗？
- 空回滚/悬挂处理了吗？
- 事件至少一次，消费者幂等吗？
- 去重表保留多久？
- 补偿失败怎么告警/人工？
- 对账/修复怎么跑？

## 12. 常见坑

1. **跨服务 @Transactional**
   本地注解管不了远程服务。

2. **Saga 当回滚**
   外部副作用不能真正撤销。

3. **补偿没有幂等**
   重试补偿重复退款/释放。

4. **忽略空回滚/悬挂**
   Cancel 先到、Try 后到，状态错乱。

5. **以为 Outbox 是 exactly-once**
   还是至少一次，消费者要去重。

6. **CDC 忽略 schema 变更**
   下游解析失败/丢字段。

7. **中间状态直接暴露**
   用户看到“半成品”订单。

8. **补偿失败不报警**
   数据永久不一致。

9. **没有对账**
   只能等用户投诉。

10. **所有流程都上分布式事务**
   复杂度和故障面远超收益。

## 13. 要点回顾

1. 先避免分布式事务；能本地事务/合并边界就本地
2. 2PC 强但阻塞、依赖协调者，适合少量短事务
3. TCC 用预留/确认/取消，要求三套幂等和空回滚处理
4. Saga 用本地事务+补偿，适合长流程，但没有隔离
5. 补偿不是回滚；外部副作用可能无法撤销
6. Outbox 保证业务和事件同事务，但至少一次
7. CDC 适合数据同步，仍要处理重复/顺序/schema
8. exactly-once 通常靠 at-least-once + 幂等去重
9. 中间状态、补偿失败、对账都要显式设计
