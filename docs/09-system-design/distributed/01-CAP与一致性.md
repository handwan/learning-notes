# CAP 与一致性

CAP 常被简化成“三选二”，但真实系统里没有这么选。

更准确的说法：

- 网络分区会发生
- 分区期间，一致性和可用性要取舍
- 没有分区时，还要在延迟和一致性之间取舍（PACELC）
- “一致性”有很多级别，不是二值

事务模式见[一致性与事务](04-一致性与事务.md)；这里讲一致性级别和 quorum。

## 1. CAP 到底说什么

| 字母 | 含义 |
|---|---|
| C | 线性一致性（linearizability）：读能看到最新已完成的写 |
| A | 可用性：非故障节点能在有限时间内返回非错误响应 |
| P | 分区容忍：网络丢包/延迟/断开时系统继续工作 |

关键点：

- P 不是“可选功能”，网络分区是现实
- CAP 讨论的是**分区期间**的取舍
- 不是“平时也三选二”
- “可用”不等于“每个请求都成功”；可以是降级/旧读
- “一致”不等于“持久”；写入落盘是另一件事

例子：

```text
分区时，银行转账可以选择拒绝写（保一致）
分区时，社交 feed 可以选择返回旧内容（保可用）
```

两者都不是“错”，是业务约束不同。

## 2. PACELC

CAP 只讲分区。PACELC 补充：

```text
如果有 Partition：在 Availability 和 Consistency 之间选
Else：在 Latency 和 Consistency 之间选
```

即使没有分区：

- 强一致要协调副本 → 延迟更高
- 异步复制 → 延迟低，但可能旧读

所以“强一致”通常不是免费的，它买的是正确性，付的是延迟/可用性/成本。

## 3. 一致性级别

| 级别 | 保证 | 典型场景 |
|---|---|---|
| 线性一致 | 读看到最新已完成写 | 余额、库存扣减、锁 |
| 顺序一致 | 所有节点顺序一致 | 某些协调服务 |
| 因果一致 | 有因果关系的写有序 | 评论/消息 |
| 读己之写 | 用户能看到自己的写 | 个人资料、订单 |
| 单调读 | 不会读到更旧的版本 | 会话/Feed |
| 最终一致 | 最终收敛，无时间保证 | 统计、搜索、Feed |

“最终一致”不是“永远不一致”，也不是“马上一致”；中间可能旧读、乱序、冲突。

## 4. 复制拓扑

| 拓扑 | 写 | 读 | 风险 |
|---|---|---|---|
| Leader-follower | 主写，从复制 | 主/从 | 复制延迟、主故障 |
| Multi-leader | 多地主写 | 本地 | 冲突、回环 |
| Leaderless | 多副本写 | 多副本读 | quorum、冲突、修复 |

Leader-follower 最常见；异步复制下，从库可能旧读。

## 5. Quorum

N 个副本，写成功 W 个，读 R 个：

```text
如果 R + W > N
则读集合和写集合至少有一个副本重叠
在无故障/无 sloppy quorum 的假设下，读有机会看到最新写
```

例：

```text
N=3, W=2, R=2 → 2+2>3，重叠 1
N=3, W=1, R=1 → 1+1<3，不保证重叠
```

但公式不是全部：

- sloppy quorum + hinted handoff 可能绕过目标副本
- read repair 最终收敛，但不等于线性一致
- 多 key 事务不满足单 key quorum 推理
- 失败节点恢复后可能长期落后
- “写成功”可能只是写进了一个临时节点

## 6. 实验：quorum 重叠

??? note "代码：N/R/W quorum 重叠"
    ```python
    def quorum(n, w, r):
        overlap = max(0, w + r - n)
        guaranteed = (w + r) > n
        return overlap, guaranteed


    CASES = [
        (3, 2, 2),
        (3, 1, 1),
        (5, 3, 3),
        (5, 2, 2),
        (3, 2, 1),
        (3, 3, 1),
    ]

    if __name__ == "__main__":
        print("N  W  R  overlap  guaranteed")
        for n, w, r in CASES:
            overlap, guaranteed = quorum(n, w, r)
            print(f"{n:1d}  {w:1d}  {r:1d}  {overlap:7d}  {guaranteed}")
    ```

输出：

```text
N  W  R  overlap  guaranteed
3  2  2        1  True
3  1  1        0  False
5  3  3        1  True
5  2  2        0  False
3  2  1        0  False
3  3  1        1  True
```

读法：

- `guaranteed=True` 只表示公式上读写集合有重叠
- `N=3,W=2,R=2`：重叠 1，常见折中
- `N=3,W=1,R=1`：重叠 0，可能旧读
- `N=3,W=3,R=1`：重叠 1，但写要全部副本，写可用性差
- `N=3,W=2,R=1`：`R+W=N`，不保证重叠
- 真实系统还要看 sloppy quorum/read repair/失败处理

## 7. 读己之写

用户写完，马上读自己的数据，异步从库可能还没有。

常见做法：

- 写后读主库
- sticky session 固定到同一副本
- 客户端带版本/时间戳，读端等待到该版本
- 写返回 token，读时带 token
- 业务上允许短暂旧读

“读己之写”比“全局强一致”便宜，也更常用。

## 8. 冲突

多主/leaderless 可能同时写：

- Last Write Wins：简单，但依赖时钟，可能丢更新
- 版本号/向量时钟：检测并发，业务合并
- CRDT：数学上可合并，但只适合特定数据结构
- 业务冲突解决：人工/规则/补偿

不要默认 LWW。时钟偏移和并发写会让“最后”不可靠。

## 9. 故障和超时

- 超时不等于失败：写可能已成功
- 重试要幂等，否则重复写
- 部分写/半成功要补偿
- 网络分区可能造成双主/脑裂
- 读修复/反熵是后台收敛，不是即时一致
- 监控复制延迟、落后副本、冲突数

## 10. 怎么选

| 场景 | 倾向 |
|---|---|
| 余额/支付/库存 | 强一致/事务，分区时拒绝或排队 |
| 社交 feed/点赞数 | 可用性优先，最终一致 |
| 购物车 | 可用性优先，可合并/CRDT |
| 目录/搜索 | 最终一致，接受旧索引 |
| 分布式锁/leader | 共识/租约，不能靠普通 quorum 猜 |
| 订单状态 | 按状态机，关键转移强一致 |

一致性不是越高越好：越高越慢、越贵、越容易不可用。要和业务后果匹配。

## 11. 检查清单

- 这个读能接受多旧的数据？
- 分区时拒绝写还是返回旧读？
- 写成功需要几个副本确认？
- 读需要几个副本？`R+W>N` 吗？
- 读己之写怎么保证？
- 冲突怎么检测/合并？
- 超时重试幂等吗？
- 复制延迟怎么监控？
- 失败副本怎么恢复/修复？
- 多 key 操作需要事务吗？

## 12. 常见坑

1. **CAP 三选二当口号**
   分区期间才有 C/A 取舍，平时还有延迟/一致性。

2. **把最终一致当“马上一致”**
   中间可能旧读/乱序/冲突。

3. **只看 R+W>N**
   忽略 sloppy quorum、read repair、失败副本。

4. **用 LWW 解决所有冲突**
   时钟偏移会丢更新。

5. **超时当失败直接重试**
   写可能已成功，重复写/重复扣款。

6. **多 key 操作套单 key quorum**
   跨 key 一致性需要事务/协调。

7. **读从库不看复制延迟**
   用户刚写完就读不到。

8. **强一致用到所有路径**
   成本和可用性被拖垮。

9. **没有冲突监控**
   多主系统长期静默分叉。

10. **把持久性当一致性**
    落盘不等于所有读看到最新。

## 13. 要点回顾

1. CAP 是分区期间的 C/A 取舍，不是平时三选二
2. PACELC 补充无分区时的延迟/一致性取舍
3. 一致性有线性、因果、读己之写、单调读、最终一致等级别
4. 复制拓扑决定旧读、冲突和故障模式
5. R+W>N 是 quorum 重叠的必要条件，不是完整保证
6. sloppy quorum/read repair/失败副本会改变实际语义
7. 读己之写通常比全局强一致更实用
8. 冲突处理不要默认 LWW；按业务选版本/CRDT/人工
9. 超时重试要幂等；持久性不等于一致性
10. 一致性级别要和业务后果匹配
