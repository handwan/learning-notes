# 复制、分区与热点

复制和分区是两件不同的事：

- **复制**：同一份数据放多个副本，解决读扩展/故障恢复
- **分区/分片**：把不同数据放到不同节点，解决容量/写扩展
- **热点**：某个 key/租户/分片承受了远高于平均的流量

它们经常一起用，但问题不能混。数据库落地/分库分表见[分库分表与读写分离](../data/02-分库分表与读写分离.md)；这里讲复制/分区的通用机制。

## 1. 先分清目标和代价

| 手段 | 解决 | 代价 |
|---|---|---|
| 复制 | 读吞吐、故障恢复、就近访问 | 复制延迟、一致性、成本 |
| 分区 | 单机容量/写吞吐 | 跨分片查询、事务、再平衡 |
| 缓存 | 热读、降低回源 | 一致性、失效、内存 |
| 拆热点 | 单 key/租户过载 | 业务改造、路由复杂度 |

不要用“加副本”解决写热点，也不要用“分片”解决读延迟。

## 2. 分区键

分区键决定数据分布和查询路径。

好的分区键：

- 高基数
- 分布均匀
- 查询经常带它
- 业务上稳定，不会频繁改
- 能支持租户隔离

常见选择：

```text
user_id
tenant_id + user_id
order_id
短码 hash
```

避免：

- 单调递增时间戳作为唯一前缀
- 低基数枚举（status/type）
- 频繁更新的字段
- 只按“当前日期”分区，导致新分区永远热

## 3. 热点从哪来

- 明星 key：一个 URL/商品/用户被大量访问
- 大租户：一个 tenant 占大部分流量
- 时间热点：整点/活动/秒杀
- 数据倾斜：分区键分布不均
- 查询模式：所有请求都按同一个二级索引查
- 重试风暴：失败后集中重试同一分片

热点不是“平均 QPS 高”，而是**某个分片/键远高于其他**。

## 4. 重分片：取模的问题

N 个分片，`hash(key) % N` 最简单，但 N 变化时几乎所有 key 都要换位置。

实验：10 万个合成 key，4 → 5 个分片。

??? note "代码：取模 vs rendezvous 的迁移比例"
    ```python
    import hashlib


    def h(value):
        return int.from_bytes(hashlib.sha256(value.encode()).digest()[:8], "big")


    def modulo_owner(key, nodes):
        return h(key) % len(nodes)


    def rendezvous_owner(key, nodes):
        return max(nodes, key=lambda node: h(f"{key}:{node}"))


    def moved(keys, old_nodes, new_nodes, owner_fn):
        count = 0
        for k in keys:
            if owner_fn(k, old_nodes) != owner_fn(k, new_nodes):
                count += 1
        return count


    if __name__ == "__main__":
        keys = [f"url:{i}" for i in range(100_000)]
        old = list(range(4))
        new = list(range(5))

        m = moved(keys, old, new, modulo_owner)
        r = moved(keys, old, new, rendezvous_owner)

        print("keys", len(keys), "shards 4 -> 5")
        print(f"modulo moved:     {m} ({m / len(keys):.1%})")
        print(f"rendezvous moved: {r} ({r / len(keys):.1%})")
    ```

输出：

```text
keys 100000 shards 4 -> 5
modulo moved:     80195 (80.2%)
rendezvous moved: 19764 (19.8%)
```

读法：

- 取模：增加一个分片，约 80% key 要迁移
- rendezvous hashing：只迁移约 20%
- 这是合成 key 的比例，不是实际数据量；实际还要算迁移字节、双写/回填成本
- rendezvous 不是唯一方案；consistent hashing + virtual nodes 也常用

关键不是“哪个算法更酷”，而是重分片时**迁移多少、怎么校验、怎么回滚**。

## 5. 再平衡

再平衡要考虑：

- 迁移单位：key/分区/逻辑分片
- 限速：别把源/目标/网络打满
- 优先级：热分片先迁
- 一致性：迁移期间读写走哪
- 校验：行数/checksum/抽样
- 回滚：迁移失败怎么切回

常见做法：

```text
逻辑分片 > 物理节点
先扩逻辑分片，再把逻辑分片搬到新节点
```

逻辑分片让扩容不必改 key 的哈希规则；但逻辑分片数量要提前留余量。

## 6. 跨分片查询

分区后，跨分片查询变贵：

- scatter-gather：查所有分片再聚合
- 二级索引/全局索引
- 读模型/宽表
- 按查询维度重新分区
- 限制跨分片 join

跨分片事务：

- 尽量避免
- 需要时用 Saga/Outbox/补偿
- 不要假设单机事务

## 7. 复制与故障

复制模式：

- leader-follower：主写从读，简单
- multi-leader：多地主写，冲突
- leaderless：quorum 读写，修复复杂

故障时注意：

- 异步复制 → 旧读
- 主故障 → 选主/脑裂
- 副本落后 → 读修复/重建
- 重试 → 幂等
- 跨地域 → 延迟/一致性取舍

复制延迟要监控：落后字节/时间、复制槽、失败重试。

## 8. 热点治理

- 热 key 拆分：加随机后缀/分桶，读时聚合
- 大租户独立分片/限流
- 本地缓存/多级缓存
- 读副本/只读副本
- 请求合并/批量
- 队列削峰/背压
- 热点隔离，避免拖垮长尾

注意：给热 key 加后缀会改变读写路径；读时要能合并/聚合。

## 9. 观测

按分片看：

- QPS、p95/p99
- 存储量、增长
- CPU/IO/网络
- 复制延迟
- 热点 key（top-N）
- 迁移进度/失败
- 跨分片查询比例

只看看全局平均，热点会被平均掉。

## 10. 检查清单

- 分区键高基数、均匀、符合查询吗？
- 有没有大租户/明星 key/时间热点？
- 扩容时迁移多少 key/字节？
- 迁移限速/校验/回滚做了吗？
- 跨分片查询/事务怎么处理？
- 复制延迟/故障切换怎么监控？
- 热点怎么发现、怎么拆？
- 逻辑分片留了多少余量？

## 11. 常见坑

1. **用加副本解决写热点**
   副本不增加单 key 写能力。

2. **分区键低基数**
   status/type/日期做 key，分片必然倾斜。

3. **只用 hash % N**
   扩容时几乎全量迁移。

4. **热 key 只靠缓存**
   缓存失效/穿透时仍然打爆后端。

5. **迁移不限速**
   再平衡把线上打挂。

6. **跨分片 join**
   查询放大，延迟不可控。

7. **没有复制延迟监控**
   用户刚写完读不到，找不到原因。

8. **逻辑分片不够**
   扩容只能改哈希，迁移量爆炸。

9. **热点不隔离**
   一个大租户拖垮所有租户。

10. **迁移没有校验/回滚**
    数据搬了一半，无法确认/恢复。

## 12. 要点回顾

1. 复制解决读/故障，分区解决容量/写，热点是分布问题
2. 分区键要高基数、均匀、符合查询
3. `hash % N` 扩容迁移大；consistent/rendezvous 可降低迁移
4. 重分片要限速、校验、回滚，不能只看算法
5. 跨分片查询/事务要单独设计
6. 复制有延迟、选主、脑裂、旧读
7. 热 key/大租户要拆分、隔离、限流
8. 按分片观测，不要只看全局平均
9. 逻辑分片和迁移流程比“哈希算法”更决定成败
