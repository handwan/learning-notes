# 需求、约束与容量估算

容量估算不是 benchmark，也不是“猜一个 QPS”。它是用明确假设，估算系统需要多少计算、存储、带宽和机器，并知道哪个假设一变，结论会怎么变。

这篇用短链服务做例子，算：

- 平均/峰值 QPS
- 存储
- 缓存
- 带宽
- 并发
- 应用节点数

所有数字都是示例假设，不是线上实测。

## 1. 先定义输入

容量计算至少需要：

| 输入 | 例子 | 影响 |
|---|---|---|
| 每日新增写 | 100 万条/天 | 写 QPS、存储 |
| 每日读取 | 5000 万次/天 | 读 QPS、缓存、带宽 |
| 峰值系数 | 3× | 机器、队列、限流 |
| 单条记录大小 | 300 B | 存储、缓存 |
| 保留期 | 5 年 | 总存储 |
| 副本/索引开销 | 3 副本 × 1.5 | 实际存储 |
| 缓存命中率 | 90% | 回源 QPS |
| 缓存条数/条目/开销 | 500 万 × 300 B × 2 | 缓存大小 |
| 响应大小 | 1 KB | 带宽 |
| 规划延迟 | 50 ms | 并发 |
| 单节点容量 | 5000 QPS | 节点数 |

输入来源可以是：

- 产品目标
- 历史监控
- 压测
- 订单/日志
- 明确的业务假设

没有数据就写“假设”，并做敏感性分析。

## 2. 基本公式

```text
平均 QPS = 每日请求数 / 86400
峰值 QPS = 平均 QPS × 峰值系数

原始存储 = 每日写入 × 记录大小 × 保留天数
实际存储 = 原始存储 × 副本数 × 索引/开销系数

回源 QPS = 峰值读 QPS × (1 - 缓存命中率)
带宽 = 峰值请求 QPS × 平均响应大小
并发 ≈ QPS × 延迟
节点数 = ceil(峰值 QPS / 单节点容量)
```

几个容易混淆的点：

- **QPS 不是并发**：并发 ≈ QPS × 延迟。
- **峰值不是平均**：容量按峰值和增长规划，不按日均。
- **存储要乘副本和索引**：只算原始数据会低估。
- **缓存命中率改变回源量**：不是所有读都打到数据库。
- **单节点容量要实测**：示例里的 5000 QPS 只是假设。

计算器使用上面的假设；所有数字都是示例，改代码顶部 `A` 即可重算。

## 3. 计算器

??? note "代码：短链容量估算"
    ```python
    import math


    A = {
        "new_links_per_day": 1_000_000,
        "redirects_per_day": 50_000_000,
        "peak_factor": 3.0,
        "record_bytes": 300,
        "retention_days": 365 * 5,
        "replicas": 3,
        "index_overhead": 1.5,
        "cache_hit_rate": 0.90,
        "response_bytes": 1024,
        "cache_entries": 5_000_000,
        "cache_entry_bytes": 300,
        "cache_overhead": 2.0,
        "per_node_qps": 5_000,
        "latency_ms": 50,  # planning latency, not p95
    }

    SECONDS_PER_DAY = 86400
    GIB = 1024 ** 3
    TIB = 1024 ** 4


    def estimate(a):
        avg_write = a["new_links_per_day"] / SECONDS_PER_DAY
        avg_read = a["redirects_per_day"] / SECONDS_PER_DAY
        peak_write = avg_write * a["peak_factor"]
        peak_read = avg_read * a["peak_factor"]
        peak_total = (avg_write + avg_read) * a["peak_factor"]

        raw_storage = (
            a["new_links_per_day"] * a["record_bytes"] * a["retention_days"]
        ) / GIB
        replicated_storage = raw_storage * a["replicas"] * a["index_overhead"]
        cache_size = (
            a["cache_entries"] * a["cache_entry_bytes"] * a["cache_overhead"]
        ) / GIB
        origin_read = peak_read * (1 - a["cache_hit_rate"])
        bandwidth_mb_s = peak_total * a["response_bytes"] / 1_000_000
        concurrency = peak_total * (a["latency_ms"] / 1000)
        app_nodes = math.ceil(peak_total / a["per_node_qps"])

        return {
            "avg_write": avg_write,
            "avg_read": avg_read,
            "peak_write": peak_write,
            "peak_read": peak_read,
            "peak_total": peak_total,
            "raw_storage": raw_storage,
            "replicated_storage": replicated_storage / 1024,
            "cache_size": cache_size,
            "origin_read": origin_read,
            "bandwidth_mb_s": bandwidth_mb_s,
            "concurrency": concurrency,
            "app_nodes": app_nodes,
        }


    if __name__ == "__main__":
        r = estimate(A)
        print("assumptions")
        for k in ["new_links_per_day", "redirects_per_day", "peak_factor",
                  "record_bytes", "retention_days", "replicas", "index_overhead",
                  "cache_hit_rate", "response_bytes", "per_node_qps", "latency_ms"]:
            print(f"  {k}: {A[k]}")

        print("\nqps")
        print(f"  avg write: {r['avg_write']:.1f}")
        print(f"  avg read:  {r['avg_read']:.1f}")
        print(f"  peak write: {r['peak_write']:.1f}")
        print(f"  peak read: {r['peak_read']:.1f}")
        print(f"  peak total: {r['peak_total']:.1f}")

        print("\nstorage / cache")
        print(f"  raw storage:        {r['raw_storage']:.1f} GiB")
        print(f"  replicated + index: {r['replicated_storage']:.2f} TiB")
        print(f"  cache:              {r['cache_size']:.2f} GiB")
        print(f"  origin read:        {r['origin_read']:.1f} QPS")

        print("\nnetwork / concurrency / nodes")
        print(f"  peak bandwidth:     {r['bandwidth_mb_s']:.2f} MB/s")
        print(f"  concurrency @ 50ms: {r['concurrency']:.1f}")
        print(f"  app nodes:          {r['app_nodes']} (N+1={r['app_nodes'] + 1})")

        print("\nsensitivity: peak factor")
        for factor in [2.0, 3.0, 5.0]:
            x = estimate({**A, "peak_factor": factor})
            print(f"  peak={factor:.0f}x -> total={x['peak_total']:.1f} QPS, "
                  f"origin={x['origin_read']:.1f} QPS")
    ```

## 4. 读结果

| 指标 | 结果 | 读法 |
|---|---:|---|
| 峰值总 QPS | 1770.8 | 读多写少 |
| 原始 / 实际存储 | 509.9 GiB / 2.24 TiB | 3 副本 + 1.5 索引 |
| 缓存 / 回源 | 2.79 GiB / 173.6 QPS | 90% 命中 |
| 峰值带宽 | 1.81 MB/s | 不是主要瓶颈 |
| 并发 / 节点 | 88.5 / 1（N+1=2） | 50ms 规划延迟 |
| 3×→5× 峰值 | 1770.8→2951.4 QPS | 容量约 1.67 倍 |

估算做规划，压测做验证；压测方法见 [Inference 第 7 篇](../../06-ai/inference/07-压测与容量规划.md)。

## 5. 容量如何影响设计

| 约束 | 设计影响 |
|---|---|
| 读多写少 | 缓存、读副本、热点隔离 |
| 写峰值高 | 队列削峰、批量写、预生成短码 |
| 存储增长快 | 保留期、压缩、冷热分层、对象存储 |
| 延迟要求高 | 边缘、缓存前置、按 p95/p99 规划 |
| 成本敏感 | 租户配额、自动缩容、冷数据下沉 |

## 6. 常见坑

1. **只算平均 QPS**
   峰值、增长和突发才是容量问题。

2. **QPS 当并发**
   并发 ≈ QPS × 延迟；高延迟会放大排队。

3. **只算原始存储**
   副本、索引、备份、日志都要算。

4. **缓存命中率拍脑袋**
   没有工作集和访问分布，90% 只是假设。

5. **单节点容量抄 benchmark**
   模型、请求大小、依赖和配置都不同；要自己压测。

6. **忽略下游**
   应用 QPS 不大，但数据库/第三方 API 可能先挂。

7. **不留 N+1/增长**
   一个节点故障或流量增长就超容量。

8. **用估算当性能保证**
   估算只是规划，最终要压测和线上验证。

## 7. 要点回顾

1. 容量估算需要明确假设：流量、峰值、记录大小、保留期、副本、缓存、延迟
2. 平均 QPS = 日请求 / 86400；峰值 = 平均 × 峰值系数
3. 存储 = 写入 × 大小 × 保留 × 副本 × 开销
4. 回源 QPS = 峰值读 × (1 - 缓存命中率)
5. 并发 ≈ QPS × 延迟；节点数按峰值/单节点容量
6. 容量估算不是 benchmark；要做敏感性分析
7. 估算和压测都要：估算做规划，压测做验证
8. 读多写少、写峰值、存储增长、延迟、成本会改变设计
9. 所有假设写出来，不把示例数字当真实数据
