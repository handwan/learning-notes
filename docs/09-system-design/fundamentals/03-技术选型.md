# 技术选型

技术选型不是“选最强的”。它是在当前约束下，选一个代价可接受、能验证、能退出的方案。

这篇讲语言、中间件、存储和架构的选型方法，最后用一个加权矩阵演示：权重一变，PostgreSQL 和 KV 的结论会翻转。存储细节见[数据建模与存储选型](../data/01-数据建模与存储选型.md)，这里讲通用选型框架。

## 1. 选型前先有输入

没有 workload，就没有选型。至少先写：

- 读写比例、峰值 QPS、数据量
- p95/p99 延迟目标
- 一致性/持久性要求
- 可用性与故障恢复
- 团队规模和运维能力
- 预算、许可、合规
- 现有技术栈和迁移成本

选型不是“先列产品再打分”，而是“先用约束缩小候选”。

## 2. 语言：看运行时和团队

语言不是系统设计的主角，但运行时会影响架构：

| 运行时 | 常见优势 | 常见代价 |
|---|---|---|
| JVM | 生态成熟、JIT、工具链 | GC、堆内存、启动 |
| Go | 并发模型简单、部署轻 | GC、泛型/生态取舍 |
| Rust | 内存安全、可预测性能 | 学习/编译成本、生态 |
| Python | 数据/科学计算生态、开发快 | GIL、CPU 密集要靠扩展/多进程 |
| Node/TS | 事件循环、前后端同栈 | CPU 阻塞、回调/异步复杂度 |

选语言看：

- 团队是否熟悉
- 延迟/吞吐/内存
- 并发模型
- 库和生态
- 部署、观测、排障
- 招聘和长期维护

不要用“Go 比 Java 快”这种单句做决策；请求形态、GC、依赖和团队都会改变结论。

## 3. 中间件：先看语义

中间件不是按名字选，是按语义选：

| 能力 | 要确认的语义 |
|---|---|
| 缓存 | TTL、淘汰、一致性、持久化、热 key |
| 消息 | 投递语义、顺序、持久化、积压、重放 |
| 关系库 | 事务、隔离级别、索引、复制、分片 |
| KV/文档 | 查询模式、一致性、容量、二级索引 |
| 搜索 | 倒排、近实时、相关性、同步 |
| 对象存储 | 大对象、生命周期、一致性、成本 |
| 入口 | 四层/七层、TLS、限流、灰度、认证 |
| 协调 | leader、租约、watch、一致性 |
| 观测 | 指标、日志、trace、采样、保留 |

候选地图：

```text
入口：Nginx / Envoy / 云 LB
缓存：Redis / Memcached / 本地缓存
消息：Kafka / RabbitMQ / SQS
关系库：PostgreSQL / MySQL
KV/文档：Redis / MongoDB / Cassandra / DynamoDB
搜索：Elasticsearch / OpenSearch
对象存储：S3 / OSS / MinIO
协调：etcd / ZooKeeper
观测：Prometheus / OpenTelemetry
```

每个候选只回答：

- 适合什么
- 不适合什么
- 关键语义
- 失败模式
- 运维成本
- 怎么验证


## 4. 架构：选的是约束，不是名词

架构风格也要选型：

- 单体
- 模块化单体
- 微服务
- 事件驱动
- CQRS

判断顺序：

```text
团队规模 → 发布频率 → 故障隔离 → 数据一致性 → 运维能力
```

小团队、低发布频率、强事务，模块化单体通常更合适；多团队、独立发布、明确边界，才考虑拆服务。

## 5. 评估维度

| 维度 | 要问什么 |
|---|---|
| 功能 | 查询/写入/事务/顺序/投递语义 |
| 性能 | p95/p99、吞吐、尾延迟、冷启动 |
| 扩展 | 水平扩展、分片、热点、容量上限 |
| 一致性 | 强/最终、读写顺序、重复/丢失 |
| 可靠 | 故障恢复、备份、降级、RTO/RPO |
| 运维 | 部署、升级、监控、排障、团队能力 |
| 成本 | 机器、存储、网络、人力、云账单 |
| 生态 | 客户端、文档、社区、托管 |
| 锁定 | 迁移成本、数据格式、退出方案 |
| 合规 | 许可、数据驻留、安全要求 |

## 6. 加权矩阵：暴露假设，不替代判断

加权矩阵的价值不是“算出唯一正确答案”，而是把：

- 评估维度
- 权重
- 候选分数
- 结论对权重的敏感性

摆到桌面上。

示例：短链存储选 PostgreSQL 还是 KV。

评分 1–5 是示例主观分，不是 benchmark：

```text
PostgreSQL: [5, 4, 3, 5, 4, 4, 5]
KV:         [2, 5, 5, 3, 3, 3, 2]
```

基础权重偏“查询灵活 + 一致性 + 团队熟悉”，PostgreSQL 胜；如果改成极端写多，KV 胜。

??? note "代码：加权选型矩阵"
    ```python
    CRITERIA = [
        "query flexibility",
        "read latency",
        "write scale",
        "consistency",
        "operations",
        "cost at current scale",
        "team familiarity",
    ]

    BASE_WEIGHTS = [0.20, 0.15, 0.15, 0.15, 0.15, 0.10, 0.10]
    WRITE_HEAVY_WEIGHTS = [0.05, 0.05, 0.50, 0.05, 0.10, 0.15, 0.10]

    SCORES = {
        "PostgreSQL": [5, 4, 3, 5, 4, 4, 5],
        "KV": [2, 5, 5, 3, 3, 3, 2],
    }


    def weighted(scores, weights):
        return sum(s * w for s, w in zip(scores, weights))


    def rank(weights):
        result = {name: weighted(scores, weights) for name, scores in SCORES.items()}
        return sorted(result.items(), key=lambda x: x[1], reverse=True)


    def show(title, weights):
        print(f"\n{title}")
        print("weights:", ", ".join(f"{c}={w:.2f}" for c, w in zip(CRITERIA, weights)))
        for name, value in rank(weights):
            print(f"  {name:10s} {value:.2f}")


    if __name__ == "__main__":
        print("criteria:", ", ".join(CRITERIA))
        print("scores (1-5, subjective):")
        for name, scores in SCORES.items():
            print(f"  {name:10s} {scores}")

        show("base: balanced", BASE_WEIGHTS)
        show("sensitivity: write-heavy", WRITE_HEAVY_WEIGHTS)

        base_winner = rank(BASE_WEIGHTS)[0][0]
        write_winner = rank(WRITE_HEAVY_WEIGHTS)[0][0]
        print("\nwinner flips:", base_winner != write_winner)
        print("base winner:", base_winner)
        print("write-heavy winner:", write_winner)
    ```

输出：

```text
criteria: query flexibility, read latency, write scale, consistency, operations, cost at current scale, team familiarity
scores (1-5, subjective):
  PostgreSQL [5, 4, 3, 5, 4, 4, 5]
  KV         [2, 5, 5, 3, 3, 3, 2]

base: balanced
weights: query flexibility=0.20, read latency=0.15, write scale=0.15, consistency=0.15, operations=0.15, cost at current scale=0.10, team familiarity=0.10
  PostgreSQL 4.30
  KV         3.30

sensitivity: write-heavy
weights: query flexibility=0.05, read latency=0.05, write scale=0.50, consistency=0.05, operations=0.10, cost at current scale=0.15, team familiarity=0.10
  KV         3.95
  PostgreSQL 3.70

winner flips: True
base winner: PostgreSQL
write-heavy winner: KV
```

读法：

- 基础权重下 PostgreSQL 4.30，KV 3.30
- 写多场景下 KV 3.95，PostgreSQL 3.70
- 结论翻转，不是算法变了，是权重变了
- 权重是业务/团队偏好，分数要有 POC/证据；矩阵只负责暴露它们

不要用矩阵制造“精确的错觉”。如果两个方案差 0.1 分，基本等于打平，应该看风险、退出成本和团队意愿。

## 7. POC：用 workload 验证

候选缩到 2–3 个后，做小 POC：

1. 用真实请求大小/读写比
2. 测 p95/p99，不只看平均
3. 注入超时、故障、重启
4. 看升级/回滚/备份
5. 算月度成本
6. 写退出方案：数据怎么迁、多久能切回

厂商 benchmark 只能当参考；你的请求形态、数据分布和配置不同。

## 8. ADR：把决策留下来

模板见[系统设计方法](01-系统设计方法.md)第 8 节。

示例：

```text
Context：短链第一版，读多写少，团队熟悉 PostgreSQL
Decision：PostgreSQL，暂不引入 KV
Consequences：查询/事务简单；写入扩展要后续分片
Alternatives：KV 写入扩展更好，但查询灵活性和团队成本更高
Revisit：写入持续超过单库容量，或 p99 受数据库限制
```

## 9. 常见坑

1. **先选产品，再找场景**
   先有 workload，再看候选。

2. **看厂商 benchmark 下单**
   请求大小、数据分布、配置都不同。

3. **只看性能，不看运维**
   团队不会运维的“高性能”方案是负债。

4. **忽略退出成本**
   数据格式、协议、托管锁定要提前想。

5. **把加权矩阵当真理**
   权重和分数都是假设；要看敏感性。

6. **追求单一总分**
   差 0.1 分没有意义；要看硬约束和风险。

7. **语言选型只看速度**
   团队、生态、部署、排障同样重要。

8. **中间件只看功能列表**
   投递语义、顺序、积压、重放才是关键。

9. **不做 POC**
   方案在 PPT 上都能赢，线上不一定。

10. **不写 ADR**
    半年后没人知道为什么选它、什么时候该换。

## 10. 要点回顾

1. 选型先有 workload 和约束，再列候选
2. 语言看运行时、团队、生态、部署，不只比速度
3. 中间件看语义：投递、顺序、持久化、积压、重放
4. 架构看团队/发布/故障隔离/一致性，不按名词选
5. 评估维度：功能、性能、扩展、一致性、可靠、运维、成本、锁定
6. 加权矩阵用来暴露假设，不替代判断
7. 权重一变，结论可能翻转；要做敏感性分析
8. POC 用真实 workload，厂商 benchmark 只当参考
9. ADR 记录选择、代价、替代方案和重新评估条件
