# 缓存一致性

缓存一致性不是“设个 TTL”就完了。要回答：

- 写数据库后，缓存怎么失效？
- 失效失败怎么办？
- 并发读写时，旧值会不会被写回？
- 读从库时，旧数据会不会被缓存？
- 业务能接受多长时间的旧读？

缓存机制/命中率/穿透雪崩见[缓存](../scalability/02-缓存.md)；这篇只讲一致性。

## 1. 两种常见写法

### 更新 DB，删除缓存

```text
写：update DB → delete cache
读：cache miss → read DB → set cache
```

优点：

- 实现简单
- 缓存不常被写，适合读多写少

风险：

- 删缓存失败
- 读请求在删缓存后回填旧值
- DB 主从延迟导致读到旧值

### 更新 DB，更新缓存

```text
写：update DB → set cache
读：cache hit → return
```

风险：

- 并发写顺序错，旧值覆盖新值
- 缓存更新失败
- 缓存和 DB 不是同一事务

大多数场景先考虑“更新 DB + 删除缓存”，但要知道竞态。

## 2. 经典竞态

时间线：

```text
1. 读请求 cache miss，读 DB = v1
2. 写请求 update DB = v2
3. 写请求 delete cache
4. 读请求把 v1 写回 cache
```

结果：

```text
DB = v2，cache = v1
```

TTL 最终会修复，但在 TTL 内一直旧读。TTL 越长，窗口越大。

## 3. 常见缓解

### 延迟双删

```text
写：delete cache → update DB → 延迟 → delete cache
```

能降低“读回填旧值”的概率，但不是严格保证；延迟时间难定。

### 版本号/水位

缓存值带版本：

```text
cache = {value, version}
```

回填前检查版本是否落后；落后就拒绝。

需要版本来源：

- DB version 字段
- 全局单调版本
- CDC LSN/GTID
- 缓存版本 key

版本比较必须能识别“旧回填”，否则只是换个地方猜。

### CDC/订阅 binlog

```text
DB commit → CDC → invalidate cache
```

优点：

- 不依赖业务代码
- 能捕获所有写路径
- 可重放/补偿

代价：

- 延迟
- 重复/顺序
- schema/运维

### 写穿/读穿

- write-through：写缓存同时写 DB
- read-through：缓存层负责回源

实现简单，但缓存层更重；写穿仍有并发顺序问题。

## 4. 读从库的旧值

读写分离下：

```text
写主库 → 从库延迟 → 读从库旧值 → 写进缓存
```

缓存把旧值放大，TTL 内持续旧读。

处理：

- 写后读主库
- 读己之写 token/version
- 缓存只从主库回填
- 短 TTL
- 业务接受旧读

## 5. 删除失败/更新失败

- 删除缓存失败：重试/补偿/消息
- 更新缓存失败：DB 已成功，缓存旧值
- 缓存宕机：回源压力/降级
- 网络超时：不知道删没删

要记录失败、重试、告警；不能假设“删了就一定删了”。

## 6. 业务一致性

缓存一致性不是越强越好：

| 数据 | 可接受旧读？ |
|---|---|
| 余额/库存 | 通常不可 |
| 商品详情/Feed | 可短时间旧 |
| 配置/权限 | 要快速生效 |
| 统计 | 可最终一致 |

先和业务确认：

- 多旧可以接受
- 出错时返回旧值还是报错
- 谁能触发强制刷新

## 7. 实验：旧值回填

??? note "代码：naive vs versioned 回填"
    ```python
    def naive_race():
        db = "v1"
        cache = None

        # reader misses and reads DB
        read_value = db

        # writer updates DB and deletes cache
        db = "v2"
        cache = None

        # reader writes stale value back
        cache = read_value
        return cache, db


    def versioned_race():
        current_version = 1
        db = {"value": "v1", "version": 1}
        cache = None

        # reader reads DB version 1
        read_value = dict(db)

        # writer updates DB to version 2 and invalidates cache
        current_version = 2
        db = {"value": "v2", "version": 2}
        cache = None

        # reader tries to fill cache, but version watermark is newer
        if read_value["version"] >= current_version:
            cache = read_value
        return cache, db


    if __name__ == "__main__":
        c, d = naive_race()
        print(f"naive: cache={c} db={d} stale={c != d}")

        c, d = versioned_race()
        print(f"versioned: cache={c} db={d['value']} "
              f"stale={c is not None and c['value'] != d['value']}")
    ```

输出：

```text
naive: cache=v1 db=v2 stale=True
versioned: cache=None db=v2 stale=False
```

读法：

- naive：读请求回填 v1，DB 已是 v2，缓存旧读
- versioned：回填前比较版本水位，旧版本被拒绝
- 版本水位本身要可信（DB version/CDC LSN/单调版本）
- 这是竞态示意，不是缓存产品 benchmark

## 8. 检查清单

- 写后删缓存还是更新缓存？
- 删缓存失败怎么办？
- 读回填会不会覆盖新值？
- 有没有版本/水位/CDC？
- 读从库会不会把旧值写进缓存？
- TTL 多长？业务能接受吗？
- 缓存宕机/回源怎么降级？
- 强制刷新/修复怎么触发？
- 缓存 key 是否带租户/版本？

## 9. 常见坑

1. **TTL 当强一致**
   过期前一直旧读。

2. **写后更新缓存**
   并发写容易旧值覆盖。

3. **删缓存失败不重试**
   旧缓存长期存在。

4. **读回填无版本**
   旧值覆盖新值。

5. **从库旧值回填**
   复制延迟被缓存放大。

6. **缓存 key 不带租户**
   跨租户泄漏。

7. **没有强制刷新**
   出问题只能等 TTL。

8. **缓存和 DB 同一事务**
   跨系统事务不成立；不要假设原子。

9. **所有数据一个 TTL**
   该快的慢，该慢的快。

10. **只靠代码评审**
    竞态要靠测试/演练/监控。

## 10. 要点回顾

1. 缓存一致性要定义写路径、失效、回填和旧读窗口
2. 更新 DB + 删除缓存常见，但有竞态
3. 读回填可能把旧值写回；版本/水位/CDC 可以防
4. 延迟双删降低概率，不是严格保证
5. 读写分离下，从库旧值会被缓存放大
6. TTL 是业务旧读窗口，不是强一致
7. 删除/更新失败要重试/告警/补偿
8. 不同数据可接受旧读不同；和业务确认
9. 缓存 key 要带租户/版本；缓存宕机要降级
