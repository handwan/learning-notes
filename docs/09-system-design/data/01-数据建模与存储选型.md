# 数据建模与存储选型

存储选型不是“先选 MySQL 还是 MongoDB”，而是先回答：

- 数据长什么样
- 怎么查
- 怎么写
- 要不要事务
- 数据多大、保留多久
- 多租户怎么隔离

数据库只是这些约束的落点。

## 1. 从访问模式开始

先列查询/写入路径：

```text
按 short_code 查一条链接
按 tenant + 创建时间列链接
按 link_id + 时间聚合点击
按 URL 搜索（可选）
删除/过期链接
导出某租户数据
```

每条路径写：

- 输入/过滤条件
- 排序/分页
- 返回字段
- QPS/延迟
- 一致性要求
- 数据量/增长

没有访问模式，表结构和索引只能猜。

## 2. 实体和键

短链例子：

```text
links(
  id,
  tenant_id,
  short_code,
  url,
  created_at,
  expires_at,
  status
)

clicks(
  id,
  tenant_id,
  link_id,
  clicked_at,
  ip_hash,
  user_agent
)
```

关键决策：

- 主键：自增/ULID/UUID？是否暴露给用户
- 业务唯一键：`short_code` 全局唯一
- 外键：数据库约束还是应用维护
- 租户键：每张表/索引都带 `tenant_id`
- 时间：创建/更新/过期/删除
- 状态：显式状态机，不要用多个布尔

短码唯一索引：

```text
unique (short_code)
```

`short_code` 全局唯一，不同租户也不能复用；租户隔离靠 `tenant_id` 查询和授权。

## 3. 索引

索引是读加速、写成本：

- 主键/唯一索引
- 复合索引：过滤 + 排序
- 覆盖索引：减少回表
- 前缀索引：长字符串
- 部分索引：status/tenant
- 全文/倒排：搜索

按查询建索引，不要按“字段都建一个”。

检查：

- 查询是否走索引
- 索引顺序是否匹配过滤/排序
- 是否有回表/排序/临时表
- 写放大/存储成本
- 低选择性索引是否值得

索引不是越多越好；每个索引都要维护。

## 4. 规范化 vs 反规范化

规范化：

- 减少重复
- 更新一致
- 查询可能要 join

反规范化：

- 读快、少 join
- 数据重复，更新要同步
- 适合读多写少/读模型

原则：

- OLTP 核心实体先规范化
- 读模型/报表可以反规范化
- 不要为了“未来查询”提前复制十份
- 复制就要定义谁是源、怎么同步、怎么修复

## 5. 存储类型

| 类型 | 适合 | 不适合 |
|---|---|---|
| 关系库 | 事务、join、复杂查询 | 超大稀疏数据/极高写入 |
| KV | 简单 key 查询、低延迟 | 复杂查询/二级索引 |
| 文档 | 嵌套对象、灵活 schema | 跨文档事务/复杂 join |
| 宽列 | 大宽表、时间序列、写扩展 | 复杂事务/ad-hoc 查询 |
| 搜索 | 全文/相关性/聚合 | 作为主库/强事务 |
| 对象存储 | 图片/视频/大文件/备份 | 低延迟随机读写 |
| 时序库 | 指标/传感器/时间窗口 | 通用事务 |
| 向量库（可选） | 向量相似检索，AI/语义场景 | 精确事务/复杂过滤 |

没有一种存储覆盖所有访问模式；多模型会增加一致性/运维成本。

## 6. 选型矩阵

| 维度 | 要问什么 |
|---|---|
| 查询 | 主键/范围/全文/聚合/join |
| 写入 | 吞吐、批量、更新频率 |
| 事务 | 单行/多行/跨实体 |
| 一致性 | 强/最终、读己之写 |
| 规模 | 数据量、增长、单分区上限 |
| schema | 固定/灵活、演进频率 |
| 延迟 | p95/p99、冷热 |
| 运维 | 备份、恢复、扩容、监控 |
| 成本 | 存储/IO/网络/人力 |
| 生态 | 客户端、托管、团队熟悉 |

短链第一版：

- links：关系库，`short_code` 全局唯一索引
- clicks：追加写；量大后进时序/列式/分析库
- 搜索：非核心，先不做或异步索引
- 对象存储：不做，短链没有大文件

这是约束下的选择，不是“关系库永远正确”。

## 7. Schema 演进

- 加字段：先可空/默认值，双写/回填
- 改类型：新字段 + 迁移，不要原地硬改
- 删字段：先停读写，再删
- 重命名：新字段 + 兼容期
- 枚举：新增值要考虑旧客户端
- 大表 DDL：在线工具/低峰/限流

schema 变更是数据迁移，不只是改 DDL。要有回填、校验、回滚。

## 8. 数据生命周期

- 保留期：业务/合规要求
- 归档：冷数据下沉
- 删除：软删/硬删/可恢复
- 租户导出/删除
- 备份/恢复
- PII 最小化/脱敏

没有生命周期，表会无限增长，查询/备份/成本都变差。

## 9. 多租户数据

- 每张业务表有 `tenant_id`
- 主键/唯一键包含 tenant 或全局唯一
- 索引前缀考虑 tenant
- 查询必须带 tenant 条件
- 防止跨租户 join/导出
- 大租户可独立分片/库

数据模型不隔离，后面靠 API 补很难。

## 10. 例子：短链

访问模式：

```text
resolve: short_code → url
list: tenant + created_at desc
stats: link_id + time range
expire: expires_at < now
```

模型：

```text
links(id, tenant_id, short_code, url, created_at, expires_at, status)
unique(short_code)
index(tenant_id, created_at)
index(status, expires_at)
```

跳转按 `short_code` 全局解析；列表/统计/管理接口再按 `tenant_id` 授权。

点击：

```text
clicks(id, tenant_id, link_id, clicked_at, ...)
index(link_id, clicked_at)
```

统计不要每次 `count(*)` 扫全表；用聚合表/流式/列式分析。

## 11. 检查清单

- 访问模式列全了吗？
- 主键/业务唯一键是什么？
- 多租户唯一性怎么定义？
- 索引匹配查询/排序吗？
- 哪些字段反规范化？谁是源？
- 事务边界在哪？
- 数据量/增长/保留期？
- schema 怎么演进？
- 分析查询会不会拖垮 OLTP？
- 备份/恢复/删除怎么做？

## 12. 常见坑

1. **先选数据库**
   没有访问模式，选型没有依据。

2. **所有查询都靠 join**
   OLTP 复杂 join 可能拖垮主库。

3. **索引越多越好**
   写放大、存储、优化器负担。

4. **短码唯一性和跳转路由不一致**
   租户内唯一 + 全局 `GET /{code}` 会解析不了；全局唯一或路由带 tenant，二选一。

5. **反规范化没有源**
   多份数据互相覆盖。

6. **分析查询打 OLTP**
   报表/聚合拖慢线上。

7. **schema 原地硬改**
   锁表/回滚困难。

8. **没有保留期**
   数据无限增长。

9. **多存储没一致性方案**
   数据重复、修复困难。

10. **把搜索库当主库**
   搜索索引不适合强事务/唯一约束。

## 13. 要点回顾

1. 先列访问模式，再选模型/存储
2. 主键、业务唯一键、租户键要一起设计
3. 索引按查询建，读加速有写成本
4. OLTP 先规范化，读模型/报表可反规范化
5. 存储类型按查询/事务/规模/成本选
6. schema 演进是数据迁移，要回填/校验/回滚
7. 数据生命周期要设计保留/归档/删除
8. 多租户隔离要落到表/键/索引/查询
9. 分析负载和 OLTP 尽量分离
10. 多存储增加一致性/运维成本，不是默认选择
