# 分库分表与读写分离

分库分表和读写分离经常一起出现，但解决的是不同问题：

- **读写分离**：主库写，从库读，扩展读吞吐
- **分库分表**：把数据/写入拆到多个库/表，扩展容量和写吞吐

它们都不能替代建模、索引、缓存和容量规划。

## 1. 先确认真的需要

先问：

- 单库容量到了吗？
- 单表行数/索引大小到了吗？
- 写 QPS/IO 到了吗？
- 读多还是写多？
- 延迟瓶颈在 DB 还是应用/网络？
- 能不能加索引/归档/缓存/读副本？
- 团队能维护路由、迁移、备份、跨库查询吗？

分片是复杂度跃迁：从“一个库的事务”变成“路由 + 跨库查询 + 分布式事务 + 迁移”。

不要因为“表看起来大”就分。

## 2. 读写分离

```text
写入 → 主库
读取 → 从库（或主库）
复制：主库 → 从库
```

适合：

- 读多写少
- 能接受短暂旧读
- 读 QPS 增长

代价：

- 复制延迟
- 读己之写问题
- 从库故障/延迟
- 主库故障切换
- 读写路由复杂

### 读己之写

用户写完立刻读，从库可能还没复制到：

```text
write at t=0，replica lag=2s
read at t=1 → 看不到
read at t=3 → 看得到
```

处理：

- 写后读主库
- sticky session
- 读等待到指定版本/LSN
- 客户端 token
- 业务接受短暂旧读

## 3. 分片方式

| 方式 | 特点 | 风险 |
|---|---|---|
| Range | 按范围（时间/ID） | 新范围热点 |
| Hash | 均匀分布 | 范围查询/扩容迁移 |
| List | 按枚举/租户 | 倾斜 |
| 复合 | tenant + hash | 路由复杂 |

分区键要：

- 高基数
- 分布均匀
- 查询常带
- 不频繁变
- 能支持租户隔离

时间作为唯一前缀容易让“最新分片”成为热点；需要结合 hash/租户/桶。

## 4. 路由

两种方式：

- 应用层路由：代码知道分片规则
- 中间件代理：对应用透明

应用层：

- 灵活
- 但每个服务都要实现路由
- 规则变更要发版

中间件：

- 统一
- 但多一层网络/运维/故障
- SQL 兼容性有限

逻辑分片：

```text
逻辑 shard 1024 → 物理库 4 个
扩容时搬逻辑 shard，不改 key 哈希
```

逻辑分片要预留足够数量，避免未来再改路由。

## 5. 跨分片查询和事务

分片后：

- 跨分片 join 变贵/不可用
- 聚合要 scatter-gather
- 排序/分页要归并
- 全局唯一 ID 要单独设计
- 跨分片事务要避免

常见方案：

- 按查询维度冗余读模型
- 全局索引/搜索
- 汇总表
- Saga/Outbox/补偿
- 接受最终一致

不要假设单库事务还能用。

## 6. 全局 ID

分片后自增 ID 不唯一：

- Snowflake/ULID
- 号段模式
- 数据库序列 + 步长
- UUID（注意索引/可读性）

ID 要：

- 全局唯一
- 大致有序（利于索引）
- 不泄露业务量/顺序（按需）
- 时钟回拨/机器 ID 要处理

## 7. 扩容和迁移

步骤：

1. 选新分片规则/逻辑分片
2. 双写/CDC
3. 历史数据回填
4. 新旧对比/校验
5. 读灰度
6. 写切换
7. 旧库下线

要点：

- 限速，别打垮源库
- 断点续跑/幂等
- 行数/checksum/抽样校验
- 保留回滚窗口
- 迁移期间路由要一致

分片迁移和哈希算法见[复制、分区与热点](../distributed/02-复制分区与热点.md)。

## 8. 读写分离的故障

- 从库延迟 → 旧读
- 从库挂 → 读失败/切主
- 主库挂 → 选主/脑裂
- 读路由把写后读打到从库
- 复制中断 → 从库长期落后
- 备份/恢复要覆盖所有分片

监控：

- 复制延迟（秒/字节/LSN）
- 从库错误/重连
- 主从切换
- 每分片 QPS/延迟/容量
- 跨分片查询比例

## 9. 实验：副本延迟

写后读从库，lag=2s/5s：

??? note "代码：写后读是否可见"
    ```python
    def visible(write_at, read_at, lag):
        return read_at >= write_at + lag


    if __name__ == "__main__":
        cases = [
            (0, 1, 2),
            (0, 3, 2),
            (10, 12, 5),
            (10, 15, 5),
        ]
        for write_at, read_at, lag in cases:
            print(f"write={write_at} read={read_at} lag={lag} "
                  f"visible={visible(write_at, read_at, lag)}")
    ```

输出：

```text
write=0 read=1 lag=2 visible=False
write=0 read=3 lag=2 visible=True
write=10 read=12 lag=5 visible=False
write=10 read=15 lag=5 visible=True
```

读法：

- 写后 1s 读，lag 2s：看不到
- 写后 3s 读：看得到
- 写后 2s 读，lag 5s：看不到
- 这不是“复制坏了”，是异步复制的正常旧读
- 真实系统要看 LSN/GTID/版本，不只看时间

## 10. 检查清单

- 真的需要分片/读写分离吗？
- 分区键/路由规则是什么？
- 跨分片查询/事务怎么办？
- 全局 ID 怎么生成？
- 逻辑分片够不够？
- 迁移/回填/校验/回滚做了吗？
- 读己之写怎么保证？
- 复制延迟/从库故障怎么处理？
- 备份/恢复覆盖所有分片吗？
- 每分片容量/延迟有监控吗？

## 11. 常见坑

1. **表大就分**
   先看索引/归档/缓存/容量，不是行数本身。

2. **分片键低基数**
   分片倾斜，热点集中。

3. **跨分片 join**
   查询放大，延迟不可控。

4. **忘记全局 ID**
   自增 ID 冲突。

5. **逻辑分片太少**
   扩容只能改路由，迁移量爆炸。

6. **读写分离不做读己之写**
   用户刚写完看不到。

7. **把从库当强一致**
   异步复制就是可能旧读。

8. **迁移不限速**
   回填打垮主库。

9. **没有校验/回滚**
   数据搬一半，无法确认。

10. **备份只备主库/单分片**
    恢复不完整。

## 12. 要点回顾

1. 读写分离扩读，分库分表扩容量/写，问题不同
2. 先确认单库瓶颈，不要因表大就分
3. 分区键要高基数、均匀、符合查询
4. 路由可应用层/中间件；逻辑分片留余量
5. 跨分片查询/事务/全局 ID 要单独设计
6. 迁移要双写/回填/校验/灰度/回滚
7. 读写分离有复制延迟和读己之写问题
8. 从库/主库故障、复制中断要监控
9. 备份恢复要覆盖所有分片
10. 分片是复杂度跃迁，不是默认优化
