# 秒杀系统

秒杀的核心不是“把接口做快”，而是：

```text
有限库存 + 高并发 + 不能超卖 + 不能拖垮系统
```

它同时考验入口限流、库存一致性、队列、幂等、支付超时和降级。

## 1. 需求

### 功能

- 活动开始/结束
- 查看商品/库存
- 抢购/预占库存
- 创建订单
- 支付/取消
- 超时释放库存
- 防重复购买

### 非功能

| 维度 | 目标 |
|---|---|
| 峰值 | 10 万 QPS（示例） |
| 库存 | 1 万件（示例） |
| 正确性 | 不超卖、不重复扣减 |
| 延迟 | 抢购 p95 < 500ms |
| 可用性 | 入口可降级，不拖垮其他业务 |
| 公平 | 每用户限购、防刷 |
| 一致性 | 库存强一致；订单/支付可最终一致 |

非目标：

- 第一版不做复杂排队公平性
- 不做跨地域强一致
- 不做预售/尾款

## 2. 总体流程

```text
活动页
  → 入口限流/防刷
  → 资格校验（登录/实名/限购）
  → 预占库存
  → 创建订单
  → 支付
  → 超时取消/释放库存
```

关键原则：

- 库存扣减是核心，不能用缓存“看起来对”
- 订单创建可以异步，但预占必须可靠
- 支付成功/失败要能对账
- 任何一步超时都要可恢复

## 3. 库存

库存是正确性核心：

- 不能先查再减（竞态）
- 不能只信缓存
- 不能扣了库存没订单/没支付

方案：

1. **DB 条件更新**作为最终真相

```sql
UPDATE stock
SET available = available - 1
WHERE item_id = ? AND available > 0;
```

检查 affected rows：

- 1：预占成功
- 0：库存不足/已抢完

2. **Redis 原子预扣**做入口闸门

- `DECR`/Lua 原子扣减
- 成功才进 DB
- Redis 与 DB 对账/补偿

3. **预占记录**

- `reservation_id`
- 用户/商品/状态/过期时间
- 唯一约束防重复

库存扣减和订单创建要幂等；失败要对账。

## 4. 实验：超卖

两个请求同时看到 stock=1：

??? note "代码：先查再减 vs 条件更新"
    ```python
    def naive():
        stock = 1
        accepted = 0
        read_a = stock
        read_b = stock
        stock = read_a - 1
        accepted += 1
        stock = read_b - 1
        accepted += 1
        return stock, accepted


    def atomic():
        stock = 1
        accepted = 0
        for _ in range(2):
            if stock > 0:
                stock -= 1
                accepted += 1
        return stock, accepted


    if __name__ == "__main__":
        s, a = naive()
        print(f"naive: stock={s} accepted={a} oversold={a > 1}")
        s, a = atomic()
        print(f"atomic: stock={s} accepted={a} oversold={a > 1}")
    ```

输出：

```text
naive: stock=0 accepted=2 oversold=True
atomic: stock=0 accepted=1 oversold=False
```

读法：

- naive：两个请求都基于 stock=1 扣减，卖出 2 件
- atomic：条件更新只允许 1 个成功
- 这是并发交错示意，不是数据库压测
- 真实系统用唯一约束/条件更新/事务保证，不靠应用层“先查”

## 5. API

## 6. 队列和异步

抢购成功后：

```text
reserve → queue → order worker → order created
```

优点：

- 削峰
- 订单创建与库存解耦
- 可重试

风险：

- 队列积压 → 用户等待
- 重复消费 → 重复订单
- 消息丢失 → 有库存没订单
- worker 失败 → 预占卡住

必须：

- 队列有界
- 幂等/去重
- DLQ/对账
- 超时释放

## 7. 支付和超时

- 预占有 TTL
- 未支付超时释放
- 支付成功要幂等确认
- 支付回调可能重复/乱序
- 晚到支付要退款/人工
- 取消/释放也要幂等

状态机：

```text
reserved → ordered → paid
reserved → expired/cancelled
paid → refunded
```

不要用多个布尔字段表示状态。

## 8. 入口和防刷

- 活动页静态化/CDN
- 入口限流（用户/IP/设备/租户）
- 验证码/风控
- 每用户限购
- 库存查询与抢购分离
- 排队/令牌
- 超时/取消

防刷不是只靠 IP；NAT/代理会误伤。设备/账号/行为/风控一起看。

## 9. 缓存

- 商品详情/静态资源：CDN/缓存
- 库存：缓存只做展示/闸门，不作为最终真相
- 用户资格：短 TTL/本地缓存
- 热点商品：本地缓存/独立池

缓存挂/脏数据不能让库存超卖。

## 10. 失败模式

| 失败 | 行为 |
|---|---|
| Redis 挂 | 降级到 DB 条件更新/限流；不要放行无库存 |
| DB 挂 | 停止预占/返回 503；不要超卖 |
| 队列积压 | 限流/排队/提示；监控 lag |
| 重复请求 | 幂等键/唯一约束 |
| 支付超时 | 释放/对账 |
| 支付回调重复 | 幂等确认 |
| 预占过期 | 释放库存 |
| 热点商品 | 独立池/限流/隔离 |
| 超卖 | 立即停止、对账、补偿/退款 |

## 11. SLO

- 预占 p95 < 500ms
- 错误率 < 0.1%
- 库存对账差异 = 0
- 队列 lag < 阈值
- 支付确认延迟
- 活动页可用性

错误预算/告警参考[可观测性与 SLO](../operations/01-可观测性与SLO.md)。

## 12. 演进

1. 单库条件更新
2. Redis 预扣 + DB 对账
3. 队列削峰
4. 热点商品独立池
5. 多活动隔离
6. 多地域按需

不要第一版就上复杂分布式事务；库存正确性优先。

## 13. ADR

### ADR-1：DB 条件更新作为最终真相

```text
Context：库存不能超卖
Decision：DB 条件更新/唯一约束保证最终扣减
Consequences：强一致；DB 是热点/瓶颈
Alternatives：只信 Redis，性能好但一致性风险
Revisit：DB 容量成为瓶颈时加预扣/分片
```

### ADR-2：预占 + 异步订单

```text
Context：峰值高，订单创建可异步
Decision：预占库存，队列创建订单
Consequences：削峰；需幂等/对账/超时释放
Alternatives：同步创建订单，链路长/易超时
Revisit：队列延迟不可接受
```

## 14. 检查清单

- 库存扣减原子吗？
- 有预占/唯一约束/状态机吗？
- 重复请求幂等吗？
- 队列有界/幂等/DLQ 吗？
- 支付超时/回调重复怎么处理？
- 入口限流/防刷/限购？
- 缓存会不会导致超卖？
- 失败时停止还是降级？
- 对账/补偿能跑吗？
- SLO/告警就绪吗？

## 15. 常见坑

1. **先查库存再减**
   并发下超卖。

2. **只信 Redis**
   缓存丢/不一致就超卖。

3. **扣库存和订单不在同一可靠性边界**
   有库存没订单/有订单没库存。

4. **重复请求**
   重复下单/重复扣减。

5. **支付回调重复**
   重复发货/重复记账。

6. **队列无界**
   积压拖垮系统。

7. **超时释放不幂等**
   释放两次/负库存。

8. **缓存库存当真相**
   展示可以，扣减不行。

9. **没有对账**
   超卖/漏单只能等投诉。

10. **活动不隔离**
   一个热点拖垮全站。

## 16. 要点回顾

1. 秒杀核心是库存正确性 + 过载保护
2. 条件更新/唯一约束保证不超卖
3. Redis 可做预扣闸门，但 DB 是最终真相
4. 预占 + 异步订单削峰，但要幂等/对账/超时释放
5. 支付回调重复/乱序要幂等
6. 入口限流/防刷/限购
7. 缓存库存只能展示/闸门，不能当真相
8. 失败时宁可停止预占，不要超卖
9. 对账/补偿/演练是闭环
10. 活动隔离，避免热点拖垮全站
