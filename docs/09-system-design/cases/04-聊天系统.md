# 聊天系统

聊天系统看起来只是“发消息、收消息”，真正的难点是：

- 长连接和断线重连
- 消息顺序/去重
- 离线/多设备同步
- 群聊 fanout
- 已读/在线状态
- 存储和热群

## 1. 需求

### 功能

- 1:1 聊天
- 群聊
- 消息历史
- 离线消息
- 多设备同步
- 已读回执（可选）
- 在线状态（可选）
- 附件/图片

### 非功能

| 维度 | 目标 |
|---|---|
| 发送延迟 | p95 < 200ms |
| 投递 | 至少一次 + 客户端去重 |
| 顺序 | 会话内有序 |
| 可用性 | 99.9% |
| 规模 | 1000 万 DAU，5000 万消息/天 |
| 并发连接 | 100 万（示例） |
| 存储 | 消息长期保留（按业务） |
| 安全 | 会话成员/拉黑/防滥用 |

非目标：

- 第一版不做端到端加密（按产品定）
- 不做全局消息顺序
- 不做复杂推荐
- 不做跨地域强一致

## 2. 容量

示例假设：

```text
DAU = 10,000,000
messages/day = 50,000,000
avg message = 300 B
concurrent connections = 1,000,000
connections per gateway = 50,000
peak factor = 3
```

粗算：

| 指标 | 结果 |
|---|---:|
| 平均消息 QPS | 578.7 |
| 峰值消息 QPS | 1736.1 |
| 1 年原始消息 | 约 5.5 TB |
| 3 副本 + 索引 | 约 21 TB |
| 网关数（100 万连接） | 20（N+1=21） |

计算口径：1 年消息 = 50M/天 × 365 × 300 B ≈ 5.5 TB；按 3 副本、索引/开销 1.3× 估算 ≈ 21 TB。

附件/图片走对象存储，不塞消息表。

## 3. 总体结构

```text
Client
  → WebSocket Gateway（长连接）
  → Message Service
  → Conversation/Storage
  → Fanout / Push
```

模块：

- Gateway：连接、鉴权、心跳、背压
- Message：写入、序号、持久化
- Conversation：成员、权限、未读
- Fanout：群聊/多设备分发
- Push：离线通知
- Presence：在线状态（可独立/可丢）

## 4. 消息流程

发送：

```text
client_temp_id
  → gateway
  → message service
  → assign message_id + conversation_seq
  → persist
  → ack to sender
  → fanout to recipients/devices
```

原则：

- 先持久化再 ack
- 会话内分配 seq
- 客户端用 temp_id 去重
- fanout 失败可重试，不阻塞发送者 ack
- 离线用户走 push/离线队列

## 5. 顺序和 ID

- 全局顺序很贵；只保证**会话内顺序**
- 服务端分配 `conversation_seq`（每会话单调）
- 消息 ID 全局唯一（ULID/Snowflake/复合）
- 客户端按 seq 排序
- 重复消息按 message_id/seq 去重

不要用客户端时间排序；时钟不可靠。

## 6. 断线重连

客户端保存：

```text
last_seq per conversation
```

重连：

```text
拉取 last_seq 之后的消息
→ 去重/排序
→ 发现缺口则补拉
```

实验：

??? note "代码：重连去重/缺口检测"
    ```python
    def sync(last_seq, incoming, server_latest):
        seen = set()
        ordered = []
        duplicates = 0
        for seq in sorted(incoming):
            if seq <= last_seq:
                continue
            if seq in seen:
                duplicates += 1
                continue
            seen.add(seq)
            ordered.append(seq)
        missing = [s for s in range(last_seq + 1, server_latest + 1) if s not in seen]
        return ordered, duplicates, missing


    if __name__ == "__main__":
        ordered, dup, missing = sync(10, [12, 11, 12, 14, 13], 15)
        print(f"ordered={ordered} duplicates={dup} missing={missing}")
    ```

输出：

```text
ordered=[11, 12, 13, 14] duplicates=1 missing=[15]
```

读法：

- 收到 12/11/12/14/13：排序、去重后 11-14
- 服务端最新 15，客户端缺 15，需要补拉
- 这是客户端同步示意，不是网络/存储压测
- 真实系统用游标/快照/服务端确认

## 7. 投递语义

- 至少一次：可能重复
- 客户端/服务端去重
- 发送方 ack 表示“服务端已持久化”，不表示对方已读
- 接收方 ack 表示“设备已收到/处理”
- 离线消息补投
- 多设备各自游标

不要承诺“恰好一次”而不做幂等。

## 8. 群聊 fanout

群消息要发给：

- 群成员
- 多设备
- 在线/离线

策略：

- 小群：直接 fanout
- 大群：读扩散/频道/拉取
- 在线设备走 gateway
- 离线走 push/离线队列
- 大群/热点群单独限流/隔离

群成员变化、禁言、拉黑要影响后续可见性。

## 9. 存储

```text
messages(
  conversation_id, seq, message_id,
  sender_id, type, body, created_at,
  primary key(conversation_id, seq)
)

conversation_member(
  conversation_id, user_id, role, joined_at
)

device_cursor(
  user_id, device_id, conversation_id, last_seq
)
```

- 消息按会话分区，按 seq 排序
- 附件存对象存储，消息存 URL/元数据
- 未读数/已读游标单独存
- 热群分片/独立存储
- 历史消息分页用 seq/cursor

参考[数据建模与存储选型](../data/01-数据建模与存储选型.md)和[分库分表与读写分离](../data/02-分库分表与读写分离.md)。

## 10. 在线/已读

- Presence 是易失状态，可接受短暂不准
- 已读回执按会话/设备游标
- 不要为每条消息写“已读”一行
- 多设备要合并/取最大已读 seq
- 隐私设置控制是否展示

## 11. 安全

- 连接鉴权、token 过期/刷新
- 会话成员校验
- 拉黑/禁言/举报
- 消息/附件内容扫描
- 限流/防刷
- 不信任客户端 sender_id/conversation_id
- 日志脱敏
- E2EE 则服务端不能读内容，搜索/审核要另设计

参考[安全与多租户](../architecture/04-安全与多租户.md)。

## 12. 失败模式

| 失败 | 行为 |
|---|---|
| gateway 断 | 重连、补拉、去重 |
| 消息重复 | 客户端/服务端去重 |
| 消息乱序 | 按 seq 排序 |
| 消息缺口 | 补拉/快照 |
| 离线 | push/离线队列 |
| 群 fanout 慢 | 限流/隔离/读扩散 |
| 存储热群 | 分片/独立池 |
| push 失败 | 重试/降级 |
| 已读丢失 | 可接受/重建 |
| 附件失败 | 重试/单独状态 |

## 13. SLO

- 发送 p95 < 200ms
- 在线投递 p95 < 1s
- 消息持久化成功率
- 重连同步成功率
- 群 fanout lag
- push 成功率
- 错误预算/告警

参考[可观测性与 SLO](../operations/01-可观测性与SLO.md)。

## 14. 演进

1. 单 Gateway + 单 Message 服务
2. Gateway 水平扩展/连接路由
3. 消息按会话分片
4. 群聊 fanout 独立
5. 热群隔离/读扩散
6. 多地域按需

## 15. ADR

### ADR-1：会话内顺序

```text
Context：全局顺序成本高，用户只关心会话内顺序
Decision：每会话 seq，客户端按 seq 排序
Consequences：简单；跨会话不保证顺序
Alternatives：全局序列，成本高
Revisit：跨会话顺序成为业务需求
```

### ADR-2：至少一次 + 去重

```text
Context：网络/重连会重复
Decision：至少一次投递，客户端 temp_id/seq 去重
Consequences：实现简单；需去重状态
Alternatives：追求 exactly-once，复杂
Revisit：重复率/成本不可接受
```

## 16. 检查清单

- 会话内顺序怎么分配？
- 客户端如何去重/排序/补缺口？
- 离线/多设备怎么同步？
- 群聊 fanout/大群怎么处理？
- 消息/附件存储怎么分片？
- 已读/在线状态一致性？
- 鉴权/成员/拉黑/限流？
- 失败时重连/补拉/降级？
- SLO/告警？
- 演进触发条件？

## 17. 常见坑

1. **客户端时间排序**
   时钟不准，消息乱序。

2. **全局顺序**
   成本高，通常不需要。

3. **ack 当对方已读**
   发送 ack 只代表服务端收到。

4. **不去重**
   重连/重试导致重复消息。

5. **缺口不补**
   用户永久丢消息。

6. **群聊全量 fanout**
   大群写放大。

7. **热群不隔离**
   一个群拖垮全站。

8. **已读每条写一行**
   存储爆炸。

9. **信任客户端 sender_id**
   冒充/越权。

10. **附件塞消息表**
    大对象拖慢消息存储。

## 18. 要点回顾

1. 聊天核心是长连接、会话内顺序、去重、离线同步
2. 只保证会话内 seq，不追求全局顺序
3. 先持久化再 ack；fanout 可异步
4. 至少一次 + 客户端去重；ack 不等于已读
5. 重连按 last_seq 补拉，检测缺口
6. 群聊 fanout 要按规模/热度分化
7. 消息按会话分片；附件走对象存储
8. 在线/已读是易失状态，别当强一致
9. 鉴权/成员/拉黑/限流是消息可见性的一部分
10. 热群隔离和演进触发条件要提前设计
