# 入口与负载均衡

用户请求进入系统时，先经过入口层：

```text
DNS → Anycast/云 LB → L4/L7 负载均衡 → 网关 → 服务
```

入口层决定：

- 请求落到哪个机房/集群/实例
- TLS 在哪里终止
- 认证/限流在哪里做
- 灰度/回滚怎么切
- 故障时怎么摘除节点

它不只是“Nginx 配一下”。

## 1. L4 和 L7

| 层 | 看什么 | 能做 | 不能做 |
|---|---|---|---|
| L4 | IP/端口/TCP/UDP | 连接转发、简单健康检查 | 看 HTTP path/header |
| L7 | HTTP/gRPC/header/path | 路由、TLS、鉴权、限流、灰度 | 不感知业务语义 |

选择：

- 纯 TCP/UDP、数据库代理、超高性能：L4
- HTTP API、gRPC、灰度、按 path 路由：L7
- 很多系统是 L4 + L7 组合

不要用 L7 网关做所有事情；它会变成新的单体。

## 2. 负载均衡算法

| 算法 | 适合 | 风险 |
|---|---|---|
| 轮询 | 实例同质 | 不感知负载/慢节点 |
| 加权轮询 | 实例容量不同 | 权重需要维护 |
| 最少连接 | 长连接/请求时长差异大 | 需要准确连接状态 |
| 一致性哈希 | 缓存亲和/分片 | 热点、迁移 |
| EWMA/延迟感知 | 尾延迟敏感 | 实现复杂、可能震荡 |

没有“最好算法”：

- 无状态短请求：轮询/加权通常够
- 长连接/慢请求：最少连接更合适
- 缓存亲和：一致性哈希，但小心热点
- 尾延迟敏感：延迟感知 + 最少连接，配合熔断

## 3. 健康检查

健康检查决定节点是否接流量。

- 浅检查：端口/进程活着
- 深检查：依赖数据库/缓存/下游
- 就绪/存活分开
- 检查间隔/超时/阈值
- 失败摘除、恢复加回
- 连接 draining

坑：

- 深检查把下游故障放大成全站摘除
- 检查太敏感，节点反复上下线
- 摘除太慢，请求继续打到坏节点
- 恢复太急，冷节点被瞬间打满

健康检查要和生产流量隔离，避免检查本身压垮服务。

## 4. 网关

网关负责入口策略：

- 路由/路径重写
- TLS 终止/证书
- 认证/租户识别
- 限流/配额
- 灰度/Canary
- 请求大小/超时
- 访问日志/trace
- WAF/DDoS 防护

不要放：

- 业务规则
- 跨服务事务
- 复杂数据聚合
- 每个接口的定制逻辑

网关是策略执行点，不是业务服务。

### 重试

入口层重试要非常谨慎：

- 只重试幂等请求
- 有次数/时间上限
- 不要对写请求盲目重试
- 重试会放大下游负载

重试细节见故障/恢复文章。

## 5. 高可用

- LB 本身不能是单点
- 多可用区/多实例
- VIP/Anycast/DNS 故障切换
- 健康检查 + 连接 draining
- 配置/证书变更可回滚
- 容量按峰值 + N+1

DNS 故障切换受 TTL 影响，不是瞬时；Anycast 也不是“自动全局一致”。

## 6. 连接和会话

- keep-alive 减少握手，但要注意空闲超时
- HTTP/2/gRPC 多路复用，注意流控
- 长连接要限制每实例连接数
- 发布时 connection draining
- 尽量无状态；需要会话用共享存储
- sticky session 会破坏扩缩容/故障转移，非必要不用

## 7. 安全

- TLS 终止后，内部是否重新加密按威胁模型定
- 不信任客户端传来的 `X-Forwarded-For`/tenant/role
- 只信可信代理追加的头
- 限制请求体/header/URL 长度
- 防请求走私：规范化和超时
- WAF 不是全部安全
- 证书/密钥轮换
- 每租户限流/配额
- 日志脱敏

入口是攻击面最大的地方之一，默认拒绝、最小暴露。

## 8. 观测

按路由/上游/租户看：

- QPS、4xx/5xx、超时
- p95/p99、上游延迟
- 连接数/队列/饱和度
- 健康检查状态
- 限流/拒绝
- 证书过期
- 灰度版本差异

只有全局平均会掩盖某条路由/某个上游的问题。

## 9. 选型卡

| 选项 | 适合 | 代价 |
|---|---|---|
| Nginx | 通用反向代理、成熟 | 动态配置/扩展要方案 |
| Envoy | L7、可观测、服务网格 | 配置复杂、运维成本 |
| 云 LB | 托管、弹性、多 AZ | 锁定、成本、功能边界 |
| API Gateway | 认证/限流/API 管理 | 容易变重、延迟 |
| 服务网格 | 服务间 mTLS/流量治理 | 复杂度高 |

选型看：

- L4/L7 需求
- 动态路由/灰度
- 认证/限流
- 可观测
- 多租户
- 成本/锁定
- 团队运维能力

## 10. 检查清单

- L4 还是 L7？需要看 path/header 吗？
- LB 算法和流量形态匹配吗？
- 健康检查浅/深怎么选？
- 发布时 connection draining 吗？
- 网关会不会变成业务单体？
- 重试幂等/上限了吗？
- 入口是否多 AZ/无单点？
- TLS/证书/密钥怎么轮换？
- 转发头/租户/角色可信吗？
- 每路由/上游/租户有指标吗？

## 11. 常见坑

1. **LB 当性能银弹**
   后端慢，LB 只会把慢请求分得更均匀。

2. **L7 网关塞业务**
   路由、鉴权、聚合、事务全放进去，变成新单体。

3. **健康检查太深**
   下游一抖，全部节点被摘。

4. **发布不 draining**
   连接被硬断，用户看到 502。

5. **盲目重试**
   入口重试放大下游故障。

6. **信任 X-Forwarded-For**
   客户端伪造 IP/租户。

7. **sticky session 当默认**
   扩缩容/故障转移变难。

8. **只监控全局 QPS**
   某路由/上游已经挂了，平均看不出来。

9. **证书过期无告警**
   入口全站不可用。

10. **单 LB/单 AZ**
    入口层自己成为单点。

## 12. 要点回顾

1. 入口是 DNS/Anycast/L4/L7/网关的组合，不是一个 Nginx
2. L4 看连接，L7 看 HTTP；按需求选
3. LB 算法要匹配流量形态，没有通用最优
4. 健康检查要浅/深结合，避免放大故障
5. 网关做策略，不做业务单体
6. 入口重试必须幂等、有上限
7. 高可用要覆盖 LB 自身、AZ、证书和配置
8. 连接 draining/sticky session/keep-alive 会影响发布
9. 入口是攻击面，转发头/租户/证书都要防
10. 按路由/上游/租户观测，不能只看全局平均
