# 消息队列与异步

队列常被当成“削峰神器”，但它不创造处理能力：

```text
到达 > 消费能力 → 积压
到达 < 消费能力 → 队列变短
```

队列能做的是：

- 解耦生产/消费
- 缓冲短时峰值
- 异步重试
- 广播/多消费者
- 削峰填谷

不能做的是：

- 让下游凭空变快
- 保证 exactly-once
- 自动解决重复/顺序/毒消息

## 1. 队列模型

| 类型 | 例子 | 适合 | 注意 |
|---|---|---|---|
| Broker | RabbitMQ、SQS | 任务分发、重试、路由 | ack/可见性/重复 |
| Log | Kafka、Pulsar | 高吞吐、回放、多消费者 | 分区/offset/保留期 |
| 云队列 | SQS、Pub/Sub | 托管、弹性 | 语义/成本/锁定 |

Broker 更像“任务队列”；log 更像“可回放的事件流”。选型看消费模式，不是只看吞吐。

## 2. 投递语义

| 语义 | 含义 | 现实 |
|---|---|---|
| At-most-once | 最多一次 | 可能丢 |
| At-least-once | 至少一次 | 可能重复 |
| Exactly-once | 恰好一次 | 端到端很难，通常靠幂等 |

“Exactly-once”在跨系统时通常不是免费保证。常见做法：

```text
at-least-once + 幂等消费 + 去重表
```

消费者必须处理重复：

- 业务唯一键
- 消息 ID + 去重表
- 状态机/条件更新
- 保留期/清理

## 3. 顺序和分区

全局顺序很贵；通常是分区内有序：

```text
key → partition → 单消费者顺序处理
```

风险：

- 同一 key 必须落同一分区
- 分区数决定并行度
- 热点 key 会压住一个分区
- rebalance 会暂停/迁移消费
- 多消费者不能保证全局顺序

需要顺序时，先问：

- 真的需要全局顺序吗？
- 还是同一订单/用户/租户有序就够？

## 4. 背压和队列边界

队列不是无限缓冲：

- 队列有上限/保留期
- 积压会增加延迟和存储
- 消费者慢时，生产者要继续写还是拒绝？
- 没有背压，内存/磁盘会爆

策略：

- 限制队列长度/保留时间
- 生产者限流/阻塞
- 消费者扩缩容
- 降级/丢弃非关键消息
- 监控 lag/age

## 5. 消费者组和扩缩容

- 分区数 ≥ 消费者数才有并行度
- 消费者多于分区，多出来的空闲
- rebalance 期间可能重复/暂停
- 扩消费者不一定线性提升
- 下游 DB/API 可能才是瓶颈

不要只看队列消费 TPS；看端到端延迟和下游承载。

## 6. 重试、死信、毒消息

- 可重试错误：超时/限流/5xx
- 不可重试：参数/权限/业务拒绝
- 重试要 backoff + 上限
- 毒消息进 DLQ，人工/自动修复
- DLQ 也要监控/保留/重放
- 重试可能放大下游故障

消息处理要幂等；否则重试会重复写。

## 7. Outbox 和事件一致性

业务写和发消息不能简单“写完再发”：

```text
DB commit 成功，消息发送失败 → 事件丢失
```

Outbox：

```text
本地事务写业务 + outbox
relay 读 outbox 发消息
消费者幂等
```

这保证“业务成功则事件最终会发”，但不是 exactly-once。细节见[一致性与事务](../distributed/04-一致性与事务.md)。

## 8. 事件还是命令

- **命令**：去做一件事，通常一个消费者
- **事件**：已经发生的事实，可以多消费者

事件命名用过去式：

```text
OrderCreated
PaymentCaptured
ShipmentDelivered
```

事件要版本化；消费者要能忽略未知字段/兼容旧版本。

## 9. 实验：队列积压

到达 120 QPS，单消费者 50 QPS，观察 60 秒：

??? note "代码：到达率 vs 消费能力"
    ```python
    def simulate(arrival_qps, service_qps_per_consumer, consumers, seconds):
        capacity = service_qps_per_consumer * consumers
        backlog = 0.0
        max_backlog = 0.0
        for _ in range(seconds):
            backlog += arrival_qps
            served = min(backlog, capacity)
            backlog -= served
            max_backlog = max(max_backlog, backlog)
        return capacity, backlog, max_backlog


    if __name__ == "__main__":
        arrival = 120
        service = 50
        seconds = 60
        print(f"arrival={arrival} qps service={service} qps/consumer window={seconds}s")
        print("consumers  capacity  backlog_end  backlog_max")
        for consumers in [2, 3, 4]:
            capacity, end, peak = simulate(arrival, service, consumers, seconds)
            print(f"{consumers:9d}  {capacity:8.0f}  {end:11.0f}  {peak:11.0f}")
    ```

输出：

```text
arrival=120 qps service=50 qps/consumer window=60s
consumers  capacity  backlog_end  backlog_max
        2       100         1200         1200
        3       150            0            0
        4       200            0            0
```

读法：

- 2 个消费者：容量 100 < 120，60 秒积压 1200
- 3 个消费者：容量 150 > 120，队列不增长
- 队列不会自己变快；加消费者/限流/降级才是办法
- 如果有初始积压，即使容量足够，也需要时间排空
- 这是合成模型，不是实际 broker 压测

## 10. 观测

- 生产速率/消费速率
- lag（消息数/时间）
- 最老消息年龄
- 重试/DLQ 数量
- 消费者错误/超时
- 分区倾斜/热点
- 端到端延迟
- 下游 DB/API 饱和度

只看队列长度不够；要看 lag 的增长趋势和下游承载。

## 11. 选型卡

| 选项 | 适合 | 注意 |
|---|---|---|
| Kafka | 高吞吐、回放、多消费者 | 分区/运维/保留 |
| RabbitMQ | 路由、任务、灵活 ack | 积压/集群 |
| SQS | 托管、简单任务 | 语义/可见性/成本 |
| Pub/Sub | 云原生广播 | 顺序/重复/锁定 |

选型看：

- 吞吐/延迟
- 顺序/分区
- 回放/保留
- 投递语义
- 运维/成本
- 云锁定

## 12. 检查清单

- 队列解决解耦还是削峰？
- 到达率/消费能力算过吗？
- 需要顺序吗？范围多大？
- 分区数/消费者数匹配吗？
- 重复怎么幂等？
- 毒消息/DLQ 怎么处理？
- 队列有上限/保留期吗？
- 生产/消费/下游谁先瓶颈？
- lag/age/重试有监控吗？
- 队列挂了怎么降级？

## 13. 常见坑

1. **把队列当容量**
   到达 > 消费，积压只会增长。

2. **以为 exactly-once 免费**
   跨系统通常靠幂等。

3. **消费者不幂等**
   重试/重复投递导致重复写。

4. **分区数不够**
   加消费者也没有并行度。

5. **热点 key 压一个分区**
   其他分区空闲，整体吞吐上不去。

6. **队列无界**
   积压吃存储，延迟失控。

7. **毒消息无限重试**
   阻塞分区/消费者。

8. **DLQ 不监控**
   坏消息永久躺着。

9. **只看队列长度**
   不看 lag 增长/最老消息年龄。

10. **忽略下游瓶颈**
   消费者扩了，DB 先挂。

## 14. 要点回顾

1. 队列解耦/缓冲/异步，不创造处理能力
2. 到达率 > 消费能力，积压增长；加消费者/限流/降级
3. at-least-once 是常态，exactly-once 靠幂等
4. 顺序通常只保证分区内；key 决定分区
5. 分区数限制并行度，热点 key 会倾斜
6. 队列要有界/保留期/背压
7. 重试要 backoff/上限，毒消息进 DLQ
8. Outbox 解决业务+事件不丢，但仍至少一次
9. 监控 lag/age/重试/DLQ/下游饱和度
10. 队列不是瓶颈的终点，下游才是
