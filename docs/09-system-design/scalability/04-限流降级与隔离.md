# 限流、降级与隔离

三件事经常被混在一起：

- **限流**：限制进入系统的请求速率
- **降级**：系统过载/依赖故障时，少做一点、返回旧数据或关闭非关键功能
- **隔离**：让一个租户/依赖/功能出问题时不拖垮其他部分

限流保护入口，降级保护体验，隔离保护爆炸半径。

## 1. 限流不是容量

限流不能把 100 QPS 的后端变成 1000 QPS：

- 它只是拒绝/排队一部分请求
- 拒绝太晚，系统已经过载
- 限流阈值要按真实容量设
- 下游 DB/第三方可能先成为瓶颈

限流的目标：

- 保护系统不被打挂
- 公平分配（租户/用户/API）
- 防滥用/刷接口
- 给付费/关键流量优先级

## 2. 常见算法

| 算法 | 特点 | 风险 |
|---|---|---|
| 固定窗口 | 简单、计数 | 窗口边界双倍突发 |
| 滑动窗口日志 | 精确 | 内存/清理成本 |
| 滑动窗口计数 | 近似、内存低 | 边界误差 |
| 令牌桶 | 允许突发，按速率补充 | 参数要调 |
| 漏桶 | 平滑输出 | 突发被排队/丢弃 |

固定窗口例子：

```text
每分钟 100 次
59 秒打 100 次，61 秒再打 100 次
跨窗口 2 秒内实际 200 次
```

令牌桶：

```text
capacity=10, rate=1/s
初始最多 10 个突发，之后按 1/s 补充
```

## 3. 限流键和范围

按什么限：

- 用户
- 租户
- API key
- IP
- 路由/接口
- 模型/任务类型
- 全局/集群/单机

注意：

- NAT/代理后面很多用户共享 IP，按 IP 会误伤
- 租户配额和用户限流要分开
- 关键接口和普通接口阈值不同
- 读/写/昂贵操作分开
- 限流要返回明确错误和 `Retry-After`

## 4. 分布式限流

| 方式 | 特点 | 代价 |
|---|---|---|
| 单机令牌桶 | 低延迟 | 全局不精确 |
| Redis/中心计数器 | 全局较准 | 网络/热点/故障 |
| 分片/单元限流 | 横向扩展 | 聚合误差 |
| 网关限流 | 入口统一 | 绕过网关就失效 |

中心限流器本身可能成为瓶颈/单点；要限流它的超时和降级策略。

## 5. 429 和客户端

返回：

```http
429 Too Many Requests
Retry-After: 2
```

客户端要：

- 遵守 `Retry-After`
- 退避 + jitter
- 不要立即疯狂重试
- 幂等请求才重试
- 区分限流和真实错误

服务端不要把限流伪装成 500，否则客户端会重试更多。

## 6. 过载保护

限流之外还要：

- 队列有界
- 快速失败/load shedding
- 优先级队列
- 并发限制
- 连接池/线程池隔离
- 超时/取消
- 自适应限流（按延迟/错误）

过载时最怕“继续收请求 + 无限排队”，最后内存/延迟一起爆。

## 7. 降级

降级要提前定义：

- 返回缓存/旧数据
- 只读模式
- 部分结果
- 关闭非关键功能（推荐/统计/动画）
- 异步化
- 转人工
- 明确错误/状态

降级不是静默返回错数据：

- 旧读可能可接受
- 业务错误不可接受
- 要告诉用户/调用方“现在不完整”
- 降级开关要可观测/可回滚

## 8. 隔离

- 线程池/连接池按依赖隔离
- 队列按租户/优先级隔离
- 大租户独立分片/配额
- 单元化/cell 隔离故障域
- 功能开关隔离非关键路径
- 资源限制（CPU/内存/连接）
- 熔断/舱壁

没有隔离，一个大租户/慢依赖会拖垮所有请求。

## 9. 实验：令牌桶

40 个请求：t=0 20 个，t=1 10 个，t=2 10 个。

??? note "代码：token bucket 接受/拒绝"
    ```python
    def simulate(events, capacity, rate):
        tokens = float(capacity)
        last = 0.0
        accepted = 0
        denied = 0
        trace = []
        for t in sorted(events):
            tokens = min(capacity, tokens + (t - last) * rate)
            last = t
            if tokens >= 1:
                tokens -= 1
                accepted += 1
                trace.append((t, "allow"))
            else:
                denied += 1
                trace.append((t, "deny"))
        return accepted, denied, trace


    if __name__ == "__main__":
        print("events: 20 at t=0, 10 at t=1, 10 at t=2")
        for capacity, rate in [(10, 1.0), (20, 5.0)]:
            accepted, denied, _ = simulate([0] * 20 + [1] * 10 + [2] * 10, capacity, rate)
            print(f"capacity={capacity:2d} rate={rate:.0f}/s -> "
                  f"accepted={accepted} denied={denied}")
    ```

输出：

```text
events: 20 at t=0, 10 at t=1, 10 at t=2
capacity=10 rate=1/s -> accepted=12 denied=28
capacity=20 rate=5/s -> accepted=30 denied=10
```

读法：

- capacity=10, rate=1/s：初始突发 10 个，之后补充很慢，大量拒绝
- capacity=20, rate=5/s：能吸收更大突发，仍会在持续过载时拒绝
- 令牌桶允许突发；漏桶更平滑
- 这是合成模型，不是网关压测

## 10. 观测

- 允许/拒绝数（按 key/租户/路由）
- 429 比例
- 队列长度/等待时间
- 过载时的 p99
- 降级开关状态
- 隔离池使用率
- 下游错误/超时
- 限流器自身延迟/错误

只看总拒绝率不够；要看谁被拒绝、是否误伤关键流量。

## 11. 选型卡

| 场景 | 方案 |
|---|---|
| 单机保护 | 本地令牌桶/并发限制 |
| 入口统一 | 网关限流 |
| 多租户配额 | 中心/分片计数器 |
| 防刷 | IP/用户/设备 + 风控 |
| 过载 | 队列上限 + load shedding |
| 大租户隔离 | 独立池/分片/cell |

## 12. 检查清单

- 限流阈值按真实容量算了吗？
- 按什么 key 限？会误伤吗？
- 固定窗口边界突发考虑了吗？
- 分布式限流器超时/故障怎么降级？
- 429 有 Retry-After 吗？
- 过载时队列有界吗？
- 降级行为明确吗？可回滚吗？
- 租户/依赖/功能隔离了吗？
- 限流/降级/隔离有指标吗？

## 13. 常见坑

1. **限流阈值拍脑袋**
   没按真实容量/下游瓶颈设。

2. **固定窗口边界**
   两倍突发穿过窗口边界。

3. **按 IP 限流误伤**
   NAT 后大量用户共享 IP。

4. **限流返回 500**
   客户端会重试更多。

5. **没有 Retry-After**
   客户端立即重试，继续打爆。

6. **队列无界**
   过载时积压吃内存。

7. **降级静默返回错数据**
   旧读可以，错误事实不可以。

8. **没有隔离**
   一个大租户拖垮全部。

9. **限流器自己成单点**
   中心 Redis 挂了全站拒绝/放行。

10. **只看拒绝率**
    不知道谁被误伤、关键流量是否受影响。

## 14. 要点回顾

1. 限流保护入口，降级保护体验，隔离保护爆炸半径
2. 限流不创造容量；阈值要按真实下游能力
3. 固定窗口有边界突发；令牌桶允许突发；漏桶更平滑
4. 限流 key/范围要避免误伤，按租户/用户/接口分层
5. 分布式限流器有延迟/热点/单点问题
6. 429 要带 Retry-After，客户端要退避
7. 过载要队列有界、快速失败、load shedding
8. 降级行为要明确、可观测、可回滚
9. 隔离要覆盖依赖/租户/功能/故障域
10. 限流/降级/隔离都要有指标和演练
