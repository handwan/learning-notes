# 缓存

缓存不是“加 Redis”。它解决的是：

- 读放大/回源压力
- 热点读延迟
- 后端容量/成本

代价是：

- 一致性/旧读
- 失效/穿透/雪崩
- 内存和运维成本
- 缓存本身成为故障点

缓存一致性/写后失效见[缓存一致性](../data/03-缓存一致性.md)；这里讲机制、命中率和故障。

## 1. 缓存放在哪

| 位置 | 例子 | 适合 | 代价 |
|---|---|---|---|
| 客户端/浏览器 | HTTP cache、ETag | 静态资源、可缓存响应 | 失效控制 |
| CDN | 图片/视频/静态页 | 地理分布、大流量 | 回源/刷新 |
| 本地进程 | Caffeine/Guava/字典 | 极低延迟、小工作集 | 多实例不一致 |
| 分布式缓存 | Redis/Memcached | 共享热数据 | 网络/一致性/运维 |
| 数据库缓存 | buffer pool/物化视图 | 查询加速 | 受 DB 限制 |

多级缓存常见：

```text
本地 → 分布式 → 数据库
```

但层数越多，失效和一致性越难。

## 2. 缓存模式

| 模式 | 读 | 写 | 风险 |
|---|---|---|---|
| Cache-aside | 未命中回源并回填 | 更新 DB + 删缓存 | 旧读/并发回填 |
| Read-through | 缓存层负责回源 | 视实现 | 缓存层复杂 |
| Write-through | 写缓存同时写 DB | 同步 | 写延迟 |
| Write-behind | 先写缓存，异步刷 DB | 快 | 丢数据/顺序 |
| Refresh-ahead | 提前刷新 | 后台 | 预测错误 |

大多数业务先用 cache-aside；写后失效比写后更新更常见，但仍有竞态。

## 3. TTL 和淘汰

- TTL 控制旧数据窗口，不是一致性保证
- TTL 加 jitter，避免同一时间大量过期
- LRU/LFU/FIFO 按访问模式选
- 容量按工作集，不是“越大越好”
- 热 key 可能挤出其他 key
- 需要 warmup，避免冷启动打爆后端

## 4. 四个常见故障

### 穿透

请求不存在的 key，每次都打 DB。

- 缓存空值（短 TTL）
- Bloom filter
- 参数/权限校验
- 限流

### 击穿

热 key 过期，瞬间大量请求回源。

- 互斥重建/单飞
- 逻辑过期 + 后台刷新
- 热点永不过期（配合主动更新）

### 雪崩

大量 key 同时过期/缓存挂掉。

- TTL jitter
- 多级缓存
- 熔断/限流/降级
- 缓存集群多 AZ

### 热 key

单个 key/租户流量远高于平均。

- 本地缓存
- key 分片/加后缀
- 读副本
- 限流/隔离

## 5. 一致性

Cache-aside 常见写法：

```text
读：cache miss → DB → set cache
写：update DB → delete cache
```

仍有竞态：

- 读回填旧值，覆盖新缓存
- 删缓存失败
- 主从延迟导致读到旧 DB
- 并发写顺序

常见缓解：

- 延迟双删
- 版本号/逻辑时间
- CDC/订阅 binlog 失效
- 短 TTL + 业务容忍
- 读写走同一主库/一致性读

缓存一致性细节见后续数据章；这里先记住：**TTL 不是强一致**。

## 6. 实验：容量和命中率

Zipf 请求 + LRU，10,000 个 key，100,000 次请求，base 1000 QPS。

??? note "代码：LRU 命中率与回源 QPS"
    ```python
    import random
    from collections import OrderedDict

    N_KEYS = 10_000
    N_REQUESTS = 100_000
    BASE_QPS = 1_000
    ALPHA = 1.1
    rng = random.Random(42)

    weights = [1.0 / ((i + 1) ** ALPHA) for i in range(N_KEYS)]
    requests = rng.choices(range(N_KEYS), weights=weights, k=N_REQUESTS)


    class LRU:
        def __init__(self, capacity):
            self.capacity = capacity
            self.data = OrderedDict()
            self.hits = 0
            self.misses = 0

        def get(self, key):
            if key in self.data:
                self.data.move_to_end(key)
                self.hits += 1
                return True
            self.misses += 1
            self.data[key] = None
            if len(self.data) > self.capacity:
                self.data.popitem(last=False)
            return False


    if __name__ == "__main__":
        print(f"keys={N_KEYS} requests={N_REQUESTS} base_qps={BASE_QPS}")
        print("capacity  hit_rate  origin_qps")
        for cap in [100, 1_000, 5_000, 10_000]:
            c = LRU(cap)
            for key in requests:
                c.get(key)
            rate = c.hits / N_REQUESTS
            origin = BASE_QPS * (1 - rate)
            print(f"{cap:8d}  {rate:8.1%}  {origin:10.1f}")
    ```

输出：

```text
keys=10000 requests=100000 base_qps=1000
capacity  hit_rate  origin_qps
     100     52.6%       473.7
    1000     77.8%       222.1
    5000     91.2%        87.7
   10000     92.5%        74.6
```

读法：

- 容量 100：命中 52.6%，回源约 474 QPS
- 容量 1000：命中 77.8%，回源约 222 QPS
- 容量 5000：命中 91.2%，回源约 88 QPS
- 容量 10000：命中 92.5%，回源约 75 QPS
- 这里包含冷启动 miss；预热后全量缓存会更高
- 命中率不是线性增长：Zipf 下热 key 很快命中，长尾仍回源
- 这是合成 workload，不是 Redis/业务 benchmark

## 7. 容量和观测

看：

- 命中率（按 key/租户/接口）
- 回源 QPS/延迟
- 内存、eviction、过期数
- 热 key/top-N
- 缓存错误/超时
- 回源失败/降级
- 缓存命中后的 p99

不要只看全局命中率；一个租户/接口可能一直穿透。

## 8. 选型卡

| 选项 | 适合 | 注意 |
|---|---|---|
| 本地缓存 | 极低延迟、小工作集 | 多实例不一致 |
| Redis | 共享缓存、数据结构 | 单点/热 key/持久化 |
| Memcached | 简单 KV、横向扩展 | 功能少、无持久化 |
| CDN | 静态/地理分布 | 刷新/回源/成本 |
| 数据库物化视图 | 复杂查询 | 刷新/存储 |

选型看：

- 工作集/命中率
- 一致性要求
- 延迟/吞吐
- 多租户隔离
- 持久化/高可用
- 运维/成本

## 9. 检查清单

- 缓存解决的是读放大还是延迟？
- 工作集多大？容量/淘汰策略？
- TTL 多长？有 jitter 吗？
- 穿透/击穿/雪崩/热 key 怎么防？
- 写后失效还是更新？竞态怎么处理？
- 多级缓存怎么失效？
- 缓存挂了怎么降级？
- 命中率/回源/热 key 有监控吗？

## 10. 常见坑

1. **把缓存当数据库**
   缓存不是持久化/强一致存储。

2. **TTL 当一致性**
   过期前仍可能旧读。

3. **所有 key 同一 TTL**
   同时过期，雪崩。

4. **不缓存空值**
   不存在的 key 反复打 DB。

5. **热 key 不隔离**
   一个 key 打爆整个缓存/回源。

6. **写后更新缓存**
   并发写容易旧值覆盖；删缓存也仍有竞态。

7. **缓存层无高可用**
   缓存挂了直接打爆 DB。

8. **只看命中率**
   命中率很高但回源热点仍可能过载。

9. **不预热**
   发布/扩容后冷缓存打爆后端。

10. **缓存 key 不带租户**
    跨租户数据泄漏。

## 11. 要点回顾

1. 缓存解决读放大/延迟，代价是一致性、失效、运维
2. 本地/分布式/CDN/DB 缓存各有位置和代价
3. cache-aside 最常见，但写后失效仍有竞态
4. TTL 控制旧读窗口，不是强一致
5. 穿透/击穿/雪崩/热 key 要用不同手段
6. 容量按工作集，命中率不是线性增长
7. 冷启动/预热/降级要设计
8. 缓存 key/隔离/租户不能漏
9. 命中率、回源、热 key、p99 要一起看
10. 缓存挂了要有熔断/限流/回源保护
