# HTTP 与 HTTPS

## 1. HTTP 是什么

**超文本传输协议**：客户端（浏览器）与服务端之间的"请求 - 响应"**文本协议**。

- **无状态**：每个请求独立（靠 Cookie / Token 维持状态）
- 底层：HTTP/1.1、HTTP/2 跑在 **TCP** 上；HTTP/3 跑在 **QUIC** 上

## 2. 报文格式

**请求**：

```text
GET /index.html HTTP/1.1
Host: example.com
User-Agent: ...

（可选 body）
```

**响应**：

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...
```

## 3. 方法（Method）

| 方法 | 语义 | 幂等 |
|------|------|:---:|
| GET | 获取 | ✅ |
| POST | 创建 / 提交 | ❌ |
| PUT | 替换（全量） | ✅ |
| PATCH | 局部更新 | ❌ |
| DELETE | 删除 | ✅ |

**GET vs POST**：

| | GET | POST |
|--|-----|------|
| 参数位置 | URL（查询串） | body |
| 长度限制 | 有（URL 长度） | 无 |
| 可缓存 | ✅ | ❌ |
| 幂等 | ✅ | ❌ |

## 4. 状态码

| 类别 | 含义 | 常见 |
|------|------|------|
| 2xx | 成功 | 200 OK、204 No Content |
| 3xx | 重定向 | 301 永久、302 临时、**304 缓存仍有效** |
| 4xx | 客户端错 | 400、401、403、**404**、429（限流） |
| 5xx | 服务端错 | **500**、502（网关错）、503、504（超时） |

## 5. Cookie / Session / Token

**问题**：HTTP 无状态——**第二个请求怎么知道"你是谁"**？

| 方案 | 做法 | 特点 |
|------|------|------|
| **Cookie** | 服务端 `Set-Cookie` → 浏览器存 → 之后自动带上 | 存在**客户端**，能被偷（XSS） |
| **Session** | 会话数据存**服务端**，只给客户端一个 **session id**（放 Cookie） | 安全；但**多机要共享**（存 Redis） |
| **Token（JWT）** | 服务端签发"签名过的凭据"，客户端每次带上 | **无状态**、适合分布式；但**撤销麻烦** |

**两种流程**：

```text
Session：登录 → 服务端建 session、返回 session_id
        → 浏览器每次带 Cookie: session_id
        → 服务端查 session 表（有状态）

JWT：   登录 → 服务端签名生成 token 返回
        → 客户端每次带 Authorization: Bearer <token>
        → 服务端验签即可（无状态，不查库）
```

**怎么选**：单体应用用 Session（简单）；分布式 / 跨域 / 移动端用 **Token**。

> JWT 为什么"撤销麻烦"：服务端不存状态，签出去的 token 在过期前**一直有效**；要撤销得额外维护黑名单。

## 6. 缓存（强缓存 vs 协商缓存）

**目标**：别再重复下载没变的东西。

| | 强缓存 | 协商缓存 |
|--|--------|---------|
| 判断 | **直接用本地**，不问服务器 | **问服务器**"变了吗" |
| 相关头 | `Cache-Control: max-age=3600`、`Expires` | `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since` |
| 命中结果 | 200（from disk/memory cache） | **304 Not Modified**（省传输，但要走一次往返） |

**完整流程**：

```text
① 强缓存还没过期？
   → 直接用本地（0 次请求）
② 过期了 → 带 If-None-Match / If-Modified-Since 请求
③ 服务端：没变 → 304（用本地副本）
          变了 → 200 + 新数据
```

**ETag vs Last-Modified**：ETag 按**内容哈希**，更精确；Last-Modified 只精确到**秒**。

**实践**：HTML 用协商缓存（保证最新）；**带哈希名的静态资源**（`app.a3f2.js`）用强缓存（长期有效）。

## 7. HTTP/1.1 → 2 → 3

| 版本 | 解决什么 | 关键特性 |
|------|---------|---------|
| **1.1** | — | 长连接（keep-alive）、管线化（少用） |
| **2** | 1.1 的队头阻塞、头部冗余 | **多路复用**（一个连接跑多个请求）、头部压缩 |
| **3** | TCP 层的队头阻塞 | **基于 QUIC（UDP）**，流之间独立 |

### 队头阻塞（HOL Blocking）

- **1.1**：前一个请求没回来，后面的只能排队
- **2**：应用层解决了（多路复用），但 **TCP 层还有**——一个包丢了，**所有流**都得等
- **3**：QUIC 各流独立 → 彻底解决

### 长连接 vs 短连接

| | 短连接 | 长连接 |
|--|--------|--------|
| 做法 | 一次请求建一次连接 | **复用**连接发多个请求 |
| 版本 | HTTP/1.0 默认 | **HTTP/1.1 默认**（`Connection: keep-alive`） |
| 开销 | 每次都要三次握手 + 慢启动 | 省掉反复建连 |

**注意**：长连接要配**超时**（idle timeout），否则连接堆积占用资源。

## 8. HTTPS = HTTP + TLS

**问题**：HTTP 是**明文**的 → 会被窃听、篡改、冒充。

**HTTPS**：在 HTTP 和 TCP 之间加一层 **TLS**，提供：

| 能力 | 靠什么 |
|------|--------|
| **加密**（防窃听） | 对称加密（AES） |
| **认证**（防冒充） | 证书 + CA 签名 |
| **完整性**（防篡改） | 消息认证码 |

## 9. TLS 握手（简化）

| 步骤 | 方向 | 内容 |
|------|------|------|
| 1 | 客户端 → 服务端 | 你好（支持的加密套件 + 随机数） |
| 2 | 服务端 → 客户端 | 你好（**证书 + 公钥** + 随机数） |
| 3 | 客户端 → 服务端 | 验证证书 → 用公钥加密"会话密钥"发过去 |
| 4 | 双方 | 用**会话密钥**（对称加密）通信 |

**为什么用两种加密**：

- **非对称加密**（RSA / ECDHE）：安全但**慢** → 只用来**交换密钥**
- **对称加密**（AES）：**快** → 用来传数据

**证书的作用**：证明"这个公钥真的是 example.com 的"（由 CA 签名背书）。

## 10. 要点回顾

1. **HTTP = 请求-响应、无状态、文本协议**
2. **GET vs POST**：参数位置、缓存、幂等
3. **状态码**：2xx 成功 / 3xx 重定向 / 4xx 客户端错 / 5xx 服务端错
4. **状态维持**：Cookie（客户端）/ Session（服务端）/ **Token（无状态）**
5. **缓存**：强缓存（`Cache-Control`，不问服务器）vs 协商缓存（`ETag` → **304**）
6. **1.1 → 2 → 3**：多路复用（2）→ QUIC（3），逐步解决**队头阻塞**；1.1 起默认**长连接**
7. **HTTPS = HTTP + TLS**：非对称交换密钥 + 对称传数据 + 证书防冒充
