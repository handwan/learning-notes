# UDP 与 QUIC

## 1. UDP 的特点

| 特点 | 说明 |
|------|------|
| **无连接** | 不用握手，直接发 |
| **不可靠** | 不保证到达、不保证顺序、不重传 |
| **面向报文** | 保留消息边界（不会粘包） |
| 快 | 没有握手 / 确认 / 重传开销 |
| 支持广播 / 多播 | TCP 不支持 |

## 2. TCP vs UDP

| | TCP | UDP |
|--|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠 / 有序 | ✅ | ❌ |
| 速度 | 慢 | 快 |
| 头部开销 | 20 字节起 | **8 字节** |
| 消息边界 | 无（会粘包） | **有** |
| 场景 | 文件、网页、大多数应用 | DNS、视频、游戏、QUIC |

## 3. 什么时候用 UDP

- **实时性 > 可靠性**：直播、语音、游戏——丢一帧没关系，**重传反而更卡**
- **一问一答、数据小**：DNS——就一次请求，握手不划算
- **想自己实现可靠性**：QUIC（在 UDP 上自建可靠传输 + 拥塞控制）

## 4. QUIC（HTTP/3 的底座）

### TCP 的先天问题

1. **队头阻塞**：一个包丢了，后面**所有**数据都得等（哪怕已经收到了）
2. **握手延迟**：TCP 握手 + TLS 握手 = 好几次往返
3. 中间设备（防火墙 / NAT）对 TCP 行为的"固化"

### QUIC 的做法：基于 UDP，在用户态重新实现

| 特性 | 说明 |
|------|------|
| **1-RTT / 0-RTT 建连** | 把 TCP 握手 + TLS 握手**合并** → 更快 |
| **无队头阻塞** | 各"流"独立，一个流丢包不拖累其他流 |
| **连接迁移** | 换网络（WiFi → 4G）连接不断（靠连接 ID，不靠 IP+端口） |

**为什么基于 UDP**：UDP 像"裸管道"，中间设备不干扰它；可靠性和拥塞控制**自己在上层实现** → 能在用户态快速迭代（不用改操作系统内核）。

**现状**：**HTTP/3 = HTTP over QUIC**，Google / Cloudflare 等已大量部署。

## 5. 要点回顾

1. **UDP = 无连接、不可靠、快、有消息边界**
2. **选择**：实时性优先（直播/游戏）、一问一答（DNS）用 UDP
3. **QUIC**：基于 UDP 自建可靠传输 → 1-RTT 建连、**无队头阻塞**、连接迁移
4. **HTTP/3** 就是跑在 QUIC 上的 HTTP
