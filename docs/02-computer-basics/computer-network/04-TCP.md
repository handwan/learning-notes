# TCP

**面向连接、可靠、字节流**的传输层协议。网络部分最核心的协议。

## 1. TCP 的特点

| 特点 | 含义 |
|------|------|
| **面向连接** | 先握手建立连接，再传数据 |
| **可靠** | 不丢、不重、有序（序号 + 确认 + 重传） |
| **字节流** | 没有消息边界（所以有"粘包"问题） |
| 全双工 | 双方可同时收发 |
| 流量控制 | 别把对方淹没（滑动窗口） |
| 拥塞控制 | 别把网络压垮（慢启动等） |

## 2. 报文头（关键字段）

| 字段 | 作用 |
|------|------|
| 源端口 / 目的端口 | 找到对方的**进程** |
| **序号 seq** | 本报文第一个字节的编号 |
| **确认号 ack** | 期望收到对方的下一个字节编号 |
| **标志位** | SYN（建连）/ ACK（确认）/ FIN（结束）/ RST（重置） |
| **窗口** | 流量控制：我还能收多少 |

## 3. 三次握手（建立连接）

| 步骤 | 方向 | 内容 |
|------|------|------|
| 1 | 客户端 → 服务端 | **SYN**（seq=x）：我想连你 |
| 2 | 服务端 → 客户端 | **SYN + ACK**：收到，我也连你 |
| 3 | 客户端 → 服务端 | **ACK**：收到 |

之后连接建立（ESTABLISHED），开始传数据。

**为什么是三次（不是两次、四次）**：

- **两次不够**：服务端无法确认"客户端收到了我的 SYN"（客户端可能没收到就挂了）
- **三次刚好**：双方都确认了"我的发送 + 对方的接收"都正常
- **四次多余**：第 2、3 步能合并（SYN + ACK 一起发）

## 4. 四次挥手（关闭连接）

| 步骤 | 方向 | 内容 |
|------|------|------|
| 1 | 主动方 → 被动方 | **FIN**：我不发了 |
| 2 | 被动方 → 主动方 | **ACK**：知道了 |
| 3 | 被动方 → 主动方 | **FIN**：我也不发了 |
| 4 | 主动方 → 被动方 | **ACK**：知道了 |

**为什么是四次（不是三次）**：TCP 是**全双工**——两个方向要**分别关闭**。

第 2 步只 ACK 不 FIN，是因为对方**可能还有数据要发**（所以 ACK 和 FIN 不能合并）。

## 5. 状态机（常见状态）

| 状态 | 含义 |
|------|------|
| LISTEN | 服务端在监听端口 |
| SYN_SENT | 客户端发了 SYN，等回复 |
| ESTABLISHED | 连接已建立，可传数据 |
| FIN_WAIT_1 / 2 | 主动关闭方：等对方确认 |
| **CLOSE_WAIT** | **被动关闭方**：收到 FIN，但自己**还没 close** |
| LAST_ACK | 被动关闭方：发了 FIN，等最后确认 |
| **TIME_WAIT** | **主动关闭方**：等 2MSL 后彻底关闭 |

### TIME_WAIT（主动关闭方）

- 主动关闭方最后进入 **TIME_WAIT**，等待 **2MSL**（约 1~4 分钟）
- **作用**：
  1. 保证最后那个 ACK 能到达（若丢了，对方重发 FIN 还能响应）
  2. 让旧连接的**迟到包消散**（否则可能污染新连接）

- **TIME_WAIT 过多**：服务端频繁主动关连接 / 短连接太多

**TIME_WAIT 优化**：

| 手段 | 说明 |
|------|------|
| `SO_REUSEADDR` | 重启服务能复用端口（不用等 TIME_WAIT 结束） |
| `net.ipv4.tcp_tw_reuse` | 允许把 TIME_WAIT 的连接**复用**给新连接 |
| 让**客户端**先关 | 把 TIME_WAIT 推给客户端（服务端不背） |
| **长连接** | 少建少关（根治） |

### CLOSE_WAIT（被动关闭方）

- **CLOSE_WAIT 多 = 代码 bug**：收到对方 FIN 了，但**自己没调 `close()`**
- 排查：检查所有路径（尤其**异常路径**）有没有关连接 → 用 RAII 包住

**记忆**：TIME_WAIT 是**正常状态**；CLOSE_WAIT **堆积**通常是漏了 close。

## 6. 可靠性怎么做到的

| 机制 | 作用 |
|------|------|
| **序号 + 确认** | 每个字节有编号，收到就回 ACK |
| **超时重传** | 发出去一段时间没 ACK → 重发 |
| **快速重传** | 收到 3 个重复 ACK → 不等超时，立刻重发 |
| 校验和 | 数据损坏就丢（等重传） |
| **滑动窗口** | 流量控制 |

### 超时重传：RTO 怎么定

**RTO**（重传超时时间）要**略大于 RTT**（往返时间）：

```text
RTO 太小 → 没丢也重传（浪费）
RTO 太大 → 真丢了等太久（慢）
```

**做法**：动态估计（Jacobson/Karels）

```text
RTO = SRTT + 4 × RTTVAR
      ↑平滑的 RTT   ↑RTT 的波动（偏差）
```

**Karn 算法**：**重传过的包，它的 ACK 不拿来更新 RTT**

- 原因：分不清这个 ACK 是回"第一次发的"还是"重传的"（会把 RTT 估错）

### 什么时候发 RST（重置）

- 连到一个**没在监听的端口** → 回 RST
- 收到"不属于任何连接"的包 → 回 RST
- 要**强行掐断**连接（异常关闭 / 拒绝服务）
- **遇到"Connection reset by peer"** = 对端进程挂了 / 被 kill / 防火墙拦截

## 7. 流量控制（滑动窗口）

**问题**：发送方发太快，接收方处理不过来 → 丢包、浪费。

**做法**：接收方在 ACK 里带**窗口大小**（"我还能收多少"），发送方据此调整：

```text
接收方："窗口 1000" → 发送方最多发 1000 字节未确认数据
接收方："窗口 0"    → 发送方停发，等窗口更新
```

### 两个窗口：发送窗口取谁

**发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)**

| 窗口 | 谁定的 | 管什么 |
|------|--------|--------|
| **接收窗口 rwnd** | **对方**告诉你的 | 接收方缓冲区还装得下多少（流量控制） |
| **拥塞窗口 cwnd** | **自己**估的 | 网络能承受多少（拥塞控制） |

**取小的**：既要对方收得下，也要**网络受得了**。

## 8. 拥塞控制（网络的"交通管制"）

**区别**：流量控制管"**对方**"（别淹没接收方）；拥塞控制管"**网络**"（别压垮中间链路）。

**四个阶段**：

| 阶段 | 做法 |
|------|------|
| **慢启动** | 拥塞窗口从 1 开始，**指数增长**（1→2→4→8…） |
| **拥塞避免** | 到阈值后改为**线性增长**（每轮 +1） |
| **快速重传** | 收到 3 个重复 ACK → 立刻重传（不等超时） |
| **快速恢复** | 阈值减半，从新阈值继续（不用回到 1） |

**超时 vs 快速重传**：

- **超时** → 认为网络严重拥堵 → 窗口降回 **1**（重新慢启动）
- **3 个重复 ACK** → 只是丢了个别包 → 窗口**减半**（快速恢复）

### 算法演进（了解）

| 算法 | 特点 |
|------|------|
| **Reno**（经典） | 就是上面这套（慢启动 + 拥塞避免 + 快速重传/恢复） |
| **CUBIC** | Linux 长期默认；窗口按三次曲线增长，高带宽下更稳 |
| **BBR**（Google） | **不靠丢包判断**，而是估"带宽 + 最小 RTT"→ 跨国/无线等高丢包链路表现更好 |

## 9. Nagle 算法与延迟确认

两个"攒一攒"的机制，凑一起会出问题：

| 机制 | 谁 | 做什么 |
|------|-----|--------|
| **Nagle 算法** | 发送方 | 小包先不发，等前面的包被 ACK 再合并发 |
| **延迟确认** | 接收方 | 收到数据不马上 ACK，等一小会（~40ms）看能否捎带数据 |

**问题**：两个互相等 → **小包延迟**（写小包 → 等 ACK → ACK 也在等捎带 → 卡住）。

**对延迟敏感的服务**（游戏 / 实时）：**关掉 Nagle**：

```cpp
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));   // 禁用 Nagle
```

## 10. keep-alive（保活）

| 类型 | 说明 |
|------|------|
| **TCP keep-alive** | 空闲时定期发探测包（**默认 2 小时**，太慢，一般不靠它） |
| **HTTP keep-alive** | 复用同一条 TCP 连接发多个请求（应用层）——见 [HTTP](06-HTTP与HTTPS.md) |

**工程做法**：自己在应用层做心跳（比如每 30 秒一个 ping 包），别依赖 TCP keep-alive。

## 11. 粘包 / 拆包（字节流的代价）

TCP 是**字节流**，没有消息边界：

```text
发送：[消息A][消息B]
接收：可能一次读到 [消息A消息B]（粘包），也可能拆成两次（拆包）
```

**解决**：应用层自己定协议划分消息边界（长度前缀最常用）。

## 12. 要点回顾

1. **三次握手**：SYN → SYN+ACK → ACK（让双方都确认收发正常）
2. **四次挥手**：FIN → ACK → FIN → ACK（全双工，两个方向分别关）
3. **TIME_WAIT**（主动关闭方，2MSL，正常，可优化）/ **CLOSE_WAIT 堆积 = 漏 close**
4. **可靠性**：序号确认 + 超时重传（**RTO 动态估、Karn 算法**）+ 快速重传；**RST** = 强断
5. **两个窗口**：发送窗口 = **min(接收窗口, 拥塞窗口)**
6. **流量控制**（管对方）vs **拥塞控制**（管网络）：慢启动 → 拥塞避免 → 快速恢复（Reno/CUBIC/BBR）
7. **Nagle + 延迟确认** → 小包延迟 → 延迟敏感服务用 `TCP_NODELAY` 关掉
8. **粘包**：字节流没有边界 → 应用层定协议
