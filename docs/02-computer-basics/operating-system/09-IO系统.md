# IO 系统

一个线程为什么能扛几万连接？epoll 明明常被叫“异步”，为什么还要自己 `read`？

因为 epoll 只通知“**可读**”，真正的 `read` 仍由应用完成——它是**同步多路复用**，不是异步 IO。

## 1. 五种 IO 模型

以“读 socket 数据”为例：

| 模型 | 过程 | 问题 |
|------|------|------|
| **阻塞 IO** | 一直等到有数据 | 一个连接占一个线程 |
| **非阻塞 IO** | 没数据立刻返回 `EAGAIN`，靠**轮询** | 轮询费 CPU |
| **IO 多路复用** | `select/poll/epoll` 同时等一堆 fd | **高并发主力** |
| **信号驱动 IO** | 数据到了发 `SIGIO`，再去读 | 少用，信号语义麻烦 |
| **异步 IO（AIO）** | 内核/运行时把 IO 做完，再通知你 | 真异步，实现复杂 |

**关键区分**：前四种都是**同步 IO**——最后的数据读写仍由应用完成（可能阻塞，也可能返回 `EAGAIN`）；只有 AIO 是“别人帮你读完”。

## 2. 两个维度：同步/异步 vs 阻塞/非阻塞

这是**两个不同维度**，别混：

| | 阻塞 | 非阻塞 |
|--|------|--------|
| **同步** | `read` 一直等 | `read` 立刻返回 `EAGAIN`，稍后再试 |
| **异步** | 等完成事件（`aio_suspend` / `io_uring_wait_cqe`）；等待会阻塞，但 IO 已由内核执行 | 提交后立刻返回，完成事件稍后取 |

- **阻塞/非阻塞**：说的是“这次调用会不会立刻返回”
- **同步/异步**：说的是“IO 由谁完成、完成时怎么知道”

所以“异步”也可以有阻塞的等待；反过来，非阻塞 `read` 仍是同步 IO。

> epoll 是“就绪通知”，不是“帮你读完”。这就是它和 io_uring/IOCP 的本质区别。

## 3. select / poll / epoll

| | select | poll | **epoll** |
|--|--------|------|-----------|
| fd 上限 | 默认 `FD_SETSIZE=1024`（可编译期调大） | 不受 `FD_SETSIZE` 限制 | 不受 `FD_SETSIZE` 限制 |
| 每次调用 | **全量拷贝 fd 集合** | 拷贝 `pollfd` 数组 | **内核维护，不重复拷贝** |
| 找就绪 fd | O(n) 遍历 | O(n) | **回调进就绪链表**，O(就绪数) |
| 触发 | LT | LT | **LT + ET** |

> poll/epoll 也不是“无限”：最终受 `RLIMIT_NOFILE`、内存和内核参数限制。

### epoll 三个系统调用

```cpp
int epfd = epoll_create1(0);               // 建实例（红黑树 + 就绪链表）
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);   // 注册 fd（O(log n)）
epoll_wait(epfd, events, maxevents, -1);   // 只返回就绪的 fd
```

**为什么快**：

1. 不用每次传整个 fd 集合——内核里存着
2. fd 就绪时由**回调**放进“就绪链表”
3. `epoll_wait` 只返回就绪的，代价是 **O(就绪数)**，不是 O(1)、更不是 O(n)

### LT vs ET

| | 水平触发 LT（默认） | 边缘触发 ET |
|--|---------------------|-------------|
| 通知 | 有数据就**一直通知** | **只在状态变化时通知一次** |
| 编程 | 简单，可以慢慢读 | **必须循环读到 `EAGAIN`** |
| 风险 | 效率略低（重复唤醒） | 没读完 → 数据“卡住” |

**ET 的硬要求**：

- fd 必须**非阻塞**（否则最后一次 `read` 会卡住）
- 必须循环读到 `EAGAIN`/`EWOULDBLOCK`
- 同时处理 `EPOLLERR` / `EPOLLHUP`；关闭前先 `EPOLL_CTL_DEL`
- 多线程处理同一 fd 时用 `EPOLLONESHOT`，处理完再 rearm

### 常见坑

- `accept` 的惊群：`EPOLLEXCLUSIVE` 或 `SO_REUSEPORT`
- 新连接用 `accept4(SOCK_NONBLOCK | SOCK_CLOEXEC)` 一次设好
- `read`/`write` 可能只处理一部分：循环 + 处理 `EINTR`
- `read` 返回 0 是 EOF，不是 `EAGAIN`

## 4. 非阻塞 IO 的细节

- `O_NONBLOCK` 让 `read`/`write` 没准备好时返回 `EAGAIN`，不是失败
- `EINTR` 是被信号打断，通常重试
- 短读/短写是常态：应用层要自己缓冲、拼帧
- `EAGAIN` 只说明“现在没有”，不代表连接断开；断开看 `read == 0` 或 `EPOLLHUP`
- 非阻塞 + 多路复用是标准组合；非阻塞 + 纯轮询会烧 CPU

## 5. DMA 与零拷贝

**DMA（直接内存访问）**：数据搬运交给 DMA 控制器，CPU 只负责设置描述符和收中断。

```text
无 DMA（PIO）：CPU 一个字节一个字节搬 → 全程占着
有 DMA：CPU 告诉 DMA“从设备搬到内存” → DMA 干活 → 搬完发中断通知 CPU
```

- 磁盘、网卡都靠 DMA；IOMMU 负责地址翻译/隔离
- DMA 是零拷贝能成立的基础

### 普通 read + write

```text
磁盘 → 内核 page cache → 用户缓冲区 → socket 缓冲区 → 网卡
```

通常是 **4 次拷贝 + 4 次上下文切换**（`read`/`write` 各两次模式切换）。

### 零拷贝

`sendfile` / `splice` 让数据**不经过用户态**：

```text
磁盘 → 内核 page cache → 网卡
```

| 方式 | 数据拷贝 | 上下文切换 | 说明 |
|------|---------|-----------|------|
| `read` + `write` | 4 | 4 | 通用，最直观 |
| `mmap` + `write` | 3 | 4 | 省一次 user 拷贝，但有缺页/TLB 开销 |
| `sendfile` | 2（SG-DMA） | 2 | 静态文件服务常用 |
| `splice` | 2（管道，视实现） | 2 | 可接管道/ socket |

**零拷贝的边界**：

- 需要网卡/驱动支持 SG-DMA；不支持时仍会多一次内核拷贝
- TLS/压缩通常要额外处理，可能让零拷贝失效（除非用内核 TLS 等方案）
- 小数据量不一定更快：省下的拷贝抵不过系统调用/复杂度
- `sendfile` 适合“文件 → socket”；Kafka 这类高吞吐场景常用

## 6. 异步 IO：AIO、io_uring

“异步”有三代实现，别混：

| 方案 | 谁执行 IO | 限制 |
|------|-----------|------|
| POSIX AIO（glibc） | 用户态线程池模拟 | 不是内核异步，线程开销 |
| Linux native AIO | 内核 `io_submit` | 主要支持 `O_DIRECT`，场景窄 |
| **io_uring** | 内核，SQ/CQ 共享环 | 新内核；部分环境禁用 |

**io_uring 的关键**：

- 提交队列（SQ）和完成队列（CQ）在用户态/内核间共享，**批量提交/收割**
- 支持 `read/write/accept/send/recv/fsync` 等，减少系统调用次数
- 可注册 buffer/file、轮询模式（SQPOLL），进一步降开销
- 是真正的异步接口，适合 Proactor 风格

**Proactor**：应用提交“读这个 fd”，内核读完再通知；IOCP 和 io_uring 都是这个模型。

## 7. Reactor / Proactor

IO 多路复用之上，**程序结构**怎么组织：

| 模型 | 谁读数据 | 对应 |
|------|---------|------|
| **Reactor** | **应用自己读**（通知“可读了”，你去 `read`） | epoll + 同步 IO |
| **Proactor** | **内核帮你读完**，通知“数据在这” | io_uring / IOCP |

**Reactor 的常见变体**：

| 变体 | 结构 | 例子 |
|------|------|------|
| 单 Reactor 单线程 | 简单，但吃不满多核 | Redis（命令执行单线程；网络 IO 可用多线程） |
| 单 Reactor 多线程 | 事件线程 + 业务线程池 | 常见服务 |
| **主从 Reactor** | 主 Reactor 只接连接，从 Reactor 管读写 | **Netty / muduo** |

**工程要点**：

- 事件循环里**不能做阻塞调用/长任务**，否则整个 loop 卡住
- CPU 密集任务丢线程池；注意**背压**，别让队列无限涨
- 一个 fd 同一时刻只让一个线程处理（`EPOLLONESHOT` 或分片）
- “一个 loop 一个线程”能减少锁；跨线程投递任务用消息队列/eventfd 唤醒

## 8. 要点回顾

1. **五种 IO 模型**：前四种是同步；只有 AIO 是“别人帮你读完”
2. **两个维度**：阻塞/非阻塞看调用是否立刻返回；同步/异步看谁完成 IO
3. **select/poll/epoll**：fd 集合拷贝、遍历 vs 回调就绪链表；epoll 是 O(就绪数)
4. **LT vs ET**：ET 必须非阻塞 + 读到 `EAGAIN`；注意 `EPOLLERR/HUP`、`EPOLLONESHOT`
5. **DMA**：数据搬运不占 CPU；CPU 仍负责发起和收尾
6. **零拷贝**：`sendfile`/`splice` 省掉用户态拷贝；受 SG-DMA、TLS、数据量限制
7. **异步 IO**：POSIX AIO（线程池）→ native AIO（`O_DIRECT`）→ io_uring（SQ/CQ、批量）
8. **Reactor vs Proactor**：应用读 vs 内核读；Reactor 注意阻塞、背压、fd 归属
