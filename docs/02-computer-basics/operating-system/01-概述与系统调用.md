# 概述与系统调用

`printf("hi")` 到屏幕上出现 `hi`，中间发生了什么？

这条链会串起 OS 的几个根本问题：**抽象、特权级、陷入、中断、隔离**。

## 1. 一条链：从 printf 到屏幕

```text
printf → stdio 缓冲区 → write(1, ...) → syscall 指令
       → 内核 → tty / 文件系统 → 终端 / 块设备
```

- `printf` 是**库函数**：先写用户态缓冲区；连终端时行缓冲（换行/`fflush` 触发），重定向到文件时全缓冲（缓冲区满/`fflush` 才写）
- `write` 是**系统调用**：真正跨越用户态/内核态边界
- 写终端走 tty（通常由终端模拟器渲染）；重定向到文件则进 page cache，再由块设备回写磁盘
- 返回时沿原路回到用户态

OS 在这条链上做了两件事：把硬件抽象成 `fd`/文件，用特权级保证只有内核能碰硬件。

## 2. OS 的职责与抽象

**OS = 管理硬件资源 + 给程序提供抽象和服务。**

| 职责 | 说明 |
|------|------|
| **管理** | CPU、内存、磁盘、外设——谁用、用多少、怎么分配 |
| **抽象** | 把硬件包装成好用的接口 |

| 硬件 | OS 抽象 |
|------|--------|
| CPU | 进程 / 线程 |
| 内存 | 虚拟地址空间 |
| 磁盘 | 文件系统 / `fd` |
| 网络 | socket |

抽象带来两个好处：**好用**（不用管硬件细节）和**可控**（权限、配额、隔离都在抽象层做）。

## 3. 两种态：为什么必须“陷进去”

CPU 有特权级（x86 有 ring0~ring3，实际只用两级）：

| | 用户态（ring3） | 内核态（ring0） |
|--|---------------|---------------|
| 能执行 | 非特权指令 | **特权指令**（改页表、开关中断、IO） |
| 能访问 | 自己的地址空间 | 全部内存 + 硬件 |
| 谁在跑 | 应用程序 | 内核代码 |

**为什么要分**：**安全 + 稳定**——用户程序不能直接动硬件或别的进程的内存。

代价是：每次进内核都要保存/恢复上下文、切换内核栈，这也是系统调用不便宜的根本原因。

## 4. 系统调用：常规入口

### 一次调用发生什么

```text
用户程序 → libc 封装 → syscall 指令 → 内核入口
        → 查表分发 → 执行 → 返回用户态
```

- x86-64 用 `syscall` 指令陷入（32 位时代是 `int 0x80`）
- 调用号放在寄存器（x86-64 是 `rax`），参数也走寄存器（`rdi/rsi/rdx/r10/r8/r9`）
- 内核按号查系统调用表（Linux 是 `sys_call_table`）分发
- 失败时内核返回负错误码，libc 转成 `-1` 并设置 `errno`——检查返回值是系统编程的底线

> 例外：Linux 的 vDSO 把 `clock_gettime`、`gettimeofday` 等少数调用做成用户态代码，libc 直接算，不陷入内核，所以 `strace` 也看不到它们。

### 常见分类

| 类别 | 代表 |
|------|------|
| 进程控制 | `fork`、`execve`、`exit`、`wait4` |
| 文件 | `openat`、`read`、`write`、`close` |
| 设备/控制 | `ioctl` |
| 信息 | `getpid`、`uname` |
| 通信 | `pipe`、`socket`、`sendto` |

### 开销与观察

| 操作 | 量级 |
|------|------|
| L1 命中 | ~1 ns |
| 内存访问 | ~100 ns |
| 系统调用 | ~0.1–1 µs |
| 上下文切换 | ~1–5 µs |
| NVMe 随机读 | ~50–100 µs |
| 同机房网络 RTT | ~0.1–0.5 ms |

> 数量级会随硬件、内核、负载变化，用来建立尺度感，不要当 benchmark。

系统调用的代价主要在三处：

1. **模式切换**（用户态 ↔ 内核态）
2. 参数/数据拷贝（用户缓冲区 ↔ 内核缓冲区）
3. 缓存/TLB 受影响（KPTI 等隔离机制下更明显）

> 所以大量小 IO 要**批量/缓冲**（如 `write` 大块、用户态缓冲），减少系统调用次数。

```bash
strace -c ./prog                 # 按系统调用统计次数/耗时
strace -f -e trace=file ./prog   # 跟子进程，只看文件相关调用
```

## 5. 中断与异常：CPU 被“打断”的两种方式

| | 中断（Interrupt） | 异常（Exception） |
|--|-----------------|-----------------|
| 来源 | **外部**（键盘、网卡、时钟） | **内部**（除零、缺页、非法指令） |
| 时机 | **异步**（随时可能来） | **同步**（执行到才触发） |
| 作用 | 通知内核处理外设 | 处理错误 / 系统调用（trap） |

> 严格说，x86-64 的系统调用用 `syscall` 指令进入内核，不属于 IDT 异常；教材通常把它归为 trap 这一类。

**中断处理流程**：

```text
保存上下文（寄存器）→ 查中断向量表 → 跳处理程序 → 处理 → 恢复上下文返回
```

- **时钟中断**是抢占式调度的基础：时间片用完靠它把进程踢下来
- **缺页异常**：访问的页不在内存 → 内核加载页 → 重新执行指令（详见内存管理）
- 很多内核把中断处理分**上半部/下半部**（Linux 是 hardirq/softirq）：紧急的在中断上下文做，耗时的推后（详见设备与 IO）

## 6. 结构：宏内核、微内核、混合

| 结构 | 特点 | 例子 |
|------|------|------|
| 宏内核 | 内核功能都在一起，性能好、耦合高 | **Linux** |
| 微内核 | 内核只留最少功能，其余在用户态，安全但服务间 IPC 开销大 | QNX、seL4 |
| 混合 | 折中 | Windows、macOS |

Linux 是宏内核，但**模块化**：核心功能 + 可加载模块，模块仍运行在内核地址空间。

这也是一个经典权衡：微内核把驱动、文件系统推到用户态，隔离更好，但每次服务调用都要 IPC；L4/seL4 这类实现把 IPC 做到很薄，说明“微内核一定慢”也不成立，取决于实现和负载。

## 7. 虚拟化：VM vs 容器

两种“一台机器跑多个环境”的方案。

**Hypervisor 两类**：Type 1 直接跑在硬件上（Xen、ESXi；KVM 是内核模块，通常也归这一类）；Type 2 跑在宿主 OS 上（VirtualBox、VMware Workstation）。

| | 虚拟机（VM） | 容器 |
|--|-------------|------|
| 隔离/限额靠 | **Hypervisor**（虚拟硬件） | **内核**（namespace 隔离 + cgroup 限额） |
| 每个实例带 | **完整的 Guest OS** | 只有应用 + 依赖 |
| 启动 | 传统 VM 分钟级（微 VM 可到百毫秒级） | **秒级 / 毫秒级** |
| 开销 | 大（多套 OS） | 小（**共享宿主内核**） |
| 隔离强度 | **强**（硬件级） | 弱一些（内核共享） |

**容器靠 namespace 隔离、cgroup 限额**，再加 capabilities、seccomp、LSM（AppArmor/SELinux）收敛权限：

| 机制 | 作用 |
|------|------|
| **namespace** | 隔离“**看得到什么**”（PID、网络、文件系统、用户…） |
| **cgroup** | 限制“**能用多少**”（CPU、内存、IO） |

> **一句话**：VM 虚拟的是**硬件**，容器做的是**操作系统级虚拟化**（共享宿主内核）。

所以普通容器里 `uname -r` 看到的是宿主内核，也换不了内核版本。轻量微 VM（Firecracker 等）把启动压到百毫秒级，隔离模型仍是硬件级——这是在密度和隔离之间找的中间点。

> 容器安全边界（user namespace、seccomp、`--privileged`）见[保护与安全](10-保护与安全.md)。

## 8. 启动：从通电到 PID 1

```text
通电 → BIOS/UEFI（自检，找到可启动设备）
     → Bootloader（GRUB：加载内核 + initramfs）
     → 内核初始化（内存管理、驱动、调度器）
     → initramfs：加载关键驱动、挂载真实根文件系统，切换过去
     → init / systemd（PID 1：启动各种用户态服务）
```

| 阶段 | 干什么 |
|------|--------|
| BIOS / UEFI | 硬件自检；UEFI 从 EFI 系统分区（ESP）加载 bootloader |
| Bootloader（GRUB） | 加载内核和 initramfs |
| 内核初始化 | 建立内存管理、加载驱动、启动调度器 |
| initramfs | 临时根文件系统：带起挂载真实 `/` 所需的驱动，再 `switch_root` |
| init / systemd | **PID 1**，启动用户态服务 |

## 9. OS 的类型

不同场景对 OS 的取舍不同：

| 类型 | 目标 | 特点 | 例子 |
|------|------|------|------|
| 批处理 | 吞吐 | 作业排队、少交互 | 早期大型机 |
| 分时 | 响应 / 公平 | 时间片、多用户 | Unix |
| 实时 | 截止时间 | 可预测、优先级 / EDF | RTOS、飞控 |
| 嵌入式 | 资源 / 功耗 | 裁剪、专用 | FreeRTOS、嵌入式 Linux |
| 分布式 | 多机协作 | 透明性、容错 | 集群 / 分布式系统 |

现代通用 OS 往往混合多种：Linux 服务器偏吞吐，桌面偏交互，硬实时靠 RT 补丁 / RTOS。分布式 OS 作为单一 OS 已不多见，现代更多是分布式中间件 / 集群调度。

## 10. 演进：为什么是今天这样

- **陷入指令**：`int 0x80` → `sysenter` → `syscall`；64 位下 `syscall` 成为标准，路径更短
- **安全**：Meltdown 之后 KPTI 拆开用户/内核页表，系统调用和中断要切 CR3，成本上升；PCID 缓解了一部分
- **IO**：select/poll 的 O(n) → epoll 的就绪队列 → io_uring 的共享环 + 批量提交，核心都是**减少陷入和扫描**
- **隔离**：进程 → 容器（namespace/cgroup）→ microVM（Firecracker），在密度和隔离之间来回找平衡

## 11. 边界：简单叙事哪里会错

- **系统调用不是唯一入口**：vDSO 让少数调用不陷入内核；中断和异常也会让 CPU 进内核，但不是请求服务
- **容器不一定弱隔离**：runc 共享内核，但 gVisor（用户态内核）、Kata/microVM 能加一层
- **VM 不一定分钟级**：Firecracker 这类微 VM 启动在百毫秒级
- **宏内核不一定最快**：微内核 IPC 优化后差距会变，选择取决于负载和隔离要求

## 12. 要点回顾

1. **一条链**：`printf` → stdio → `write` → `syscall` → 内核 → tty/文件系统 → 终端/块设备
2. **两种态**：特权指令、为什么陷入；代价是上下文/栈切换
3. **系统调用**：调用号 + 寄存器传参、`-1` + `errno`、vDSO 例外
4. **代价量级**：系统调用 ~µs、上下文切换 ~µs、NVMe 随机读 ~百 µs；大量小 IO 要批量
5. **中断 vs 异常**：异步/同步；时钟中断支撑抢占；缺页异常；上半部/下半部
6. **结构权衡**：宏内核性能、微内核隔离、Linux 的模块化；IPC 成本决定边界
7. **VM vs 容器**：Hypervisor vs namespace 隔离 + cgroup 限额（外加 capabilities/seccomp/LSM）；microVM 是折中
8. **启动**：UEFI → bootloader → 内核 → initramfs → init/systemd
9. **OS 类型**：批处理 / 分时 / 实时 / 嵌入式 / 分布式；现代通用 OS 往往混合多种
10. **演进主线**：更短的陷入路径、更少的拷贝、隔离在密度和强度之间取舍
