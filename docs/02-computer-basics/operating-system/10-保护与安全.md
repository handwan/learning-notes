# 保护与安全

普通用户执行 `passwd`，为什么能改 `/etc/shadow`？容器里的 root，为什么有时能读宿主机文件？

这两个问题跨的是不同边界：前者是“应用 → 数据”（setuid/DAC），后者是“容器 → 宿主”（user namespace/capabilities）。安全就是一道道**信任边界**：每跨一道，都要有检查点。

## 1. 安全的目标

| 目标 | 含义 |
|------|------|
| **保密性** | 不该看的看不到 |
| **完整性** | 不该改的改不了 |
| **可用性** | 该用的时候用得上 |

几条基本原则：

- **隔离**：进程/用户/容器之间不能互相越界
- **最小权限**：只给完成任务所需的权限
- **完全中介**：每次访问都经过检查（reference monitor：不可绕过、可验证、足够小）
- **纵深防御**：一层被突破，还有下一层

**认证**（你是谁）和**授权**（你能做什么）是两件事；安全机制大多在管后者。

威胁模型：恶意应用、不可信输入、本地普通用户、网络攻击者。**假设应用可能被攻破**，不要只防“外部”。

> 安全是属性，不是某个开关；`chmod 777` 关掉的是“保护”这个属性。

## 2. 五道信任边界

| 边界 | 防止什么 | 主要机制 | 典型失效 |
|------|---------|---------|---------|
| **固件 → 内核** | 启动链被替换 | Secure Boot、IMA/EVM、dm-verity、模块签名 | 密钥泄漏、降级、bootloader 漏洞 |
| **内核 → 用户** | 用户程序执行特权操作 | 特权级、页表 U/S、KPTI、SMEP/SMAP | 内核/驱动漏洞 |
| **进程 → 进程** | 读/改别的进程内存 | 页表隔离、ASLR、ptrace/Yama、`/proc` 权限 | 同 UID ptrace、`/proc` 泄漏 |
| **容器 → 宿主** | 容器 root 逃逸 | user namespace、capabilities、seccomp、LSM、namespace | `--privileged`、挂宿主机目录、内核漏洞 |
| **应用 → 数据** | 越权读写文件 | DAC/ACL、capabilities、setuid、安全打开 | TOCTOU、符号链接、PATH |

后面按这五道边界展开。

> 表和正文用 Linux/Unix 举例；Windows 对应 token/ACL/AppContainer/WDAC，macOS 对应 sandbox/entitlements/SIP/TCC。名字不同，边界和最小权限的思想相同。

## 3. 固件 → 内核：启动链

- **Secure Boot**：固件验证 bootloader/kernel 签名，建立启动链信任
- **IMA/EVM**：度量/校验文件完整性；**dm-verity**：块设备只读完整性
- **模块签名 + kernel lockdown**：限制运行时加载未签名模块、改内核
- **TPM measured boot**：把启动过程度量值存起来，供远程证明/审计

**边界在哪**：Secure Boot 只保证“启动的是被签名的东西”，不保护运行中的漏洞；密钥管理、回滚攻击、bootloader 自身漏洞仍是失效点。

## 4. 内核 → 用户：特权级与内存保护

- 用户态/内核态：用户程序不能执行特权指令
- 系统调用是受控入口：内核要验证用户指针（`copy_from_user`）、参数和权限
- 页表权限：R/W/X、NX、user/supervisor；W^X 让内存不能同时可写可执行
- **KPTI**：隔离用户/内核页表，缓解 Meltdown
- **SMEP/SMAP**：阻止内核执行/访问用户页

**边界在哪**：内核不是“绝对可信”。驱动、`ioctl`、文件系统、网络栈都是攻击面；内核被攻破，上面几道边界一起失效。

## 5. 进程 → 进程：隔离与窥探

- 每个进程独立页表：不能直接读写别人的地址空间
- **ASLR**：随机化地址布局，增加利用难度（提高门槛，不是边界）
- `ptrace` 能读写同 UID 进程内存；**Yama** 的 `ptrace_scope` 限制范围
- `/proc/<pid>/mem`、`environ`、`cmdline` 也受权限/ptrace 检查
- core dump 可能带出内存内容；敏感进程要禁用或限制
- `hidepid` 可以收紧 `/proc` 的可见性

**边界在哪**：**同 UID 不是安全边界**。同用户的进程之间，ptrace、`process_vm_readv`、`/proc` 都可能成为窥探通道；真正隔离要靠不同用户、沙箱或 VM。

## 6. 容器 → 宿主：root 的真相

单靠 `chroot` 不够——root 能逃出去。容器是几层叠加：

| 层 | 作用 |
|----|------|
| namespace | 隔离 PID/网络/挂载/用户等视图 |
| cgroup | 限制 CPU/内存/IO |
| capabilities | 丢弃不需要的特权 |
| seccomp | 过滤系统调用 |
| LSM | SELinux/AppArmor 再收紧 |

- **user namespace**：容器内 uid 映射到宿主机非 root；这才是“容器 root 不是宿主 root”
- **默认 Docker 不开 user namespace**：容器内 uid 0 仍是内核的 uid 0，靠 capabilities/seccomp/LSM/namespace 限制
- `--privileged`、挂宿主机目录、挂 `docker.sock` 都会大幅削弱隔离，甚至直接等价宿主 root
- **seccomp-bpf**：按系统调用号/参数过滤；不能解引用指针，复杂检查要靠 LSM
- gVisor（用户态内核）、Kata/microVM 提供更强隔离；VM 最强但更重

> 容器不是“轻量 VM”；它共享内核。隔离强度取决于配置，不取决于名字。

## 7. 应用 → 数据：访问控制与文件攻击

### DAC / ACL

- Unix `uid/gid/mode`：owner/group/other 的 rwx
- **ACL**：给单个用户/组额外授权
- `umask` 决定新建文件的默认权限；sticky bit（如 `/tmp`）防删别人的文件
- root 默认绕过检查——所以“以 root 跑”风险最大

### 能力（Capabilities）

把 root 的“全能”拆成细粒度权限：

- `CAP_NET_BIND_SERVICE`：绑定低端口
- `CAP_DAC_OVERRIDE`：绕过文件权限
- `CAP_SYS_ADMIN`：非常广，尽量别给
- 文件能力（`setcap`）、进程 bounding/ambient 集合
- `no_new_privs`：禁止通过 setuid/文件能力提权

### MAC（强制访问控制）

- **SELinux**：给对象打标签，按策略决定谁能访问谁
- **AppArmor**：按路径/配置文件限制程序
- 管理员策略决定，普通用户不能改——所以叫“强制”

| 模型 | 谁决定 | 粒度 | 例子 |
|------|--------|------|------|
| DAC | 文件属主 | 用户/组/other | Unix mode、ACL |
| MAC | 管理员策略 | 标签/路径 | SELinux、AppArmor |
| 能力 | 内核 + 文件/进程 | 具体特权 | `CAP_NET_RAW` |

### setuid / setgid

- setuid 程序运行时，**有效 UID** 变成文件属主（常见是 root）
- 真实/有效/保存 UID 是三个概念；`sudo` 本质也是受控提权
- Linux **忽略脚本上的 setuid 位**；setuid 程序要自己防 PATH 等注入
- 能不用 setuid 就不用：用 `sudo` 规则、capabilities、守护进程更安全

**回到开头**：`passwd` 是 setuid root 程序——它用文件属主的权限改 `/etc/shadow`，但只做“改密码”这一件事。风险在于：setuid 程序一旦有漏洞，普通用户就可能借它提权。

### TOCTOU 与符号链接

**TOCTOU**（time-of-check to time-of-use）：检查时是一个文件，使用时被换成另一个。

防御：

- 用 fd 相对操作：`openat` + `fstat`，避免“检查路径再打开路径”
- `O_NOFOLLOW`；`openat2` 的 `RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS`
- 临时文件用 `mkstemp`/`O_EXCL`，别用可预测文件名
- setuid 程序用绝对路径、清理环境；Linux 在 secure-exec 下忽略 `LD_PRELOAD`
- 不在命令行/环境变量里放密钥

## 8. 工程规则

- **最小权限**：非 root、drop capabilities、按需授权
- **默认拒绝**：seccomp/防火墙/文件权限都从最小集合开始
- **纵深防御**：namespace + cgroup + seccomp + LSM，不押注单一机制
- **假设失陷**：密钥、日志、备份要能扛住单点被攻破
- **可审计**：auditd、日志、异常行为告警
- **及时更新**：内核/驱动/基础镜像是最大攻击面之一

## 9. 要点回顾

1. **五道边界**：固件→内核、内核→用户、进程→进程、容器→宿主、应用→数据
2. **CIA + 隔离/最小权限/完全中介/纵深防御**；安全是属性，不是开关
3. **内核→用户**：特权级、页表权限、KPTI、SMEP/SMAP；内核也会被攻破
4. **进程→进程**：页表 + ASLR + ptrace/Yama；同 UID 不是边界
5. **容器→宿主**：userns/caps/seccomp/LSM/ns；默认 Docker 的 uid 0 仍是宿主 uid 0
6. **应用→数据**：DAC/ACL/capabilities/MAC；setuid 的有效 UID；`passwd` 为什么能改 shadow
7. **TOCTOU/符号链接**：fd 相对操作、`O_NOFOLLOW`、`openat2`
8. **启动完整性**：Secure Boot、IMA/EVM、dm-verity、模块签名；不等于运行时安全
