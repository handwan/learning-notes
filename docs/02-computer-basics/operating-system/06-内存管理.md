# 内存管理

`malloc(1GB)` 可能瞬间返回，`free` 之后 RSS 又可能不降——虚拟内存到底承诺了什么？

它承诺的是**地址空间**，不是物理内存。真正的物理页，等到第一次访问才分配。

## 1. 为什么需要虚拟内存

如果程序直接用物理地址：

- 进程之间**不隔离**（能改别人的内存）
- 程序要自己管“我的代码放在哪块物理内存”
- 内存不够时不好处理，碎片也没法收拾

**虚拟内存**：每个进程看到一个**独立的虚拟地址空间**，由 OS/MMU 映射到物理内存。

| 好处 | 说明 |
|------|------|
| **隔离** | 进程只能访问自己的地址空间 |
| **简化编程** | 不用关心物理布局，链接器按固定虚拟地址来 |
| **超售** | 虚拟地址可以大于物理内存；不常用的页换到磁盘 |
| **共享** | 共享库、`fork` 的 COW、`mmap` 同一文件 |

> 虚拟内存不等于“把磁盘当内存”。它是**地址空间抽象 + 按需映射**；swap 只是后备存储之一。

## 2. 地址转换：页表与 TLB

把虚拟地址空间和物理内存都切成固定大小的**页**（通常 4KB）：

```text
虚拟地址 = 虚拟页号 + 页内偏移
              ↓ 查页表（PTE）
物理地址 = 物理页号 + 页内偏移
```

- **页表**记录“虚拟页 → 物理页”，每个进程一张（内核部分共享）
- 页表项（PTE）除了物理页号，还有 **present / writable / user / accessed / dirty / NX** 等标志
- 32 位、4KB 页、4 字节 PTE：一张页表就是 `2^20 × 4B = 4MB`；64 位更夸张

### 多级页表

页表再分页——**没用到的下级页表不分配**，用时间换空间。

- x86-64 常见 **4 级**页表（5 级也已出现），一次 miss 要多次访存
- 页表越深，地址转换越慢；所以需要 TLB

### TLB（页表缓存）

- CPU 里的“页表高速缓存”（几十 ~ 几百项）
- 命中 → 直接拿物理页号；未命中 → 查页表（page walk），再填入 TLB
- **进程切换要换 TLB**；现代 CPU 用 **ASID/PCID** 打标记，避免整表刷掉
- 多核上改页表还要 **TLB shootdown**（IPI 通知其他核失效），这也是页表操作不便宜的原因

> 程序的实际性能，很多时候取决于 **TLB 命中率**，而不是纸面上的页表级数。

## 3. 分段与段页式

**分页是“物理视角”**（切固定块），**分段是“逻辑视角”**（按程序结构切）。

| | 分页 | 分段 |
|--|------|------|
| 切分依据 | **固定大小**（如 4KB） | **逻辑单位**（代码段/数据段/栈） |
| 大小 | 固定 | 可变 |
| 对用户 | **不可见**（透明） | **可见**（编译器按段组织） |
| 地址 | 一维（线性地址） | **二维**（段号 + 段内偏移） |
| 碎片 | **内部碎片**（最后一页填不满） | **外部碎片**（段间空隙） |
| 主要目的 | 内存利用率 + 虚拟内存 | 共享 / 保护 / 动态增长 |

**段页式**：先按逻辑**分段**，每段内部再**分页**——“逻辑上分段，物理上分页”。

现代 x86-64 的段基本退化成平坦模型，主要靠分页；`FS`/`GS` 还留着，用来做线程本地存储（TLS）。

## 4. 缺页异常（Page Fault）

访问的页**不在物理内存**时触发。但“不在”分好几种：

| 类型 | 触发场景 | 要不要读磁盘 |
|------|---------|-------------|
| **minor** | 页已在内存（page cache/零页），只是没建映射 | 否 |
| **major** | 页在磁盘（文件/swap），要读进来 | **是** |
| **COW** | 写一个只读的共享页，要复制一份 | 通常否（内存在） |
| **invalid** | 地址没映射 / 越权 | 不处理，发 `SIGSEGV` |

处理流程（以 major 为例）：

```text
1. CPU 访问虚拟地址 → 查页表：present = 0
2. 触发缺页异常 → 陷入内核（x86 把 faulting address 放在 CR2）
3. 内核判断：合法地址？权限够？→ 不合法就 SIGSEGV
4. 找空闲页框（没有就回收/置换一页，脏页要先写回）
5. 从文件或 swap 把内容读进来（page cache 命中就是 minor，不走这里）
6. 更新页表，返回用户态
7. 【重新执行】那条指令（这次命中）
```

**关键**：是“重新执行”不是“继续”——所以对程序**透明**。但只对合法缺页透明；非法访问会收到 `SIGSEGV`。

代价差别很大：minor 通常微秒级；major 取决于存储，NVMe 几十~几百微秒，HDD 可能到毫秒级。

## 5. 页面置换算法

内存满了，得选一页换出去。选谁？

| 算法 | 思路 | 问题 |
|------|------|------|
| **OPT** | 换出**未来最久不用**的页 | 理论最优，无法实现；做基准 |
| **FIFO** | 先进先出 | 可能换掉常用页；**Belady 异常**（页框变多，缺页反而变多） |
| **LRU** | 换出**最久没用过**的 | 符合局部性；精确实现贵（每次访问都要更新） |
| **Clock（二次机会）** | 环形队列 + 访问位，转一圈找访问位 0 的 | 近似 LRU；教学和部分系统常用 |
| **LFU** | 换出使用次数最少的 | 老热门页赖着不走 |

- **LRU 为什么理论好**：依据**局部性原理**——最近用过的，大概率马上还用；而且 LRU 是栈算法，不会有 Belady 异常
- **为什么不精确实现 LRU**：硬件只提供 accessed/dirty 位，没有“上次访问时间”；每次访问都维护链表/时间戳太贵
- **Linux 实际**：用 active/inactive 双链表近似 LRU，配合 refault 判断和 `kswapd` 水位回收，不是经典的 Clock

### 工作集与抖动

- **工作集（working set）**：进程在最近 Δ 时间内实际用到的页集合
- 如果所有进程的工作集之和超过物理页框数，就可能频繁缺页、刚换出又换入 → **抖动（thrashing）**
- 表现：缺页率高、CPU 利用率反而低、磁盘/swap 很忙
- 解法：减少并发度、调整页面分配、加内存；不是“换个更聪明的算法”就能解决

## 6. 工程视角

### `malloc`、`brk` 与 `mmap`

- `malloc` 小块从**堆**要（`brk`/`sbrk`）；大块直接 `mmap`
- `free` 不一定还给 OS：allocator 会缓存起来复用 → **RSS 不降**
- 大块 `mmap` 的释放可能直接 `munmap`，RSS 会降；也可以用 `malloc_trim` / `madvise(MADV_DONTNEED)` 主动还
- **VSZ** 是虚拟大小，**RSS** 是实际驻留的物理页；两者差很多是正常的

### page cache 与内存回收

- 文件页缓存在 page cache 里；内存紧张时内核优先回收干净的文件页
- `free` 的 `buff/cache` 不是浪费；RSS 只算进程实际驻留的页
- `mmap` 文件页会映射进地址空间；读写/`fsync`/readahead 的细节见[文件系统](07-文件系统.md)

### swap 与 overcommit

- swap：把不常用的匿名页写到磁盘，腾出物理页
- **频繁 swap = 性能灾难**（磁盘比内存慢几个数量级）；SSD 上也好不到哪去
- Linux 默认 **overcommit**：`malloc` 可能成功，但首次访问/内存紧张时才真正分配；分配失败可能表现为 OOM，而不是 `malloc` 返回 NULL
- `vm.overcommit_memory` 可调策略（0 启发式、1 总是、2 严格）

### OOM 与 cgroup

- 物理内存 + swap 都满了 → **OOM Killer** 按 `oom_score` 挑进程杀掉；`oom_score_adj` 可调
- 容器里还有 **cgroup OOM**：`memory.max` 到了就杀 cgroup 内的进程，不一定影响整机
- “进程突然消失、exit code 137” 常见就是被 OOM kill

### 写时复制（COW）

- `fork()` 后，父子进程**共享**同一份物理页（只读）
- 谁**写**，才复制一份出去；只读的代码页、`exec` 前没写过的数据都可能一直共享
- 好处：fork 快、省内存；代价：写时触发缺页和复制

### NUMA 与亲和

多路服务器里，CPU 访问“**自己插槽**”的内存快，访问别的插槽慢（NUMA）。

| 手段 | 作用 |
|------|------|
| **NUMA 亲和** | 让线程优先用**本地内存**，避免跨节点访问（`numactl`） |
| **CPU 亲和** | 把线程绑到固定核（`taskset` / `sched_setaffinity`），减少迁移、提升缓存命中 |

### 大页（Huge Pages）

普通页 4KB；大页是 **2MB / 1GB**（x86-64）。

- 好处：**页表项大幅减少** → TLB 覆盖范围变大、缺页少 → 大内存应用（数据库、AI）受益
- 两种用法：**显式大页**（hugetlbfs/`mmap(MAP_HUGETLB)`）和 **THP**（透明大页，内核自动合并）
- 代价：内部碎片、分配延迟、THP 的 `khugepaged` 可能带来抖动；不是所有负载都适合

### 内核内存分配（伙伴系统 / slab）

| 机制 | 解决什么 |
|------|---------|
| **伙伴系统** | 按 2 的幂管理**页框**，相邻空闲块可合并 → 缓解**外部碎片** |
| **slab/SLUB** | 给频繁分配的小对象（inode、task_struct）建**缓存池**，避免反复构造/析构 |

## 7. 要点回顾

1. **虚拟内存**：隔离、简化编程、超售、共享；它承诺地址空间，不承诺物理页
2. **地址转换**：页表 → 多级页表 → TLB；page walk 多次访存，TLB 命中决定实际性能
3. **分页 vs 分段**：固定/逻辑、一维/二维、内部/外部碎片；x86-64 主要靠分页
4. **缺页类型**：minor / major / COW / invalid；合法缺页透明，非法访问 `SIGSEGV`
5. **置换算法**：OPT 基准、FIFO 有 Belady、LRU 好但贵、Clock 近似、LFU 会赖着
6. **工作集与抖动**：工作集之和超过页框数就可能 thrashing；加内存/降并发，不是换算法
7. **`malloc`/RSS**：`brk` + `mmap`；`free` 不一定还 OS；VSZ ≠ RSS
8. **page cache / swap / overcommit**：文件页可回收；swap 频繁是灾难；overcommit 把失败推到 OOM
9. **OOM**：全局 OOM 按 `oom_score`，cgroup OOM 按 `memory.max`；exit 137 常见
10. **COW / NUMA / 大页 / 伙伴系统 / slab**：fork 省拷贝；本地内存和 TLB 覆盖影响性能；内核用小对象缓存
