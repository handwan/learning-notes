# CPU 调度

## 1. 为什么需要调度

CPU 少、进程多——**谁先用、用多久、下一个是谁**，就是调度。

**目标**（互相冲突，要权衡）：

| 指标 | 含义 |
|------|------|
| 吞吐量 | 单位时间完成多少任务 |
| 周转时间 | 从提交到完成 |
| 响应时间 | 交互程序要快（点一下得有反应） |
| 公平性 | 别饿死谁 |

## 2. 抢占 vs 非抢占

| | 非抢占 | 抢占 |
|--|-------|------|
| 规则 | 进程不让出就一直跑 | 时间片到/高优先级来 → **踢下来** |
| 优点 | 简单、切换少 | 响应好、公平 |
| 缺点 | **一个长任务卡住所有人** | 切换有开销 |
| 例子 | 早期批处理 | 现代 OS |

## 3. 经典调度算法

### FCFS（先来先服务）

- 最简单
- 问题：**护航效应**——一个长任务把后面全堵住

### SJF（短作业优先）

- **平均等待时间最短**（可证明最优）
- 问题：
  - 事先**不知道要跑多久**（只能估计）
  - 长作业可能**饿死**（总有短作业插队）

### 时间片轮转（RR）

每个进程跑一个**时间片**，轮着来。

**时间片大小的权衡**：

| 时间片 | 后果 |
|--------|------|
| 太小 | 切换开销占比高，吞吐下降 |
| 太大 | 退化成 FCFS，响应变差 |

### 优先级调度

- 高优先级先跑
- 问题：低优先级**饿死** → 解法：**老化（aging）**（等越久优先级越高）

### 多级反馈队列

多个队列，优先级不同、时间片不同：

```
新进程 → 最高优先级队列（时间片小）
用完没跑完 → 降到下一级（时间片变大）
```

**效果**：

- **短任务/交互任务**（很快跑完）→ 一直高优先级，**响应快**
- **CPU 密集长任务** → 自动降级，**不挡别人**

现代通用 OS 调度的基本思想。

## 4. 优先级反转

**RTOS / 并发里经典的坑。**

场景：三个优先级 L < M < H。

```
1. L 拿了锁
2. H 来了，要同一把锁 → 阻塞等待
3. M 就绪，抢占 L（L 优先级低）
4. L 跑不了 → 锁不释放 → H 一直等，被 M "间接"卡住
```

**结果**：优先级最高的 H 反而最后完成。

**解法**：

| 方案 | 做法 |
|------|------|
| **优先级继承** | L 持有锁期间，暂时**继承 H 的优先级**，不被 M 抢占 |
| **优先级天花板** | 拿锁时直接把优先级提到最高 |

> 现实案例：火星探路者号（Pathfinder）就因优先级反转反复重启。

## 5. 实时调度

**实时任务的关键不是"快"，而是"不能晚"**——必须在**截止时间**前完成。

| 类型 | 含义 | 例子 |
|------|------|------|
| **硬实时** | 错过截止 = 事故 | 刹车控制、飞控 |
| **软实时** | 错过 = 体验差 | 音视频播放 |

两种经典算法：

| 算法 | 思路 |
|------|------|
| **RMS**（速率单调） | 周期越短 → 优先级越高（**静态**优先级） |
| **EDF**（最早截止优先） | 截止越近 → 优先级越高（**动态**） |

**和普通调度的区别**：普通调度追求公平/吞吐；实时调度追求**可预测性**——能证明"最坏情况也不超时"。

## 6. 要点回顾

1. **RR 时间片怎么权衡**（太小切换多、太大变 FCFS）
2. **SJF 为什么最优 + 什么问题**（理论最优，但会饿死长作业）
3. **多级反馈队列的思路**（短任务优先 + 用完降级）
4. **优先级反转**（说清场景 + 优先级继承）
5. **RMS / EDF**（实时调度的优先级怎么定）
