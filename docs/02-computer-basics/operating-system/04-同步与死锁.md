# 同步与死锁

两个线程各执行 100 万次 `count++`，最后为什么常常不是 200 万？

因为 `count++` 不是一步，而是“读 → 加 → 写”：

```text
T1: load count = 0
T2: load count = 0
T1: store count = 1
T2: store count = 1     ← 丢了一次更新
```

这就是**竞态条件**：结果取决于调度顺序。

## 1. 竞态与临界区

**临界区（Critical Section）**：访问共享资源的那段代码。

经典教材列 4 条：

| 条件 | 含义 |
|------|------|
| **忙则等待**（互斥） | 同一时刻只有一个在临界区 |
| **空闲让进**（前进） | 没人占用时，想进的能进 |
| **有限等待** | 不能把某个进程饿死 |
| **让权等待** | 进不去就**别占着 CPU**（睡眠/释放） |

前三条是**正确性**要求，第四条是**效率**要求——自旋锁就故意违反第四条，用空转换低延迟。

还要分清两个词：

- **互斥**：解决“不能同时”——同一时刻只允许一个执行流进临界区
- **同步**：解决“先后顺序”——A 必须先做完，B 才能开始

互斥锁主要做前者；信号量两者都能做；条件变量负责等待/通知，互斥仍靠它配合的 mutex。

## 2. 同步原语

### 互斥锁（Mutex）

`lock` 拿到才能进，`unlock` 释放。

- 有**所有权**：谁锁的谁解（POSIX 下别的线程解是未定义行为）
- `trylock` 不阻塞，拿不到就返回失败
- 递归锁可重入，但容易掩盖设计问题

### 信号量（Semaphore）

**一个整数 + 两个原子操作**：

```text
P（wait）  ：sem -= 1；若 sem < 0 则阻塞
V（signal）：sem += 1；若 sem <= 0 则唤醒一个等待者
```

| 初值 | 用途 |
|------|------|
| `sem = 1` | 当**互斥锁**用（二值信号量） |
| `sem = N` | 限制“最多 N 个并发”（连接池、限流） |
| 用作**同步** | 生产者等消费者、事件通知 |

**和互斥锁的区别**：

| | 互斥锁 | 信号量 |
|--|--------|--------|
| 所有权 | 有（谁锁谁解） | 无（任何线程都能 V） |
| 初值 | 1 | N |
| 用途 | 互斥 | 互斥 / 限流 / 同步 |
| 优先级继承 | 可支持 | 通常不支持 |
| 递归 | 可有递归锁 | 不适用 |

> 二值信号量能当锁用，但没有所有权，也拿不到优先级继承——不能完全替代 mutex。

### 条件变量（Condition Variable）

等待“某个条件成立”，必须配合 mutex：

```cpp
std::unique_lock<std::mutex> lock(mtx);
cv.wait(lock, [&]{ return !queue.empty(); });   // 释放锁 + 睡；条件成立才返回
```

- `wait` 原子地释放锁并睡眠；被唤醒后重新拿锁，再检查条件
- `notify_one` / `notify_all`
- **用 predicate 重载**（内部就是 `while` 循环）；手写 `cv.wait(lock)` 时要自己放循环里，防**虚假唤醒**
- 改条件要在持锁时做；否则可能**丢失唤醒**（notify 发生在 wait 之前）

### 管程（Monitor）

把“共享数据 + 操作 + 同步”封装成一个整体——Java 的 `synchronized` 就是管程。

C++ 没有语言级管程，只能用 `mutex` + `condition_variable` 模拟。

### futex：Linux 的快速路径

用户态锁在**无竞争**时只做用户态原子操作，不进内核；有竞争才调 `futex(FUTEX_WAIT)` 睡眠，释放时 `FUTEX_WAKE` 唤醒。

所以“加锁”不等于“一定进内核”——这也是 mutex 在无竞争时很便宜的原因。

## 3. 硬件基础：原子指令

软件层的锁，底层靠 CPU 提供的**原子指令**实现。

| 指令 | 干什么 |
|------|--------|
| **TAS**（Test-And-Set） | 读出旧值，并原子地设为 1 |
| **CAS**（Compare-And-Swap） | 若值等于期望值，就原子地换成新值 |

**自旋锁的朴素实现**：

```text
while (TAS(&lock) == 1) { /* 空转 */ }   // 拿不到就一直自旋
// ---- 临界区 ----
lock = 0;                                 // 释放（要有 release 语义）
```

- 自旋**不睡眠、不切上下文** → 适合**临界区极短**、竞争不激烈的场景
- 临界区长 → 空转浪费 CPU，不如 mutex 睡觉
- 内核自旋锁通常还要**关抢占**；单核上纯自旋没有意义（持有者可能被换下去）

**多核前提**：原子指令保证操作不可分割；跨核的可见性和顺序还要靠**缓存一致性**（MESI 等）与**内存屏障**。

- 加锁用 acquire，解锁用 release；`std::atomic` 的默认 `seq_cst` 最保守，通常也最贵
- `volatile` **不是同步**——它只阻止编译器优化，不保证原子性和顺序

## 4. 三个经典模型

### 生产者-消费者

缓冲区满 → 生产者等；空 → 消费者等。

```text
初始：empty = N, full = 0, mutex = 1

生产者：P(empty) → P(mutex) → put → V(mutex) → V(full)
消费者：P(full)  → P(mutex) → get → V(mutex) → V(empty)
```

**顺序不能反**：如果生产者先 `P(mutex)` 再 `P(empty)`，缓冲区满时它会**持锁睡眠**，消费者拿不到锁 → 死锁。消费者同理。

### 读者-写者

| 操作 | 规则 |
|------|------|
| 读 + 读 | ✅ 可并发 |
| 读 + 写、写 + 写 | ❌ 互斥 |

变体：

- **读者优先**：读多写少时吞吐好，但可能**饿死写者**
- **写者优先**：防止写者饿死，但可能**饿死读者**

工程里直接用**读写锁**（`pthread_rwlock` / `std::shared_mutex`），不要自己拿信号量拼。

### 哲学家就餐

5 个人、5 根筷子，每人要拿两根才能吃。

- 朴素做法：每人先拿左再拿右 → 5 人同时拿左 → **循环等待 → 死锁**
- 解法：奇偶策略（奇数先拿右）/ 一次拿两根 / 限制同时吃的人数（仲裁者）

## 5. 死锁

### 四个必要条件（缺一不可）

| # | 条件 | 含义 |
|---|------|------|
| 1 | **互斥** | 资源一次只能一个占 |
| 2 | **持有并等待** | 已经拿了，还等着要别的 |
| 3 | **不可剥夺** | 不能强行抢走 |
| 4 | **循环等待** | 形成等待环（A 等 B，B 等 A） |

> 四条是**必要条件，不是充分条件**：满足四条也不一定真死锁；但破坏任意一条，就一定不会死锁。

### 处理策略

| 策略 | 做法 |
|------|------|
| **预防** | **破坏任一条件**：一次性申请所有资源（破 2）、按序申请（破 4）、可抢占（破 3） |
| **避免** | 运行时判断是否安全 → **银行家算法** |
| **检测 + 恢复** | 允许发生，检测到就回滚/杀进程/抢占资源 |
| 忽略 | 鸵鸟策略（多数通用 OS 的选择） |

“破坏互斥”一般做不到——打印机、写文件这类资源本来就不能同时用。

### 银行家算法（了解思路）

分配资源**之前**先算：

> “假如给它，之后**还存在一个安全序列**（所有进程都能跑完的顺序）吗？”
> 存在 → 分配；不存在 → 让它等。

现实中很少用：要预知每个进程的**最大需求**，开销也大。

### 死锁检测（资源分配图）

**和银行家的区别**：银行家是“**事前避免**”（分配前算安全性）；检测是“**事后判断**”（已经卡住了，找出是谁）。

**资源分配图**：进程和资源画成有向图（进程 → 资源 = 在**请求**；资源 → 进程 = 已**占有**）。

**化简法**：

```text
① 找“能跑完”的进程（它请求的资源都够）→ 让它跑完、释放资源（删掉它的边）
② 重复 ①
③ 所有进程都能删掉 → 无死锁
   剩下删不掉的     → 死锁（互相等）
```

- **单实例**资源：图里有环就是死锁
- **多实例**资源：有环不一定死锁，要靠化简/矩阵检测

### 活锁与饥饿

| | 死锁 | 活锁 | 饥饿 |
|--|------|------|------|
| 状态 | **都不动**（卡死） | **都在动**，但谁也没进展 | 一直轮不到 |
| 原因 | 循环等待 | 互相“让路”，反复重试 | 优先级/调度不公平 |
| 解法 | 破坏条件 / 检测恢复 | 随机退避（如 CSMA/CD） | 老化、公平调度 |

> 活锁例子：两人窄路相遇，都往同一边让，又同时换另一边——来回僵持。

## 6. 工程规则与边界

- **固定加锁顺序**：所有线程都按同一顺序拿多把锁，破循环等待
- **临界区尽量短**：锁里不要做 IO、不要调用未知代码（可能再拿锁）
- **用 RAII**：`lock_guard` / `unique_lock`；多把锁用 `std::scoped_lock`（C++17）一次性锁，避免手写顺序死锁
- **锁不是免费**：竞争会带来上下文切换、cache line 争用，甚至优先级反转
- **伪共享**：不同线程写同一 cache line 里的不同变量，也会互相拖慢
- **lock-free 不等于 wait-free**：CAS 循环可能一直失败；ABA、内存回收是另一层问题
- 怀疑并发 bug 时先上 **ThreadSanitizer**，比盯着代码猜有效

## 7. 要点回顾

1. **竞态与临界区**：`count++` 的丢更新；四条条件里前三条是正确性、第四条是效率
2. **互斥 vs 同步**：一个管“不能同时”，一个管“先后顺序”
3. **mutex vs 信号量**：所有权、初值、用途、优先级继承；P/V 的语义
4. **条件变量**：predicate、虚假唤醒、丢失唤醒；改条件要持锁
5. **原子指令**：TAS/CAS、自旋锁、acquire/release；`volatile` 不是同步
6. **经典模型**：生产者-消费者的 P 顺序、读者-写者、哲学家
7. **死锁**：四条件（必要不充分）、预防/避免/检测、银行家安全序列、单实例 vs 多实例
8. **活锁/饥饿**：都在动 vs 一直轮不到；随机退避、老化
9. **工程规则**：固定锁序、短临界区、RAII/`scoped_lock`、TSan
