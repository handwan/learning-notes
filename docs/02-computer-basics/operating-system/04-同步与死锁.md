# 同步与死锁

## 1. 为什么需要同步

多个执行流共享资源时，并发访问会产生**竞态条件**（结果取决于调度顺序，每次不一样）。

**临界区（Critical Section）**：访问共享资源的那段代码。

**临界区条件**（国内教材常列 4 条）：

| 条件 | 含义 |
|------|------|
| **忙则等待**（互斥） | 同一时刻只有一个在临界区 |
| **空闲让进**（前进） | 没人占用时，想进的能进 |
| **有限等待** | 不能把某个进程饿死 |
| **让权等待** | 进不去就**别占着 CPU**（睡眠/释放） |

## 2. 同步原语

### 互斥锁（Mutex）

最简单的：`lock` 拿到才能进，`unlock` 释放。

### 信号量（Semaphore）

**一个整数 + 两个原子操作**：

```
P（wait）  ：sem -= 1；若 sem < 0 则阻塞
V（signal）：sem += 1；若 sem <= 0 则唤醒一个等待者
```

| 初值 | 用途 |
|------|------|
| `sem = 1` | 当**互斥锁**用 |
| `sem = N` | 限制"最多 N 个并发"（如连接池） |
| 用作**同步** | 生产者等消费者（见下） |

### 条件变量

等待"某条件成立"，配合 mutex 用：

```cpp
std::unique_lock lock(mtx);
cv.wait(lock, []{ return !queue.empty(); });   // 释放锁 + 睡；条件成立才醒
```

- `wait` / `notify_one` / `notify_all`
- **必须放循环里判断条件**（防止**虚假唤醒**）

### 管程（Monitor）

把"共享数据 + 操作 + 同步"封装成一个整体——Java 的 `synchronized`、C++ 的 mutex+condvar 组合。

## 3. 硬件基础：原子指令

软件层的锁，底层靠 CPU 提供的**原子指令**实现。

| 指令 | 干什么 |
|------|--------|
| **TAS**（Test-And-Set） | 读出旧值，并原子地设为 1 |
| **CAS**（Compare-And-Swap） | 若值等于期望值，就原子地换成新值 |

**自旋锁的朴素实现**：

```
while (TAS(&lock) == 1) { /* 空转 */ }   // 拿不到就一直自旋
// ---- 临界区 ----
lock = 0;                                 // 释放
```

- 自旋**不睡眠、不切上下文** → 适合**临界区极短**的场景
- 临界区长 → 空转让出 CPU，还不如 mutex 睡觉

**多核前提**：原子指令要靠**缓存一致性协议**（如 MESI）配合，并涉及**内存序**问题。

## 4. 三个经典模型

### 生产者-消费者

```
缓冲区满 → 生产者等；空 → 消费者等
```

- 两个信号量：`empty`（空位数）、`full`（已有数）
- 一个互斥锁：保护缓冲区本身

### 读者-写者

| 操作 | 规则 |
|------|------|
| 读 + 读 | ✅ 可并发 |
| 读 + 写、写 + 写 | ❌ 互斥 |

变体：**读者优先** / **写者优先**（防写者饿死）

### 哲学家就餐

5 个人、5 根筷子，每人要拿两根才能吃。

- 朴素做法：每人先拿左再拿右 → 5 人同时拿左 → **循环等待 → 死锁**
- 解法：奇偶策略（一个先拿右）/ 一次拿两根 / 限制同时吃的人数

## 5. 死锁

### 四个必要条件（缺一不可）

| # | 条件 | 含义 |
|---|------|------|
| 1 | **互斥** | 资源一次只能一个占 |
| 2 | **持有并等待** | 已经拿了，还等着要别的 |
| 3 | **不可剥夺** | 不能强行抢走 |
| 4 | **循环等待** | 形成等待环（A 等 B，B 等 A） |

### 处理策略

| 策略 | 做法 |
|------|------|
| **预防** | **破坏任一条件**：一次性申请所有资源（破 2）、按序申请（破 4）、可抢占（破 3） |
| **避免** | 运行时判断是否安全 → **银行家算法** |
| **检测 + 恢复** | 允许发生，检测到就回滚/杀进程 |
| 忽略 | 鸵鸟策略（多数通用 OS 的选择） |

### 银行家算法（了解思路）

分配资源**之前**先算：

> "假如给它，之后**还存在一个安全序列**（所有进程都能跑完的顺序）吗？"
> 存在 → 分配；不存在 → 让它等。

现实中很少用：要预知每个进程的**最大需求**，开销也大。

### 死锁检测（资源分配图）

**和银行家的区别**：银行家是"**事前避免**"（分配前算安全性）；检测是"**事后判断**"（已经卡住了，找出是谁）。

**资源分配图**：进程和资源画成有向图（进程 → 资源 = 在**请求**；资源 → 进程 = 已**占有**）。

**化简法**：

```text
① 找"能跑完"的进程（它请求的资源都够）→ 让它跑完、释放资源（删掉它的边）
② 重复 ①
③ 所有进程都能删掉 → 无死锁
   剩下删不掉的     → 死锁（互相等）
```

### 活锁（Livelock）

| | 死锁 | 活锁 |
|--|------|------|
| 状态 | **都不动**（卡死） | **都在动**，但谁也没进展 |
| 原因 | 循环等待 | 互相"让路"，反复重试 |

> 例子：两人窄路相遇，都往同一边让，又同时换另一边——来回僵持。
> 解法：让"重试"带上**随机退避**（如以太网 CSMA/CD）。
