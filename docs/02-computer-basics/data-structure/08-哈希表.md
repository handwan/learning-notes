# 哈希表

哈希表把"查找"从 O(log n) 变成**平均 O(1)**——两个核心问题：**哈希函数好不好**、**冲突怎么处理**。

> 本篇全部为**手写实现**。

## 1. 目标与结构

**目标**：key → 位置，直接算出来（不像树那样一路比较）。

```
哈希表 = 桶数组 + 哈希函数 + 冲突处理
  位置 = hash(key) % 桶数
```

两个问题必须解决：

1. **哈希函数**：不同 key 尽量落到不同桶（均匀、雪崩）
2. **冲突**：落到同一个桶怎么办（链式 / 开放寻址）

## 2. 哈希函数：低位参与很重要

**好哈希的性质**：1 位输入变化引起一半输出位变化（雪崩）；高位低位都参与。

**实测（低位全 0 的 key，`i * 4096`，取模后只落在 16 个桶）**：

| 哈希 | 平均探测次数 |
|------|:---:|
| 恒等哈希 + 取模（坏） | **624.5 次** |
| 乘法混合（`k * 0x9E3779B97F4A7C15` 取高位） | **0.000 次** |

**工程教训**：

- 直接用 `% 桶数` 很危险（桶数常是 2 的幂，只看低位）
- 好做法：先**乘法混合**（Fibonacci/xxHash/splitmix64 风格）再取模
- **自定义 key 一定要自己写好哈希**（别把各字段简单相加）

## 3. 冲突处理：链式 vs 开放寻址

| | 链式（拉链） | 开放寻址（线性探测） |
|--|------------|-------------------|
| 结构 | 每桶一条链 | 冲突就找下一个空槽 |
| 实测（100 万 insert+find） | 慢 | **快 6 倍多**（2 倍空间） |
| 缓存友好度 | 差（指针跳） | 好（连续探测） |
| 负载因子容忍 | 可以 >1 | 必须 <1（否则找不到空槽） |
| 删除 | 简单 | 麻烦（要墓碑标记） |

**开放寻址为什么快 6 倍多**：探测在**同一块连续内存**里走，cache line 复用率高；链式每插一个 key 都要 `new` 一个节点（还跳指针）。

**线性探测的"聚集"问题**：冲突后一路占下去，形成长簇；改进用**二次探测**或**双散列**（步长也哈希出来）。

**两种都手写一遍**：

```cpp
/* ① 链式：桶数组 + 节点链 */
struct HEntry { int key, val; HEntry* next; HEntry(int k, int v, HEntry* n) : key(k), val(v), next(n) {} };
struct HashMap {
    HEntry** buckets; int nb, n;
    explicit HashMap(int nb_ = 8) : buckets(new HEntry*[nb_]), nb(nb_), n(0) {
        for (int i = 0; i < nb; ++i) buckets[i] = nullptr;
    }
    ~HashMap() {
        for (int i = 0; i < nb; ++i) { HEntry* e = buckets[i];
            while (e) { HEntry* nx = e->next; delete e; e = nx; } }
        delete[] buckets;
    }
    static unsigned hash(int k) { return (unsigned)k * 2654435761u; }   // 乘法混合
    void rehash() {                                  // 桶数翻倍，所有节点重挂
        int nb2 = nb * 2; HEntry** b2 = new HEntry*[nb2];
        for (int i = 0; i < nb2; ++i) b2[i] = nullptr;
        for (int i = 0; i < nb; ++i) for (HEntry* e = buckets[i]; e;) {
            HEntry* nx = e->next; int j = hash(e->key) % nb2;
            e->next = b2[j]; b2[j] = e; e = nx;
        }
        delete[] buckets; buckets = b2; nb = nb2;
    }
    void put(int k, int v) {
        if (n >= nb) rehash();                       // 负载因子到 1 就扩
        int i = hash(k) % nb;
        for (HEntry* e = buckets[i]; e; e = e->next) if (e->key == k) { e->val = v; return; }
        buckets[i] = new HEntry(k, v, buckets[i]); ++n;   // 头插进桶
    }
    int* get(int k) {
        for (HEntry* e = buckets[hash(k) % nb]; e; e = e->next) if (e->key == k) return &e->val;
        return nullptr;
    }
};
// 实测：插 100 万 key（多次 rehash），全部可查

/* ② 开放寻址：键/值/状态三个数组，状态 0 空 / 1 占用 / 2 墓碑 */
struct OpenMap {
    int *keys, *vals; char* st; int cap, n;
    explicit OpenMap(int c) : keys(new int[c]), vals(new int[c]), st(new char[c]()), cap(c), n(0) {}
    ~OpenMap() { delete[] keys; delete[] vals; delete[] st; }
    void put(int key, int val) {
        int i = HashMap::hash(key) % cap, tomb = -1;
        while (st[i]) {                              // 找到空槽或找到 key
            if (st[i] == 1 && keys[i] == key) { vals[i] = val; return; }
            if (st[i] == 2 && tomb < 0) tomb = i;    // 记下第一个墓碑（可复用）
            i = (i + 1) % cap;
        }
        int at = tomb >= 0 ? tomb : i;
        keys[at] = key; vals[at] = val; st[at] = 1; ++n;
    }
    int* get(int key) {
        int i = HashMap::hash(key) % cap;
        while (st[i]) {                              // 碰到空槽才停（墓碑要继续）
            if (st[i] == 1 && keys[i] == key) return &vals[i];
            i = (i + 1) % cap;
        }
        return nullptr;
    }
    bool erase(int key) {
        int i = HashMap::hash(key) % cap;
        while (st[i]) {
            if (st[i] == 1 && keys[i] == key) { st[i] = 2; return true; }   // 只能标墓碑
            i = (i + 1) % cap;
        }
        return false;
    }
};
// 实测：删除 7、8 后，7/8 查不到、9 依然能查到（墓碑不截断探测链）
```

**关键点**（都体现在代码里）：

- rehash 要**遍历旧桶数组、逐个重挂**（不能只拷贝桶指针——新桶数不同，位置全变）
- 遍历链时用 `E* e = b_[i]`，**别用引用 `E*& e`**——否则走链过程中会把桶指针改掉（丢链）
- 开放寻址的**删除必须留墓碑**：直接置空会截断后面探测链（那些"越过它放"的元素就找不到了）
- 墓碑多了会拖慢性能 → 定期**原地重哈希**（把墓碑清掉）

## 4. 负载因子与 rehash

**负载因子 = 元素数 / 桶数**：

- 开放寻址：> 0.7 后探测次数爆炸（0.9 时平均探测 ~50 次）→ 一般 0.5~0.7 就该扩容
- 链式：容忍更高（1.0 也行），但查找退化成扫链

**rehash 的代价**：扩容后**所有元素都要重新算位置**——实测（手写）：

```
20 万个 key 插入：
  从 8 桶开始逐步扩（多次 rehash）：基准
  一开始就分配 26 万桶：略快（差距不大）
```

差得不多，因为 rehash 是**均摊**的（总重挂量 ≈ 2n）——但**已知规模时先分配好**仍然更稳（也省内存碎片）。

**桶数怎么取**：2 的幂取模快（`& (n-1)`），但要配合好哈希；否则用质数桶数减少聚集。

## 5. 自定义哈希表的实现要点

1. **哈希质量第一**（§2 的 624 次 vs 0 次就是教训）
2. **冲突策略看场景**：追求速度用开放寻址（实测 6.6 倍），删除频繁/负载高用链式
3. **扩容时机**：链式 0.75~1.0；开放寻址 0.5~0.7
4. **节点分配是链式的最大开销**：可以自己管理节点池（一次 malloc 一大块）——就像索引/对象池的思路
5. **键要不可变**：改了 key，哈希变、位置变，就找不到了

## 6. 哈希表的边界：不有序

哈希表**不保证任何顺序**（跟插入顺序也无关）——这些需求它做不了：

| 需求 | 该用的结构 |
|------|-----------|
| 有序遍历、范围查询（≥ x 的最小 key） | 平衡树 / 跳表（见树与堆、工程结构篇） |
| 前缀查找、自动补全 | Trie |
| 每次拿最值 | 堆 |

**选择**：纯查找 → 哈希表；**只要带"有序/范围"→ 树或跳表**。

## 7. 工程要点

- **哈希 DoS**：攻击者构造一堆同桶 key → 查找退化成 O(n)。服务端用**带随机种子的哈希**（SipHash 之类），别用固定哈希函数对外
- 性能敏感场景：自己写**开放寻址**的表（实测快 6.6 倍），或用成熟的开放寻址实现（absl/folly 风格）
- 哈希表不是"银弹"：范围、有序、前缀都不行（§6）

## 8. 要点回顾

1. **位置 = 哈希 + 取模**：哈希质量决定一切——恒等取模平均探测几百次，乘法混合基本一次命中（实测）
2. **冲突两大流派**：链式（简单、能高负载）vs 开放寻址（缓存友好、实测快 6 倍多、删除麻烦要墓碑）
3. **负载因子**：开放寻址 >0.7 就危险；扩容要 rehash 全部元素（均摊 ≈ 2n；预分配略快）
4. **手写要点**：rehash 逐个重挂、走链别用指针引用、墓碑不能省、节点池省分配
5. **要有序/范围 → 树/跳表**；前缀 → Trie；纯查找 → 哈希
6. **别把 key 各字段相加**当哈希；自定义 key 必须写好 hash；键不可变
7. **哈希 DoS 要防**：对外服务用带随机种子的哈希
