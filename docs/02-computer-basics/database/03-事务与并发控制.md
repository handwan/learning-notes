# 事务与并发控制

事务保证"要么全做、要么全不做"；并发控制解决"多个人同时改"——核心概念是 **ACID、隔离级别、MVCC**。

> 示例基于 PostgreSQL 16（两个会话交错执行）；MySQL/SQLite 的差异在每节标注。

## 1. 事务与 ACID

**事务** = 一组要么全成功、要么全撤销的操作。

| 特性 | 含义 | 靠什么实现 |
|------|------|-----------|
| **A** 原子性 | 全做或全不做 | undo/回滚段 |
| **C** 一致性 | 事务前后数据满足约束 | 约束 + 应用逻辑 + 其他三个特性 |
| **I** 隔离性 | 并发事务互不干扰（按级别） | 锁 + MVCC |
| **D** 持久性 | 提交后不丢 | WAL（先写日志再写数据） |

```sql
BEGIN;                              -- 开始事务
UPDATE emp SET salary = salary + 1000 WHERE id = 1;
SAVEPOINT s1;                       -- 保存点
UPDATE emp SET salary = 0 WHERE id = 2;
ROLLBACK TO s1;                     -- 回滚到保存点（id=2 的改动撤销）
COMMIT;                             -- 提交（id=1 的改动生效）
-- 或 ROLLBACK; 整体撤销
```

**要点**：

- **事务要短**：长事务会占锁、拖慢 VACUUM/undo 回收（见 §9）
- DDL（建表/改表）各家行为不同：PG 支持事务里 DDL，MySQL 8.0 的 DDL 是隐式提交（不能回滚）

## 2. 并发异常（四种）

| 异常 | 场景 | 一句话 |
|------|------|--------|
| **脏读** | 读到别人**未提交**的修改 | 别人回滚了，你读的是"幻觉数据" |
| **不可重复读** | 同一事务里，两次读**同一行**结果不同 | 别人在你两次读之间改了并提交 |
| **幻读** | 同一事务里，两次**范围查询**行数不同 | 别人在你两次查之间插入了新行 |
| **丢失更新** | 两人都"读-改-写"，后写的覆盖先写的 | 典型：`balance = 读到的值 + 100` |

```
丢失更新的例子（两个会话）
A: 读 balance = 100
B: 读 balance = 100
A: 写 balance = 100 + 50 = 150   （提交）
B: 写 balance = 100 + 30 = 130   （提交）→ A 的 +50 丢了！
```

## 3. 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|------|:---:|:---:|:---:|------|
| READ UNCOMMITTED | ✅ 可能 | ✅ | ✅ | 基本没人用 |
| READ COMMITTED | ❌ | ✅ 可能 | ✅ 可能 | **PG / Oracle / SQL Server 默认** |
| REPEATABLE READ | ❌ | ❌ | 🔸 标准允许，InnoDB 实际避免 | **MySQL InnoDB 默认** |
| SERIALIZABLE | ❌ | ❌ | ❌ | 最强；冲突时报错重试 |

**各库默认级别**：

| 数据库 | 默认 |
|--------|------|
| PostgreSQL | **READ COMMITTED** |
| MySQL (InnoDB) | **REPEATABLE READ** |
| SQLite | SERIALIZABLE（单写者，天然串行） |

**怎么设置**：

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;   -- 只影响当前事务
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- 整个会话
SHOW default_transaction_isolation;      -- 看默认（PG: read committed）
```

## 4. MVCC：读不阻塞写

**MVCC（多版本并发控制）**：写时不覆盖旧数据，而是**产生新版本**；读时按自己的"快照"选一个可见版本——所以**读不阻塞写、写不阻塞读**。

| | PostgreSQL | MySQL (InnoDB) |
|--|-----------|----------------|
| 旧版本存哪 | **表内**（每行有 `xmin`/`xmax` 事务号，VACUUM 清理死行） | **undo log**（回滚段里，purge 线程清理） |
| 快照 | 事务开始/语句开始时的"可见事务集合" | Read View（活跃事务列表） |
| 行头信息 | 直接在行上（`xmin`/`xmax`） | 隐藏列（`DB_TRX_ID`/`DB_ROLL_PTR`） |

**"快照读" vs "当前读"**：

- 普通 `SELECT` = **快照读**（读 MVCC 版本，不加锁）
- `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` = **当前读**（读最新版本 + 加行锁）

**为什么你删了数据，表还这么大**：旧版本要等 VACUUM（PG）/ purge（InnoDB）清理——**长事务会挡住清理**，导致表膨胀。

## 5. 隔离级别的真实行为（PG 实测）

**① READ COMMITTED：不可重复读会出现**

```
会话 A（RC）                          会话 B
BEGIN;
SELECT balance → 100
                                      BEGIN; UPDATE ... SET balance=200; COMMIT;
SELECT balance → 200   ← 变了！（RC 下每次语句都取新快照）
```

**② READ COMMITTED：不会脏读**

```
会话 A（RC）                          会话 B
BEGIN;
SELECT balance → 100
                                      BEGIN; UPDATE ... SET balance=999;（不提交）
SELECT balance → 100   ← 还是旧值（读不到未提交数据）
                                      ROLLBACK;
```

**③ REPEATABLE READ：一致性快照（同一事务里读到的都一样）**

```
会话 A（RR）                          会话 B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance → 100
                                      UPDATE ... SET balance=200; COMMIT;
SELECT balance → 100   ← 没变（快照固定在事务开始）
```

**④ REPEATABLE READ：写冲突会报错**（不是静默覆盖，这是 PG 比 MySQL 严格的地方）

```
                                     UPDATE ... SET balance=200; COMMIT;
SELECT ... FOR UPDATE / UPDATE → ERROR: could not serialize access due to concurrent update
```

**⑤ SERIALIZABLE：写偏斜（write skew）也能检测**

```
经典场景：两个医生值班，要求"至少一人值班"
A: 查到现在有 2 人值班 → 认为可以走 → 把自己的值班取消
B: 查到现在有 2 人值班 → 认为可以走 → 把自己的值班取消
结果：没人值班（各自看的数据都对，合起来违反约束）
→ PG SERIALIZABLE 会让其中一个事务失败：could not serialize access...
```

**结论**：**应用要准备好"重试"**——串行化隔离级别下，事务可能因为冲突被终止（这不是错误，是设计）；捕获 `40001`（serialization_failure）/ `40P01`（deadlock_detected）后重试即可。

## 6. 锁

| 锁 | 加在哪 | 场景 |
|----|--------|------|
| 行级锁（`FOR UPDATE`） | 具体行 | "读-改-写"防丢失更新 |
| 行级锁（`FOR SHARE`） | 具体行 | 只读但要防止别人改 |
| 表级锁（`LOCK TABLE`） | 整表 | 批量操作（如大批量导入） |
| 意向锁 / 元数据锁 | 内部 | DDL 与 DML 互斥 |

```sql
-- 显式锁：把"读-改-写"变成原子的（防止丢失更新）
BEGIN;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;   -- 锁住这一行（别人要改得等）
UPDATE account SET balance = balance + 50 WHERE id = 1;
COMMIT;                                                -- 锁释放
```

**要点**：

- 普通 `SELECT` **不加锁**（靠 MVCC）——所以"两个事务都读了旧值再写"会丢更新
- `FOR UPDATE` 后，别人对同一行的写会**阻塞**（等到锁释放），而不是报错
- **两段锁（2PL）**：事务先只加锁、后只解锁——是保证可串行化的经典协议
- 行锁是**加在索引上**的：如果 `WHERE` 没走索引，可能锁很多行甚至全表（MySQL 尤为明显）

## 7. 死锁

**成因**：两个事务互相等对方持有的锁。

```
A: UPDATE row1 （持有 row1 锁）
B: UPDATE row2 （持有 row2 锁）
A: UPDATE row2 → 等 B
B: UPDATE row1 → 等 A       → 死锁
```

**数据库会检测并处理**：PG/InnoDB 都有死锁检测，**主动杀掉其中一个事务**并报错：

```
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 67890; blocked by process 54321.
```

**避免死锁**：

1. **统一加锁顺序**（所有事务都按"先小 id 后大 id"）
2. **事务小、快**（减少持锁时间）
3. 需要多行锁时一次锁完（`SELECT ... FOR UPDATE` 一次查出来，别一条条锁）
4. 设置锁等待超时（`SET lock_timeout = '3s'`）避免无限等
5. 死锁报错后**重试**（应用层的标准做法）

## 8. 长事务的危害

| 危害 | 说明 |
|------|------|
| 挡住 MVCC 清理 | PG 的 VACUUM 不能清理"老事务还能看到"的死行 → **表膨胀**；InnoDB 的 undo 不能 purge → 回滚段变大 |
| 占锁 | 别人等锁，连锁反应 |
| 复制延迟 | 长事务提交前，从库看不到它的改动；若开启 `hot_standby_feedback`，还会拖住主库的 VACUUM |
| 事务号回卷（PG） | 极端情况下会导致数据库停机保护（PG 会提前告警） |

**排查**：

```sql
-- PG：看运行超过 5 分钟的事务
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL AND now() - xact_start > interval '5 minutes'
ORDER BY duration DESC;
```

**实践**：事务里**不要**做网络请求/等用户输入/大批量计算；`BEGIN` 了就要尽快 `COMMIT`/`ROLLBACK`。

## 9. 要点回顾

1. **ACID**：原子性（undo）/ 隔离性（锁+MVCC）/ 持久性（WAL）；DDL 在 MySQL 里是隐式提交
2. **四种并发异常**：脏读 / 不可重复读 / 幻读 / **丢失更新**；隔离级别就是用锁和快照把它们逐个挡掉
3. **默认级别**：PG/Oracle = RC；**InnoDB = RR**（实际还避免了幻读）；SQLite = 串行
4. **MVCC 让读不阻塞写**：PG 旧版本在表内（VACUUM 清理）、InnoDB 在 undo（purge 清理）
5. **RC 不可重复读**、**RR 一致性快照**、**RR/SERIALIZABLE 写冲突会报错**（40001）→ **应用要重试**
6. **`SELECT` 是快照读不加锁**；要防丢失更新用 `SELECT ... FOR UPDATE`（当前读 + 行锁）
7. **死锁**：统一加锁顺序 + 小事务 + 超时 + 重试；数据库会自动检测并杀一个
8. **长事务**是万恶之源：挡 VACUUM/purge → 膨胀；事务里别做慢操作
