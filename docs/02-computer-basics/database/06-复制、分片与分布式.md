# 复制、分片与分布式

单机扛不住之后：**复制**（同一份数据多副本）、**分片**（不同数据分开存）、**分布式事务**（跨节点一致性）。

> 示例基于 PostgreSQL 16 双实例（5432 + 5433）；MySQL/SQLite 差异标注在各节。

## 1. 复制解决的四个问题

| 目的 | 说明 |
|------|------|
| 高可用 | 主库挂了从库顶上（failover） |
| 读扩展 | 主写从读，读流量分摊 |
| 容灾 | 异地副本 |
| 备份/迁移 | 在从库上做备份、迁移不停机 |

复制有两个维度：**物理 vs 逻辑**（复制什么）、**异步 vs 同步**（提交等不等）。

## 2. 物理流复制：WAL 发过去重放

原理：从库像"**实时崩溃恢复**"——主库持续发 WAL，从库持续重放（和前一章的恢复机制同源）。

搭建要素：

| 主库 | 从库 |
|------|------|
| `wal_level = replica`（逻辑复制要 `logical`） | `pg_basebackup` 打底 |
| `max_wal_senders > 0` | `standby.signal` 标记 |
| 有 `REPLICATION` 权限的角色 | `primary_conninfo`（连接主库） |
| `pg_hba.conf` 允许复制连接 | `hot_standby = on`（默认） |
| **replication slot**（推荐） | — |

**slot 的作用**：记住从库消费到哪，从库断线时**主库帮你保留 WAL**（不会被回收）；代价是忘了删 slot 会一直堆 WAL，**撑爆磁盘**。

实测（两实例）：

- 主库写 100 行，从库 **0.011 秒**后读到（`pg_is_in_recovery() = t`）
- 从库**只读**：写会报 `cannot execute INSERT in a read-only transaction`
- 从库提升后 `pg_is_in_recovery() = f`，可以写

**怎么监控**：

| 看哪 | 命令 | 说明 |
|------|------|------|
| 主库 | `pg_stat_replication` | `sent_lsn` / `replay_lsn` / `sync_state` |
| 从库 | `pg_last_wal_replay_lsn()` | 已重放到哪个位置 |
| 从库 | `now() - pg_last_xact_replay_timestamp()` | 延迟秒数 |

实测注意：**普通用户看 `pg_stat_replication` 只有一列名字**（PG 16 权限限制，字段全空）——要 `pg_read_all_stats` 或超级用户。

**制造延迟看效果**（实测）：从库 `pg_wal_replay_pause()` → 主库写入后 lsn 领先 **12944 字节**、从库看不到新行 → `pg_wal_replay_resume()` 后 **0.06 秒**追平。

## 3. 异步 vs 同步复制

- **异步**（默认）：提交不等从库 → 快；主库崩可能丢最后几条
- **同步**：`synchronous_standby_names` 指定从库 → 不丢；提交要等多一个来回

实测：

| 模式 | 每次提交延迟 |
|------|:---:|
| 异步 | 基准（不等从库） |
| 同步 | **约慢 1 倍**（要多一个来回；跨机房更大） |

写法（都实测生效）：单从库可用 `'*'`，或**把名字加引号** `'"16/replica"'`（名字 = `application_name`/`cluster_name`；含特殊字符必须加引号）。

两个注意点：

- 同步 = 等从库**刷到盘**才算提交成功（`synchronous_commit` 可用 `remote_write` 等档位放松）
- **从库全挂了，同步提交会一直等**（不是超时失败）——生产上要设计降级

## 4. 逻辑复制：行级变更流

**物理复制是整集群的字节流，逻辑复制是"行级变更"**：发布端（publication）→ 订阅端（subscription），用 `pgoutput` 协议传输（日志里可见 `proto_version '4'`）。

实测：

- 发布端插 50 行 → 订阅端 **0.004 秒**收到；更新同步
- 订阅端本地写入**不会**传回发布端（**单向**）
- 发布端 `pg_replication_slots` 有逻辑 slot（`plugin=pgoutput`、`active=t`）；订阅端 `pg_stat_subscription` 可见
- 逻辑复制连接**也会出现在主库的 `pg_stat_replication` 里**（名字是订阅名）

| | 物理流复制 | 逻辑复制 |
|--|-----------|---------|
| 单位 | WAL 字节流（整个集群） | 行级变更 |
| 版本 | **必须相同大版本** | 可跨版本 |
| 粒度 | 全部库/表 | **可选表**（`FOR TABLE`） |
| 方向 | 单向 | 单向（双向要自己处理冲突） |
| 典型 | 高可用、读扩展 | 迁移、部分同步、多主 |

## 5. 故障切换（failover）

实测手动切换：

```
pg_ctlcluster 16 replica promote
→ 日志: "received promote request" / "redo done"
→ 从库变可写（pg_is_in_recovery() = f），原主库的复制连接消失
```

自动切换用 **Patroni / repmgr** 等；核心是**避免脑裂**（两个节点都以为自己该当主）：需要 quorum/见证节点。

切完还有收尾工作：**旧主库重新加入**（不能直接回退成从库，要做 rewind 或重建）、应用连接地址切换（VIP/DNS/中间件）。

## 6. 读写分离的坑：复制延迟

主写从读分摊了读流量，但异步复制有延迟——**"写完立刻读"可能读不到刚写的数据**（用户的经典反馈："我的修改不见了"）。

实测延迟近实时，网络 + 负载下会到秒级。

解法（按可靠性排序）：

1. **关键读走主库**：写之后的读（或用户的"我的数据"）强制打到主库
2. **等待追上**：记住主库当时的 LSN，轮询从库 `pg_last_wal_replay_lsn() >= 目标 LSN` 再读
3. 非关键路径接受**最终一致**

## 7. 分片：把数据切开

- **垂直分片**：按表/业务拆库（用户库、订单库）
- **水平分片**：按**分片键**把行散到多节点（hash / range）

实测（两个节点当两个分片，应用层路由 `id % 2`）：

- 写 10 个用户 → 两片各 5 行
- 按 `id` 查 → 路由到对应分片，单节点查询
- **跨片聚合**：SQL 做不到 → 扇出到两个节点再合并
- **跨片 JOIN**：同理做不了 → 冗余维表 / 应用层拼接 / 中间件（Citus、ShardingSphere）

**分片键怎么选**：高基数、查询条件里总带着它（否则每次都要扇出）；选不好就出**热点**——比如按日期分片，今天的片会被写爆。

**扩容**：用预分片/一致性哈希，避免"`id % N` 一改 N 就要全量搬迁"。

## 8. 分布式事务

跨节点要原子提交（扣库存 + 扣款不能只成功一半）——**两阶段提交（2PC）**：prepare（各节点做好准备、但未提交）→ commit/rollback。

实测（PG 的 `PREPARE TRANSACTION`，跨两节点）：

```sql
BEGIN; INSERT ...; PREPARE TRANSACTION 'xa1';   -- 阶段一
COMMIT PREPARED 'xa1';                          -- 阶段二（或 ROLLBACK PREPARED）
```

- 两边 PREPARE 后：`pg_prepared_xacts` 有记录，**数据对任何人不可见**
- 两边都 COMMIT PREPARED：数据可见；ROLLBACK PREPARED 则一直不可见

**2PC 的代价**：

- **悬挂事务**：prepare 之后协调者挂了 → 锁和行版本一直挂着、挡 VACUUM
- 同步阻塞、协调者是单点

现代系统多用**最终一致**替代：TCC（预留/确认/取消）、Saga（补偿事务）、本地消息表、事务消息。

底层取舍就是 **CAP**：网络分区发生时，一致性和可用性只能保一个；工程上用 **BASE**（基本可用、软状态、最终一致）换可用性。

## 9. 要点回顾

1. **物理流复制 = 持续重放 WAL**：basebackup 打底 + `standby.signal` + `primary_conninfo` + slot；实测从库只读、近实时可见
2. **监控**：主库 `pg_stat_replication`（sent/replay/sync_state），从库 `pg_last_wal_replay_lsn()` 与 `pg_last_xact_replay_timestamp()`；普通用户看不到主库视图字段
3. **异步快、同步稳**：同步提交要多一个来回（约慢 1 倍）；从库全挂时同步提交会一直等；slot 不清理会撑爆 WAL 磁盘
4. **逻辑复制**：行级、可选表、可跨版本、单向；物理复制是整集群字节流、要求同大版本
5. **failover**：`promote` 把从库变主（实测）；自动化要 quorum 防脑裂；旧主要 rewind/重建才能回归
6. **读写分离**要防"写完读不到"：关键读走主、等 LSN、或接受最终一致
7. **分片**：垂直按业务、水平按分片键；单键能路由、跨片只能扇出合并、跨片 JOIN 靠中间件；分片键决定热点与扩容难度
8. **2PC** 能跨节点原子提交（PREPARE → COMMIT/ROLLBACK，实测），代价是悬挂事务与阻塞；现代多用 Saga/TCC + 最终一致；CAP 是底层原因
