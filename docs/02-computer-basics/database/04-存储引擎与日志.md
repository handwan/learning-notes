# 存储引擎与日志

数据怎么落在磁盘上、更新怎么保证不丢：**页 → B+ 树/LSM → 缓冲池 → WAL**。

> 示例基于 PostgreSQL 16（含 `pageinspect`/`pg_buffercache`/`pgstatindex`）；MySQL/SQLite 差异标注在各节。

## 1. 存储单位是"页"

数据库不按"行"读写磁盘，而是按**页**（page/block）：

| | 页大小 | 说明 |
|--|:---:|------|
| PostgreSQL | **8 KB**（实测 `SHOW block_size`） | 可编译期调整 |
| MySQL InnoDB | 16 KB | `innodb_page_size` |
| SQLite | 4 KB（默认，=(OS 块)） | `PRAGMA page_size` |

**为什么按页**：磁盘/SSD 也是按块（4KB）读写，一次 IO 就是一页——顺手把"一次读上来的数据"缓存复用（局部性）。行的大小差异很大（几十字节到几 KB），但**访问单位统一是页**。

## 2. 行怎么存：堆表 vs 聚簇

**Heap（堆表，PG）**：行**不按顺序**放在页里，用物理地址定位：

```sql
SELECT ctid, * FROM emp;      -- ctid = (页号, 页内编号)，就是"行指针"
```

**聚簇索引（InnoDB）**：**按主键排序存放整行**（主键即数据），二级索引叶子存主键 → 查二级索引要**回表**。

> SQLite 两种都不是：每张表本身就是一棵按 **rowid** 排序的 B 树（rowid 隐式自增），性质更接近聚簇。

| | Heap（PG） | 聚簇（InnoDB） |
|--|-----------|---------------|
| 行的位置 | 与主键无关 | 按主键排序 |
| 主键查询 | 索引 → ctid → 取行 | 直接在叶子拿到整行 |
| 二级索引查询 | 索引 → ctid → 取行 | 索引 → 主键 → 再查主键树（**两次树查找**） |
| 插入 | 随便找有空位的页 | 必须插到主键位置（可能**页分裂**） |

**UPDATE 不是原地改**（MVCC）：旧版本保留、写入新版本——所以更新后 `ctid` 会变，旧 ctid 指向"死行"（等 VACUUM 清理）。

```sql
-- 实测：更新前后 ctid 变化（PG 16，p4 表）
SELECT ctid, v FROM p4 WHERE id = 5;    -- (0,5)  5
UPDATE p4 SET v = 999 WHERE id = 5;
SELECT ctid, v FROM p4 WHERE id = 5;    -- (4,97) 999 ← 新版本，甚至换了页
```

## 3. 页里面长什么样

**页内部从前往后**：页头（LSN/校验和）→ 行指针数组（每行的"槽位"）→ 空闲空间 ← 行数据区（从页尾往前长）。

| 区域 | 作用 |
|------|------|
| 页头 | LSN、校验和等元信息 |
| 行指针数组 | 指向每个行数据的偏移（先有槽位、后有数据） |
| 空闲空间 | 中间空白：新槽位从前往后要、行数据从后往前要 |
| 行数据区 | 实际的行数据（从页尾往前长） |

**页分裂**：页写满后插入新行 → 拆成两页（并更新父节点）——**随机主键**（如 UUID）会让插入点分散、频繁分裂、索引膨胀；**自增/有序主键**则总是往最后写（这也是"主键用自增"的一个原因）。

实测（`pageinspect`）：p4 表第 0 页有 226 个行槽位；UPDATE 之后该页多出 1 个**死行槽位**（旧版本还在，等 VACUUM 清）——这就是"更新不回原地"的直接证据。

## 4. B+ 树：为什么数据库都用它

| 结构 | 问题 |
|------|------|
| 二叉搜索树 | 太高（100 万行 ~20 层）→ 每次一层一次 IO |
| 哈希表 | 不支持范围查询和排序 |
| **B+ 树** | **高扇出**（一个节点几百个 key）→ 100 万行只要 **3~4 层**；叶子有链表 → 范围扫描顺序读 |

```
100 万行的 B+ 树：根(1 页) → 内部层(几十页) → 叶子(几万页)
一次点查 ≈ 3~4 次页访问（大多能命中缓冲池）
```

实测（PG 16，100 万行）：表 35 MB、主键索引 21 MB；`pgstatindex` 报告 **level = 2**（点查路径 ≈ 根 → 内部 → 叶子 3 次页访问）、叶子页 2733 个。

**扇出为什么大**：内部节点只存 key + 子指针（不存整行）→ 一页能放几百个 → 树矮。

## 5. LSM 树：写优化的另一条路

**B+ 树的痛点是随机写**（更新要找到页、可能分裂、就地改）——机械盘上随机写很慢。**LSM（Log-Structured Merge Tree）**把随机写变成顺序写：

| | B+ 树 | LSM 树 |
|--|-------|--------|
| 写 | 就地改页（随机 IO + 页分裂） | 内存 memtable → 满了**顺序写**成 SSTable 文件 |
| 读 | 一次树查找 | 可能要查多层文件（**读放大**） |
| 后台 | VACUUM/purge 清死行 | **compaction** 合并文件（写放大） |
| 适合 | **读多写少、范围查询**（MySQL/PG） | **写密集**（RocksDB/LevelDB/Cassandra/HBase） |
| 代表 | InnoDB、PG 的 heap+btree | RocksDB、LevelDB、ClickHouse 的 MergeTree |

**RocksDB 也是 AI infra 里的常客**（KV 缓存、特征存储）。

## 6. 缓冲池（Buffer Pool）

**内存里缓存页**，避免每次都读盘：

```
读：查缓冲池 → 命中就直接用；miss 才读盘并放入
写：改缓冲池里的页（变"脏页"）→ 由后台线程刷盘（checkpoint/刷脏）
```

| | PG | InnoDB |
|--|----|--------|
| 名称 | `shared_buffers`（实测 128MB） | `innodb_buffer_pool_size`（常设内存 60~70%） |
| 淘汰 | Clock-sweep（类 LRU） | LRU（分 young/old 区） |
| 查缓存 | `pg_buffercache` 扩展 | `INFORMATION_SCHEMA.INNODB_BUFFER_POOL_STATS` |

**为什么"内存越大越快"**：命中率高就不用读盘；但**写还是要落盘**（靠 WAL 保证）。

实测：全表扫一遍那张 35 MB 的表之后，`pg_buffercache` 显示它的 **4429 个页**都进了缓冲池（shared_buffers 128 MB）。

## 7. WAL：先写日志，再写数据

**核心思想**：**顺序写日志**（快）代替**随机写数据页**（慢）——提交时只要 WAL 落盘（fsync），数据页可以慢慢刷。

```
UPDATE 的执行路径：
① 改缓冲池里的页（脏页）
② 往 WAL 追加一条"改了什么"的记录（顺序写）
③ COMMIT → fsync WAL（到此就算"提交成功"，持久性达成）
④ 后台慢慢把脏页刷到数据文件（即使此时崩溃，也能用 WAL 重做）
```

| | PG | InnoDB |
|--|----|--------|
| 重做日志 | **WAL**（`pg_wal/`，段文件 16MB 循环/归档） | **redo log**（`#innodb_redo/`，8.0.30 前是 `ib_logfile*`，循环写） |
| 回滚日志 | **不需要单独的 undo**：旧版本行留在表里（MVCC），VACUUM 清 | **undo log**（回滚 + MVCC 都靠它） |
| 附加日志 | 可选归档（`archive_mode`） | **binlog**（复制/归档；与 redo 两阶段提交保证一致） |

**实测：WAL 的体积**（写入量会比数据本身大，这叫**写放大**）：

```sql
SELECT pg_current_wal_insert_lsn();       -- 记下开始位置
INSERT INTO big SELECT ...;               -- 批量写入
SELECT pg_current_wal_insert_lsn();       -- 差值 = 这次写入产生的 WAL 字节数
```

实测：插 10 万行（表 13.8 MB）产生 **WAL 15.7 MB**——比数据本身还大（写放大）。

**fsync 与 group commit**：`synchronous_commit = on` 时每次提交都要 fsync；并发提交会**攒一批一起 fsync**（group commit），所以"批量提交比逐条提交快得多"。

实测：300 次单行 INSERT 逐条提交，`synchronous_commit=on` 比 `off` 慢约 8 倍——时间全花在 fsync 上。

## 8. 崩溃恢复：WAL 怎么救回来

```
崩溃 → 重启 → 从最后一个 CHECKPOINT 的 redo LSN 开始：
① 分析（哪些事务提交了）
② 重做（redo）：把已提交但没刷数据页的改动补上
③ 回滚（undo）：把未提交的事务撤销
→ 恢复完成，数据库可用
```

```sql
CHECKPOINT;                                        -- 手动触发检查点
SELECT redo_lsn, checkpoint_time FROM pg_control_checkpoint();
```

**关键点**：

- **提交过的一定在**（WAL 已 fsync）
- **没提交的一定不在**（恢复时 undo）
- 这就是"WAL + 检查点"的崩溃恢复保证，也是所有数据库的通用套路

实测（`kill -9` 打死 postmaster，再启动）：

```
LOG:  database system was not properly shut down; automatic recovery in progress
LOG:  redo starts at 0/39D3F2A0
LOG:  redo done at 0/39DD2598
→ 已提交的行还在；崩溃时未提交的那行消失
```

## 9. 工程影响

| 现象 | 原因 |
|------|------|
| 批量插入比逐条快很多 | 每条 INSERT 一个事务 = 每次 fsync；批量 = 一次 fsync + 顺序写 |
| 表格删了很多数据，文件还很大 | MVCC 死行等 VACUUM/purge 清理；`VACUUM FULL`（PG，要 ACCESS EXCLUSIVE 锁）/`OPTIMIZE TABLE`（MySQL，重建表）才真正收缩 |
| 随机 UUID 主键插入慢、索引大 | 页分裂 + 索引膨胀（见 §3） |
| 副本/主从延迟 | 从库要重放 WAL/binlog |
| 写多的场景考虑 LSM | 随机写 → 顺序写 |

实测：另一个会话持有表的读锁时，`VACUUM FULL` 会**一直等锁**（后台持锁多久，它就等多久）——生产上别随手跑。

## 10. 要点回顾

1. **IO 单位是页**：PG 8KB、InnoDB 16KB；按页缓存（缓冲池）才有局部性红利
2. **堆表（PG）vs 聚簇（InnoDB）**：二级索引都要"回表"（InnoDB 还要再查一次主键树）
3. **UPDATE = 写新版本**（MVCC）→ ctid/位置会变、旧版本等清理；**自增主键**能避免页分裂
4. **B+ 树赢在"矮"**（高扇出，百万行实测 level=2、点查 ≈3 次页访问）和**叶子链表**（范围扫描）；**LSM 赢在顺序写**（写密集场景）
5. **缓冲池**缓存页：读快靠它；写还是要落盘（靠 WAL）
6. **WAL 是持久性的核心**：先写日志（顺序）→ 提交 fsync → 数据页后台刷；写放大是代价
7. **崩溃恢复** = 从检查点 redo 已提交 + undo 未提交 → 提交的不丢、没提交的没有
8. **工程结论**：批量提交、别用随机主键、长事务挡清理、写密集考虑 LSM
