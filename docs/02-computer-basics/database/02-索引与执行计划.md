# 索引与执行计划

索引让"找一行"从"全表扫"变成"走树找"——但要建对、用对，得会看执行计划。

> 示例基于 PostgreSQL 16；MySQL/SQLite 的差异在每节标注。

## 1. 索引是什么

**没有索引**：查 `WHERE id = 100000` 要一行行看（**Seq Scan**，O(n)）。
**有索引**：B+ 树里按 key 找（O(log n)），拿到位置再取行。

```
B+ 树索引的样子（示意图，非对齐）

              [ 50 | 120 ]              ← 内部节点：只存 key 和指针
              /     |      \
      [10|30]   [60|90]   [130|180]     ← 叶子节点：存 key → 行位置
       ↓  ↓      ↓  ↓       ↓   ↓
     （叶子之间还有链表 → 支持范围查询）
```

**要点**：

- 索引**不是免费的**：占空间、拖慢写入（每次 INSERT/UPDATE/DELETE 都要维护索引）
- **主键自带唯一索引**；外键列**不会**自动建索引（PG/MySQL 都不会！JOIN/删除父行时会慢）
- 索引的选择性（区分度）越高越有用：`status`（只有几个值）通常不值得单独建索引

## 2. 创建索引与类型

```sql
CREATE INDEX idx_emp_dept ON emp (dept_id);              -- 普通索引
CREATE UNIQUE INDEX idx_emp_name ON emp (name);          -- 唯一索引
CREATE INDEX idx_emp_dept_salary ON emp (dept_id, salary);  -- 联合索引
CREATE INDEX idx_emp_lower_name ON emp (LOWER(name));    -- 表达式索引
CREATE INDEX idx_emp_active ON emp (dept_id) WHERE salary > 0;  -- 部分索引
DROP INDEX idx_emp_dept;
```

| 类型 | 适合 | 说明 |
|------|------|------|
| **B-tree**（默认） | 等值、范围、排序、前缀匹配 | 90% 的场景 |
| Hash | 只等值 | 少用（B-tree 也能等值） |
| **GIN** | 全文、数组、JSONB 包含 | `@>`、`?` 等操作符 |
| GiST | 几何、范围类型 | 空间数据 |
| BRIN | 超大表、物理有序（时间序列） | 索引极小 |

## 3. 聚簇 vs 非聚簇（"回表"）

| | InnoDB（MySQL） | PostgreSQL | SQLite |
|--|----------------|-----------|--------|
| 表的存储 | **按主键聚簇**（主键即数据，叶子存整行） | **堆表**（无序存放） | rowid 表（近似聚簇） |
| 二级索引 | 叶子存**主键值** → 要**回表**按主键再查一次 | 叶子存 **ctid**（行物理位置）→ 也要回表 | 存 rowid → 回表 |
| 顺序扫描 | 全表扫 或 全索引扫 | Seq Scan | 全表扫 |

**"回表"的意思**：走二级索引找到主键/位置，再去主表把整行取出来（**多一次随机 IO**）。

**覆盖索引**能避免回表：查询要的列都在索引里，就不用回表：

```sql
-- 索引 (dept_id, salary) 覆盖了这个查询 → 只读索引
SELECT dept_id, salary FROM emp WHERE dept_id = 1;

-- PG 可以显式加"附带列"（只存不排序，用于覆盖）
CREATE INDEX idx_emp_dept_inc ON emp (dept_id) INCLUDE (name, salary);
```

**PG 的 Index Only Scan 有个前提**：行的"可见性"要已知——**VACUUM 之后**（visibility map 标记了全可见页）才能真正跳过堆表；否则会看到 `Heap Fetches: N`。

## 4. 联合索引与最左前缀

**规则**：`(a, b, c)` 的索引可以用于 `a`、`(a,b)`、`(a,b,c)` 的前缀查找，**不能跳过 a 直接用 b/c**。

| 查询条件 | 能否**定位**（缩小扫描区间） |
|---------|:---:|
| `a = ?` | ✅ 用 a 定位 |
| `a = ? AND b = ?` | ✅ 用 a、b 定位 |
| `a = ? AND c = ?` | 🔸 **只用 a 定位**；c 只能"索引内过滤"（EXPLAIN 里可能也写在 `Index Cond` 一行，但它不参与树查找） |
| `b = ?`（跳过 a） | ❌ 不能定位；但 PG 可能选"**全索引扫描**"（读整个索引筛 b，比读表便宜时——**扫描范围仍是全索引**） |
| `a = ? AND b > ? AND c = ?` | 🔸 定位只到 b（范围之后的 c 在 b 区间内无序，无法继续定位），c 做索引内过滤 |

**怎么判断真实的定位范围**：别只看"EXPLAIN 里出现了索引名"，要看 **`rows`（要扫多少行）**——`Index Cond` 里出现某列 ≠ 该列参与了定位（可能只是索引内过滤）。

实测对比（20 万行、`a` 只有 10 个取值（每个两万行），索引 `(a,b,c)`，看 `BUFFERS` 的索引页访问次数）：

```
WHERE a=5 AND b=7 AND c=9   → 三列都参与定位     → 索引页访问 2 次
WHERE a=5 AND c=9           → 只有 a 参与定位     → 索引页访问 21 次（相差 10 倍）
```

**建联合索引的顺序**：**等值条件在前、范围/排序在后**；多个等值列则"选择性高的在前"（其实区别不大，PG 都能用）。

## 5. 看执行计划：EXPLAIN

```sql
EXPLAIN SELECT * FROM emp WHERE dept_id = 1;                    -- 估算（不真跑）
EXPLAIN ANALYZE SELECT * FROM emp WHERE dept_id = 1;            -- 真跑 + 实际耗时
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM emp WHERE dept_id = 1; -- 加上 IO 统计
```

**输出怎么读**（从内到外、从下到上）：

| 节点 | 含义 |
|------|------|
| **Seq Scan** | 全表顺序扫（没走索引） |
| **Index Scan** | 走索引 + 回表 |
| **Index Only Scan** | 只读索引（覆盖索引，最快） |
| **Bitmap Heap Scan** | 先位图汇总索引结果、再批量回表（匹配行多时更划算） |
| Sort / Hash Join / Nested Loop | 排序 / 连接方式 |

```
Seq Scan on emp  (cost=0.00..18334.00 rows=100000 width=8) (actual time=0.015..95.2 rows=99999 loops=1)
                     └─ 估算成本 ─┘  └─ 估算行数 ─┘   └───── 实际耗时(ms) ─────┘ └ 实际行数 ┘
```

**关键对比**：`rows`（估算）和 `actual rows` 差很远 → 统计信息过期（`ANALYZE 表名`）。
`cost` 是相对单位（不是毫秒），`actual time` 才是真实耗时。

**MySQL 的对应**（MySQL 用 `EXPLAIN`，字段名不同）：

| MySQL 字段 | 含义 |
|-----------|------|
| `type` | 访问方式（`ALL` 全表 / `ref` 等值 / `range` 范围 / `index` 全索引扫描） |
| `key` | 实际用的索引（`NULL` = 没用索引） |
| `rows` | 估算扫描行数 |
| `Extra` | `Using index`（覆盖）/ `Using filesort`（额外排序）/ `Using temporary` |

## 6. 为什么索引会"失效"（用不上）

| 场景 | 例子 | 怎么办 |
|------|------|--------|
| **对列做了函数/运算** | `WHERE lower(name) = 'amy'`、`WHERE salary + 1 > 100` | 表达式索引；或把运算移到常量侧 |
| **前导模糊匹配** | `LIKE '%abc'`、`LIKE '%abc%'` | 无法用 B-tree（除非全文/trigram 索引） |
| 前缀匹配但排序规则不是 C | `LIKE 'abc%'` | 默认 collation 下普通 B-tree 也走不了；建 `text_pattern_ops` 索引（实测：建了之后 `Index Cond` 变成 `~>=~`/`~<~` 的范围） |
| 类型不匹配 | MySQL 里 `varchar_col = 123`（隐式转换整个列） | 让类型一致（PG 会直接报错，反而安全） |
| `OR` 两边不都有索引 | `WHERE a = 1 OR b = 2`（b 无索引） | 给 b 建索引（PG 能用 BitmapOr）或改 `UNION` |
| 条件选择性差 | `WHERE status = 1`：**50% 命中 → Bitmap Heap Scan；90% 命中 → Seq Scan** | 优化器按成本在 Index / Bitmap / Seq 之间选，不是"有索引就走索引" |
| 统计信息过期 | 大批量导入后 | `ANALYZE table;`（PG）/ `ANALYZE TABLE`（MySQL） |

**注意两个方向**：

- **"没走索引"不一定是坏事**：返回大部分行时 Seq Scan 比"走索引再逐行回表"更快（实测 90% 命中时 Seq Scan 更快）
- **"走了索引"也不一定是定位查找**：可能只是"全索引扫描"或"索引内过滤"——判断标准是 **`rows`（扫描行数）** 和实际耗时

## 7. 什么时候不该建索引

- 写多读少（索引维护成本 > 查询收益）
- 低区分度列（如布尔、性别）——除非用**部分索引**（`WHERE status = 'pending'`）
- 小表（全表扫也就几页）
- 已经被联合索引前缀覆盖的列（`(a,b)` 已能服务 `a = ?`，别单独再建 a）

**索引数量要有节制**：一般单表 5 个以内；用 `pg_stat_user_indexes`（PG）看索引是否被用到。

## 8. 慢查询排查流程

```
1. 找到慢 SQL（日志：PG 配 log_min_duration_statement；MySQL 开慢查询日志；或用 pg_stat_statements / performance_schema）
2. EXPLAIN ANALYZE 看：走没走索引？rows 估算准不准？哪一步耗时最多？
3. 对症下药：加/改索引（顺序、覆盖、部分）→ 改写 SQL（子查询→JOIN、避免函数）→ 更新统计信息
4. 再 EXPLAIN 对比（BUFFERS 看 IO 少了多少），用真实数据验证
```

**改完必测**：索引不是"加上就好"——它可能让写变慢、也可能根本没被选中（优化器看成本）。

## 9. 要点回顾

1. **索引 = B+ 树**：O(log n) 定位；代价是占空间 + 拖慢写；**外键不会自动建索引**
2. **联合索引看最左前缀**：`(a,b,c)` 能服务 `a`、`(a,b)`、`(a,b,c)`；**范围条件之后的列不能用于定位**
3. **回表**：二级索引找到位置后要回主表取行；**覆盖索引**（+ `INCLUDE`）可以避免；PG 的 Index Only Scan 还要 **VACUUM** 配合
4. **EXPLAIN 是照妖镜**：Seq Scan（全表）/ Index Scan（走索引+回表）/ Index Only Scan / Bitmap Heap Scan；看 `rows` 估算 vs 实际、`BUFFERS` 看 IO
5. **索引失效**常见原因：列上做运算、前导模糊 `%x`、`OR` 无索引分支、选择性差、统计过期
6. **Seq Scan 不一定是坏事**——返回行多时它就是最优解
7. **索引要节制**：写多读少、低区分度、小表都别乱建；用统计视图看"哪些索引从没被用过"
8. **排查流程**：慢日志 → EXPLAIN ANALYZE → 加/改索引或改 SQL → 再测
