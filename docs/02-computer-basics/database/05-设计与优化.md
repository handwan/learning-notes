# 设计与优化

表怎么设计（范式/反范式/主键/类型）、查询怎么写（JOIN/分页/批量）、慢了怎么查（`pg_stat_statements` + `EXPLAIN`）。

> 示例基于 PostgreSQL 16；MySQL/SQLite 差异标注在各节。

## 1. 范式：为什么要拆表

范式就是"**同样的信息只存一份**"的规则，每一级都在消灭一种冗余：

| 范式 | 一句话 | 反例 |
|------|-------|------|
| 1NF | 字段原子（不可再分） | 一个 `phones` 列存 "138,139,150" |
| 2NF | 非主键列完全依赖**整个**主键 | 复合主键 (订单, 商品) 里塞"客户地址"（只依赖订单） |
| 3NF | 非主键列不依赖其他非主键列 | 订单表里存"客户地址"（依赖客户，不直接依赖订单） |
| BCNF | 每个"决定因素"都是候选键 | 3NF 之上的特例修正（一个表里有多个重叠候选键时） |

**这些异常不规范化就会发生**（实测）：

```sql
-- 反例：订单表里重复存客户地址
-- (1,'张三','北京'), (2,'张三','北京'), (3,'张三','北京')
UPDATE od SET addr = '上海' WHERE order_id = 1;   -- 只改了一行
SELECT count(DISTINCT addr) FROM od WHERE cust = '张三';  -- 结果 2！
```

- **更新异常**：同一事实多处存储，改一处就打架
- **插入异常**：想录一个新客户，但没订单就没地方存
- **删除异常**：删掉最后一笔订单，客户信息跟着没了

拆成 `customers(name PK, addr)` + `orders(order_id PK, cust FK, qty)` 后：地址只存一份，`UPDATE` 一行就全对。

## 2. 反范式：什么时候故意冗余

范式不是教条：**JOIN 很贵、读远多于写**时，可以故意存冗余换读性能。

| 手段 | 例子 | 代价 |
|------|------|------|
| 冗余列（快照） | 订单里存"下单时的客户名/价格" | 写入时要同步；且历史快照本就不该变（**不是**不一致） |
| 汇总表 | 每日销售额汇总表 | 定时/触发更新，可能短暂落后 |
| 物化视图 | PG 的 `MATERIALIZED VIEW`（`REFRESH` 更新） | 占用存储、刷新有开销 |

**判断标准**：先按 3NF 设计，**有实测瓶颈**再反范式；冗余的地方要明确"谁是源、谁负责同步"。
（订单快照是**有意的历史记录**，和"图省事的冗余"是两回事。）

## 3. 主键与类型的选择

**主键：自增 vs 随机 UUID**（各插 10 万行，实测）：

| 主键 | 插入 | 主键索引大小 |
|------|:---:|:---:|
| `bigserial`（自增） | 基准 | **≈2.2 MB** |
| `uuid DEFAULT gen_random_uuid()` | **慢约 1 倍** | **≈4.4 MB**（大一倍） |

原因：随机值插入点分散 → 页分裂、索引膨胀（见前一章 §3）；索引本身也大一倍。

**分布式下非要 UUID 怎么办**：用**有序**的 UUID（UUIDv7/ULID，时间前缀）——保留全局唯一，插入又是顺序的。

**类型选择**：

- 用**够用**的类型（`int` 够就别上 `bigint`），行更小、一页装更多
- **时间用 `timestamptz`**（带时区）而不是 `timestamp`——省掉"存的是什么时区"的扯皮
- `char(n)` 会补空格，用 `varchar`/`text`（PG 里后两者性能无差）
- 金额用 `numeric`，别用 `float`

**约束**（都是"数据库帮你防脏数据"，写入有检查开销，但通常值得）：

`NOT NULL`、`UNIQUE`、`CHECK(条件)`、`FOREIGN KEY`。应用层也能校验，但**并发下只有数据库约束才可靠**。

## 4. JOIN 的三种算法

| 算法 | 思路 | 适合 |
|------|------|------|
| **Nested Loop** | 外层每行 → 内层查一次（走内表索引） | **驱动表小 + 内表命中索引** |
| **Hash Join** | 小表建哈希表 → 扫大表逐行探测 | **等值连接**、两边都大 |
| **Merge Join** | 两边排序 → 归并式对扫 | 两边**已有序**（索引/排序输出） |

**同一句话，三种计划**（实测，两表各 2 万行、等值连接）：

| 计划 | 对比 |
|------|:---:|
| 默认（Hash Join） | 基准 |
| 禁用 hash（Merge Join） | 差不多 |
| 禁用 hash + merge（Nested Loop） | **慢几千倍** |

Nested Loop 灾难的原因：内表 `jb.id` **没有索引** → 每一行都要全表扫 → 2 万 × 2 万 ≈ 4 亿次比较。

**要点**：NL 不是"坏算法"——内表有索引时它是最快的（小结果集点查）；**没有索引时才灾难**。

## 5. 慢查询怎么定位

**第一步：谁在慢** —— `pg_stat_statements`（要 `shared_preload_libraries` 预加载）：

```sql
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
```

实测注意：**非超级用户只能看到自己的语句**，别人的显示 `<insufficient privilege>`。

**第二步：慢在哪** —— `EXPLAIN (ANALYZE, BUFFERS)` 读三个东西：

1. **估算 rows vs 实际 rows**：差几个数量级 → `ANALYZE` 更新统计信息
2. **Buffers**：读了多少页（shared hit=内存 / read=磁盘）
3. **节点类型**：Seq Scan 大表、Nested Loop 大表、Sort 溢出到磁盘 = 危险信号

**第三步：改** —— 常见手段（按性价比排序）：

| 手段 | 说明 |
|------|------|
| 加/改索引 | 覆盖 WHERE、ORDER BY、JOIN 的列 |
| 改写 SQL | **别让函数/运算包住索引列** |
| 减少返回列/行 | `SELECT *` 改具体列；加 LIMIT |

**"函数包列"实测**（5 万行、`created_at` 上有索引）：

```sql
-- ❌ 索引列被函数包住 → Seq Scan（每行都要算 date_trunc）
WHERE date_trunc('day', created_at) = date_trunc('day', now())

-- 改成范围 → Index Scan
WHERE created_at >= date_trunc('day', now())
  AND created_at <  date_trunc('day', now()) + interval '1 day'
```

**类型比较**（PG 比 MySQL 严格，实测）：

- `int_col = '123'`：能跑（字符串字面量转成 int）
- `varchar_col = 123`：**直接报错** `operator does not exist: character varying = integer`

MySQL 会做隐式转换（`varchar` 列和数字比时**索引可能失效**）——跨库移植时注意。

## 6. 深分页：OFFSET 的代价

```sql
-- 第 4 万页，每页 10 条
SELECT * FROM page_t ORDER BY id LIMIT 10 OFFSET 400000;
```

实测（50 万行表）：

| 写法 | 对比 | 访问页数 |
|------|:---:|:---:|
| `OFFSET 400000` | 基准 | **约 4800 页** |
| `WHERE id > 400000 ORDER BY id LIMIT 10` | **快约三个数量级** | **7 页** |

OFFSET 慢的本质：**前 40 万行也要被读取、然后丢掉**（即使有索引、不需要排序）——翻得越深越慢，时间随 OFFSET 线性增长。

**keyset 分页（游标分页）**：

```sql
-- 记住上一页最后一条的 id，下一页从它之后取
SELECT * FROM page_t WHERE id > :last_id ORDER BY id LIMIT 10;
```

代价：**不能跳页**（只能一页页翻）。排序键不唯一时用组合键当游标，如 `(created_at, id)`。

## 7. 写入与连接的优化

**批量导入**（10 万行，实测）：

| 方式 | 对比 |
|------|:---:|
| `COPY`（`copy_expert` 实测） | 基准（一次事务搞定） |
| 多值 `INSERT`（1000 行/条） | 慢约 7 倍 |
| 逐行 `INSERT`（自动提交） | **慢上千倍**（每次提交一次 fsync） |

差距的主因是**每次提交一次 fsync**（见前一章）：逐行 INSERT ≈ 10 万次 fsync；COPY 一次事务搞定。

**连接开销**（socket）：

- 每次新建连接：固定开销（握手 / 认证 / 后端进程启动）
- 复用连接后每次查询：**快一个数量级**（走网络时差距更大）

→ 这就是**连接池**存在的意义；连接池还会限制总连接数（PG 每连接一个进程，几百连接就压力山大）。

**N+1 查询**（ORM 的经典坑，实测）：

- 循环里 1000 次单条查询：基准（1000 个来回）
- 一次 JOIN 拿完：**快两个数量级**

**大事务**：持锁时间长、挡 VACUUM（死行清不掉）、回滚代价高——拆小（危害与排查见『事务与并发控制』§8）。

## 8. 要点回顾

1. **范式 = 一事实一处存**：1NF 原子、2NF 全依赖、3NF 无传递依赖；否则更新/插入/删除异常（实测一改就出现两个地址）
2. **反范式是权衡**：读多写少才考虑；快照/汇总/物化视图都要明确"谁同步"；先 3NF、有实测瓶颈再反范式
3. **主键优先自增/有序**：随机 UUID 插入慢一倍、索引大一倍（实测）；分布式用 UUIDv7/ULID
4. **JOIN 三算法**：Hash 适合大表等值、Merge 适合已有序、NL 适合小驱动表 + 内表索引；NL 无索引会退化到 O(n²)（实测慢 ~3700 倍）
5. **慢查询三步**：`pg_stat_statements` 找 → `EXPLAIN (ANALYZE, BUFFERS)` 看（估算 vs 实际、页数、节点）→ 加索引/改写
6. **别用函数包索引列**：改成范围条件，Seq Scan → Index Scan（实测）；PG 类型严格、MySQL 隐式转换要小心
7. **深分页用 keyset**：OFFSET 要扫并丢弃前面所有行（实测 4834 页 vs 7 页）；代价是不能跳页
8. **写入/连接**：COPY ≫ 多值 ≫ 逐行（fsync 次数决定）；用连接池；消灭 N+1；事务别开太大
