# 总线、IO 与外部设备

CPU 再快，数据也要从设备搬进来——**总线和 IO 是"算力之外的硬约束"**（部署 AI 时尤其明显：模型加载、数据传输都卡在这里）。

## 1. 总线（Bus）

**总线 = 一组共享的传输线**（数据线 + 地址线 + 控制线），按位置分：

| 类型 | 连接 | 例子 |
|------|------|------|
| 片内总线 | CPU 内部模块 | 寄存器堆 ↔ ALU |
| 系统总线 | CPU ↔ 内存 | 内存总线（现代直连内存控制器） |
| **IO 总线** | CPU ↔ 外设 | **PCIe**、USB、SATA |

**性能指标**：带宽 = 位宽 × 频率（再乘每次传输次数）。

| PCIe 版本 | 每 lane 单向 | x16 单向（约） |
|:---:|:---:|:---:|
| Gen3 | ~1 GB/s | ~16 GB/s |
| Gen4 | ~2 GB/s | ~32 GB/s |
| Gen5 | ~4 GB/s | ~64 GB/s |

**对 AI 部署的意义**：GPU 通过 PCIe 连主机——**模型权重从内存传到显存、每步输入数据上传、结果回传都要过这条路**。x16 Gen4 单向 ~32 GB/s，而 GPU 显存带宽是几百 GB/s 到 TB/s 级 → **PCIe 往往是"喂数据"的瓶颈**（推理优化里的"减少 H2D 传输、算子融合"就是在省这个）。

（**总线仲裁**——多个设备抢总线谁先发、**同步/异步定时**——教材考点，见[速查篇](09-组成原理速查.md)。）

## 2. IO 控制方式

| 方式 | 做法 | 谁在等 | 适用 |
|------|------|--------|------|
| 程序查询 | CPU 轮询设备状态 | CPU 空转 | 简单设备 |
| **中断** | 设备完成后打断 CPU | CPU 干别的 | 通用 |
| **DMA** | 设备直接读写内存，完成才通知 CPU | CPU 不参与搬运 | 大块数据传输（磁盘/网卡/GPU） |
| 通道/IO 处理器 | 专用处理器执行 IO 程序 | CPU 只发指令 | 大型机 |

**工程上你已经天天在用**：`read()/write()` 背后就是中断 + DMA；`O_DIRECT`、`mmap`、`io_uring` 都是在改"数据怎么进出"（细节见[IO 系统](../operating-system/09-IO系统.md)）。

## 3. 磁盘：顺序 vs 随机

| 类型 | 随机访问 | 顺序带宽 | 特点 |
|------|---------|---------|------|
| HDD（机械） | 寻道+旋转 ~10 ms | 100~200 MB/s | 随机是灾难（磁头移动） |
| SATA SSD | ~100 µs | ~500 MB/s | 无机械部件 |
| **NVMe SSD** | ~10~100 µs | **GB/s 级** | PCIe 直连、并行队列 |

**实测（WSL 虚拟盘）**：

| 项目 | 实测 |
|------|:---:|
| 顺序写（`dd` 512MB，direct） | **5.7 GB/s** |
| 顺序读 | **7.9 GB/s** |
| 随机读 4KB × 2000 次 | **~几十 µs/次** |

**读法**：顺序带宽是随机延迟的"另一种量纲"（GB/s vs µs/次）——**数据库/模型加载关心随机、大文件传输关心顺序**（数据库篇的"随机 IO 慢"就来自这里）。

**IOPS**：每秒 IO 次数，衡量随机能力（NVMe 能到几十万 IOPS；HDD 只有 ~100）。

**调度算法**（FCFS / SSTF / SCAN / C-SCAN）：机械盘时代直接决定寻道量，见 [设备与磁盘](../operating-system/08-设备与磁盘.md)篇。

**RAID**：多盘换带宽/可靠性（0 条带 / 1 镜像 / 5 分布式校验 / 10）——级别与选型见 [设备与磁盘](../operating-system/08-设备与磁盘.md)篇。

## 4. AI 部署视角：数据路径

```
磁盘（模型文件，GB 级）
   ↓ 读文件（顺序读，GB/s 级）
内存（页缓存/缓冲区）
   ↓ PCIe（~32 GB/s，可能多卡）
显存（GPU，几百 GB/s 带宽）
   ↓ 片上存储（SM/cache）
计算单元
```

**每一级都可能是瓶颈**：

- 冷启动：模型加载时间 = 文件大小 / 磁盘带宽（8GB 模型 ~1-2 s @ 5 GB/s）
- 推理时：batch 输入上传 + 中间张量 H2D/D2H（PCIe）→ 优化手段是"少传、合并传、异步传"
- 多卡：NVLink/RDMA 的带宽决定切分/并行的效率

## 5. 深入实测：块大小、fsync、页缓存与网络

### 块大小决定带宽（10 倍差距）

**实测（O_DIRECT 顺序写 512MB）**：

| 块大小 | 带宽 |
|:---:|:---:|
| 4 KB | **143 MB/s** |
| 64 KB | **1.4 GB/s**（10 倍） |

**读法**：小块 = 更多"每次 IO 的固定开销"（系统调用、DMA 设置、设备处理）；**大块顺序 IO 才能打满带宽**——所以：

- 模型文件/数据集加载用**大块顺序读**（带缓冲/`readahead`）
- 小文件多 → 打包（tar/parquet）避免随机小 IO

### fsync：真正的"落盘"要多久

**实测**（写 4KB + `fsync` × 100，O_DIRECT）：

| 指标 | 延迟 |
|------|:---:|
| 中位 | **几百微秒** |
| P99 | **毫秒级** |

**读法**：一次"确认落盘"~0.3 ms（比内存慢 5 个数量级）——这就是数据库章里"逐条提交比关闭 fsync 慢近一个数量级"的来源（每条提交都在买这个保险）。

### 页缓存：文件 IO 的"免费加速层"

**实测**：2000 次随机 4KB 读同一个 64MB 文件：

| 场景 | 每次延迟 |
|------|:---:|
| 页缓存命中（刚写过，在内存里） | **~1 µs** |
| NVMe 裸盘（O_DIRECT，见存储篇） | **~几十 µs** |

**读法**：**页缓存让"热文件"快 40 倍**——所以"读模型文件第一遍慢、第二遍快"很正常；也是数据库 `shared_buffers` 之外还有 OS 页缓存的道理（两边都缓存，各管一段）。

### 网络延迟（AI 部署的"另一条总线"）

**实测**：

| 目标 | 平均 RTT |
|------|:---:|
| 回环 | 亚毫秒级 |
| 公网（223.5.5.5） | 几十毫秒 |

**读法**：

- 回环也亚毫秒级（WSL 虚拟化开销）；同一台机器**能不走网络就不走**（同机用 Unix socket 更快）
- 公网 RTT 几十 ms：**跨机调用比本地慢 5~6 个数量级** → "少 RPC、批量传、异步流水线"是分布式推理/训练的基本原则

### 查自己机器的命令清单

```bash
dd if=/dev/zero of=t bs=1M count=512 oflag=direct   # 顺序写带宽
fio --rw=randread --bs=4k --numjobs=8               # IOPS（需安装 fio）
nvidia-smi -q | grep -A6 "GPU Link Info"            # GPU 的 PCIe 链路
nvidia-smi topo -m                                   # 多卡拓扑（NVLink/PCIe）
ping -c3 <host>                                      # RTT
ethtool <iface>                                      # 网卡速率（如 1000Mb/s）
```

## 6. 中断与 DMA、PCIe 算账

### 中断与异常：先分类

| 类别 | 来源 | 例子 | 与当前指令的关系 |
|------|------|------|------------------|
| **外中断**（通常说的"中断"） | CPU 之外 | 时钟、IO 完成、键盘 | 无关（异步） |
| **内中断**（异常） | 执行指令时 | 缺页、除零、断点、系统调用 | 有关（同步） |

异常再分三类——**处理策略完全不同**：

| 类型 | 含义 | 处理后 | 例子 |
|------|------|--------|------|
| **故障（fault）** | 可修复的出错 | **重新执行**当前指令 | 缺页、缺段 |
| **陷阱（trap）** | 有意触发 | 执行**下一条**指令 | 系统调用、断点 |
| **终止（abort）** | 不可恢复 | 终止进程 | 硬件 / 总线错误 |

**工程对应**：缺页 = fault（把页面调进来后重跑那条指令）；`syscall` = trap（故意"打断自己"进内核）；内核修不了的 fault 交用户态处理（`SIGSEGV`）。

### 中断处理完整流程（和 DMA 对照）

```
设备发中断请求
 → CPU 响应条件：当前指令执行完 + 允许中断 + 有请求
 → 中断隐指令：关中断 → 保存断点（PC/PSW）→ 取中断入口
 → 保护现场：保存通用寄存器（软件/硬件）
 → 执行中断服务程序
 → 恢复现场 → 开中断 → 返回（iret）
DMA：整块搬完**只中断一次**（不是每个字节都打断 CPU）
```

### DMA 的三种传送方式

| 方式 | 做法 | CPU 代价 | 场景 |
|------|------|----------|------|
| **停止 CPU 访存** | 传数据期间 CPU 完全不访存 | 整块时间白等 | 高速设备、大批量 |
| **周期挪用**（周期窃取） | 每传一个字"偷"一个存储周期 | 每次只被拖慢一点 | 教材最常见 |
| **交替访问** | 总线时间片固定交替给 CPU / DMA | 互不干扰 | 硬件复杂、速度匹配难 |

**现代对应**：PCIe 设备作为**总线主控（bus master）**按需占用链路——相当于"周期挪用"的升级版（链路上靠分片/仲裁调度）；`nvidia-smi` 里的 PCIe 代宽/利用率看的就是它。

### PCIe 传输算账（部署常用）

| 场景 | 计算 | 结果 |
|------|------|------|
| 8 GB 模型传显存（Gen4 x16 理论 32 GB/s） | 8 / 32 | **0.25 s**（实际效率 ~60-70% → 0.4 s 级） |
| 量化到 INT8（4 GB） | 4 / 32 | 0.12 s（**减半**） |
| 每步推理上传 batch 输入 | 按 batch × 特征字节数 | 常常是延迟瓶颈 |

**结论**：**模型常驻显存**（避免每次传）、**量化**（字节减半）、**异步/流水线**（传输与计算重叠）——三条都是"跟 PCIe 抢时间"。

## 7. 现代 IO 的两个"隐形部件"

| 部件 | 作用 | 部署意义 |
|------|------|---------|
| **APIC**（高级可编程中断控制器） | 中断分发、优先级、核间中断（IPI） | 中断打给哪个核影响延迟（**中断亲和性**：Linux 的 `irqbalance`/`/proc/interrupts`） |
| **IOMMU** | 设备的地址翻译（设备视角的"虚拟内存"） | 虚拟机 **GPU/网卡直通**（VFIO）、DMA 安全隔离；没有它设备只能看物理地址 |

**为什么部署关心**：容器/虚拟机跑推理时，设备直通（IOMMU/VFIO）决定 GPU 能不能给到容器；中断亲和性决定高并发下的延迟抖动。

## 8. 要点回顾

1. **总线 = 数据线+地址线+控制线**；带宽 = 位宽 × 频率；**PCIe Gen4 x16 ≈ 32 GB/s** 是 GPU 喂数据的上限
2. **IO 四种方式**：查询/中断/**DMA**/通道——大块数据传输都靠 DMA（OS 章有细节）
3. **磁盘**：HDD 随机 ~10 ms（灾难）、NVMe 随机 ~几十 µs、顺序 GB/s 级
4. **顺序和随机是两种量纲**：大文件看带宽、数据库/随机访问看延迟与 IOPS
5. **AI 部署的数据路径**：磁盘→内存→PCAe→显存→计算——**每级都可能成为瓶颈**，PCIe 常是"喂数据"的短板
6. 优化直觉：**别让数据搬来搬去**（少传、合并传、异步传）
7. **块大小是 IO 带宽的关键**：4KB 143 MB/s vs 64KB 1.4 GB/s（实测 10 倍）
8. **fsync 是要花钱的**（中位几百微秒、P99 毫秒级）——"确认落盘"的成本，数据库批量提交的动机
9. **页缓存**让热文件快几十倍（微秒级 vs 几十微秒）；**网络**：回环亚毫秒、公网几十毫秒 → 少 RPC、批量传
10. **中断 vs 异常**：外中断异步、异常同步——故障（重执行）/ 陷阱（下一条）/ 终止；**DMA 三种方式**里"周期挪用"是主流直觉
