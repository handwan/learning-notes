# 存储系统与 Cache

"内存墙"是性能问题的主因：**CPU 快、内存慢**——靠层次结构和缓存把差距藏起来。这一篇的数字（延迟/带宽）是所有性能优化的底层依据。

## 1. 存储层次：延迟差 5 个数量级

**实测：指针追逐（随机环）测不同工作集的访存延迟**：

| 工作集 | 实测延迟 | 落在哪一层 |
|:---:|:---:|------|
| 4 KB | **~1 ns** | 寄存器/L1 |
| 32 KB | ~1 ns | L1（48 KB/核） |
| 256 KB | **~4 ns** | L2（2 MB/核） |
| 2 MB | ~8 ns | L2/L3 交界 |
| 8 MB | **~26 ns** | L3（30 MB 共享） |
| 32 MB | ~90 ns | 内存（DRAM） |
| 64 MB | **~100 ns** | 内存（DRAM） |

**读法**：延迟从 1 ns 涨到 ~100 ns（**80 倍**）——这就是"缓存命中率决定性能"的原因；也是"数据布局"（数组 vs 链表）为什么值钱。

**带宽**（实测）：顺序读 ~5.6 GB/s、memcpy ~6.5 GB/s（WSL 下）。**延迟和带宽的比值**就是"多少次连续访问才能喂饱 CPU"的直觉来源。

## 2. Cache 基础

| 概念 | 说明 |
|------|------|
| **cache line** | 最小搬运单位 = **64 字节**（所以"访问 1 个 int"实际搬 16 个 int） |
| 直接映射 | 一个内存块只能进一个固定位置（冲突多、硬件简单） |
| **组相联（主流）** | 每组 N 行（N 路），块可放进组内任意行——折中 |
| 全相联 | 任意放（适合小容量、如 TLB） |
| 替换策略 | LRU 近似（硬件不精确实现）、随机 |
| 写策略 | 写回（write-back）+ 写分配（write-allocate）为主流 |

**局部性**：

- **时间局部性**：刚用过的数据很可能再用（缓存有用武之地）
- **空间局部性**：用了一个地址，附近的也会用（cache line 预取 64B 的前提）

**实测（空间局部性的代价）**：遍历 100 万个 int——每次取 1 个 vs 每 16 个取 1 个（访问次数只有 1/16）：耗时接近（差不到一倍）。两者都要把全部 cache line 拖进来，说明**瓶颈是访存不是运算**；步长大的版本没能"省 16 倍"，反而证明了一次搬运 64B 的固定成本。

## 3. 伪共享（False Sharing）

**问题**：两个线程改**不同变量**，但它们在**同一条 cache line** 上 → 缓存行在两个核之间来回搬（缓存一致性协议），性能下降。

```cpp
struct Data {
    int a;   // 线程 1 疯狂写
    int b;   // 线程 2 疯狂写 —— a、b 同一 cache line → 打架
};
// 解决：alignas(64) 让热点变量各自独占一行
struct Data {
    alignas(64) int a;
    alignas(64) int b;      //（或用 padding 凑满 64 字节）
};
```

**实测**（两线程各写 3 亿次，绑核到不同 CPU）：

| 布局 | 耗时 |
|------|:---:|
| 同一 cache line 的两个变量 | 慢一些 |
| 各自 64B 对齐隔离 | 快一些（差距不大） |

**诚实说明**：这里只测出 ~10% 差距（现代 store buffer 会把连续的写合并、WSL 虚拟化也会掩盖一部分）；教科书场景（bare metal + 真实负载）通常 2~10 倍。**结论不变**：热点并发变量用 `alignas(64)` 隔离是零成本的保险。

## 4. 主存与其他存储

| 类型 | 特点 | 用途 |
|------|------|------|
| SRAM | 快、贵、不需要刷新 | Cache |
| DRAM | 慢、便宜、需要周期性刷新 | 主存 |
| ROM/Flash | 断电不丢 | 固件、SSD |

**虚拟内存与 TLB**：页表把虚拟地址翻译成物理地址，翻译结果缓存在 **TLB**（可以理解为"地址翻译的 cache"）；TLB 未命中要查页表（多次访存）——大页（2MB/1GB）就是为了减少 TLB 未命中。细节见 OS 的[内存管理](../operating-system/06-内存管理.md)篇。

**DRAM 的启发**：随机访问慢是"打开行（row）→ 读列"的物理特性决定的；顺序访问能命中同一行（row buffer）→ **"数据连续"从内存芯片层面就是优势**（CSR/数组遍历的底气，见数据结构章）。

## 5. 深入实测：带宽扫描、冲突缺失、预取器

### 带宽 vs 工作集（找容量拐点）

**实测**（16 次读取最好一次，long 数组顺序求和）：

| 工作集 | 带宽 |
|:---:|:---:|
| 16 KB ~ 4 MB | **~40 GB/s**（L1/L2/L3 内） |
| 64 MB | **20 GB/s**（DRAM） |

**读法**：缓存内和内存的带宽差 **2 倍**；但真正拉开差距的是**延迟**（1 ns vs 100 ns）和**随机 vs 顺序**（见下）。顺便：之前"顺序读 5.6 GB/s"是**逐字节**读的版本——**瓶颈在循环而不是内存**（换成 long + 向量化就有 20 GB/s）——同一个"内存带宽"能测出 4 倍差距，这就是基准测试的坑。

### 冲突缺失：步长打爆组相联

同样 100 万次访问，只改步长（64MB 缓冲）：

| 步长 | 每次访问耗时 |
|:---:|:---:|
| 1 KB / 2 KB / 8 KB / 16 KB | 同一档（几 ns） |
| **4 KB** | **明显最差**（冲突缺失） |

**为什么 4KB 最差**：组号只看地址的某几位（64B 行、64 组时是第 6~11 位）；步长 4096 = 2¹² **不改变这些位** → 每次访问都落进**同一组** → 冲突缺失（容量明明够，却互相顶掉）。**工程套路**：数组步长/矩阵分块尺寸**避开 2 的幂次附近**，或加 padding（`alignas(64)` 的同类技巧）。

### 预取器：顺序 vs 随机差 16 倍

**实测**（64MB 数组各取 800 万次）：

| 访问方式 | 耗时 | 带宽 |
|---------|:---:|:---:|
| 顺序 | 基准 | **~20 GB/s** |
| 随机 | **慢 16 倍** | **~1.3 GB/s** |

**读法**：顺序访问被**硬件预取器**提前拉数据 + DRAM 行缓冲命中；随机访问两次延迟都要暴露。**这是"链表/哈希/指针追逐慢"的完整解释**——不是访问次数多，是"没法预取 + 每次都付延迟"。

### 从寄存器到磁盘：一条完整的延迟链（本笔记各章实测汇总）

| 层级 | 实测延迟 |
|------|:---:|
| L1 / 寄存器 | ~1 ns |
| L2 | ~4 ns |
| L3 | ~26 ns |
| DRAM（随机） | ~100 ns |
| 页缓存命中（文件读） | ~1 µs（实测 2000 次随机 4KB 读，全在缓存） |
| NVMe 裸盘随机 | ~几十 µs（O_DIRECT 实测） |

**每一级差 ~10 倍**——优化时"让数据在更上一层"就是最直接的收益。

## 6. AMAT 与写策略（Cache 的定量与取舍）

### AMAT：把"命中率"和"延迟"算成一笔账

```
AMAT（平均访存时间）= 命中时间 + 缺失率 × 缺失代价
多级：AMAT = L1命中 + L1缺失率 × (L2命中 + L2缺失率 × (L3命中 + L3缺失率 × 主存代价))
```

**用上面的延迟数字算**（L1 ~1 ns、L2 ~4 ns、L3 ~26 ns、DRAM ~100 ns）：

| 假设 | AMAT |
|------|:---:|
| L1 命中率 95% | ≈1 + 0.05×100 ≈ **6 ns** |
| L1 命中率 80% | ≈1 + 0.20×100 ≈ **21 ns**（慢 3 倍多） |

**两个结论**：命中率下降一点点、性能掉几倍（**降低缺失率最值钱**）；也解释了"为什么分块/局部性优化常常立竿见影"。

### 写策略的取舍

| 组合 | 做法 | 适合 |
|------|------|------|
| **写回 + 写分配**（主流） | 写只改 Cache（脏位），被替换时才写回；写缺失先调入 | 通用负载（写后可能再读） |
| 写直达 | 每次写都同步到下层 | 简单/多核共享数据 |
| 非写分配 | 写缺失直接写主存，不调入 | **流式写**（大数组只写不读，防污染缓存） |

**工程用法**：一次写大数组且不再读 → 用非临时存储（`movntdq`/`_mm_stream_si128`）绕过缓存；多线程共享写用写直达语义更直观，但带宽压力大。

## 7. TLB 与页大小：地址翻译也是缓存

**TLB** 缓存"虚拟地址 → 物理地址"的翻译（表项几十到几千个）。**覆盖范围 = 表项数 × 页大小**：

| 页大小 | 64 项 TLB 覆盖 | 意味 |
|:---:|:---:|------|
| 4 KB | **256 KB** | 超过 256KB 的工作集就开始 TLB 缺失（每次要查多级页表 = 多次访存） |
| **2 MB（大页）** | **128 MB** | 同样 TLB 能覆盖 512 倍的内存 |

**这解释了两件事**：

1. **大页（HugePage/THP）对"大内存随机访问"很值**：TLB 缺失率暴跌（THP、`vm.nr_hugepages` 可调）
2. 我们的指针追逐实测（4KB→64MB 延迟 ~1→~100 ns）里，**大工作集的延迟里就混着 TLB 缺失**（不只是 cache 缺失）

## 8. 替换算法：LRU 不是永远最好（模拟实测）

**模拟**（20 万次访问、缓存 256 行，命中率）：

| 访问模式 | LRU | FIFO | 随机 | OPT（理论最优） |
|---------|:---:|:---:|:---:|:---:|
| **循环 512 块（>缓存容量）** | **0.0%** | **0.0%** | **20.3%** | 49.7% |
| 随机 4096 块 | 6.3% | 6.3% | 6.3% | 30.2% |
| 热点 100 块（<缓存） | 100% | 100% | 100% | 100% |

**读法（经典结论）**：

- **循环访问且工作集 > 缓存**：LRU/FIFO 抖动到 **0%**（刚淘汰的马上又用）——**随机替换反而更好**（实测 20.3%）；这也是数据库/存储层用"分段 LRU / 随机化"的原因
- **随机访问**：三种差不多（都被容量卡住）
- **热点集中且装得下**：都能 100%
- **OPT 只是上界**（要预知未来），用来衡量"离最优差多远"

**硬件现实**：精确 LRU 要记录每行的访问序（代价高）→ CPU 里用**近似 LRU**（clock/NRU：一行一个"最近用过"位，扫描淘汰）——所以"LRU"在硬件里大多是近似。

## 9. 要点回顾

1. **延迟层次**（实测）：L1 ~1 ns → L2 ~4 ns → L3 ~26 ns → 内存 ~100 ns（**80 倍差距**）
2. **cache line = 64 字节**：访问 1 个 int 会搬 16 个——所以**空间局部性**几乎是白送的性能
3. **组相联 + 写回 + LRU 近似**是主流设计；映射/替换/写策略是"容量与命中率的折中"
4. **伪共享**用 `alignas(64)` 隔离（实测只 1.1 倍，但保险且零成本；教科书场景 2~10 倍）
5. **延迟 ≠ 带宽**：顺序读是 GB/s 级带宽、随机访问却是 ~100 ns 延迟——优化的方向完全不同
6. **连续内存的优势是物理层的**（DRAM row buffer、cache line、预取器三重加持）——实测顺序 20 GB/s vs 随机 1.26 GB/s（**16 倍**）
7. **4KB 步长最坑**（冲突缺失）→ 分块/步长避开 2 的幂；**基准数字要写清测法**（同叫"内存带宽"能差 4 倍）
