# 概述与编译流程

编译 = 把"给人看的源码"翻译成"给机器跑的目标码"——中间靠**一串 IR 变换（pass 流水线）**。这一篇立骨架，后面逐段展开。

## 1. 编译器长什么样

```
源码 ──前端──→ 中间表示(IR) ──优化──→ 目标代码
      ↑                            ↑
   与语言/机器都相关的部分      与语言无关、与机器相关的部分
```

| 阶段 | 干什么 | 教材叫法 |
|------|--------|---------|
| 词法分析 | 字符流 → token 流 | Scanner / Lexer |
| 语法分析 | token → 语法树 | Parser |
| 语义分析 | 查符号表、类型检查、填语义信息 | Semantic Analysis |
| 中间代码生成 | 语法树 → IR（三地址码/SSA） | IR Generation |
| 优化 | 在 IR 上做等价变换 | Optimizer |
| 目标代码生成 | IR → 汇编/机器码 | Codegen |

**前端**（词法/语法/语义）与**后端**（优化/代码生成）的分界就是 IR：换语言只改前端、换芯片只改后端——这也是"为什么 LLVM 能支持那么多语言和芯片"的原因。

## 2. 实测：一行源码变成哪些文件

```bash
clang++ -E t.cpp -o t.i          # ① 预处理：展开 #include/#define
clang++ -S t.cpp -o t.s          # ② 编译：生成汇编
clang++ -c t.cpp -o t.o          # ③ 汇编：生成目标文件
clang++ -emit-llvm -S t.cpp -o t.ll   # ④ 直接生成 LLVM IR（观察编译器内部的窗口）
```

**读产物**：`.i` 会大得多——里面几乎全是头文件展开出来的声明（引 `<iostream>` 能到 MB 级）；`.s`/`.o` 反而小，因为**声明不生成代码、只有函数体生成代码**。

**IR 长什么样**（`-O0`，未优化；节选）：

```llvm
define dso_local noundef i32 @_Z3addii(i32 noundef %0, i32 noundef %1) #0 {
  %3 = alloca i32, align 4        ; 在栈上开空间（-O0 的典型低效写法）
  store i32 %0, ptr %3, align 4
  ...
  %7 = add nsw i32 %5, %6         ; 真正的加法
```

**汇编长什么样**（同一个函数）：

```asm
_Z3addii:
	pushq	%rbp                  ; 建立栈帧
	movq	%rsp, %rbp
```

**为什么中间要有 IR**：直接"源码 → 汇编"要每种语言 × 每种芯片写一遍；有了 IR，**前端 N 个 + 后端 M 个 = N+M 个模块**（而不是 N×M）。

## 3. 编译 vs 解释 vs JIT

| 方式 | 流程 | 例子 |
|------|------|------|
| **编译** | 事前全部翻成机器码 | C/C++、Rust |
| **解释** | 运行时逐条执行源码/AST | Python（CPython）、Shell |
| **JIT** | 运行时把"热点"编译成机器码 | Java JVM、V8（JS）、PyPy |
| **AOT + 图编译** | 事先生成计算图并优化 | TensorRT/ONNX Runtime、TVM（AI 场景） |

AI 推理大多是"**图编译 + JIT**"：模型是一张计算图，推理引擎在**加载时/运行时**做图优化再生成内核（第 9 篇展开）。

## 5. 要点回顾

1. **编译 = 前端 + IR + 后端**；六阶段：词法/语法/语义/IR 生成/优化/代码生成
2. **IR 是枢纽**：前后端解耦（N+M 而不是 N×M）——也是 LLVM 生态的根基
3. **产物链**：`.i`（预处理：头文件全展开）→ `.s` → `.o` → 可执行；`-emit-llvm` 直接看 IR
4. **编译/解释/JIT 是三种策略**：C++ 编译、Python 解释、JVM/V8 JIT；AI 推理多为"图编译 + JIT"
5. 后面每一篇都对应流水线的一段：第 2~3 篇前端、第 5~6 篇 IR 与存储、第 7~8 篇优化与代码生成、第 9 篇 AI 编译器
