# 词法分析

编译器第一站：**字符流 → token 流**（关键字、标识符、数字、运算符……）。理论工具是**正则表达式 + 有限自动机**。

## 1. 词法单元（token）

```
total = (x1 + 42) * 3 - _y / 2
  ↓ 词法分析
标识符(total)  运算符(=)  界符(()  标识符(x1)  运算符(+)  数字(42) ...
```

设计要点：

- **最长匹配**（maximal munch）：`>=` 是一个 token、不是 `>` 加 `=`；`123abc` 怎么切由规则决定
- **关键字 vs 标识符**：都是"字母开头"，用一张关键字表区分（先按标识符扫，再查表）
- **空白/注释**：直接丢掉（但行号要维护——错误信息要用）

## 2. 理论：正则 → NFA → DFA

| 概念 | 含义 |
|------|------|
| 正则表达式 | 描述 token 的模式（`[A-Za-z_][A-Za-z0-9_]*`） |
| **NFA** | 非确定有限自动机：同一状态同一输入可有多个去向、还能走 ε |
| **DFA** | 确定有限自动机：每个状态每个输入**唯一**去向 |
| 子集构造 | NFA → DFA（一组 NFA 状态 = 一个 DFA 状态） |
| 最小化 | 合并等价状态，得到状态最少的 DFA |

**为什么要 DFA**：词法分析要**线性时间**扫描（每个字符走一步）——DFA 正好是"一个字符一步、无回溯"。

**实测**（手写 Thompson 构造 + 子集构造，正则 `(a|b)*abb`）：

```
DFA 状态数（子集构造后）: 4
  D0  --a--> 1   --b--> 0
  D1  --a--> 1   --b--> 2
  D2  --a--> 1   --b--> 3
  D3  --a--> 1   --b--> 0   ← 接受
"abb" → 接受    "aabb" → 接受    "ababb" → 接受
"ab" → 拒绝      "abba" → 拒绝
```

**一个真实的坑**（写 NFA 时踩到）：`(a|b)*` 的循环和后续 "abb" 的**首字符都是 a**——必须用 ε 跳转把"继续循环"和"开始匹配后缀"两条路分开（第一版没留 ε，字符串 `abb` 被误拒）。

## 3. 手写一个词法分析器

```cpp
// 核心结构：while 扫字符 → 匹配数字/标识符/运算符 → 产出 token
std::vector<Token> tokenize(const std::string& src) {
    std::vector<Token> out;
    for (size_t i = 0; i < src.size(); ) {
        char c = src[i];
        if (isspace(c)) { ++i; continue; }
        if (isdigit(c)) {                       // 数字：[0-9]+
            std::string s;
            while (i < src.size() && isdigit(src[i])) s += src[i++];
            out.push_back({Tok::Num, s});
        } else if (isalpha(c) || c == '_') {    // 标识符：[A-Za-z_][A-Za-z0-9_]*
            ...
        } else {
            switch (c) {                        // 单字符运算符
                case '=': ... case '+': ... case '(': ...
                default: /* 词法错误：报错并返回 */
            }
        }
    }
    return out;
}
```

**输出示例**（输入 `total = (x1 + 42) * 3 - _y / 2`）：

```
标识符 total | 运算符 = | 界符 ( | 标识符 x1 | 运算符 + | 数字 42 | 界符 ) | 运算符 * | 数字 3 | 运算符 - | 标识符 _y | 运算符 / | 数字 2
```

**错误处理**（同一程序，输入含 `#`）：

```
非法字符 '#'（词法错误）
```

**工程现实**：手写 tokenizer 通常够用且更快；要复杂模式才上 **flex**（从正则生成 C 代码 第 4 篇用）。

## 4. 正则的边界：为什么还需要文法

正则能描述 token，但**描述不了配对结构**（如"括号必须配对"、`if`/`else` 嵌套）——这需要**上下文无关文法**（下一站）。乔姆斯基体系的 3 型（正则）↔ 2 型（上下文无关）分界就在这里（速查篇有表）。

## 5. 要点回顾

1. **词法分析 = 字符流 → token 流**；最长匹配、关键字表、丢空白但记行号
2. **正则 ↔ NFA ↔ DFA**：Thompson 构造（正则→NFA）、子集构造（NFA→DFA）、最小化；DFA 保证**无回溯线性扫描**
3. **实测**：`(a|b)*abb` 子集构造后 4 个状态；"abb/aabb/ababb" 接受、"ab/abba" 拒绝
4. **坑**：循环部分和后续模式共享字符时要用 ε 连接（否则误拒）；flex 的 `.` 不含换行（第 4 篇实测）
5. **正则描述不了配对/嵌套** → 交给语法分析（上下文无关文法）
