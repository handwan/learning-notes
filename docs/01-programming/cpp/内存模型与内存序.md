# 内存模型与内存序

C++ 内存模型 = 多线程下"内存操作可见性和顺序"的规则。中高级并发的核心内容。

## 1. 为什么需要内存模型

**问题**：你写的代码顺序，和 CPU 实际执行的内存操作顺序**可能不一致**，原因有三：

1. **编译器重排**：优化时调整指令顺序
2. **CPU 乱序执行**：硬件并行，指令不按顺序执行
3. **缓存**：多核各自缓存，一个核的写另一个核未必立刻看到

```cpp
// 你以为：
data = 42;
ready = true;

// CPU 实际可能先执行 ready = true，再执行 data = 42（重排）
// 另一个线程看到 ready=true 就以为 data 准备好了，其实没有 → 出错
```

**内存模型的作用**：规定"在多线程环境下，哪些重排允许、哪些禁止"，保证多线程能正确同步。

## 2. 数据竞争（Data Race）

**定义**：两个线程访问同一内存位置，**至少一个写**，且**没有同步**：

```cpp
int x = 0;
// 线程1：x = 1;
// 线程2：x = 2;
// 没有锁/原子 → 数据竞争
```

**关键结论**：**数据竞争 = UB**（未定义行为），不只是"结果不确定"，而是"标准不保证任何事"。

所以多线程共享数据的正确做法：锁 或 原子操作 或 用现成的同步原语。

## 3. happens-before

**定义**：如果 A **happens-before** B，那么 A 的所有内存写入对 B **可见**。

**这是内存模型的核心**——它定义了"哪些操作的结果能被其他操作看到"。

### 3.1 线程内：sequenced-before

同一线程内，代码按顺序就是 sequenced-before（A 在 B 前面）：

```cpp
int a = 1;      // ①
int b = 2;      // ②
// ① sequenced-before ②
```

### 3.2 线程间：synchronizes-with

通过**同步操作**建立线程间关系（如 release/acquire、锁的加解锁）：

```cpp
// 线程1：              // 线程2：
data = 42;
flag.store(1, release);  flag.load(acquire);
                          read(data);   // 保证看到 42

// flag.store(release) synchronizes-with flag.load(acquire)
```

### 3.3 happens-before = 传递

```
A sequenced-before B（线程内）
B synchronizes-with C（线程间）
C sequenced-before D（线程内）
→ A happens-before D
```

**也就是说**：线程1 在 release 之前的所有写，线程2 在 acquire 之后都能看到。

## 4. 内存序（memory order）

`std::atomic` 操作可以指定内存序，控制"重排的允许程度"和"开销"：

| 内存序 | 语义 | 开销 |
|--------|------|------|
| `relaxed` | 只保证原子性，**不保证顺序** | 最低 |
| `consume` | 依赖数据的顺序（已废弃，别用） | — |
| `acquire` | 之后的读写不能排到前面（读操作） | 中 |
| `release` | 之前的读写不能排到后面（写操作） | 中 |
| `acq_rel` | acquire + release（读改写操作） | 较高 |
| `seq_cst` | **全局单一顺序**（默认，最严格） | 最高 |

### relaxed（最弱）

```cpp
// 只保证"这个操作是原子的"，不管顺序
counter.fetch_add(1, std::memory_order_relaxed);
// 用途：只关心计数最终正确，不需要和其他内存同步（如统计计数）
```

### acquire / release（成对）

```cpp
// 生产者：
data = 42;                                    // 普通写
ready.store(true, std::memory_order_release); // ① 发布
// 语义：① 之前的所有写（data=42）都不能排到 ① 之后

// 消费者：
while (!ready.load(std::memory_order_acquire)) { }  // ② 获取
use(data);   // 保证看到 42
// 语义：② 之后的所有读都不能排到 ② 之前
```

**记忆**：

- `release`：把之前的写"推出去"（像发布）
- `acquire`：把之后的读"拦下来"（像获取）
- 两者配对，保证数据可见性

### seq_cst（默认，最强）

```cpp
ready.store(true);   // 默认就是 seq_cst
// 所有 seq_cst 操作在全局有"单一总顺序"，所有线程看到一致
// 最安全，也最慢（需要内存屏障）
```

**为什么默认 seq_cst 最慢**：它要求全局一致的顺序，需要额外同步（内存屏障），限制了 CPU/编译器的优化空间。

### 怎么选

```cpp
// 默认不确定 → 用 seq_cst（安全）
// 简单计数 → relaxed（最快）
// 生产者-消费者传数据 → release/acquire（性能和安全平衡）
```

## 5. 无锁编程（Lock-Free）

**思想**：不用锁，靠 **CAS**（Compare-And-Swap）原子操作实现线程安全。

### CAS 是什么

```cpp
// 原子操作：如果当前值 == expected，就替换成 desired，返回是否成功
bool compare_exchange_weak(T& expected, T desired);

// 用法（无锁自增）：
void increment(std::atomic<int>& a) {
    int old = a.load();
    while (!a.compare_exchange_weak(old, old + 1)) {
        // 失败（别人改过了），重试
    }
}
```

### 无锁计数器示例

```cpp
std::atomic<int> counter{0};
// 多个线程无锁自增
counter.fetch_add(1, std::memory_order_relaxed);   // 本身就是无锁的原子自增
```

### ABA 问题

```
线程1：读 A → 想改成 C
（此时线程2：把 A 改成 B，又改回 A）
线程1：CAS 发现还是 A → 成功改成 C
问题：中间状态 B 被忽略了，可能有隐患
```

**解决**：带版本号（`std::atomic<std::pair<T, int>>` 或 tagged pointer）。

### 为什么无锁难写对

1. 内存序要精确配对
2. ABA、内存回收（一个线程刚读完指针，另一个线程就释放了）
3. 编译器/CPU 重排

**结论**：无锁是"专家领域"，业务代码优先用锁（`mutex`）+ 原子（简单场景）。

## 6. 内存屏障（Memory Barrier）

**作用**：挡住重排。分两种：

| 类型 | 挡谁 | 对应 |
|------|------|------|
| **编译器屏障** | 编译器重排 | `std::atomic_signal_fence` |
| **CPU 屏障** | CPU/缓存重排 | `std::atomic_thread_fence` |

```cpp
std::atomic_thread_fence(std::memory_order_release);   // 相当于 release 的"纯屏障"
```

**关系**：`release`/`acquire` 内存序**内部就包含了屏障**（所以能保证顺序）。手动用 `fence` 是更细粒度的控制，业务代码极少直接用。

## 7. 要点回顾

1. **为什么需要内存模型**：编译器重排 + CPU 乱序 + 缓存导致多线程看到不一致的顺序
2. **数据竞争 = UB**（不只是结果不确定）
3. **happens-before**：A 的写对 B 可见；由 sequenced-before + synchronizes-with 传递而来
4. **内存序**：relaxed（最弱）/ acquire / release / acq_rel / seq_cst（默认最强最慢）；`consume` 已废弃别用
5. **release/acquire 配对**：release 发布写、acquire 获取读，保证数据可见
6. **无锁**：靠 CAS，难写对（ABA、内存回收），业务优先用锁
7. **内存屏障**：挡重排，release/acquire 内部已包含
