# 并发编程

C++11 起标准库提供多线程支持（`<thread>`、`<mutex>`、`<atomic>`）。核心问题：**多线程共享数据时怎么不出错**。

## 1. 线程基础

### 创建线程

```cpp
#include <thread>

void task(int x) { /* 线程要干的事 */ }

std::thread t(task, 42);   // 创建线程，传参
// ...主线程继续干别的
t.join();                  // 等待 t 结束

// 或分离（不等待，线程自己跑，但注意资源释放）：
t.detach();                // ⚠️ 用 detach 要小心（主线程结束程序就没了）
```

**join vs detach**：

- `join()`：等待线程结束
- `detach()`：线程后台运行，不等待（小心：主线程退出，detach 的线程也会被终止）

### 数据竞争（Data Race）

**问题**：两个线程同时读写同一数据，结果不确定：

```cpp
int counter = 0;

void add() {
    for (int i = 0; i < 10000; i++) counter++;   // 两个线程同时执行
}

std::thread t1(add), t2(add);
t1.join(); t2.join();
// counter 不一定是 20000！可能 15000、18000...
// 因为 counter++ 不是原子操作（读-改-写三步，可能互相覆盖）
```

**数据竞争 = 未定义行为**，必须用锁或原子操作解决。

## 2. 互斥锁（mutex）

### mutex + lock_guard

```cpp
#include <mutex>

std::mutex m;
int counter = 0;

void add() {
    for (int i = 0; i < 10000; i++) {
        std::lock_guard<std::mutex> lg(m);   // 加锁，出作用域自动解锁
        counter++;
    }
}
// 现在 counter == 20000 ✓
```

**lock_guard**：RAII 风格，构造加锁、析构解锁，**不会忘解锁**（即使抛异常也安全）。

### unique_lock（更灵活）

```cpp
std::unique_lock<std::mutex> ul(m);   // 比 lock_guard 灵活
ul.unlock();                          // 可以手动提前解锁
ul.lock();                            // 再锁
// 常用于配合条件变量
```

### 死锁（Deadlock）

**场景**：两个线程各自持有一把锁，又等对方的锁：

```cpp
std::mutex m1, m2;

// 线程1：先锁 m1 再锁 m2
// 线程2：先锁 m2 再锁 m1
// 可能：线程1 持 m1 等 m2，线程2 持 m2 等 m1 → 互相等，卡死！
```

**解决**：

1. **加锁顺序一致**（都先锁 m1 再锁 m2）
2. **std::lock 一次锁多个**（自动避免死锁）：
```cpp
std::scoped_lock lock(m1, m2);   // C++17，一次锁多个，不会死锁
```

### 死锁的四个必要条件

死锁必须**同时满足**这四条，缺一不可：

1. **互斥**：资源一次只能被一个线程占用
2. **持有并等待**：拿着一个资源，还等另一个
3. **不可剥夺**：别人占的资源抢不走
4. **循环等待**：A 等 B，B 等 A（成环）

**破坏任意一条即可防死锁**：

| 破坏哪条 | 做法 |
|---------|------|
| 破坏循环等待 | **加锁顺序一致** |
| 破坏持有并等待 | 一次锁全部（scoped_lock） |
| 破坏互斥/不可剥夺 | 难，一般不从这里下手 |

### 自旋锁（spinlock，了解）

```cpp
// 互斥锁：拿不到锁 → 线程睡眠（系统调用，开销大）
// 自旋锁：拿不到锁 → 线程原地转圈等（忙等，不睡眠）

std::atomic_flag flag = ATOMIC_FLAG_INIT;

void spin_lock() {
    while (flag.test_and_set(std::memory_order_acquire)) { }  // 忙等
}
void spin_unlock() {
    flag.clear(std::memory_order_release);
}
```

**对比**：

| | mutex | 自旋锁 |
|--|-------|--------|
| 拿不到锁 | 睡眠（让出 CPU） | 原地转圈（占着 CPU） |
| 适合 | 临界区长（等待久） | 临界区极短（等一下就拿到了） |
| 开销 | 系统调用 | 无系统调用，但费 CPU |

**结论**：临界区**极短**（几行代码、几纳秒）时自旋锁更快；否则用 mutex。业务代码几乎都用 mutex，自旋锁了解即可。

### 条件变量（condition_variable）

**用途**：线程间"等待某个条件成立"（生产者-消费者模型）：

```cpp
std::mutex m;
std::condition_variable cv;
std::queue<int> q;

// 生产者：
{
    std::lock_guard<std::mutex> lg(m);   // 改 q 之前必须加锁
    q.push(item);
}
cv.notify_one();                  // 通知一个等待的线程

// 消费者：
std::unique_lock<std::mutex> ul(m);
cv.wait(ul, []{ return !q.empty(); });   // 等队列非空（自动解锁/加锁）
int item = q.front(); q.pop();
```

**关键**：`wait` 传条件，防止"虚假唤醒"（被唤醒但条件没满足）。

### shared_mutex（读写锁）

**场景**：读多写少（读很频繁，写很少）。普通 mutex 读也要互斥（浪费），读写锁让**多个读并行**、**写独占**：

```cpp
std::shared_mutex m;
std::map<std::string, int> cache;

// 读：共享锁，多个线程可同时读
int get(const std::string& key) {
    std::shared_lock<std::shared_mutex> lk(m);   // 读锁，共享
    return cache[key];
}

// 写：独占锁，写时没人能读
void set(const std::string& key, int v) {
    std::unique_lock<std::shared_mutex> lk(m);   // 写锁，独占
    cache[key] = v;
}
```

**记忆**：`shared_lock` = 读（共享），`unique_lock` = 写（独占）。

### recursive_mutex（递归锁，偶尔问）

普通 mutex **同一线程重复加锁 = 死锁**；`recursive_mutex` 允许同一线程加多次（计数，解锁同样次数）：

```cpp
std::recursive_mutex m;

void f() {
    std::lock_guard<std::recursive_mutex> lk(m);
    g();          // g 里也加同一把锁 → 普通 mutex 死锁，recursive_mutex 可以
}
```

**注意**：能用普通 mutex 解决就别用递归锁（递归锁说明设计可能有问题）。

### 小工具：this_thread / thread_local

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(100));   // 睡 100ms
std::this_thread::yield();          // 主动让出 CPU
std::this_thread::get_id();         // 当前线程 ID

thread_local int tls = 0;           // 线程局部变量：每个线程有自己的一份
```

## 3. 原子操作（atomic）

### 为什么需要 atomic

```cpp
// 上面用 mutex 保护 counter++，但开销大（系统调用）
// 简单计数用 atomic 更快：

std::atomic<int> counter{0};

void add() {
    for (int i = 0; i < 10000; i++) counter++;   // 原子自增，线程安全
}
// counter == 20000 ✓，无锁，更快
```

**atomic 是什么**：保证操作的**原子性**（读-改-写不可分割），硬件层面用 CAS 指令实现，比 mutex 轻量。

### 常用操作

```cpp
std::atomic<int> a{0};
a++;                  // 原子自增
a.fetch_add(1);       // 同上
a.load();             // 原子读
a.store(5);           // 原子写
a.compare_exchange_weak(expected, desired);   // CAS：相等才替换
```

### atomic vs mutex

| | mutex | atomic |
|--|-------|--------|
| 保护范围 | 一段代码（多个操作） | 单个变量 |
| 开销 | 较大（系统调用） | 小（硬件指令） |
| 场景 | 保护复杂数据结构 | 简单计数、标志位 |

**规则**：**单个简单变量用 atomic，多个变量的组合操作用 mutex**。

### volatile vs atomic

```cpp
volatile int x;          // ❌ 不是线程安全！
std::atomic<int> y;      // 才是线程安全
```

**区别**：

| | volatile | atomic |
|--|---------|--------|
| 作用 | 告诉编译器"别优化这个变量"（每次从内存读） | 保证操作的原子性 |
| 线程安全 | ❌ 不能（只管编译器优化，不管并发） | ✅ 能 |
| 用途 | 硬件寄存器、信号处理 | 多线程共享变量 |

**一句话**：volatile 管"编译器优化"，atomic 管"并发原子性"，两码事。多线程共享用 atomic，别用 volatile。

### STL 容器的线程安全

| 操作 | 安全吗 |
|------|--------|
| 多线程**同时读** | ✅ 安全 |
| 多线程**同时写**（只要有写） | ❌ 不安全（数据竞争） |
| 读写同时 | ❌ 不安全 |

```cpp
std::vector<int> v{1, 2, 3};

// 多线程只读：安全
// ❌ 两个线程同时 push_back：数据竞争，未定义行为
// ❌ 一个读一个写：不安全
```

**规则**：STL 容器**不提供任何内置线程安全**。要么加锁，要么每个线程用自己的容器。

### call_once 与线程安全单例

```cpp
#include <mutex>

// 方式1：call_once（保证只执行一次）
std::once_flag flag;
std::unique_ptr<Config> config;

Config& get_config() {
    std::call_once(flag, []{
        config = std::make_unique<Config>();   // 只执行一次
    });
    return *config;
}

// 方式2：局部 static（C++11 起线程安全，最简单）
Config& get_config2() {
    static Config c;    // ⚠️ C++11 保证初始化线程安全
    return c;
}
```

**经典问题**："手写线程安全的单例" → 用**局部 static**（方式2）最简洁，C++11 起初始化就是线程安全的。

## 4. 内存序（详见「内存模型与内存序.md」）

```cpp
std::atomic<int> x{0};
x.store(1, std::memory_order_release);   // 默认 memory_order_seq_cst
x.load(std::memory_order_acquire);
```

**默认（seq_cst）最安全也最慢**，一般不用改。**无锁编程才需要研究内存序**。

内存模型（happens-before、5 种内存序、无锁编程、内存屏障）内容较多，单独成篇，见 [内存模型与内存序](内存模型与内存序.md)。

### 同步原语：latch / barrier / semaphore（C++20）

```cpp
#include <latch>
#include <barrier>
#include <semaphore>

// latch：一次性计数器（等 n 个线程都到达）
std::latch l{3};
// 每个线程做完一段：l.count_down();
// 主线程：l.wait();   // 等 3 个都 count_down

// barrier：可复用的屏障（每轮都同步）
std::barrier b{3};
// b.arrive_and_wait();   // 到达并等待其他线程

// semaphore：信号量（控制并发数）
std::counting_semaphore<2> sem{2};
// sem.acquire();  // 拿许可（不够就阻塞）
// sem.release();  // 还许可
```

**场景**：分阶段并行（barrier）、限流（semaphore）、等所有线程就绪（latch）。比手写 condition_variable 简洁。

## 5. 异步任务（async / future）

```cpp
#include <future>

int heavy_task() { return 42; }

// 异步执行，不阻塞
std::future<int> fut = std::async(std::launch::async, heavy_task);

// ...主线程干别的

int result = fut.get();   // 这里阻塞，等结果
```

**用途**：把耗时任务丢后台，结果用 future 拿。类似"启动一个任务，回头取结果"。

### future / promise / packaged_task（异步三件套）

future 是"消费者"（取结果），有三个"生产者"可以给它喂结果：

| 生产者 | 说明 | 场景 |
|--------|------|------|
| `std::async` | 最方便，启动任务 + 自动管理线程 | 简单异步任务 |
| `std::promise` | 手动 `set_value` | 线程间传值 |
| `std::packaged_task` | 包装可调用对象，自动生成 promise/future | 把任务传给线程池 |

**① promise/future（线程间传值）**：

```cpp
std::promise<int> prom;
std::future<int> fut = prom.get_future();

std::thread t([&prom] {
    prom.set_value(42);      // 设置结果
    // prom.set_exception(...);  // 或传异常
});

int x = fut.get();           // 阻塞等结果（异常会在这里抛出来）
t.join();
```

**② packaged_task（把函数打包成任务）**：

```cpp
std::packaged_task<int()> task(heavy_task);   // 包装函数
std::future<int> fut = task.get_future();     // 拿到关联的 future

std::thread t(std::move(task));   // 任务丢给线程执行
int x = fut.get();                // 取结果
t.join();
```

**③ async（最方便，底层就是 ①②）**：上面讲过。

### future 的细节与坑

```cpp
std::future<int> fut = std::async(...);

fut.get();       // ⚠️ 只能调一次！第二次调用 = 未定义行为
fut.valid();     // 是否还有结果可取
fut.wait();      // 只等，不取
fut.wait_for(std::chrono::seconds(1));   // 限时等待
```

- **get() 只能一次**：future 是"一次性"的，结果被取走就没了
- **future 不可拷贝**（只能移动，`std::move`），因为结果所有权唯一
- **shared_future 可拷贝**：`fut.share()` 转成 `std::shared_future`，多个线程都能 get

```cpp
std::shared_future<int> sf = fut.share();   // 转 shared_future
int a = sf.get();   // 多次 get 都行
int b = sf.get();   // 所有线程共享同一结果
```

### launch 策略

```cpp
std::async(std::launch::async, f);      // 强制开新线程
std::async(std::launch::deferred, f);   // 延迟执行（get 时才在当前线程跑）
std::async(f);                          // 默认 = async | deferred（编译器决定）
```

## 6. 锁的优化与选型

### 锁粒度

```cpp
// 粗锁：一把大锁保护所有数据 → 简单，但并发差（大家抢一把锁）
std::mutex global_mutex;

// 细锁：每个数据一把锁 → 并发好，但复杂、易死锁
std::mutex m1, m2;

// 分段锁：把数据分成多段，每段一把锁（如 concurrent hashmap 按桶加锁）
std::array<std::mutex, 16> seg_mutex;   // 16 段，各自加锁
```

**权衡**：锁越细并发越高，但锁管理开销和死锁风险也越高。

### 锁的饥饿（Starvation）

**读写锁的"写饥饿"**：读操作一直来，写操作永远抢不到锁：

```cpp
// 读多写少时，shared_mutex 的读锁不断获取 → 写线程一直等
// 解决：公平锁（按顺序）、写优先策略
```

**结论**：**读写锁不一定比 mutex 快**——读写锁有额外开销（维护读写计数），读写比不够悬殊时，普通 mutex 反而更快。要用基准测试决定。

### 自旋锁的适用边界

（前文讲过）**只在临界区极短时用**——否则线程空转烧 CPU。业务代码几乎都用 mutex。

### 减少锁竞争的其他手段

1. **减小临界区**：锁内只放必要代码（别在锁内做 IO/计算）
2. **读写分离**：读多写少用 `shared_mutex`
3. **无锁/原子**：单个变量用 `atomic`
4. **线程本地（thread_local）**：每个线程用自己的数据，最后合并（如每线程一个局部计数器）
5. **避免锁嵌套**：防止死锁

## 7. 并发数据结构

### 并发队列

**任务分发的核心结构**：

| 类型 | 说明 |
|------|------|
| **阻塞队列** | 空时取会阻塞、满时放会阻塞（线程池任务队列） |
| 无锁队列 | 用 CAS 实现，性能高但难写对 |

```cpp
// 阻塞队列（用 mutex + condition_variable）：
template <typename T>
class BlockingQueue {
    std::queue<T> q_;
    std::mutex m_;
    std::condition_variable not_empty_, not_full_;
    size_t cap_;
public:
    void push(T item) {
        std::unique_lock<std::mutex> lock(m_);
        not_full_.wait(lock, [this]{ return q_.size() < cap_; });   // 满则等
        q_.push(std::move(item));
        not_empty_.notify_one();
    }
    T pop() {
        std::unique_lock<std::mutex> lock(m_);
        not_empty_.wait(lock, [this]{ return !q_.empty(); });       // 空则等
        T item = std::move(q_.front());
        q_.pop();
        not_full_.notify_one();
        return item;
    }
};
```

### thread_local 进阶

```cpp
thread_local int cache = 0;   // 每个线程独立一份

// 构造/析构时机：
// - 构造：线程第一次访问时（惰性初始化）
// - 析构：线程退出时
// ⚠️ 跨动态库：不同库里的 thread_local 可能不共享（ABI 问题）
// ⚠️ 性能：访问 thread_local 比普通变量慢（要查线程局部存储）

// 工程用法：线程局部缓存（每个线程一份，避免锁）
thread_local std::vector<char> buffer;   // 每线程一个缓冲区
```

**用途**：避免锁（每线程独占数据）、线程局部缓存、错误码（errno 就是 thread_local）。

## 8. 为什么需要线程池

线程池 = **预先创建一批线程，循环从任务队列取任务执行**。避免"每个任务都新建/销毁线程"的开销。经典手写题。

**问题**：频繁创建/销毁线程开销大：

```cpp
// ❌ 每个任务都新建线程：
for (auto& task : tasks) {
    std::thread t(task);   // 创建线程 = 系统调用，开销大
    t.detach();
}

// 用线程池：线程复用
```

**线程创建的成本**：分配栈空间、内核数据结构、上下文切换——频繁创建很慢。

## 9. 核心原理

```
提交任务 → 任务队列（线程安全：mutex + condition_variable）→ 工作线程（循环取任务执行）
```

**组成**：

1. **任务队列**（线程安全）
2. **工作线程池**（一组线程循环取任务）
3. **提交接口**（往队列加任务）

## 10. 简化实现

```cpp
#include <thread>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <functional>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i) {
            workers_.emplace_back([this] {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lock(mtx_);
                        cv_.wait(lock, [this] {
                            return stop_ || !tasks_.empty();   // 有任务或要停
                        });
                        if (stop_ && tasks_.empty()) return;   // 退出
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }
                    task();   // 执行任务（锁外执行，避免占锁）
                }
            });
        }
    }

    template <typename F>
    void submit(F&& f) {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            tasks_.emplace(std::forward<F>(f));
        }
        cv_.notify_one();   // 唤醒一个工作线程
    }

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            stop_ = true;
        }
        cv_.notify_all();                          // 唤醒所有线程
        for (auto& t : workers_) t.join();         // 等它们退出
    }

private:
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool stop_ = false;
};
```

**关键点**：

1. `condition_variable` 的 `wait` 要传条件（防虚假唤醒）
2. **任务在锁外执行**（否则串行化，失去并发意义）
3. 析构时 `stop_` + `notify_all` + `join`（优雅退出）

## 11. 线程数设置

| 任务类型 | 线程数 |
|---------|--------|
| **CPU 密集**（计算） | ≈ **CPU 核数**（再多也抢不到 CPU） |
| **IO 密集**（网络/磁盘） | **核数 × (1 + 等待时间/计算时间)**（等待时让出 CPU） |

```cpp
unsigned int n = std::thread::hardware_concurrency();   // 获取 CPU 核数
```

**经验**：CPU 密集 = 核数；IO 密集可多一些（如核数×2~4），具体要压测调优。

## 12. 固定 vs 弹性线程池

| | 固定线程池 | 弹性线程池 |
|--|-----------|-----------|
| 线程数 | 固定 | 按负载增减（如核心线程 + 最大线程 + 空闲回收） |
| 优点 | 简单、稳定 | 适应负载波动 |
| 缺点 | 负载高时排队 | 复杂、线程创建销毁开销 |

## 13. 任务优先级

**简单线程池**：FIFO 队列（无优先级）。
**带优先级**：用优先队列（`priority_queue`）代替普通队列，按优先级取任务。

```cpp
// 任务带优先级，高优先级先执行
std::priority_queue<Task, std::vector<Task>, CompareByPriority> tasks_;
```

## 14. 要点回顾

1. **数据竞争**：多线程同时读写同一数据 = 未定义行为
2. **mutex + lock_guard**：RAII 加锁，不会忘解锁
3. **死锁**：互相等对方的锁；解决：顺序一致 / scoped_lock 一次锁多个
4. **条件变量**：wait 要传条件，防虚假唤醒
5. **atomic vs mutex**：单变量用 atomic（快），多操作用 mutex
6. **join vs detach**：join 等待，detach 分离（小心使用）
7. **内存序**：默认 seq_cst 就够，无锁编程才深究
8. **future 三件套**：async（最方便）/ promise（手动传值）/ packaged_task（打包任务）
9. **future.get() 只能一次**：一次性取结果；要共享用 shared_future
10. **为什么用**：避免频繁创建/销毁线程
11. **核心组成**：任务队列 + 工作线程 + 提交接口
12. **关键点**：condition_variable 防虚假唤醒、任务锁外执行、优雅退出
13. **线程数**：CPU 密集 = 核数；IO 密集 = 核数 × 放大系数
14. **手写**：能默写一个简化线程池（mutex + cv + queue）

| 需求 | 工具 |
|------|------|
| 创建线程 | `std::thread` |
| 保护一段代码 | `mutex` + `lock_guard` / `unique_lock` |
| 等待条件 | `condition_variable` |
| 单个变量原子操作 | `std::atomic` |
| 异步任务 | `async` / `future` |
| 避免多锁死锁 | `scoped_lock` 或统一加锁顺序 |
线程池是多线程服务的基础设施：**固定数量的线程 + 任务队列**，达到"线程复用、控制并发度"的目的。腾讯/字节等大厂 C++ 岗常让手写。
