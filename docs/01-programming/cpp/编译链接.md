# 编译链接

从源码到可执行程序的过程，以及静态库/动态库。核心问题：**编译有哪几步**。

## 1. 编译流程

```
源代码 .cpp
   │ ① 预处理
   ▼
.i（展开宏、#include、去掉注释）
   │ ② 编译（词法、语法、语义分析 + 优化 + 代码生成）
   ▼
.s（汇编代码）
   │ ③ 汇编
   ▼
.o（目标文件，机器码）
   │ ④ 链接
   ▼
可执行文件
```

```bash
# 一条命令完成全部四步：
g++ main.cpp -o main

# 分步看：
g++ -E main.cpp -o main.i    # ① 只预处理
g++ -S main.i -o main.s      # ② 只编译到汇编
g++ -c main.s -o main.o      # ③ 只汇编成目标文件
g++ main.o -o main           # ④ 链接成可执行
```

**每步干什么**：

| 步骤 | 输入 | 输出 | 干什么 |
|------|------|------|--------|
| 预处理 | .cpp | .i | 宏展开、`#include` 展开、条件编译 |
| 编译 | .i | .s | 语法分析 → 优化 → 汇编代码 |
| 汇编 | .s | .o | 汇编 → 机器码（目标文件） |
| 链接 | .o | 可执行 | 合并目标文件、解析符号引用 |

## 2. 链接干了什么

**链接** = 把多个 .o 目标文件和库**合并**成一个可执行文件，做两件事：

1. **符号解析**：把"引用的符号"和"定义的符号"对上
2. **重定位**：修正代码里的地址引用

```cpp
// a.cpp 定义了函数 f
// main.cpp 调用了 f（但 main.cpp 里没有 f 的定义）
// 链接阶段：找到 a.o 里的 f，把 main.o 里对 f 的引用"接上"
```

**常见链接错误**：

```bash
undefined reference to `f'   # 找不到定义（只声明没定义，或库没链接上）
multiple definition of `f'   # 重复定义（两个 .o 都有 f）
```

## 3. 静态库 vs 动态库

| | 静态库 `.a` | 动态库 `.so` |
|--|-----------|-------------|
| 编译时 | 代码**拷贝进**可执行文件 | 只记录引用 |
| 体积 | 可执行文件大 | 可执行文件小 |
| 运行时 | 不依赖库文件 | 需要 .so 存在 |
| 更新 | 必须重新编译 | 换 .so 即可 |

```bash
# 静态库制作
g++ -c foo.cpp -o foo.o
ar rcs libfoo.a foo.o                    # 打包静态库
g++ main.cpp -L. -lfoo -o main           # 链接

# 动态库制作
g++ -c -fPIC foo.cpp -o foo.o            # -fPIC 必须
g++ -shared foo.o -o libfoo.so           # 生成动态库
g++ main.cpp -L. -lfoo -o main           # 编译时链接
export LD_LIBRARY_PATH=.                 # 运行时找 .so
```

## 4. 头文件与包含守卫

```cpp
// 防止头文件被重复包含
#ifndef MY_HEADER_H
#define MY_HEADER_H

// 头文件内容

#endif

// 或现代写法：
#pragma once
```

**头文件放什么**：声明（函数声明、类定义）；**不放什么**：函数定义（放 .cpp）、变量定义（会重复定义）。

## 5. 声明 vs 定义、ODR 单定义规则

**声明（declaration）**：告诉编译器"有这么个东西"（不分配存储）：

```cpp
int f(int x);              // 函数声明（只有签名，没有函数体）
extern int global_var;     // 变量声明（extern，不定义）
class A;                   // 前置声明（类只知道名字）
```

**定义（definition）**：实际创建（分配存储/生成代码）：

```cpp
int f(int x) { return x; }   // 函数定义（有函数体）
int global_var = 0;          // 变量定义（分配内存）
class A { /* 成员 */ };      // 类定义
```

**ODR（One Definition Rule，单定义规则）**：

```cpp
// 1. 函数/变量：整个程序只能有一个定义（可以多处声明）
// 2. 类/模板/内联函数：每个翻译单元可以各有一份定义（但要完全一致）
```

**典型违规场景**：

```cpp
// 头文件里定义变量 → 多个 .cpp 包含 → 多重定义！
// header.h:
int global = 1;              // ❌ 定义放在头文件

// 正确：头文件只声明，.cpp 里定义
// header.h:
extern int global;           // 声明
// one.cpp:
int global = 1;              // 唯一定义
```

**症状：链接期 `multiple definition`**

两个 `.cpp` 各写一个同名同签名的自由函数（都默认是**外部链接**）→ 链接直接报：

```
b.cpp:(.text+0x0): multiple definition of `expand(char const*, int, int)'
a.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

把它改成**内部链接**就能各写各的（两种都实测通过）：`static` 或**匿名 namespace**（后者更推荐，能装类/模板/常量）——见[基础 · static 的用法](基础.md)。

**前置声明的作用**（工程常用）：

```cpp
class B;                     // 前置声明：只知道 B 是个类

class A {
    B* pb;                   // 指针/引用可以用前置声明
    // B b;                  // ❌ 成员对象不行，需要完整定义
};

// 好处：减少头文件依赖，加快编译
```

## 6. 编译选项（工程常用）

```bash
g++ -O2 main.cpp -o main        # -O0/-O1/-O2/-O3 优化等级（0 无优化，3 最高）
g++ -g main.cpp -o main         # 加调试信息（配合 gdb）
g++ -Wall -Wextra main.cpp      # 打开警告（强烈建议总是开）
g++ -std=c++17 main.cpp         # 指定 C++ 标准版本

# 内存/未定义行为检测：
g++ -fsanitize=address -g main.cpp   # ASan：内存错误（越界、泄漏）
g++ -fsanitize=undefined -g main.cpp # UBSan：未定义行为（溢出、移位等）
```

### 优化等级做了什么

| 等级 | 做什么 |
|------|--------|
| `-O0` | 无优化（默认，方便调试） |
| `-O1` | 基础优化（删死代码、简化表达式） |
| `-O2` | **常用**：更多优化（内联、循环优化、指令调度、寄存器分配） |
| `-O3` | 激进优化（向量化、更强的循环展开），可能增大体积 |
| `-Os` | 优化体积（嵌入式） |

**`-O2` 比 `-O0` 快在哪**（典型回答）：

1. **内联**：小函数展开，省调用开销
2. **循环优化**：循环展开、将不变量提到循环外
3. **寄存器分配**：减少内存访问
4. **指令重排**：配合流水线
5. **删死代码 / 常量折叠**

**注意**：优化会暴露 UB（见「未定义行为」篇），`-O0` 正常的代码 `-O2` 可能出错。

## 7. 预处理与宏（# / ##）

### 预处理做什么

`#include` 展开、宏替换、条件编译、去注释——**纯文本替换**（不理解语法）。

### 宏的两个运算符

```cpp
// # 字符串化：把参数变成字符串
#define STR(x) #x
STR(hello);          // → "hello"

// ## 连接：把两个 token 拼成一个
#define CONCAT(a, b) a##b
CONCAT(foo, bar);    // → foobar（一个标识符）
```

### 条件编译

```cpp
#ifdef DEBUG
    log("debug mode");
#endif

#ifndef HEADER_H
#define HEADER_H
// ...
#endif
```

**宏 vs 内联函数**：宏是文本替换（无类型检查、易出错），现代 C++ 优先用 `inline` / `constexpr` / 模板替代宏。

## 8. gcc vs g++

| | gcc | g++ |
|--|-----|-----|
| 用途 | C 编译器 | C++ 编译器 |
| 编译 .cpp | 要手动链接 libstdc++ | 自动链接标准库 |
| 链接 C++ 代码 | 可能报"找不到 std::xxx" | ✅ 正确 |

```bash
gcc main.cpp -lstdc++ -o main   # gcc 编译 C++ 要手动加 -lstdc++
g++ main.cpp -o main            # g++ 自动处理
```

**一句话**：C 代码用 gcc，C++ 代码用 g++（否则链接标准库麻烦）。

## 9. 链接器深入：符号解析、重定位、PLT/GOT

### 符号解析

```cpp
// 符号分两类：
// 强符号：函数定义、已初始化的全局变量
// 弱符号：未初始化的全局变量（BSS）、标记为 weak 的符号
//   ⚠️ 注意：GCC 10 / Clang 起默认 -fno-common，
//      未初始化全局变量也变成"强定义"了（老教材的"common 符号"行为已不是默认）

// 链接规则：
// 1. 多个强符号同名 → 错误（multiple definition）
// 2. 强 + 弱同名 → 用强符号
// 3. 多个弱符号同名 → 任选一个（危险！）
```

```cpp
int g1 = 1;          // 强符号
int g2;              // 弱符号（BSS）
__attribute__((weak)) void f();   // 显式弱符号
```

**弱符号的用途**：库提供"默认实现"，用户可覆盖（如 Hook）。

### 重定位

链接器把各目标文件里的"地址引用"修正为最终地址：

```cpp
// a.o 调用 f，但 f 在 b.o 里
// 链接时：把 a.o 里对 f 的"占位地址"改成 f 的真实地址
```

### PLT / GOT 延迟绑定（动态库调用慢的原因）

**问题**：动态库函数地址**运行时才知道**，每次调用都要查地址 → 慢。

**解决**：

- **GOT**（全局偏移表）：存放函数/变量的实际地址
- **PLT**（过程链接表）：函数调用的跳板
- **延迟绑定**：第一次调用时才真正解析地址（之后走缓存）

```assembly
; 调用动态库函数 f：
call f@plt        ; 跳到 PLT
; PLT 里：第一次 → 查 GOT（慢，解析地址）；之后 → GOT 已有地址，直接跳（快）
```

**所以动态库函数调用比静态库慢**：多一次间接跳转（PLT/GOT）。

**优化**：
```bash
-fno-plt          # 不用 PLT（直接通过 GOT 调用）
# 或编译时用 -fvisibility=hidden 隐藏符号，减少动态符号表
```

## 10. 典型链接错误排查

| 错误 | 原因 | 排查 |
|------|------|------|
| `undefined reference to f` | 只声明没定义 / 库没链接 / 符号没导出 | 检查库、链接顺序、`nm` 看符号 |
| `multiple definition of f` | 重复定义（头文件定义变量/函数） | 头文件只放声明 |
| 静态库符号找不到 | **链接顺序**问题 | 依赖者在前，被依赖在后 |
| C/C++ 互调失败 | 名字修饰不匹配 | 加 `extern "C"` |

**静态库链接顺序**：

```bash
# 链接器从左到右扫描，左边没解析的符号，从右边找
# 所以"依赖者在前，被依赖者在后"：
g++ main.o -lA -lB    # A 依赖 B 时，A 在前
# 循环依赖：用 --start-group / --end-group 包起来
```

**排查工具**：
```bash
nm libfoo.a | grep symbol_name     # 看库里的符号
ldd ./main                          # 看动态依赖
objdump -T libfoo.so                # 看导出的动态符号
```

## 11. LTO / PGO 优化

**LTO（Link Time Optimization，链接时优化）**：

```bash
g++ -flto main.cpp -o main
# 问题：每个 .cpp 单独编译，编译器看不到全局，跨文件无法优化
# LTO：把优化推迟到链接阶段（看到所有代码），能跨文件内联、删死代码
```

**PGO（Profile-Guided Optimization，剖面引导优化）**：

```bash
# 1. 先编译带插桩的版本，跑一遍典型负载收集数据
g++ -fprofile-generate main.cpp -o main_prof
./main_prof    # 运行，生成 profile 数据
# 2. 用数据重新编译（编译器知道哪些分支常走、哪些函数热点）
g++ -fprofile-use main.cpp -o main
```

**收益**：更好的分支预测、热点代码布局，通常提速 5%~20%。

## 12. 名字修饰与符号可见性

### 名字修饰（Name Mangling）

**C++ 编译后，函数名会变**（为了支持重载）：

```cpp
// 源码：
void f(int);
void f(double);

// 编译后的符号名（Itanium ABI，GCC/Clang）：
// _Z1fi      （f(int)）
// _Z1fd      （f(double)）
// _Z1fPKc    （f(const char*)）
```

**规则**：`_Z` + 名字长度 + 名字 + 参数类型编码。所以**同名不同参数 → 不同符号**（这就是重载的实现）。

**查看符号**：

```bash
nm main.o | grep f        # 看目标文件的符号
c++filt _Z1fi             # 把修饰名还原成可读的：f(int)
```

**C 没有名字修饰**（没有重载）→ 函数名直接是 `f`。

### extern "C" 的完整原理

```cpp
extern "C" void f(int);   // 告诉编译器：f 不做名字修饰，按 C 规则
```

**为什么需要**：

- C++ 调 C 库：C 库的符号是 `f`，C++ 默认找 `_Z1fi` → 找不到 → `undefined reference`
- **`extern "C"` 让编译器按 C 的方式生成/查找符号**

```cpp
// 标准写法（头文件里兼容 C 和 C++）：
#ifdef __cplusplus
extern "C" {
#endif

void c_function(int);

#ifdef __cplusplus
}
#endif
```

### 符号可见性（动态库导出控制）

**问题**：动态库默认**导出所有符号**，可能符号冲突、也暴露内部实现。

```cpp
// 只导出需要的符号，隐藏其他（减小体积、防冲突）
__attribute__((visibility("hidden")))   // GCC/Clang：隐藏这个符号
```

```bash
# 编译动态库时：
g++ -fvisibility=hidden -shared ...     # 默认全部隐藏，显式标记的才导出
```

**工程做法**：用宏统一定义导出标记：

```cpp
#define EXPORT __attribute__((visibility("default")))

EXPORT void public_api();        // 只导出这个
void internal_helper();          // 默认隐藏
```

**用途**：插件化动态库、避免符号污染、减小动态库体积。

## 13. 显式运行时加载（dlopen / dlsym）

动态库的高级用法：运行时加载（插件）、ABI 兼容、C++ 跨库的坑。

**之前讲的动态库是"链接时加载"**（编译时 `-lfoo`，启动时自动加载）。还有一种是**运行时手动加载**：

```cpp
#include <dlfcn.h>

// 1. 打开动态库
void* handle = dlopen("./libplugin.so", RTLD_LAZY);
if (!handle) {
    std::cerr << dlerror();
    return;
}

// 2. 查找符号（函数）
using FuncType = int (*)(int);
FuncType func = (FuncType)dlsym(handle, "process");
if (!func) { std::cerr << dlerror(); }

// 3. 调用
int result = func(42);

// 4. 关闭（引用计数归零才真正卸载）
dlclose(handle);
```

**编译时要加 `-ldl`**：

```bash
g++ main.cpp -ldl -o main
```

**用途**：插件系统、热更新、按需加载（不用就不加载）。

## 14. 插件架构实现

**思路**：主程序定义接口，插件实现接口，运行时用 dlopen 加载：

```cpp
// 主程序定义接口（纯虚类）
class IPlugin {
public:
    virtual void run() = 0;
    virtual ~IPlugin() = default;
};

// 插件实现接口，并导出"创建函数"
extern "C" IPlugin* create_plugin() {   // extern "C" 保证符号名不修饰
    return new MyPlugin();
}

// 主程序加载插件：
void* h = dlopen("./libplugin.so", RTLD_LAZY);
auto create = (IPlugin*(*)())dlsym(h, "create_plugin");
IPlugin* p = create();
p->run();
```

**关键点**：

1. **接口用纯虚类**（主程序和插件共享头文件）
2. **导出 `extern "C"` 的工厂函数**（避免名字修饰，方便 dlsym 查找）

## 15. ABI 兼容性

**ABI（Application Binary Interface）** = 二进制层面的约定（函数调用、内存布局、名字修饰、异常传播）。

**ABI 稳定**：库升级后，已编译的程序**不用重新编译**就能用新库。

**哪些改动会破坏 ABI**：

| 改动 | 是否破坏 ABI |
|------|-------------|
| 加/删虚函数 | ❌ 破坏（改 vtable 布局） |
| 改成员变量顺序/类型 | ❌ 破坏（改类大小/偏移） |
| 改函数签名 | ❌ 破坏 |
| 加非虚成员函数 | ✅ 不破坏 |
| 加新类 | ✅ 不破坏 |
| 改函数实现（不改签名） | ✅ 不破坏 |

**为什么 C++ ABI 脆弱**：C++ 有 vtable、名字修饰、inline、模板——细节多，不同编译器/版本 ABI 都不同。

**版本兼容策略**：

1. **用 PIMPL**：把私有成员藏到实现类（改内部不影响 ABI）
2. 只增不改（保留旧接口）
3. 用 C 接口暴露（C ABI 稳定）

## 16. C++ 动态库的坑

### 坑 1：名字修饰

C++ 函数名被修饰，`dlsym` 找 `process` 找不到（实际符号是 `_Z7processi`）→ **导出接口用 `extern "C"`**。

### 坑 2：异常跨库抛出

```cpp
// 库 A 抛异常，库 B 捕获 → 可能崩溃/未定义
// 原因：异常传播依赖 ABI，不同编译器/标准库的异常实现不同
// 解决：异常在库内部处理完，不要跨库边界传播（或统一编译器/标准库）
```

### 坑 3：对象跨库传递

```cpp
// 主程序 new 对象，库 delete；或库 new，主程序 delete
// → 可能崩溃（不同库的堆/内存分配器不同，不能跨库 free）
// 解决：谁分配谁释放；用统一的分配接口；用 shared_ptr + 自定义删除器
```

### 坑 4：inline / 模板跨库

模板和 inline 函数在每个翻译单元各有一份实例，跨库可能重复/不一致（ODR），要保证一致。

## 17. 要点回顾

1. **编译四步**：预处理 → 编译 → 汇编 → 链接
2. **链接干什么**：符号解析 + 重定位
3. **静态库 vs 动态库**：编译期拷贝 vs 运行期加载
4. **undefined reference**：只声明没定义，或库没链接上
5. **头文件**：只放声明，用包含守卫
6. **声明 vs 定义**：声明不分配存储，定义分配；ODR 单定义规则
7. **优化等级**：-O2 的内联、循环优化、寄存器分配
8. **宏**：# 字符串化、## 连接、条件编译
9. **强弱符号**：多个强符号报错；动态库调用慢在 PLT/GOT
10. **静态库链接顺序**：依赖者在前、被依赖者在后
11. **LTO/PGO**：链接时优化、剖面引导优化
12. **gcc vs g++**：C 用 gcc，C++ 用 g++
13. **dlopen/dlsym**：运行时加载动态库、查符号、调用（插件基础）
14. **插件架构**：纯虚接口 + `extern "C"` 工厂函数
15. **ABI 兼容**：加虚函数/改成员顺序会破坏；用 PIMPL 规避
16. **C++ 动态库坑**：名字修饰（用 extern "C"）、异常跨库、对象跨库 delete
17. **一句话**：C++ 动态库比 C 麻烦（修饰、ABI、异常），接口尽量用 C 风格
