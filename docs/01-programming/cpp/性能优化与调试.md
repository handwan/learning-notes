# 性能优化与调试

**定位瓶颈、分析性能、优化代码**——C++ 工程能力里最吃深度的一环。

## 1. 性能分析方法论（先测再优化）

**铁律**：**不要猜瓶颈，要测量**。

```
① 定位：用工具找出真正的瓶颈（哪段代码慢）
② 测量：量化当前性能（耗时/内存/CPU）
③ 优化：针对瓶颈优化
④ 验证：再测量，确认提升且没引入问题
```

**常见误区**：凭直觉优化"看起来慢"的地方——结果优化了不 hot 的代码，性能没变，还增加了复杂度。**先 profiling**。

## 2. 性能分析工具

| 工具 | 用途 |
|------|------|
| **perf** | Linux 采样分析（CPU 热点、调用栈） |
| **火焰图** | perf 数据的可视化（一眼看出热点） |
| **gprof** | GCC 插桩分析（`-pg` 编译） |
| **valgrind --tool=callgrind** | 指令级分析 |
| **/usr/bin/time** | 测程序总耗时/内存 |

### perf + 火焰图

```bash
# 1. perf 采样（记录程序运行时的调用栈）
perf record -g ./program      # -g 记录调用栈
# 2. 生成报告
perf report
# 3. 生成火焰图（要两步：先折叠调用栈，再画图）
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

**火焰图怎么读**：

- 横轴 = 时间占比（越宽越耗时）
- 纵轴 = 调用栈深度
- **找"又宽又高"的方块** = 热点

### 分类型排查

| 瓶颈类型 | 排查手段 |
|---------|---------|
| CPU 瓶颈 | perf、火焰图（找热点函数） |
| 内存瓶颈 | valgrind massif、监控内存增长 |
| IO 瓶颈 | iostat、strace |
| 锁竞争 | perf lock、看线程阻塞时间 |

## 3. 常见性能陷阱

### 3.1 伪共享（False Sharing）

**问题**：两个线程改**不同变量**，但它们在同一 CPU Cache Line 上 → 缓存行反复失效，性能暴跌。

```cpp
// ❌ 伪共享：a 和 b 在同一 cache line（64 字节）
struct Data {
    int a;   // 线程1 疯狂改 a
    int b;   // 线程2 疯狂改 b
    // a、b 同在一个 cache line → 互相"打架"
};

// 解决：用 alignas 让它们在不同 cache line
struct Data {
    alignas(64) int a;   // a 独占一个 cache line
    alignas(64) int b;
};

// 或用 padding：
struct Data {
    int a;
    char padding[60];    // 填充到 64 字节
    int b;
};
```

**原理**：CPU 缓存以 Cache Line（通常 64 字节）为单位，一个核改了 a，其他核的包含 b 的缓存行全部失效——即使 b 没变。

### 3.2 缓存局部性（Cache Locality）

```cpp
// 连续访问（缓存友好）：一次加载 cache line，后续命中
std::vector<int> v(1000);
for (int x : v) { /* 顺序访问，快 */ }

// ❌ 链表遍历（缓存不友好）：每个节点跳转，cache miss
std::list<int> l;
for (int x : l) { /* 节点分散，慢 */ }
```

**这就是 vector 遍历比 list 快很多的原因**（即使复杂度相同）——连续内存的缓存命中率高。

### 3.3 分支预测失败

```cpp
// 随机数据的分支 → 预测失败 → 流水线清空
if (data[i] > 128) { ... }   // 如果条件是随机的，CPU 猜不准

// 优化：把大概率的分支放前面 / 用无分支写法（查表、位运算）
```

### 3.4 冗余拷贝

```cpp
// ❌ 按值传大对象（拷贝）
void process(std::vector<int> v);        // 拷贝整个 vector！

// 按 const 引用 / 移动
void process(const std::vector<int>& v);  // 不拷贝
void process(std::vector<int>&& v);       // 移动（右值）
```

### 3.5 虚函数调用开销

```cpp
// 虚函数调用 = vptr 间接跳转（不能内联）→ 热点路径上有开销
// 优化：CRTP 静态多态（编译期绑定，可内联）替代虚函数
```

## 4. 向量化（SIMD）

一条指令处理多个数据（SSE / AVX / NEON）。顺序：**先让编译器自动做 → 改数据布局 → 最后才手写**。

### 编译器什么时候会自动向量化

要同时满足几条：

- **连续访问**（`a[i]` 步长 1；链表、跨步访问基本没戏）
- **循环次数可判定**（不是 `while (!found)` 这种）
- **无跨迭代依赖**（本轮不依赖上一轮的结果）
- **无别名疑虑**——编译期能证明两块内存不重叠；`__restrict` 是给编译器的承诺
- **归约要能重排**：整数求和可以；**浮点求和默认不行**（FP 加法不满足结合律，重排会改变结果）

```cpp
void scale(float* __restrict a, const float* __restrict b, size_t n) {
    for (size_t i = 0; i < n; ++i) a[i] = a[i] * b[i];   // 会向量化
}

float sum_f(const float* a, size_t n) {
    float s = 0;
    for (size_t i = 0; i < n; ++i) s += a[i];            // ❌ 浮点归约，默认不
    return s;
}
```

### 怎么确认

| 编译器 | 命令 |
|--------|------|
| GCC | `-fopt-info-vec-all`（只看命中用 `-fopt-info-vec-optimized`） |
| Clang | `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize` |

输出长这样：

```text
simd.cpp:4:26: optimized: loop vectorized using 32 byte vectors   ← GCC（32 字节 = AVX2 宽度）
simd.cpp:5:5: remark: vectorized loop (vectorization width: 8)    ← Clang
simd.cpp:11:5: remark: loop not vectorized [-Rpass-missed=...]    ← 没命中也会说原因
```

**编译开关的差异**（同一份代码实测）：

| 开关 | 结果 |
|------|------|
| GCC `-O2` | 本例 0 个循环命中（代价模型保守） |
| GCC `-O3` | 命中 |
| Clang `-O2` | 命中 |
| `-march=native` | 决定用多宽的指令（不写通常只到 SSE2） |
| `-ffast-math` | 连浮点归约也能向量化——**改变数值结果**，慎用 |

### 数据布局：AoS vs SoA

```cpp
// AoS：一个对象的字段挨在一起
struct Particle { float x, y, z; };
Particle ps[N];

// SoA：所有对象的同一个字段挨在一起
struct Particles { float* x; float* y; float* z; };
```

处理"所有点的 x"时：AoS 每次跨 12 字节，SoA 连续。

**注意**：简单场景两者都可能被向量化（编译器会做交织/收集，实测 Clang 对 AoS 的逐字段更新也向量化了）；但**复杂场景（只取部分字段、不同字段走不同分支）AoS 更容易失败**。性能敏感的数据结构优先考虑 SoA。

### 手写 SIMD

- **intrinsics**（`<immintrin.h>`、`_mm256_*`）：控制力最强，但 SSE/AVX/AVX-512 各写一套，可移植性差
- **`std::simd`**：C++26 标准化的可移植 SIMD（GCC 已有 `std::experimental::simd`）
- 手写前先看 `-fopt-info-vec-missed`：多数情况改布局、加 `__restrict`、升 `-O` 就够了

### 别忽略内存带宽

SIMD 提升的是**计算吞吐**。瓶颈在**内存带宽**时（大数组流式读写），向量化收益有限——先用 perf 看 IPC / 缓存命中 / 带宽，再决定值不值得。

## 5. 工程级优化手段

| 手段 | 说明 |
|------|------|
| **池化** | 对象池/内存池/连接池，避免频繁分配 |
| **预分配** | `vector::reserve(n)`，避免扩容搬移 |
| **批量处理** | 减少系统调用（批量读写、批量提交） |
| **移动语义** | 转移资源代替拷贝 |
| **减少临时对象** | `emplace_back` 原地构造 |
| **编译期计算** | `constexpr` 把计算挪到编译期 |
| **缓存友好** | 用 vector 代替 list、结构体成员排序 |
| **避免伪共享** | `alignas` 隔离热点变量 |

## 6. 优化优先级

```
1. 算法/数据结构优化（量级提升，O(n²)→O(n log n)）
2. 减少拷贝/分配（内存层面）
3. 缓存优化（局部性、伪共享）
4. 指令级优化（分支预测、内联）
```

**先做"高杠杆"的**（换算法、去拷贝），别一上来抠指令级细节。

## 7. core dump（崩溃现场）

程序崩溃、内存错误、偶现 bug 的排查——**工程里最吃经验的能力**。

**core dump** = 程序崩溃时，内核把进程内存状态存成的文件。**事后分析崩溃原因**。

### 开启与生成

```bash
# 1. 允许生成 core 文件（默认可能关闭）
ulimit -c unlimited           # 当前 shell 生效
ulimit -c                    # 查看当前设置

# 2. 程序崩溃时，生成 core 文件（如 core.12345）
./crash_program              # 崩溃 → 生成 core

# 3. 常见路径：
# ./core  或  /var/lib/systemd/coredump/  或  /proc/sys/kernel/core_pattern 指定的位置
```

### 分析 core

```bash
# 用 gdb 加载"可执行文件 + core 文件"
gdb ./crash_program core.12345

# 进去后：
(gdb) bt          # backtrace：看崩溃时的调用栈（关键！）
(gdb) frame 2     # 切到第 2 层栈帧
(gdb) print var   # 看变量值
(gdb) info locals # 看所有局部变量
```

**关键**：`bt` 看到崩溃的调用栈，定位到出错的函数和行号（需要 `-g` 编译）。

## 8. gdb 高级用法

### 启动与断点

```bash
gdb ./program
(gdb) break main            # 在 main 打断点
(gdb) break file.cpp:42     # 在文件第 42 行打断点
(gdb) run arg1 arg2         # 运行
(gdb) next                  # 单步（不进入函数）
(gdb) step                  # 单步（进入函数）
(gdb) continue              # 继续到下一个断点
```

### 条件断点（调循环/偶现 bug 利器）

```bash
# 只在 i == 100 时停下（否则循环 1000 次要按 1000 次）
(gdb) break file.cpp:42 if i == 100
```

### 观察点（watch，变量被改时停）

```bash
(gdb) watch x               # x 被修改时停下
(gdb) watch -l x            # 监视某地址
# 用途：找出"谁改坏了这个变量"（内存被踩）
```

### 查看信息

```bash
(gdb) backtrace / bt        # 调用栈
(gdb) print x / p x         # 打印变量
(gdb) info locals           # 局部变量
(gdb) info threads          # 所有线程
(gdb) thread 2              # 切到线程 2
(gdb) frame 3               # 切换栈帧
```

### 多线程调试

```bash
(gdb) info threads          # 看所有线程
(gdb) thread apply all bt   # 所有线程的调用栈（看谁卡住）
```

## 9. 内存错误排查

| 错误 | 现象 | 排查 |
|------|------|------|
| **越界访问** | 可能崩、可能不崩（踩到别的变量） | ASan、valgrind |
| **double free** | 崩溃 | ASan、valgrind |
| **悬垂指针**（use-after-free） | 偶现崩溃、数据错乱 | ASan、valgrind |
| **野指针**（未初始化） | 偶现崩溃、随机地址 | Valgrind、MSan；ASan 可能只报 SEGV |
| **内存泄漏** | 内存持续上涨 | valgrind、ASan |
| **未初始化读取** | 随机值、偶现 bug | valgrind、MSan |

### 工具对比

| 工具 | 检测 | 开销 | 说明 |
|------|------|------|------|
| **ASan**（AddressSanitizer） | 越界、悬垂、泄漏 | 中 | 编译时加 `-fsanitize=address`，快 |
| **UBSan** | 未定义行为 | 低 | `-fsanitize=undefined` |
| **MSan** | 未初始化内存 | 高 | `-fsanitize=memory` |
| **TSan** | 数据竞争、死锁 | 高（5–15×） | `-fsanitize=thread`；单独 build（和 ASan 互斥） |
| **valgrind** | 内存错误、泄漏 | 很高（慢 10-50 倍） | 不用重编译，但慢 |

```bash
# ASan（推荐，快）
g++ -fsanitize=address -g main.cpp -o main
ASAN_OPTIONS=detect_stack_use_after_return=1 ./main

# 标准库轻量断言（不是完整越界检查）
g++ -D_GLIBCXX_ASSERTIONS -g main.cpp -o main

# valgrind（不用重编译，但慢）
valgrind --leak-check=full ./main
```

`_GLIBCXX_ASSERTIONS` 只开部分检查；`_GLIBCXX_DEBUG` 检查更全，但会改变 ABI，不能和普通编译的目标文件混链。

## 10. 崩溃排查思路（实战）

```
1. 看 core dump / bt 的调用栈 → 定位崩溃函数和行号
2. 看信号/退出码，对照下面的速查表
3. 用 ASan/valgrind 复现，拿详细报告
4. 偶现崩溃（并发/内存踩踏）：
   - gdb 的 watch 找谁改了内存
   - ASan 抓越界
   - 加日志缩小范围
```

### 信号速查

| 信号 | 退出码 | 典型原因 |
|------|-------:|----------|
| `SIGSEGV` | 139 | 空/野/悬垂指针、越界、写只读内存、栈溢出 |
| `SIGABRT` | 134 | `assert`、未捕获异常触发 `terminate`、double free/堆损坏、栈保护 |
| `SIGBUS` | 135 | 未对齐访问、`mmap` 超出文件长度、总线/硬件错误 |
| `SIGFPE` | 136 | 整数除零、算术异常；浮点异常通常默认屏蔽 |
| `SIGILL` | 132 | 非法指令、CPU 不支持；跳到错误地址也可能报 `SIGSEGV` |
| `SIGKILL` | 137 | OOM killer、cgroup、外部强杀；不可捕获 |
| `SIGTERM` | 143 | 正常终止请求，不是崩溃 |
| `SIGPIPE` | 141 | 写已关闭的管道/socket；常被忽略 |
| `SIGINT` | 130 | Ctrl+C |

`SIGSEGV` 崩在非法地址访问；越界写可能过很久才崩，崩溃点不一定是第一现场。`SIGABRT` 是进程自己 `abort()`，不是硬件异常。

### std::terminate 触发链

未捕获异常、`noexcept` 函数抛异常、析构函数抛异常、栈展开过程中再次抛异常 → `std::terminate()` → 默认 `abort()` → `SIGABRT`。

`std::set_terminate` 可以记录日志，但默认仍然终止。

### 栈保护与堆损坏

```text
*** stack smashing detected ***
malloc(): corrupted top size
free(): double free detected
```

这些通常是 `abort()` → `SIGABRT`，不是 `SIGSEGV`：

- 栈保护：`-fstack-protector-strong` 检测到栈溢出，调用 `__stack_chk_fail`
- 堆损坏：glibc 的 malloc/free 检测到元数据被踩坏

堆越界也可能不立刻报，过一会踩到别的对象才 `SIGSEGV`；用 ASan 抓第一现场。

### OOM 与被杀

OOM killer 发 `SIGKILL`（137），不是 `SIGSEGV`，通常也没有 core：

```bash
dmesg -T | grep -i oom
journalctl -k | grep -i oom
cat /sys/fs/cgroup/memory.max      # cgroup v2
cat /sys/fs/cgroup/memory.events   # cgroup v2
```

`memory.events` 里的 `oom` / `oom_kill` 增长，说明被 cgroup 杀过。

`new` 失败通常抛 `std::bad_alloc`；但如果系统 overcommit，可能分配成功、访问时才被 OOM killer 杀掉——所以“没抛异常却退出 137”很常见。

### 加载期错误

```text
error while loading shared libraries: libfoo.so: cannot open shared object file
version `GLIBCXX_3.4.xx' not found
undefined symbol: ...
```

这些不是段错误，进程可能还没跑到 `main`（常见退出码 127）。排查：

```bash
ldd ./app
readelf -d ./app | grep -E 'NEEDED|RPATH|RUNPATH'
LD_DEBUG=libs,bindings ./app
nm -D libfoo.so | grep symbol_name
```

- 缺库：查 `LD_LIBRARY_PATH`、RPATH/RUNPATH、安装路径
- `GLIBCXX` 版本不对：运行环境 `libstdc++` 太旧；统一工具链，或谨慎使用 `-static-libstdc++`
- `undefined symbol`：`.so` 版本不匹配、符号被隐藏、ABI 不一致；`dlopen` 失败时用 `dlerror()` 看原因

### 只有地址

```bash
addr2line -Cfipe ./app 0x0000000000401234
```

前提是保留 `-g`、没 strip；`backtrace()` 想拿到可读符号通常还要 `-rdynamic`。

## 11. 观察者效应：gdb 下不崩怎么办

典型场景：**跑着好好的，一挂 gdb 就不崩了**——观察行为改变了被观察对象。别急着"让 gdb 抓住"，先换成不打扰程序的抓捕方式。

### 为什么 gdb 下不崩（三个主因）

| 主因 | 机制 | 验证信号 |
|------|------|----------|
| **时序** | gdb 让程序慢几个数量级、线程被 ptrace 串行化 → 竞态消失 | 加/去 delay 行为就变；单核复现不同 |
| **内存布局** | gdb 默认**关 ASLR**，堆栈环境也不同 → 未初始化内存/越界踩到的东西变了 | `setarch -R` 下不崩、重启后随机崩 |
| **信号** | gdb 接住并改变信号行为 | gdb 里是"停下等你看"（那是好事，直接 `bt`） |

**先分辨**：gdb 里是真跑得好，还是**停在 SIGSEGV 等你**？后者 `bt` + `thread apply all bt full` 就是答案。

### 证据优先（不监视也能拿到现场）

```bash
echo $?                 # 先拿退出码，对照 §10 的信号速查表
dmesg -T | grep -iE 'segfault|oom'      # 内核记了每次段错误的地址与错误码
coredumpctl list        # 有 core 就事后分析：coredumpctl gdb <pid>
```

什么都没有 → 大概率**不是崩，是被杀**（OOM、cgroup、watchdog）——查 `journalctl`。

### 抓手（按"打扰程度"从低到高）

```bash
# ① core dump：零打扰。放开后循环跑到崩
ulimit -c unlimited && while ! ./app; do :; done
coredumpctl gdb <pid>          # 或 gdb ./app core

# ② Sanitizer：不崩也报错（日常常驻）
g++ -fsanitize=address,undefined -g -O1 app.cc    # ASan + UBSan
g++ -fsanitize=thread -g -O1 app.cc               # TSan：竞态头号克星

# ③ rr：录制 + 确定性重放，"观察"不再改变行为
rr record ./app && rr replay

# ④ 必须用 gdb 时，把干扰调回生产条件
(gdb) set disable-randomization off    # 保持 ASLR
(gdb) handle SIGPIPE nostop noprint pass
(gdb) set follow-fork-mode child       # 崩在子进程时
# 反向验证：非 gdb 下也关 ASLR——不崩了就是布局问题
setarch $(uname -m) -R ./app

# ⑤ 放大复现
taskset -c 0 ./app        # 单核：竞态必现或必不现，都是信息
```

| 症状 | 嫌疑 | 首查 |
|------|------|------|
| 加日志/延迟就不崩 | 竞态 | TSan |
| 重启/换机器行为就变 | 内存布局、未初始化 | ASan、`set disable-randomization off` |
| `-O2` 崩 `-O0` 不崩 | UB 被优化 | UBSan + 对比编译 |
| 无 segfault 记录、退出码 137 | 被外部杀 | `journalctl -k \| grep oom` |

**顺序**：证据（1 分钟）→ core 循环复现 → ASan/TSan 常驻 → 最后才是 gdb 选项。

## 12. 要点回顾

1. **先测再优化**：perf + 火焰图找热点，别凭直觉
2. **伪共享**：不同变量在同一 cache line，用 `alignas(64)` 解决
3. **缓存局部性**：vector 比 list 快的原因（连续内存）
4. **常见陷阱**：冗余拷贝、虚函数开销、分支预测失败
5. **优化手段**：池化、预分配、移动、编译期计算
6. **向量化**：连续访问 + 无别名 + 归约可重排才自动向量化（浮点归约默认不）；布局优先 SoA
7. **优先级**：算法 > 拷贝 > 缓存 > 指令 > 手写 SIMD
8. **core dump**：内核存崩溃现场，用 `gdb + bt` 看调用栈
9. **gdb 高级**：条件断点（循环中调试）、watch（找谁改内存）、多线程调试
10. **内存错误**：ASan（快）/ valgrind（慢但全）
11. **信号速查**：SIGSEGV 139、SIGABRT 134、SIGBUS 135、SIGFPE 136、SIGILL 132、SIGKILL 137；SIGKILL 常是 OOM
12. **偶现 bug 排查**：watch + ASan + 日志缩小范围
13. **观察者效应**（gdb 下不崩）：先取证据（退出码/dmesg/core），再 ASan/TSan；`set disable-randomization off` 保持生产条件、`setarch -R` 反向验证
14. **加载错误**：`error while loading shared libraries` 查 `ldd`/`readelf`/RPATH/`GLIBCXX`，不是段错误
