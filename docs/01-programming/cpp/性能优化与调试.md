# 性能优化与调试

**定位瓶颈、分析性能、优化代码**——C++ 工程能力里最吃深度的一环。

## 1. 性能分析方法论（先测再优化）

**铁律**：**不要猜瓶颈，要测量**。

```
① 定位：用工具找出真正的瓶颈（哪段代码慢）
② 测量：量化当前性能（耗时/内存/CPU）
③ 优化：针对瓶颈优化
④ 验证：再测量，确认提升且没引入问题
```

**常见误区**：凭直觉优化"看起来慢"的地方——结果优化了不 hot 的代码，性能没变，还增加了复杂度。**先 profiling**。

## 2. 性能分析工具

| 工具 | 用途 |
|------|------|
| **perf** | Linux 采样分析（CPU 热点、调用栈） |
| **火焰图** | perf 数据的可视化（一眼看出热点） |
| **gprof** | GCC 插桩分析（`-pg` 编译） |
| **valgrind --tool=callgrind** | 指令级分析 |
| **/usr/bin/time** | 测程序总耗时/内存 |

### perf + 火焰图

```bash
# 1. perf 采样（记录程序运行时的调用栈）
perf record -g ./program      # -g 记录调用栈
# 2. 生成报告
perf report
# 3. 生成火焰图（要两步：先折叠调用栈，再画图）
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

**火焰图怎么读**：

- 横轴 = 时间占比（越宽越耗时）
- 纵轴 = 调用栈深度
- **找"又宽又高"的方块** = 热点

### 分类型排查

| 瓶颈类型 | 排查手段 |
|---------|---------|
| CPU 瓶颈 | perf、火焰图（找热点函数） |
| 内存瓶颈 | valgrind massif、监控内存增长 |
| IO 瓶颈 | iostat、strace |
| 锁竞争 | perf lock、看线程阻塞时间 |

## 3. 常见性能陷阱

### 3.1 伪共享（False Sharing）

**问题**：两个线程改**不同变量**，但它们在同一 CPU Cache Line 上 → 缓存行反复失效，性能暴跌。

```cpp
// ❌ 伪共享：a 和 b 在同一 cache line（64 字节）
struct Data {
    int a;   // 线程1 疯狂改 a
    int b;   // 线程2 疯狂改 b
    // a、b 同在一个 cache line → 互相"打架"
};

// 解决：用 alignas 让它们在不同 cache line
struct Data {
    alignas(64) int a;   // a 独占一个 cache line
    alignas(64) int b;
};

// 或用 padding：
struct Data {
    int a;
    char padding[60];    // 填充到 64 字节
    int b;
};
```

**原理**：CPU 缓存以 Cache Line（通常 64 字节）为单位，一个核改了 a，其他核的包含 b 的缓存行全部失效——即使 b 没变。

### 3.2 缓存局部性（Cache Locality）

```cpp
// 连续访问（缓存友好）：一次加载 cache line，后续命中
std::vector<int> v(1000);
for (int x : v) { /* 顺序访问，快 */ }

// ❌ 链表遍历（缓存不友好）：每个节点跳转，cache miss
std::list<int> l;
for (int x : l) { /* 节点分散，慢 */ }
```

**这就是 vector 遍历比 list 快很多的原因**（即使复杂度相同）——连续内存的缓存命中率高。

### 3.3 分支预测失败

```cpp
// 随机数据的分支 → 预测失败 → 流水线清空
if (data[i] > 128) { ... }   // 如果条件是随机的，CPU 猜不准

// 优化：把大概率的分支放前面 / 用无分支写法（查表、位运算）
```

### 3.4 冗余拷贝

```cpp
// ❌ 按值传大对象（拷贝）
void process(std::vector<int> v);        // 拷贝整个 vector！

// 按 const 引用 / 移动
void process(const std::vector<int>& v);  // 不拷贝
void process(std::vector<int>&& v);       // 移动（右值）
```

### 3.5 虚函数调用开销

```cpp
// 虚函数调用 = vptr 间接跳转（不能内联）→ 热点路径上有开销
// 优化：CRTP 静态多态（编译期绑定，可内联）替代虚函数
```

## 4. 向量化（SIMD）

一条指令处理多个数据（SSE / AVX / NEON）。顺序：**先让编译器自动做 → 改数据布局 → 最后才手写**。

### 编译器什么时候会自动向量化

要同时满足几条：

- **连续访问**（`a[i]` 步长 1；链表、跨步访问基本没戏）
- **循环次数可判定**（不是 `while (!found)` 这种）
- **无跨迭代依赖**（本轮不依赖上一轮的结果）
- **无别名疑虑**——编译期能证明两块内存不重叠；`__restrict` 是给编译器的承诺
- **归约要能重排**：整数求和可以；**浮点求和默认不行**（FP 加法不满足结合律，重排会改变结果）

```cpp
void scale(float* __restrict a, const float* __restrict b, size_t n) {
    for (size_t i = 0; i < n; ++i) a[i] = a[i] * b[i];   // 会向量化
}

float sum_f(const float* a, size_t n) {
    float s = 0;
    for (size_t i = 0; i < n; ++i) s += a[i];            // ❌ 浮点归约，默认不
    return s;
}
```

### 怎么确认

| 编译器 | 命令 |
|--------|------|
| GCC | `-fopt-info-vec-all`（只看命中用 `-fopt-info-vec-optimized`） |
| Clang | `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize` |

输出长这样：

```text
simd.cpp:4:26: optimized: loop vectorized using 32 byte vectors   ← GCC（32 字节 = AVX2 宽度）
simd.cpp:5:5: remark: vectorized loop (vectorization width: 8)    ← Clang
simd.cpp:11:5: remark: loop not vectorized [-Rpass-missed=...]    ← 没命中也会说原因
```

**编译开关的差异**（同一份代码实测）：

| 开关 | 结果 |
|------|------|
| GCC `-O2` | 本例 0 个循环命中（代价模型保守） |
| GCC `-O3` | 命中 |
| Clang `-O2` | 命中 |
| `-march=native` | 决定用多宽的指令（不写通常只到 SSE2） |
| `-ffast-math` | 连浮点归约也能向量化——**改变数值结果**，慎用 |

### 数据布局：AoS vs SoA

```cpp
// AoS：一个对象的字段挨在一起
struct Particle { float x, y, z; };
Particle ps[N];

// SoA：所有对象的同一个字段挨在一起
struct Particles { float* x; float* y; float* z; };
```

处理"所有点的 x"时：AoS 每次跨 12 字节，SoA 连续。

**注意**：简单场景两者都可能被向量化（编译器会做交织/收集，实测 Clang 对 AoS 的逐字段更新也向量化了）；但**复杂场景（只取部分字段、不同字段走不同分支）AoS 更容易失败**。性能敏感的数据结构优先考虑 SoA。

### 手写 SIMD

- **intrinsics**（`<immintrin.h>`、`_mm256_*`）：控制力最强，但 SSE/AVX/AVX-512 各写一套，可移植性差
- **`std::simd`**：C++26 标准化的可移植 SIMD（GCC 已有 `std::experimental::simd`）
- 手写前先看 `-fopt-info-vec-missed`：多数情况改布局、加 `__restrict`、升 `-O` 就够了

### 别忽略内存带宽

SIMD 提升的是**计算吞吐**。瓶颈在**内存带宽**时（大数组流式读写），向量化收益有限——先用 perf 看 IPC / 缓存命中 / 带宽，再决定值不值得。

## 5. 工程级优化手段

| 手段 | 说明 |
|------|------|
| **池化** | 对象池/内存池/连接池，避免频繁分配 |
| **预分配** | `vector::reserve(n)`，避免扩容搬移 |
| **批量处理** | 减少系统调用（批量读写、批量提交） |
| **移动语义** | 转移资源代替拷贝 |
| **减少临时对象** | `emplace_back` 原地构造 |
| **编译期计算** | `constexpr` 把计算挪到编译期 |
| **缓存友好** | 用 vector 代替 list、结构体成员排序 |
| **避免伪共享** | `alignas` 隔离热点变量 |

## 6. 优化优先级

```
1. 算法/数据结构优化（量级提升，O(n²)→O(n log n)）
2. 减少拷贝/分配（内存层面）
3. 缓存优化（局部性、伪共享）
4. 指令级优化（分支预测、内联）
```

**先做"高杠杆"的**（换算法、去拷贝），别一上来抠指令级细节。

## 7. core dump（崩溃现场）

程序崩溃、内存错误、偶现 bug 的排查——**工程里最吃经验的能力**。

**core dump** = 程序崩溃时，内核把进程内存状态存成的文件。**事后分析崩溃原因**。

### 开启与生成

```bash
# 1. 允许生成 core 文件（默认可能关闭）
ulimit -c unlimited           # 当前 shell 生效
ulimit -c                    # 查看当前设置

# 2. 程序崩溃时，生成 core 文件（如 core.12345）
./crash_program              # 崩溃 → 生成 core

# 3. 常见路径：
# ./core  或  /var/lib/systemd/coredump/  或  /proc/sys/kernel/core_pattern 指定的位置
```

### 分析 core

```bash
# 用 gdb 加载"可执行文件 + core 文件"
gdb ./crash_program core.12345

# 进去后：
(gdb) bt          # backtrace：看崩溃时的调用栈（关键！）
(gdb) frame 2     # 切到第 2 层栈帧
(gdb) print var   # 看变量值
(gdb) info locals # 看所有局部变量
```

**关键**：`bt` 看到崩溃的调用栈，定位到出错的函数和行号（需要 `-g` 编译）。

## 8. gdb 高级用法

### 启动与断点

```bash
gdb ./program
(gdb) break main            # 在 main 打断点
(gdb) break file.cpp:42     # 在文件第 42 行打断点
(gdb) run arg1 arg2         # 运行
(gdb) next                  # 单步（不进入函数）
(gdb) step                  # 单步（进入函数）
(gdb) continue              # 继续到下一个断点
```

### 条件断点（调循环/偶现 bug 利器）

```bash
# 只在 i == 100 时停下（否则循环 1000 次要按 1000 次）
(gdb) break file.cpp:42 if i == 100
```

### 观察点（watch，变量被改时停）

```bash
(gdb) watch x               # x 被修改时停下
(gdb) watch -l x            # 监视某地址
# 用途：找出"谁改坏了这个变量"（内存被踩）
```

### 查看信息

```bash
(gdb) backtrace / bt        # 调用栈
(gdb) print x / p x         # 打印变量
(gdb) info locals           # 局部变量
(gdb) info threads          # 所有线程
(gdb) thread 2              # 切到线程 2
(gdb) frame 3               # 切换栈帧
```

### 多线程调试

```bash
(gdb) info threads          # 看所有线程
(gdb) thread apply all bt   # 所有线程的调用栈（看谁卡住）
```

## 9. 内存错误排查

| 错误 | 现象 | 排查 |
|------|------|------|
| **越界访问** | 可能崩、可能不崩（踩到别的变量） | ASan、valgrind |
| **double free** | 崩溃 | ASan、valgrind |
| **野指针**（use-after-free） | 偶现崩溃、数据错乱 | ASan、valgrind |
| **内存泄漏** | 内存持续上涨 | valgrind、ASan |
| **未初始化读取** | 随机值、偶现 bug | valgrind、MSan |

### 工具对比

| 工具 | 检测 | 开销 | 说明 |
|------|------|------|------|
| **ASan**（AddressSanitizer） | 越界、悬垂、泄漏 | 中 | 编译时加 `-fsanitize=address`，快 |
| **UBSan** | 未定义行为 | 低 | `-fsanitize=undefined` |
| **MSan** | 未初始化内存 | 高 | `-fsanitize=memory` |
| **valgrind** | 内存错误、泄漏 | 很高（慢 10-50 倍） | 不用重编译，但慢 |

```bash
# ASan（推荐，快）
g++ -fsanitize=address -g main.cpp -o main
./main    # 出错直接打印位置和类型

# valgrind（不用重编译，但慢）
valgrind --leak-check=full ./main
```

## 10. 崩溃排查思路（实战）

```
1. 看 core dump / bt 的调用栈 → 定位崩溃函数和行号
2. 看是段错误（SIGSEGV）还是别的信号
   - SIGSEGV → 空指针/野指针/越界
   - SIGABRT → assert 失败 / double free / 未被捕获的异常
3. 用 ASan/valgrind 复现，拿详细报告
4. 偶现崩溃（并发/内存踩踏）：
   - gdb 的 watch 找谁改了内存
   - ASan 抓越界
   - 加日志缩小范围
```

**段错误（SIGSEGV）常见原因**：

1. 解引用空指针
2. 解引用野指针/悬垂指针
3. 数组越界
4. 栈溢出（递归太深）

**SIGABRT 常见原因**：

1. `assert` 失败
2. `std::terminate`（异常没被捕获、noexcept 函数抛异常）
3. double free / 堆损坏（glibc 检测到）

## 11. 要点回顾

1. **先测再优化**：perf + 火焰图找热点，别凭直觉
2. **伪共享**：不同变量在同一 cache line，用 `alignas(64)` 解决
3. **缓存局部性**：vector 比 list 快的原因（连续内存）
4. **常见陷阱**：冗余拷贝、虚函数开销、分支预测失败
5. **优化手段**：池化、预分配、移动、编译期计算
6. **向量化**：连续访问 + 无别名 + 归约可重排才自动向量化（浮点归约默认不）；布局优先 SoA
7. **优先级**：算法 > 拷贝 > 缓存 > 指令 > 手写 SIMD
8. **core dump**：内核存崩溃现场，用 `gdb + bt` 看调用栈
9. **gdb 高级**：条件断点（循环中调试）、watch（找谁改内存）、多线程调试
10. **内存错误**：ASan（快）/ valgrind（慢但全）
11. **SIGSEGV**：空/野指针、越界、栈溢出；**SIGABRT**：assert、异常未捕获、double free
12. **偶现 bug 排查**：watch + ASan + 日志缩小范围
