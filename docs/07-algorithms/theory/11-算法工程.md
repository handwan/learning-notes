# 算法工程

算法分析回答“数量级对不对”；算法工程回答：

- 代码真的对吗？
- 边界在哪？
- 实测真的更快吗？
- 换台机器/换个输入还成立吗？

它不是刷更多题，而是把“能跑”变成“可靠、可测、可维护”。

## 1. 先正确，再谈性能

顺序不能反：

```text
正确性测试 → 边界测试 → 随机对拍 → 性能测试 → 优化 → 回归测试
```

一个快 10 倍但偶尔算错的实现，没有工程价值。

## 2. 正确性测试

### 边界用例

先手写这些：

- 空输入 / 单元素
- 全部相同
- 已排序 / 逆序
- 有重复值
- 最大/最小值
- 负数、零
- 刚好卡在边界（`n=1`、`k=n`、容量刚好满）
- 会触发溢出的组合

边界用例不需要多，但要覆盖“代码里所有 if 的分支”。

### 单元测试

把核心逻辑抽成纯函数，输入输出明确：

```cpp
int solve(const vector<int>& a, int k);
```

不要把所有逻辑塞进 `main` 和全局变量，否则很难单独测。

### 断言

```cpp
assert(lo <= hi);
assert(0 <= idx && idx < n);
```

注意：`NDEBUG` 下 `assert` 会被去掉；不要在有副作用的表达式里用 `assert`。

## 3. 随机对拍

对拍（stress test）是算法工程最有效的工具之一：

1. 写一个**暴力/朴素**版本（小数据正确）
2. 写一个**优化**版本
3. 随机生成小数据
4. 两者跑同一组输入，比较输出
5. 不一致就保存输入，复现

```cpp
mt19937_64 rng(12345);
uniform_int_distribution<int> dist(1, 8);

for (int iter = 0; iter < 10000; ++iter) {
    int n = dist(rng);
    vector<int> a = gen(n, rng);

    auto fast = solve_fast(a);
    auto slow = solve_slow(a);

    if (fast != slow) {
        print_case(a);
        break;
    }
}
```

### 对拍要点

- 数据要**小**：暴力版本能跑
- 数据要**随机**：覆盖人手想不到的组合
- **固定种子**：失败可复现
- **保存失败用例**：不要只打印“错了”
- 比较时注意输出格式、顺序、浮点误差
- 对拍通过不代表证明正确，只代表“这批输入没抓到”

### 生成器也要测

生成器要覆盖：

- 极端小/大
- 全相同、全不同
- 有序/逆序
- 重复值
- 特殊结构（链、星、完全图）

只生成均匀随机，容易漏边界。

## 4. 性能测试

### 不要用一次运行下结论

```cpp
auto t0 = chrono::steady_clock::now();
for (int i = 0; i < R; ++i) run();
auto t1 = chrono::steady_clock::now();
```

- 先 warm-up
- 多次重复，取中位数/最小值
- 固定输入、固定编译选项
- 关掉后台负载，尽量绑核
- 防止编译器把整个计算优化掉（用 `volatile` 或 benchmark 库的 `DoNotOptimize`）

### 比较的是同一个问题

- 输入规模相同
- 编译选项相同
- 是否包含 I/O、内存分配要说清楚
- 多线程版本要说明线程数

### 复杂度 vs 常数

同是 `O(n)`，数组和链表可能差数倍；同是 `O(n log n)`，快排和归并的常数/缓存表现不同。

先用复杂度筛掉量级不对的，再用实测比较同量级实现。

## 5. Profiling

不要靠猜热点。常用：

```bash
perf stat ./app
perf record -g ./app
perf report
```

- `perf stat`：整体指标（cycles、IPC、cache miss）
- `perf record/report`：函数级热点
- `cachegrind`/`callgrind`：缓存/指令级模拟
- `gprof`：老工具，采样/插桩有局限

工具用法见 [perf](../../05-tools/perf/index.md)。原则：

1. 先测基线
2. 找最大热点
3. 只改一个变量
4. 重新测
5. 确认正确性没退化

### Amdahl 定律

如果热点只占 20%，把它优化到 0，总时间最多快 1.25 倍。先优化占比最大的部分。

## 6. 内存与缓存

### 减少分配和拷贝

```cpp
v.reserve(n);              // 避免反复扩容
v.emplace_back(...);       // 原地构造
auto w = std::move(v);     // 转移所有权
```

- 循环里 `push_back` 不 `reserve`，可能多次扩容+搬移
- 大量 `substr`、`vector` 拷贝会拖慢
- 小对象传值/传引用要看语义，不要盲目拷贝

### 局部性

- 连续内存通常比链表快
- 结构体数组（AoS） vs 数组结构体（SoA）：看访问模式
- 频繁随机访问大表，cache miss 可能比指令数更致命

### 伪共享

多线程写同一 cache line 的不同变量，会互相失效：

```cpp
struct alignas(64) Counter {
    long long value;
};
```

每个线程一个独立 cache line，避免伪共享。

## 7. 溢出与未定义行为

### 有符号溢出是 UB

```cpp
int x = INT_MAX;
x + 1;        // 未定义行为，不是“回绕”
```

- 用 `long long`/`__int128`
- 加法前判断 `a > INT_MAX - b`
- 不要依赖 `-fwrapv` 作为通用方案

### 移位

- 移位位数必须 `< 位宽`
- 左移负数可能 UB
- 用无符号类型做位运算更安全

### 未初始化读

未初始化的局部变量是 UB；可能“看起来正常”，换编译器/优化级别就变。

### Sanitizer

```bash
g++ -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer app.cpp
```

- ASan：越界、use-after-free、泄漏
- UBSan：有符号溢出、移位、类型双关等
- TSan：数据竞争

Sanitizer 不能替代测试，但能抓到很多“偶然才崩”的问题。

## 8. 浮点

### 不要直接比较相等

```cpp
if (a == b)          // 错
if (fabs(a - b) < eps)  // 相对/绝对误差要选合适
```

- 大数用相对误差，小数用绝对误差
- `NaN != NaN`，比较前先判 `std::isnan`
- 浮点排序时，`NaN` 会破坏严格弱序

### 累加误差

大量浮点求和，顺序不同结果可能不同；需要可复现时：

- 固定求和顺序
- Kahan 求和
- 用整数/定点数

## 9. 并发

### 数据竞争是 UB

两个线程无同步地访问同一内存，至少一个是写 → 数据竞争。

- 用 mutex/atomic 保护
- atomic 只保证原子性，不自动保证复合操作正确
- 内存序默认 `seq_cst` 最安全，性能敏感再考虑 acquire/release

### 测试并发很难

- 用 TSan
- 压力测试重复跑
- 固定随机种子
- 不要用“跑一次没崩”证明正确

### 并发里的伪共享

见上一节：独立计数器也可能因为同一 cache line 互相拖慢。

## 10. 可复现

算法工程里，“复现”比“跑通”重要：

- 固定随机种子
- 保存失败输入
- 输出不要依赖 `unordered_map` 的遍历顺序
- 浮点结果固定求和顺序
- 记录编译器、编译选项、运行环境
- 多线程要有确定的调度/种子，或至少记录线程数

## 11. 代码结构

### 核心逻辑与 I/O 分离

```cpp
vector<int> solve(const vector<int>& input);   // 可测
int main() { read(); auto ans = solve(...); print(ans); }
```

这样对拍、单元测试、benchmark 都能直接调用 `solve`。

### 少用全局状态

全局变量会让测试之间互相污染；必须用时，明确初始化/清理。

### 不变量写清楚

- 循环不变式
- 数据结构维护的约束
- 指针/迭代器有效期
- 线程安全边界

### 先写朴素版本

朴素版本可以作为：

- 对拍 oracle
- 性能基线
- 理解问题的起点

## 12. 优化闭环

```text
1. 正确版本 + 边界测试
2. 基准测试，记录基线
3. profile，找最大热点
4. 只改一个地方
5. 重跑正确性 + 对拍
6. 重跑基准
7. 收益不够就停
```

不要同时改三件事，否则不知道哪个有效。

### 什么时候停

- 热点已经不在你的代码里（I/O、系统调用、库）
- 收益小于维护成本
- 优化让代码难以理解/测试
- 已经满足实际约束

## 13. 常见坑

- 只测样例，不测边界
- 对拍数据太小/太均匀，漏特殊结构
- 对拍失败不保存输入
- benchmark 只跑一次，或把 `clock()` 当墙钟（它测 CPU 时间）
- 编译器把计算优化掉，测了个空循环
- 不同编译选项/输入规模比较
- 只看平均，忽略尾延迟
- 靠猜优化，不 profile
- 循环里反复分配/拷贝
- 忽略 cache 局部性
- 有符号溢出、移位越界、未初始化读
- 浮点直接 `==`，或忽略 NaN
- 数据竞争靠“跑几次没崩”判断
- 输出依赖哈希表遍历顺序
- 优化后没跑回归测试

## 14. 要点回顾

1. **顺序**：正确性 → 边界 → 对拍 → 性能 → 优化 → 回归
2. **对拍**：暴力 oracle + 随机小数据 + 固定种子 + 保存失败用例
3. **基准**：warm-up、多次、固定输入/编译选项、防止优化掉
4. **优化**：先 profile，只改一个变量，Amdahl 定律看占比
5. **内存**：reserve/移动/局部性；多线程注意伪共享
6. **UB**：有符号溢出、移位、未初始化读；用 sanitizer
7. **浮点**：不要直接相等；NaN 破坏排序；累加顺序影响结果
8. **并发**：数据竞争是 UB；TSan + 压力测试，不靠“跑一次没崩”
9. **可复现**：种子、输入、环境、顺序都要固定/记录
